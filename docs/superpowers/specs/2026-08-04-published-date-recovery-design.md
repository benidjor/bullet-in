# 발행일 복구 설계 (2026-08-04)

## 1. 배경

사용자가 라이브 화면에서 발견했다.
BBC 기사 `9956234a…` 의 원문 발행일은 7월 14일 (수정 7월 15일) 인데 사이트는 7월 19일로 보여 주고 있었다.

저장값을 열어 보니 발행일이 수집 시각과 64초 차이였다.

```
published_at         2026-07-18 21:57:55
fetched_at           2026-07-18 21:56:51
published_precision  NULL
```

원문 HTML 에는 발행일이 그대로 들어 있다.

```
"datePublished":"2026-07-14T14:11:47.899Z"
"dateModified":"2026-07-15T17:50:52.460Z"
```

즉 수집 당시 발행일을 못 읽어 **수집 시각으로 대체**된 것이고, 화면은 그 값을 KST 로 옮겨 정직하게 보여 주고 있었다.

## 2. 원인

`pipeline._published()` 는 payload 에서 발행일을 읽지 못하면 수집 시각을 돌려준다.

```python
raw = payload.get("published") or payload.get("created_at")
try:
    dt = dtparser.parse(raw)
except (TypeError, ValueError):
    return fetched_at
```

HTML 어댑터는 `extract_published_at()` 이 성공했을 때만 `payload["published"]` 를 채운다.
추출이 실패하면 폴백이 조용히 동작하고 경고도 남지 않는다.

**추출기 자체는 정상이다.**
문제의 URL 을 다시 받아 `extract_published_at()` 를 돌리면 `2026-07-14 14:11:47` · precision `time` 을 정확히 반환한다.
수집 당시에만 실패한 것이므로 이 설계는 코드 결함이 아니라 **잔존 데이터**를 다룬다.

`bbc_sport` 14건이 시점으로 깨끗하게 갈리는 것이 그 근거다.

| 수집 시기 | `published_precision` | 발행일 상태 |
| --- | --- | --- |
| 06-30 ~ 07-18 (5건) | NULL | 전부 수집일과 같음 |
| 07-23 이후 (9건) | `time` | 정상 (07-08 발행 · 07-26 수집 등) |

07-26 에 재수집된 3건 (`revision 3`) 은 재수집하면서 올바른 날짜를 되찾았다.
**다시 가져오면 고쳐진다는 뜻이다.**

## 3. 대상

### 3.1. 판별 기준

`published_precision IS NULL` 인 것과 "발행일이 수집 시각의 5분 이내" 인 것이 소스별로 정확히 겹친다.
두 조건을 함께 쓴다.

| 소스 | 대상 |
| --- | --- |
| bbc_gossip | 45 |
| fmkorea | 21 |
| goal | 16 |
| skysports | 15 |
| bbc_sport | 5 |
| **합계** | **102** |

### 3.2. 제외

- **트윗 133건** (`x_afcstuff` 128 · `x_ornstein` 5)
— JSON-LD 가 없는 것이 정상이고 날짜는 `created_at` 에서 온다.
평균 시차가 7.3시간으로 실제 값임이 확인된다.
- **guardian 5건**
— `published_precision` 은 비어 있으나 발행일이 수집 시각과 달라 실제 값이다.

## 4. 방식

### 4.1. 기존 재수집 도구를 쓰지 않는다

`refetch_urls.py` 는 제목 · 본문 · 이미지 · 저자를 모두 다시 가져오고 **번역 4필드를 리셋**한다.
102건에 그것을 적용하면 재번역이 따라와 Gemini 과금이 생기고, 이 트랙의 전제가 무너진다.

### 4.2. 발행일만 갱신하는 좁은 모듈

새 모듈 `backfill_published_at.py` 를 둔다.

- 대상 행의 URL 을 받아 HTML 을 가져온다
- `extract_published_at()` 만 돌린다
- `published_at` · `published_precision` **두 칸만** UPDATE 한다

다른 컬럼은 읽지도 쓰지도 않는다.

### 4.3. 안전 장치

- **추출 실패면 건드리지 않는다**
— 기존 값을 더 나쁜 값으로 덮지 않는다.
- **`fetched_at + 1시간` 을 넘는 값은 버린다**
— `_published()` 가 쓰는 오파싱 가드와 같은 기준이다.
- **요청 간격 1.5초**
— 기존 백필들이 쓰는 `REQUEST_GAP_SEC` 관례를 따른다.
- **멱등하다**
— 성공하면 `published_precision` 이 채워져 다음 실행의 대상 조건에서 빠진다.
- **`--dry-run` 이 먼저다**
— 저장값과 추출값을 나란히 출력하고 아무것도 쓰지 않는다.

`--dry-run` 을 반드시 먼저 도는 이유가 있다.
`bbc_gossip` 45건은 매일 나오는 칼럼이라 수집일과 발행일이 원래 같을 수 있다.
쓰기 전에 실제로 몇 건이 틀렸는지 눈으로 확인한다.

### 4.4. 실행을 둘로 나눈다

- **1차 · 언론사 81건** (bbc_gossip · goal · skysports · bbc_sport)
— 요청 간격 1.5초 기준 약 2분.
- **2차 · fmkorea 21건**
— fmkorea 행의 URL 은 원문 언론사 주소이므로 이 실행은 fmkorea.com 에 접촉하지 않는다.
따라서 430 확인 절차는 이 트랙에 해당하지 않는다.
해외 언론사로 요청이 나가므로 실패가 섞인다 — 언론사 결과와 구분하려고 따로 돌린다.

**여기서 예상이 빗나갔다** (§9 참조).
초안은 "실패가 다수 나오는 것이 정상" 이라고 적었는데 실제로는 21건 중 16건이 성공했다.
근거로 든 "26건 중 25건이 406 · 403 · 페이월" 은 수집 시점에 본문을 받아 오는 경로의 수치였고, 나중에 URL 하나만 다시 여는 것과는 조건이 다르다.

## 5. 안전 확인

`content_hash` 는 제목과 URL 로만 만들어진다 (`canonical.py:17`).

```python
def content_hash(title: str, url: str) -> str:
    norm_title = " ".join(title.split())
    payload = f"{norm_title}|{canonical_url(url)}".encode("utf-8")
    return hashlib.sha256(payload).hexdigest()
```

발행일이 해시에 들어가지 않으므로 값을 바꿔도 `article_players` 귀속 · 상세 페이지 주소 · 선수 페이지 링크가 모두 그대로다.

## 6. 검증

- 트윗을 제외한 `published_precision IS NULL` 건수가 102 에서 크게 줄어든다
- 표본 대조 — BBC 트로사르 기사가 `2026-07-18` 에서 `2026-07-14` 로 바뀐다
- 재렌더 후 홈 정렬과 신선도 지표를 확인한다

## 7. 부수 영향

- **홈 정렬이 바뀐다**
— 실제로는 오래된 기사가 제자리로 가는 것이다.
- **가십 7일 창에 걸리는 건수가 줄 수 있다**
— `serve/render.py` 는 가장 최신 가십 날짜 기준 7일보다 오래된 카드를 접는다.
가장 큰 묶음인 `bbc_gossip` 45건의 발행일이 과거로 이동하면 재렌더 후 가십 섹션에 보이는 건수가 줄 수 있다.
- **정밀도가 `day` 인 행은 카드에서 시각 표시가 사라진다**
— `time_in_group` 이 `day` 정밀도에 빈 문자열을 준다.
정확해지는 방향이다.
- **상세 페이지 주소는 안 바뀐다** (§5).
- **재렌더가 필요하다**
— 정렬과 날짜 표시가 모두 이 값을 쓴다.

## 8. 범위 밖

- `_published()` 의 폴백 자체를 바꾸지 않는다
— 추출기가 이미 정상 동작하므로 지금 고칠 결함이 없다.
- 발행일 추출 실패를 경고로 올리는 관측 보강은 별도 안건으로 둔다.
- 선수 페이지 진행 단계 사다리는 이 트랙 뒤에 붙인다.

### 9.1. 손상 원인은 배치였다

저장된 발행일이 **몇 개의 수집 시각에 뭉쳐** 있었다.

- `2026-06-29 13:53:27` 하나에 `bbc_gossip` **24건**이 몰려 있었고, 실제 발행일은 06-05 ~ 06-28 로 하루씩 달랐다.
- `2026-07-13 23:34:41` · `2026-07-14 21:50:50` · `2026-07-18 21:57:55` 에도 여러 건이 뭉쳐 있었다.

산발적인 추출 실패가 아니라 **몇 번의 백필 배치가 통째로 그 시각으로 찍힌 것**이다.
`bbc_gossip` 45건이 수집일과 발행일이 원래 같을 수 있다는 §4.3 의 우려는 이 실측으로 해소됐다 — 하루씩 다른 날짜가 한 값에 뭉쳐 있었다.

### 9.2. 리다이렉트 가드가 실제로 걸렸다

최종 리뷰가 "삭제된 기사가 목록 페이지로 넘어가면 무관한 날짜가 채택될 수 있다" 고 경고했다.
무변경 2건이 정확히 그 부류였고 발행일이 안 읽혀 건드리지 않았다.

두 URL 은 애초에 기사 주소가 아니었다.
별도 안건으로 기록했다 — `docs/troubleshooting/2026-08-05-non-article-urls-stored-as-articles.md`.
