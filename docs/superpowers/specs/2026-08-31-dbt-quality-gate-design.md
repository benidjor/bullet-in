# dbt 품질 검사를 회차의 배포 게이트로 세우는 설계 (2026-08-31)

`CLAUDE.md` 첫 줄이 「dbt 품질 게이트 (DuckDB)」 라고 말하는데 사실이 아니다.
모델 6개와 컬럼 테스트 10개가 저장소에 있지만 회차도 배포 스크립트도 이것을 부르지 않는다.
이 설계는 그 검사를 회차 안에서 실제로 돌리고, 실패했을 때 배포가 나가지 않게 만든다.

## 1. 지금 상태와 실측

### 1.1. 없는 것은 테스트가 아니라 실행이다

- `dbt/models/` 에 staging 3개 · marts 3개가 있고 `dbt/models/sources.yml` 에 컬럼 테스트 10개가 붙어 있다.
- `run.py` 와 `infra/deploy-site.sh` 어디에도 dbt 호출이 없다.
- CI 는 `dbt parse` 만 돌린다.
  모델 참조가 깨진 것은 잡지만 테스트가 실제로 통과하는지는 안 본다.
- **운영 VM 에는 dbt 가 설치돼 있지도 않다.**
  `dbt-duckdb` 가 `pyproject.toml` 의 `dev` extra 에만 있고 운영은 그 extra 없이 동기화돼 있다.
  2026-08-31 확인에서 VM 의 `uv run dbt --version` 이 실행 파일을 못 찾고 실패했다.

즉 이 안건은 테스트를 더 쓰는 일이 아니라 설치와 접속을 실제로 잇는 일이 절반이다.

### 1.2. 후보 테스트가 오늘 운영 데이터에서 통과하는가

착수 전에 운영 DB 를 읽어서 세었다 (2026-08-31 11시대 KST · 읽기 전용).
게이트를 세게 걸었을 때 첫날부터 빨간불이 날 자리를 미리 알아야 임계를 정할 수 있다.

| 후보 테스트 | 오늘 위반 |
| --- | --- |
| `content_hash` · `url` 유일 · 결측 없음 | 0 |
| `title_original` 결측 없음 | 0 |
| `tier` 값이 6종 안에 있음 | 0 |
| `source_id` 결측 없음 | 0 |
| `players.id` 유일 · 결측 없음 | 0 |
| `article_players.player_id` 가 `players` 를 가리킴 | 0 |
| `article_players.role` 값이 2종 안에 있음 | 0 |
| **`article_players.content_hash` 가 `articles` 를 가리킴** | **259쌍** |
| `transfer_stage` 값이 10종 안에 있음 | 0 |
| `transfer_direction` 값이 3종 안에 있음 | 0 |

기사 954건 · 귀속 3,696쌍 · 선수 531명 기준이다.

`transfer_stage` · `transfer_direction` 은 손으로 짠 프로브 쿼리로는 결측 1건이 잡혔지만, `accepted_values` 는 NULL 행을 안 세므로 이 테스트 자체의 판정은 0이다.
프로브와 제품이 실제로 돌리는 검사의 판정이 여기서 갈렸다.

### 1.3. 참조 무결성 테스트를 붙일 수 없는 자리가 하나 있다

잔여 안건 메모리는 `articles.source_id` 가 `sources` 표를 가리키는지 보는 테스트를 후보로 적어 두었다.
실측하니 **`sources` 표는 0행이다.**
스키마가 표를 만들지만 파이프라인이 채우지 않고, 소스 정의는 `config/sources.yaml` 에 산다.
이 테스트를 붙이면 954건 전량이 실패한다.

데이터 결함이 아니라 쓰이지 않는 표다.
이번 설계에서는 테스트를 붙이지 않고 사실만 기록한다.

## 2. 결정

### 2.1. 게이트는 회차 맨 끝에 둔다

`pipeline_runs` 적재와 `ops.html` 렌더가 끝난 뒤, `print(summary)` 앞에서 `dbt build` 를 부른다.

잔여 안건 메모리는 「렌더 앞에 두면 진짜 게이트가 된다」 고 적어 두었지만, 실물을 보고 끝자리로 바꾼다.
근거 셋이다.

- **차단 효과가 같다.**
  `bullet-in.service` 는 `ExecStart` 뒤에 `ExecStartPost` 로 배포 스크립트를 달아 두었고, systemd 는 앞 단계가 실패하면 뒤 단계를 돌리지 않는다.
  `run.py` 가 0 아닌 코드로 끝나기만 하면 렌더 앞이든 뒤든 배포는 나가지 않는다.
- **마트가 이번 회차를 본다.**
  `slo_rollup` 은 `pipeline_runs` 를, 신선도 모델은 `source_freshness` 를 읽는다.
  두 표에 이번 회차 행이 들어간 뒤에 돌려야 마트가 최신을 담는다.
  렌더 앞에 두면 마트가 늘 한 회차 뒤처진다.
- **실패한 회차의 기록이 남는다.**
  렌더 앞에서 끊으면 그 회차의 `pipeline_runs` 행과 `ops.html` 이 통째로 안 생긴다.
  사고가 난 회차만 관측 기록이 없는 셈이라 가장 나쁘다.

대가는 `site/` 가 로컬에 만들어진다는 것이다.
배포는 나가지 않고 다음 성공 회차가 덮는다.

### 2.2. 테스트를 두 축으로 가른다

**계약 축은 실패하면 배포를 세운다 (`severity: error`).**
오늘 위반이 0이고, 깨졌다면 파이프라인이 고장 난 것이다.

- `stg_articles` 의 `content_hash` · `url` 유일 · 결측 없음
- `stg_articles.title_original` 결측 없음
- `stg_articles.tier` 값 6종
- `stg_articles.source_id` 결측 없음 — 신설
- `stg_players.id` 유일 · 결측 없음 — 신설
- `stg_article_players.player_id` 가 `stg_players` 를 가리킴 — 신설
- `stg_article_players.role` 값 2종 — 신설

**품질 축은 한 테스트 안에서 경고 구간과 차단 구간을 가른다 (`warn_if` · `error_if`).**
값이 틀어지면 화면이 나빠지지만 파이프라인이 죽은 것은 아니다.

- `stg_article_players.content_hash` 가 `stg_articles` 를 가리킴 — 신설
- `stg_articles.transfer_stage` 값 10종 — 신설
- `stg_articles.transfer_direction` 값 3종 — 신설

**두 축 모두 `severity` 는 `error` 로 둔다.**
`severity: warn` 을 쓰면 `error_if` 가 통째로 무시돼 위반이 아무리 늘어도 배포가 안 막힌다.
2026-08-31 에 로컬에서 확인했다 — 고아를 1건 심고 임계를 0으로 낮췄는데도 판정이 경고에 머물렀고 종료 코드가 0이었다.
구간을 가르는 것은 `severity` 가 아니라 `warn_if` 와 `error_if` 다.
같은 실측에서 `severity: error` · `warn_if: ">0"` · `error_if: ">100"` 조합은 위반 1건에서 경고와 종료 코드 0을, 임계를 넘겼을 때 차단과 종료 코드 1을 냈다.

### 2.3. 임계는 실제 사건의 크기에서 가져온다

임계를 눈대중으로 고르면 나중에 왜 그 숫자인지 아무도 답할 수 없다.
그래서 관측된 사건의 크기를 잣대로 쓴다.

| 테스트 | 경고 | 차단 | 차단 임계의 근거 |
| --- | --- | --- | --- |
| 고아 귀속 | 1건 이상 | **100건 초과** | 알려진 가장 큰 단일 사건이 43건이었다 (2026-08-29 주소 정정) · 그 두 배가 넘으면 정상 운영에서 나올 수 없다 |
| `transfer_stage` 값 이탈 | 1건 이상 | 20건 초과 | 오늘 1건 · 분류 패스가 한 회차에 만지는 건수보다 큰 값 |
| `transfer_direction` 값 이탈 | 1건 이상 | 20건 초과 | 위와 같다 |

임계를 바꿀 때는 이 표의 근거 칸을 함께 고친다.
근거 없이 숫자만 올리면 게이트가 서서히 무력해진다.

### 2.4. 고아 귀속 259쌍은 지우고 0에서 시작한다

기사와 선수를 잇는 `article_players` 에, 기사 쪽이 이미 사라진 짝이 259쌍 남아 있다 (기사 76건 몫).
추출 시각은 2026-08-12 부터 2026-08-30 까지 흩어져 있다.

이 부채를 남긴 채 게이트를 켜면 임계를 부채 크기에 맞춰 잡아야 하고, 그 숫자는 근거가 약해진다.
지우고 시작하면 재발이 첫 건부터 보인다.

- 정리 수단은 이미 있다 — `python -m bullet_in.migrate_url_identity --apply --purge-orphans`.
- 운영 데이터를 지우는 일이므로 `--dry-run` 으로 대상 수를 세어 보이고 승인을 받은 뒤 실행한다.
- 지운 뒤에도 테스트는 경고로 둔다.
  원인이 아직 안 밝혀졌으므로 차단으로 걸면 재발하는 순간 사람이 손쓸 때까지 화면 갱신이 멈춘다.

**원인 규명은 이 설계의 범위 밖이다.**
`content_hash` 는 원문 제목과 정규화된 주소로 만들어져서 둘 중 하나가 바뀌면 해시가 갈리고 참조가 고아로 남는다.
2026-08-29 에 그렇게 43건이 생긴 사례가 `docs/troubleshooting/2026-08-29-the-rule-moved-but-the-stored-addresses-did-not.md` 에 있다.
다만 오늘의 259쌍은 그 사건 하나로 설명되지 않는다.

### 2.5. 계보를 dbt 안으로 들인다

지금 staging 모델은 `maria.articles` 를 문자열로 직접 읽는다.
dbt 가 원천을 모르므로 계보가 dbt 밖에서 끊긴다.

- `sources:` 블록을 선언하고 staging 모델을 `{{ source('maria', 'articles') }}` 형태로 바꾼다.
- 참조 테스트를 걸 대상이 필요하므로 staging 모델 둘을 신설한다 — `stg_players` · `stg_article_players`.

### 2.6. 접속 정보를 환경 변수로 옮긴다

`dbt/profiles.yml` 에 `password=bulletin` 이 박혀 있다.
로컬 개발용 값이지만 공개 저장소에 그대로 실려 있고, 운영 비밀번호와 다르므로 VM 에서는 붙지도 않는다.

- `run.py` 가 `MARIADB_URL` 을 파싱해 `DBT_MARIA_HOST` · `DBT_MARIA_PORT` · `DBT_MARIA_USER` · `DBT_MARIA_PASSWORD` · `DBT_MARIA_DB` 다섯을 자식 프로세스 환경에 넣는다.
- `profiles.yml` 은 그 다섯을 `env_var` 로 읽되 기본값을 지금 값으로 둔다.
- 그래서 로컬과 CI 는 아무 설정 없이 지금과 똑같이 돌고, VM 만 `.env` 를 따라간다.

접속 정보의 단일 출처가 `MARIADB_URL` 하나가 된다.

### 2.7. 실패했을 때 일어나는 일

- **계약 축 실패**
  → `dbt/target/run_results.json` 을 읽어 어떤 테스트가 몇 행에서 깨졌는지 사고 채널 (`CHANNEL_INCIDENT`) 로 보내고 0 아닌 코드로 끝낸다.
  배포가 나가지 않고 `OnFailure` 에 물린 유닛이 한 번 더 알린다.
  두 알림의 역할이 다르다 — 앞의 것은 무엇이 깨졌는지 말하고, 뒤의 것은 유닛이 죽었다는 사실만 말한다.
- **품질 축 경고**
  → `WARNING` 로그 한 줄로 테스트 이름과 행 수를 남긴다.
  알림은 보내지 않는다 — 하루 8회 회차에서 같은 부채가 매번 울리면 그 알림은 곧 무시된다.
  감시는 `error_if` 임계가 대신한다.
- **dbt 자체가 못 돌 때**
  → 설치 누락이나 attach 실패는 데이터 결함이 아니라 게이트 고장이다.
  **이것도 배포를 세운다.**
  조용히 넘어가면 게이트가 있다는 착각만 남는다.

## 3. 함께 따라오는 변경

- `dbt-duckdb` 를 `dev` extra 에서 운영 의존성으로 옮긴다.
  옮기지 않으면 VM 에서 한 줄도 돌지 않는다.
- CI 의 `dbt parse` 를 `dbt build` 로 올린다.
  러너에 MariaDB 가 이미 떠 있어서 붙는다.
  데이터가 없어 테스트는 빈 채로 통과하지만 SQL 과 YAML 의 오류를 잡는다.
  CI 의 「이 CI 가 안 보는 것」 목록에서 dbt 줄을 지운다.
- `CLAUDE.md` 첫 줄의 dbt 서술이 이 시점에 사실이 된다.
  Airflow 서술은 안건 2ε 의 몫이라 그대로 둔다.

## 4. 검증 기준

- **게이트가 「있음」 을 남기는지 먼저 본다.**
  로컬에서 계약 축을 일부러 깨뜨려 (예: 중복 `content_hash` 삽입) `dbt build` 가 실패하고 `run.py` 가 0 아닌 코드로 끝나는 것을 확인한 뒤 되돌린다.
  없음을 확인하는 검사는 안 돌아도 없음을 내므로, 있음을 낼 수 있는지부터 봐야 한다.
- **경고가 배포를 안 막는 것도 확인한다.**
  품질 축만 깨진 상태에서 `run.py` 가 0으로 끝나야 한다.
- **운영에서는 첫 회차 저널을 읽는다.**
  고아 정리 뒤라면 경고 0 · 차단 0 이 나와야 한다.
- 기존 테스트 1,441건이 그대로 통과해야 한다.

## 5. 범위 밖

- **`sources` 표가 0행인 것** — 채울지 지울지는 별도 판단이 필요하다.
- **고아 귀속이 쌓이는 원인** — 안건 χ 로 남긴다.
- **`transfer_stage` 가 비어 있는 기사 1건** — `transfer_stage` · `transfer_direction` 에 새로 붙인 `not_null` 테스트가 경고로 드러낸다 (§1.2 에서 밝혔듯 `accepted_values` 는 이걸 못 본다).
  값 정정은 별건이다.
- **dbt 결과를 `ops.html` 에 싣는 것** — 이번에는 저널과 알림까지만 한다.

## 6. 되짚을 자리

- 게이트가 도는 것과 게이트가 막는 것은 다른 축이다.
  「돌았다」 만 확인하고 「막았다」 를 확인하지 않으면 §4 의 첫 항목을 건너뛴 것이다.
- 임계는 부채의 현재 크기가 아니라 사건의 크기에서 와야 한다.
  부채를 먼저 지우기로 한 이유가 이것이다.
- **설정 이름이 뜻대로 동작하는지는 대 봐야 안다.**
  `severity: warn` 과 `error_if` 를 함께 쓰는 조합은 문법이 통과하고 테스트도 초록불이지만 차단이 한 번도 안 걸린다.
  설계 단계에서 위반을 심어 보지 않았다면 게이트가 있다고 믿으면서 아무것도 안 막는 상태로 배포됐을 것이다.

### 6.1. 남은 결과 파일이 죽은 게이트를 통과로 보고했다

`run_gate` 는 `proc.returncode` 를 안 보고 `dbt/target/run_results.json` 만으로 판정했다.
profile 파싱 오류 · MariaDB 접속 실패 · extension 로드 실패처럼 dbt 가 뭘 돌기도 전에 죽으면 그 파일을 새로 안 쓴다.
운영 VM 에서는 파일이 회차 사이에 남아 있어서, 두 번째 회차부터는 게이트가 고장 나도 지난 회차의 「전부 통과」 파일을 그대로 읽고 통과를 냈다.
죽은 포트로 dbt 를 겨눠 종료 코드 2 를 내고도 남은 파일 때문에 통과가 나는 것을 2026-08-31 에 실측으로 확인했다.

과제 단위 리뷰가 이걸 매번 놓친 이유는 검증마다 `target/` 을 새로 만드는 자리에서 돌았기 때문이다.
파일이 늘 그 회차가 쓴 것이었으니 결과 파일만 보는 판정이 매번 맞는 답을 냈다.
전체 브랜치 리뷰가 회차를 반복해 도는 운영 VM 의 조건을 대 보고서야 남은 파일이라는 자리가 드러났다.

## 7. 로컬에서 확인한 사실

착수 전에 로컬 DuckDB · MariaDB 로 문법과 동작을 대 봤다.

- `dbt build` 는 모델 6개와 테스트 10개를 **0.7초**에 끝낸다.
  회차 시간에 부담이 없다.
- 테스트 인자는 dbt 1.11 문법인 `arguments:` 블록으로 넘긴다.
  `relationships` 도 `arguments: to · field` 형태다.
- **로컬 개발 DB 의 스키마가 운영보다 뒤처져 있을 수 있다.**
  `article_players.role` 이 없어 신설 모델이 실패했고 `MartStore.ensure_schema()` 를 돌려서 맞췄다.
  구현을 시작하기 전에 이것부터 한다.
