# SLO-5 가 「끊김」 만 재도록 신호를 나누는 설계 (2026-10-02)

## 1. 배경

### 1.1. 문제

SLO-5 는 소스마다 마지막 원본 수집 이후 경과 시간이 임계 (`freshness_hours`) 를 넘었는지로 「끊김」 을 판정한다 (`quality.evaluate_freshness`).
이적 시장이 닫힌 뒤 BBC Sport · Sky Sports · The Guardian 은 이적 키워드에 맞는 기사가 드물어져, 소스는 멀쩡한데 새 원본이 0 이 된다.
이 「조용함」 이 「끊김」 과 같은 신호로 들어와서, 어떤 임계를 골라도 오탐 아니면 늦은 탐지 중 하나를 받아들여야 한다.

경위와 재측정은 `docs/troubleshooting/2026-10-01-a-threshold-cannot-tell-a-quiet-source-from-a-broken-one.md` 가 정본이다.
이 설계는 그 문서 §6 이 남긴 과제를 푼다.

### 1.2. 이미 있는 재료

- **HTML 어댑터의 수집 단계 기록** — 실행마다 목록 페이지에서 고른 링크 · 중복을 뺀 링크 · 제목이 확인된 링크 · 키워드를 통과한 링크의 수 (`selected` · `deduped` · `titled` · `passed`) 를 `pipeline_runs.fetch_detail.funnels` 에 남긴다 (`adapters/html.py`).
- **후보 수** (`pipeline_runs.candidate_counts`) — 키워드 필터를 통과한 뒤의 수라서 HTML 에서는 `passed` 와 같다.
  조용한 날에는 0 이 되므로 끊김 판정 재료로는 쓸 수 없다.
- **후보 절벽 알림** (#218 · `quality.candidate_cliffs`) — 직전 실행에 후보가 있다가 이번에 0 이 되는 전이를 한 번 알린다.
  이 설계는 이 알림을 건드리지 않는다.
- **X 와 fmkorea 의 실행 중 정보** — X 어댑터는 필터 전 트윗 목록 (`raw_tweets`) 을, fmkorea 어댑터는 검색 실패 수와 실패 코드 (`search_failure_codes`) 를 실행 중에만 갖고 있고 저장하지 않는다.
- **레이크하우스 적재** — `warehouse.ensure_table` 이 기존 표에 `union_by_name` 으로 새 칼럼을 붙인다.
  MariaDB 표에 칼럼을 **추가만** 하면 `ops_source_freshness` 는 다음 적재에서 칼럼이 자동으로 붙고 옛 행은 빈 값이 된다.
- **SLO-5 를 읽는 곳 둘** — 수집 현황 화면 (`serve/ops_view.py` 의 `_freshness` · `_tiles` · `_slo_rows`) 과 dbt Gold (`dbt/models/gold/gold_slo_rollup.sql` 의 `sum(stale)`) 이다.

### 1.3. 설계 중에 확인한 사실 둘 (2026-10-01 16:39 UTC)

**끝나지 않은 공백은 최대값이 아니다.**
트러블슈팅 2026-10-01 §3 의 「비수기 최대 공백」 은 측정 시점에 아직 이어지던 공백을 잰 값이었다.
공개 수집 현황 화면 (10-01 15:00 UTC 생성) 에서 BBC Sport 216h · Sky Sports 213h · The Guardian 210h · Ornstein 147h 로 계속 늘고 있었다.
이적 키워드로 거르는 소스는 비수기에 다음 이적 기사가 언제 나올지 상한이 없다.
그래서 상한을 「새 원본이 없는 시간」 으로 재면 결국 다시 조용함을 재게 된다 (2.3 의 기준을 바꾼 이유).

**BBC Sport 목록에서 제목이 확인되지 않는다.**
세 소스의 목록 페이지를 한 번씩 받아 어댑터와 같은 규칙으로 셌다 (본문은 받지 않음).

| 소스 | HTTP | 기사 링크 | 제목 확인 | 키워드 통과 |
| --- | --- | --- | --- | --- |
| The Guardian | 200 | 20 | 20 | 1 |
| Sky Sports | 200 | 11 | 11 | 3 |
| BBC Sport | 200 | 7 | 1 | 0 |

BBC Sport 의 아스날 팀 페이지는 기사 카드 목록이 아니라 짧은 글이 이어지는 피드 모양이었다.
제목 칸 (`LinkPostHeadline`) 이 있는 카드는 09-28 기사 하나뿐이고, 나머지 여섯 링크는 피드 글 본문 속 링크였다.
그 가운데 아르테타 재계약 기사는 이적 키워드 (agree · deal) 를 담고도 제목이 확인되지 않아 키워드 검사까지 가지 못했다.
09-30 의 기록도 「기사 링크 9 · 제목 확인 2」 라서 최소 이틀째 같은 모양이다.
지금 규칙으로는 이 상태가 응답으로 판정된다 (2.2 에 제목 확인 비율을 넣은 이유).

## 2. 판정 규칙

### 2.1. 상태 넷

감시 대상은 지금처럼 `freshness_hours` 가 0 보다 큰 소스 일곱 곳이다 (bbc_sport · bbc_gossip · guardian · skysports · x_afcstuff · x_ornstein · fmkorea).
공홈 (`arsenal_official`) 과 Goal 은 지금처럼 감시에서 뺀다.

| 상태 | `state` 값 | 조건 | SLO-5 | 알림 |
| --- | --- | --- | --- | --- |
| 끊김 | `broken` | 목록 무응답 2회 연속 · 또는 목록 내용이 상한 넘게 그대로 | 센다 | 보낸다 |
| 응답 없음 1회 | `no_response` | 이번 실행만 무응답 | 안 센다 | 안 보낸다 |
| 조용함 | `quiet` | 목록 응답 · 새 원본 경과 > `freshness_hours` | 안 센다 | 안 보낸다 |
| 정상 | `ok` | 그 밖 | 안 센다 | — |

판정 순서는 위에서 아래다.

### 2.2. 「목록이 응답했다」 의 뜻

이번 실행에 그 소스의 예외 (`fetch_detail.errors`) 가 없고, 수집 단계 기록이 아래 조건을 만족하면 응답한 것이다.

| 어댑터 | 응답 조건 | 무응답이 되는 고장 |
| --- | --- | --- |
| `html` | 기사 링크 (`deduped`) 가 1개 이상이고, 그 가운데 제목이 확인된 링크 (`titled`) 가 절반 이상 | 목록 셀렉터 변경 · 제목 셀렉터 변경 · 페이지 구성 변경 · 차단 |
| `x_playwright` | 타임라인에서 가져온 트윗 (`scraped`) 이 1개 이상 | 로그인 만료 · 계정 접근 차단 |
| `fmkorea` | 검색에 성공한 검색어 (`searched`) 가 1개 이상이고 검색 결과에서 가져온 글 (`listed`) 이 1개 이상 | 모든 검색어 430 · 검색 결과 셀렉터 변경 |

- **제목 확인 비율** — 목록에서 찾은 기사 링크 가운데 제목까지 확인된 링크의 비율이다 (`titled ÷ deduped`).
  제목이 확인되지 않은 링크는 이적 키워드 검사까지 가지 못하고 버려진다.
  1.3 의 BBC Sport (7 개 중 1 개 · 14%) 가 이 조건으로 무응답이 된다.
- fmkorea 는 검색어 가운데 하나라도 성공하면 응답으로 본다.
  일부 검색어만 430 을 받는 일은 흔하고, 그때도 수집은 이어진다.
- 예외가 없는데 수집 단계 기록이 비어 있으면 무응답으로 본다.
  기록하는 코드가 고장 난 것도 감시가 눈을 감은 상태라서 알려야 한다.
  알림 사유는 「수집 단계 기록 없음」 으로 따로 적어 소스 고장과 구분한다 (4.1).

### 2.3. 상한 — 목록 내용이 그대로인 시간

상한은 「목록은 응답하는데 옛 글만 계속 보여 주는」 고장 (사이트 갱신 정지 · 캐시된 페이지 · 오래된 검색 결과) 을 잡는 안전판이다.
이 고장은 응답 조건을 통과하므로 상한만이 잡는다.
07-31 의 억제 규칙 (#174 · 「후보가 잡히면 알리지 않는다」) 이 이런 안전판 없이 13일 침묵을 만들었다 (`docs/troubleshooting/2026-08-15-alert-suppression-becomes-silence.md`).

- **기준은 키워드 필터 앞의 목록이다.**
  실행마다 목록의 링크 묶음으로 짧은 지문 (`list_sig`) 을 만들고, 지문이 직전 실행과 달라진 시각을 `list_changed_at` 에 이어 적는다.
  목록 내용이 그대로인 시간 = 지금 − `list_changed_at` 이다.
- **상한은 모든 소스에 48시간이다** (`list_unchanged_cap_hours: 48`).
  아스날 팀 페이지 · 가십 페이지는 이적 기사가 없어도 다른 기사로 매일 바뀐다 (1.3 의 Guardian 목록 20건 가운데 키워드 통과는 1건).
  X 타임라인과 fmkorea 검색 결과도 필터 앞에서는 매일 바뀐다.
  그래서 계절과 상관없이 같은 값을 쓰고, 성수기 · 비수기를 나누지 않는다.
- **지문을 만드는 링크 묶음**

| 어댑터 | 링크 묶음 |
| --- | --- |
| `html` | 중복을 뺀 기사 링크 (`deduped` 에 든 주소) |
| `x_playwright` | 타임라인에서 가져온 트윗 주소 (고정 트윗 포함 · 필터 전) |
| `fmkorea` | 모든 검색어의 검색 결과 글 주소 (필터 전) |

  주소를 정렬해 이어 붙인 문자열의 해시 앞 16자를 쓴다.
  목록 안의 순서가 바뀌는 것만으로는 바뀐 것으로 보지 않는다.

### 2.4. 새 원본 경과와 `freshness_hours` 의 새 역할

새 원본 경과는 지금처럼 원본 수집 (`raw_items`) 의 마지막 시각에서 잰다 (설계 2026-08-20 §3.1).
이 값은 끊김 판정에서 빠지고 조용함 판정에만 쓴다.

`freshness_hours` 는 화면의 「조용함」 표시선이 된다.
`stale` 칼럼은 계속 「새 원본 경과 > `freshness_hours`」 를 기록하므로 7월부터 쌓인 이력과 뜻이 같다.

### 2.5. 이어 적는 값과 첫 실행

- `miss_streak` 은 응답하면 0, 무응답이면 직전 행의 값 + 1 이다.
- `list_changed_at` 은 응답한 실행에서 지문이 직전 행과 다르면 이번 실행 시각, 같으면 직전 행의 값이다.
  무응답 실행은 지문이 없으므로 직전 행의 값을 그대로 잇는다.
- 직전 행이 없거나 직전 행의 새 칼럼이 비어 있으면 (이 설계 배포 전의 행) `miss_streak` 은 0, `list_changed_at` 은 이번 실행 시각으로 시작한다.
  그래서 배포 뒤 첫 실행에서는 끊김이 나지 않는다.
  BBC Sport 처럼 지금 무응답 조건에 걸리는 소스는 둘째 실행 (3시간 뒤) 에 끊김이 된다.
- 직전 행은 지금처럼 `MartStore.previous_freshness` 가 읽는다 (이번 실행 행을 넣기 전).

## 3. 기록과 저장

### 3.1. 수집 단계 기록

| 어댑터 | 키 | 뜻 |
| --- | --- | --- |
| `html` | `selected` · `deduped` · `titled` · `passed` · `list_sig` | 지금 넷에 지문을 더한다 |
| `x_playwright` (새로) | `scraped` · `passed` · `list_sig` | 타임라인에서 가져온 트윗 (필터 전) · 필터 뒤 후보 · 지문 |
| `fmkorea` (새로) | `keywords` · `searched` · `listed` · `passed` · `list_sig` | 검색어 수 · 한 페이지라도 성공한 검색어 수 · 검색 결과에서 가져온 글 (필터 전) · 필터 뒤 후보 · 지문 |

- 세 어댑터 모두 `fetch()` 첫 줄에서 `self.funnel = {}` 로 초기화한다.
  중간에 예외가 나면 빈 기록과 오류가 함께 남는다.
- `run.adapter_funnels` 가 어댑터의 `funnel` 속성을 모아 `fetch_detail.funnels` 에 넣는 지금 경로를 그대로 쓴다.
  키 이름 `funnels` 는 이미 저장된 이름이라 그대로 두고, 문서와 화면에서는 「수집 단계 기록」 이라고 부른다.
  `pipeline_runs` 스키마는 바뀌지 않는다.
- fmkorea 의 `listed` 는 검색 결과 셀렉터 (`item_selector`) 가 고른 글의 수다.
  이미 적재된 글 · `[공홈]` 말머리 · 제목 필수어 필터로 빠지는 글도 센다.

### 3.2. `source_freshness` 칼럼 추가

`schema.sql` 에 `ALTER TABLE source_freshness ADD COLUMN IF NOT EXISTS` 다섯 줄을 더한다.

| 칼럼 | 타입 | 뜻 |
| --- | --- | --- |
| `state` | `VARCHAR(16) NULL` | `ok` · `quiet` · `no_response` · `broken` |
| `miss_streak` | `INT NULL` | 연속 무응답 횟수 |
| `list_sig` | `VARCHAR(16) NULL` | 이번 실행 목록의 지문 (무응답이면 빈 값) |
| `list_changed_at` | `DATETIME NULL` | 목록 내용이 마지막으로 바뀐 시각 |
| `cap_hours` | `FLOAT NULL` | 그 실행에 쓴 상한 |

- `stale` 과 `threshold_hours` 는 뜻을 바꾸지 않는다.
- 레이크하우스 `ops_source_freshness` 는 다음 적재에서 다섯 칼럼이 붙는다 (1.2).
- 백업은 표 단위 덤프라 바꿀 것이 없다.

### 3.3. 설정

`config/sources.yaml` 최상위에 `list_unchanged_cap_hours: 48` 을 두고, 근거 (목록 페이지가 매일 바뀐다는 관측 · 1.3) 를 주석으로 남긴다.
감시 대상은 지금처럼 `freshness_hours` 로 정한다.

### 3.4. 판정 위치와 함수

판정은 지금 신선도 판정이 도는 자리 (`run.py` 의 게시 단계) 에서 한다.
그 자리에는 그 실행의 수집 단계 기록 · 오류 · 후보 수가 `pipeline_runs` 행에서 읽혀 와 있다 (`FetchSummary.funnels` · `FetchSummary.errors`).

`quality.py` 에 표준 라이브러리만 쓰는 순수 함수 둘을 더한다.

- `responded(adapter: str, funnel: dict | None, errored: bool) -> tuple[bool, str]` — 2.2 의 표를 그대로 옮기고, 무응답이면 사유 (오류 · 기록 없음 · 기사 링크 0 · 제목 확인 비율 · 트윗 0 · 검색 실패) 를 함께 돌려준다.
- `evaluate_states(records, responses, caps, previous, now) -> None` — `SourceFreshness` 에 `state` · `miss_streak` · `list_sig` · `list_changed_at` · `cap_hours` 를 채운다.

`SourceFreshness` 데이터클래스에 다섯 필드를 더하고, `MartStore.record_freshness` 와 `previous_freshness` 가 다섯 칼럼을 쓰고 읽는다.

## 4. 알림 · 화면 · dbt

### 4.1. 알림

- 끊김만 디스코드로 보낸다.
  `no_response` 와 `quiet` 는 지금 「신선도 판정」 로그 한 줄에 소스 이름과 함께 남긴다.
- 끊김이 된 실행에 한 번 보내고, 끊김이 이어지면 48시간마다 다시 보낸다 (`FRESHNESS_REALERT_HOURS` 그대로).
  지금처럼 직전 행과 비교하는 무상태 판정이다.
  - 목록이 그대로여서 끊긴 경우 — 상한을 넘은 시간을 48시간 구간으로 센다.
  - 무응답으로 끊긴 경우 — `miss_streak` 이 2 를 넘은 횟수를 16회 (3시간 × 16 = 48시간) 구간으로 센다.
  - 직전 행이 끊김이 아니었거나, 끊긴 사유가 바뀌었거나, 구간이 올라가면 보낸다.
- 문안에는 사유를 적는다.
  - 오류 — 「목록 무응답 2회 연속 · 오류: HTTP 403」
  - 제목 확인 비율 — 「목록에서 기사 링크 7개를 찾았지만, 제목까지 확인된 것은 1개뿐 (14%) · 2회 연속」
  - 트윗 · 검색 — 「타임라인 트윗 0개 · 2회 연속」 · 「검색어 3개 모두 실패 (430) · 2회 연속」
  - 기록 없음 — 「수집 단계 기록 없음 · 2회 연속 — 소스가 아니라 감시 기록이 고장 났을 수 있음」
  - 목록 그대로 — 「목록은 응답 · 목록 내용이 52시간째 그대로 (상한 48시간)」
- 지금 `quality.freshness_alert_split` 의 자리를 새 분할 함수 (`broken_alert_split`) 가 맡는다.
  `notify.build_freshness_alert` 는 사유를 받아 문안을 가르도록 고친다.

### 4.2. 수집 현황 화면 (`ops.html`)

- 신선도 절 표에 상태 칸과 수집 단계 칸을 둔다.
  - 상태 — 정상 · 조용함 · 응답 없음 1회 · 끊김 (색 넷) · `state` 가 빈 옛 행은 「판정 이전」
  - 수집 단계 — HTML 「기사 링크 7 · 제목 확인 1」 · X 「트윗 30」 · fmkorea 「검색어 3/3 · 글 40」
- 지금 미터 (새 원본 경과 ÷ `freshness_hours`) 는 그대로 두고 「조용함 정도」 로 설명을 바꾼다.
  목록 내용이 그대로인 시간은 상태 칸 옆에 「목록 그대로 N시간」 으로 보인다 (상한의 절반을 넘을 때만).
- 위 타일 「Stale Sources」 를 「Broken Sources · 끊긴 소스 (SLO-5)」 로 바꾸고 끊김 수를 센다.
- SLO 표 5행 「소스 신선도 · 끊긴 소스 0」 은 끊김 수를 쓰고, 측정 칸은 「목록 응답 · 목록 변화 · 소스별 상태」 로 바꾼다.
- 절 설명문 「미터가 다 차면 수집이 끊겼다」 를 새 규칙에 맞게 고친다.

### 4.3. dbt Gold

- `stg_source_freshness` 가 `state` 를 고른다.
- `gold_slo_rollup` 의 SLO-5 를 `sum(case when stale ...)` 에서 `state = 'broken'` 인 소스 수로 바꾸고, 지표 설명 「수집 끊긴 소스 수 (최신 run)」 는 그대로 둔다.
- `stg_source_freshness.state` 에 `accepted_values` 테스트를 두고 `where: state is not null` 로 옛 행을 뺀다.
  게이트의 dbt 테스트는 21 종에서 22 종이 된다.

## 6. 기각한 대안

- **SLO 를 둘로 나누기 (끊김 · 신선도)** — 신선도 지표가 비수기에 계속 빨갛고, 「SLO 6종」 이라는 서술이 바뀐다.
- **지표는 그대로 두고 표시만 더하기** — 오탐이라는 문제 자체가 남는다.
- **X · fmkorea 를 후보 수로 판정하기** — Ornstein 은 `#AFC` 필터 뒤 후보가 비수기에 0 이 흔해, 끊김과 조용함이 다시 같은 신호가 된다.
- **X · fmkorea 만 지금 임계 방식으로 두기** — 소스마다 규칙이 둘이고 Ornstein 오탐이 남는다.
- **HTML 응답 조건을 「제목 확인 1개 이상」 으로 두기** — 1.3 의 BBC Sport 처럼 대부분의 기사를 놓치는 상태가 응답으로 판정된다.
- **상한을 새 원본 기준으로 두기 (소스별 비수기 최대 × 1.2)** — 기준으로 삼은 최대값이 끝나지 않은 공백이었고 (1.3), 배포 시점에 이미 BBC Sport · Sky 가 넘을 값이었다.
- **새 원본 기준 상한을 성수기 · 비수기로 나누기** — 이적 키워드 소스는 비수기 공백에 상한이 없어, 오탐을 피하려면 비수기 상한을 몇 주로 둬야 한다.
- **칼럼 없이 읽는 쪽에서 계산하기** — 같은 판정 로직이 알림 · 화면 · dbt 세 곳에 생기고, dbt 가 JSON 을 풀어야 한다.
- **`stale` 의 뜻을 끊김으로 바꾸기** — 바꾼 날 앞뒤로 같은 칼럼의 뜻이 달라져 이력이 섞인다.
- **무응답 1회에 바로 끊김** — 소스 한 곳 단위 단발 오류 (13주 435회 중 21회 · 전부 `error_count = 1` · 트러블슈팅 2026-09-11) 마다 SLO-5 가 흔들린다.
- **최근 4회 중 3회** — 탐지가 최대 12시간 늦고 판정에 이력 넷이 필요하다.

## 7. 범위 밖

- **비수기 수집 기준** — 조용함의 원인은 이적 키워드 필터다 (1.3 의 Guardian 목록 20건 가운데 키워드 통과 1건).
  수집 기준을 넓히는 일은 번역 · 요약 비용과 화면 구성까지 바뀌는 제품 범위의 결정이라 새 안건으로 따로 다룬다.
