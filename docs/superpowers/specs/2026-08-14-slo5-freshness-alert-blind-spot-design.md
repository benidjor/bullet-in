# 신선도 알림이 조용히 죽은 소스를 못 알리는 문제 — 설계 (2026-08-14)

## 1. 배경

수집 소스가 조용히 멈춰도 파이프라인은 「0건 성공」 으로 넘어간다.
그 사각을 메우려고 만든 것이 SLO-5 신선도 감시다.

이 설계는 그 감시가 **정반대 방향으로 고장 나 있다** 는 실측에서 출발한다.
2026-08-14 기준으로 `x_ornstein` 은 13일째 새 기사를 한 건도 못 가져오는데 알림이 한 번도 나가지 않았다.
같은 기간 신선도 알림 발송은 **0건**이다.

### 1.1. 이 트랙의 원래 문제는 이미 해결됐다

트랙 메모리와 착수 지시는 2026-07-30 시점의 문제 정의를 담고 있었다.
「어댑터 종류만 보고 고정 문구를 원인으로 붙인다」 는 오진 문제다.

그 처방은 그 뒤 이틀 사이에 두 PR 로 들어갔고, 지금 코드에는 전부 반영돼 있다.

| 원래 처방 | 반영 |
| --- | --- |
| 소스별 후보 건수 기록 | #169 — `run.py` 가 `candidate_counts` 를 세어 `pipeline_runs` 에 남긴다 |
| 후보 0건일 때만 어댑터 힌트 | #169 — `build_freshness_alert` 가 조건부로 붙인다 |
| 저빈도 소스 임계 상향 | #169 — `guardian` 168h · `arsenal_official` 은 그 뒤 감시 제외 |

**따라서 이 설계는 오진을 고치는 것이 아니라 침묵을 깨는 것이다.**
문제 정의가 뒤집혔다는 사실 자체를 여기 남긴다.
다음에 옛 트랙 메모리를 읽는 사람이 이미 닫힌 문제로 되돌아가지 않게 하기 위해서다.

### 1.2. 침묵의 원인은 둘이고 서로 이어져 있다

**원인 ① — 임계가 소스의 실제 리듬과 어긋난다.**

`x_ornstein` 의 임계는 24h 다.
근거는 `config/sources.yaml` 주석의 「X 는 고빈도 소스」 다.
그런데 그 소스는 살아 있던 기간에도 공백의 95 백분위가 111h 였다.
그래서 정상 동작 중에도 판정 112회 중 103회가 stale 이었다.
경고가 상시로 켜져 있으면 그것은 경고가 아니다.

**원인 ② — 그 상시 경고를 끄려고 넣은 억제가 영구적이었다.**

#174 는 stale 중 **후보 0건 또는 fetch 오류** 인 소스만 발송 대상으로 추렸다.
근거는 진단 문서의 「후보는 있으나 전부 중복 = 알릴 필요 없음」 이다.

그 문장은 원래 **한 회차의 상태 판정**이었다.
「이번 회차에 새 글이 없는 것은 정상이다」 라는 뜻이다.
#174 는 그것을 **영구 발송 금지 규칙**으로 승격했다.
상태 판정에는 시간 축이 없으므로 승격된 규칙에도 시간 축이 없다.
그래서 후보만 잡히면 4일이든 13일이든 똑같이 침묵한다.

**두 원인은 인과로 이어진다.**
임계가 어긋나 상시 경고가 됐고
→ 매 회차 도배가 나서 억제를 넣었고
→ 그 억제 때문에 진짜로 죽었을 때 아무도 몰랐다.

#174 커밋 본문이 억제의 근거 사례로 든 소스가 **바로 그 `x_ornstein`** 이다.
그때 96h 였던 것이 억제 아래에서 303h 로 자랐다.

## 2. 실측 (2026-08-14)

측정 창은 2026-07-24 ~ 08-14 이고 판정 행 1,476개 · 회차 166회다.
출처는 운영 DB 의 `source_freshness` · `pipeline_runs` 와 Mongo `raw_items` 다.

### 2.1. 알림 실태

최근 5일 신선도 알림 발송은 0건이다.
stale 소스 셋 ( `x_ornstein` 303h · `bbc_sport` 63h · `skysports` 105h ) 이 전부 후보를 갖고 있어 억제에 걸렸다.
같은 기간 유일한 fetch 오류는 08-13 09:04 의 `arsenal_official` 503 인데, 그 소스는 `freshness_hours: 0` 이라 감시 대상이 아니다.

### 2.2. 조용한 정지는 실재한다

`x_ornstein` 은 `articles` 마지막 적재가 08-01 이고 Mongo `raw_items` 의 마지막 신규 URL 이 08-06 이다.
그 뒤 8일간 매 회차 같은 후보 5건만 반복해서 가져온다.

### 2.3. 「후보가 며칠째 그대로」 는 신호로 못 쓴다

「후보는 있는데 신규가 0」 인 회차가 이어진 최장 길이다.

| 소스 | 최장 | 현재 진행 | 실제 상태 |
| --- | --- | --- | --- |
| x_ornstein | 59회 | 59회 | 죽음 |
| guardian | 37회 | 6회 | 정상 |
| skysports | 35회 | 9회 | 정상 |
| bbc_sport | 31회 | 3회 | 정상 |

정상 소스가 31 ~ 37회씩 침묵한다.
연속 회차로 가르려면 임계를 60쯤 잡아야 하는데, 그것은 시간을 회차로 환산한 값일 뿐이다.
**후보 갱신 정지 판정은 신선도 임계의 재발명이므로 채택하지 않는다.**
URL 집합을 회차마다 저장하는 새 스키마도 그래서 필요 없다.

`bbc_sport` 목록 URL 을 1회 요청해 `html.py` 의 발견 단계를 그대로 재현했다 ( HTTP 200 · 527,635자 ).

## 3. 설계 — 소스별 임계 재조정

임계는 「이 소스치고 비정상적으로 조용하다」 의 선이다.
각 소스의 공백 95 백분위를 24h 배수로 올려 정한다.
회차 스무 번에 한 번 울리는 수준이고, 운영이 읽기 쉬운 값이다.

| 소스 | 지금 | 새 임계 | 근거 |
| --- | --- | --- | --- |
| fmkorea | 48h | **24h** | 95% 15h |
| x_afcstuff | 24h | 24h | 95% 15h — 유지 |
| bbc_gossip | 48h | **24h** | 95% 21h |
| bbc_sport | 48h | **96h** | 95% 75h |
| skysports | 48h | **120h** | 95% 99h |
| guardian | 168h | **192h** | 95% 168h |
| x_ornstein | 24h | **120h** | 95% 111h ( 살아 있던 구간 ) |
| arsenal_official | 0 | 0 | 이벤트 구동 — 감시 제외 유지 |
| goal | 48h | — | 수집 중단 대상 · 5절 |

전역 기본값 `freshness_default_hours: 48` 은 그대로 둔다.
새로 붙는 소스가 처음부터 오버라이드를 갖지는 않기 때문이다.

**되돌리기는 `config/sources.yaml` 한 줄씩이고 코드 변경이 아니다.**

### 3.1. 표본이 21일이라는 한계

이적 시장이 닫히면 모든 소스의 공백이 길어져 새 임계가 좁게 느껴질 수 있다.
값을 못 박되 재측정 절차를 런북에 남긴다.

```sql
SELECT source_id,
       COUNT(*) AS checks,
       ROUND(MAX(age_hours), 1) AS max_age,
       SUM(stale) AS stale_n
FROM source_freshness
WHERE checked_at >= NOW() - INTERVAL 30 DAY
GROUP BY source_id ORDER BY stale_n DESC;
```

stale 비율이 한 소스에서 20% 를 넘으면 그 소스의 임계를 다시 잰다.

## 4. 설계 — 억제 제거와 재알림 간격

### 4.1. 후보 조건을 발송 판정에서 뺀다

`freshness_alert_targets` 의 「후보 0건 또는 fetch 오류」 조건을 없앤다.
stale 이면 알린다.

**임계가 실태에 맞으면 억제가 필요 없다.**
3절의 새 임계로 21일을 다시 판정하면 정상 소스의 stale 비율이 이렇게 떨어진다.

| 소스 | 옛 임계 stale | 새 임계 stale |
| --- | --- | --- |
| skysports | 44/166 ( 27% ) | 0/166 ( 0% ) |
| bbc_sport | 37/166 ( 22% ) | 1/166 ( 1% ) |
| guardian | 9/166 ( 5% ) | 0/166 ( 0% ) |
| bbc_gossip | 0/166 ( 0% ) | 3/166 ( 2% ) |
| fmkorea | 3/166 ( 2% ) | 3/166 ( 2% ) |

후보 계수는 버리지 않는다.
**발송 조건에서 빼고 진단 재료로 옮긴다** — 문안에 사실로 적어 사람이 원인을 좁히게 한다.

### 4.2. 재알림은 48h 고정 간격

계속 stale 인 소스가 매 회차 울리는 것은 막아야 한다.
임계를 넘으면 한 번 알리고, 그 뒤 경과가 48h 씩 늘 때마다 다시 알린다.

**배수 ( 임계의 K배 ) 방식은 기각했다.**
임계를 실태에 맞추면 저빈도 소스의 임계가 커지는데, 거기에 배수를 곱하면 재알림이 영영 안 온다.
`x_ornstein` 임계 120h 에 3배면 15일인데 실제 경과가 12.6일이라 한 번도 안 울린다.
**간격은 임계와 독립이어야 한다.**

판정은 무상태로 한다.
`source_freshness` 이력의 직전 회차 행과 비교해 「이번에 새로 간격을 넘었는가」 만 본다.
`candidate_cliffs` 가 이미 쓰는 전이 판정과 같은 방식이다.

### 4.3. 시뮬레이션 — 21일 총 14건

3절 임계 + 4.1 억제 제거 + 4.2 간격 48h 로 21일 ( 166회차 ) 을 돌린 결과다.

| 소스 | 새 임계 | 21일 알림 | 첫 알림 |
| --- | --- | --- | --- |
| x_ornstein | 120h | 6건 | 경과 123h ( 5.1일 ) |
| bbc_gossip | 24h | 3건 | 경과 24h ( 1.0일 ) |
| fmkorea | 24h | 3건 | 경과 112h ( 4.7일 ) |
| bbc_sport | 96h | 1건 | 경과 96h ( 4.0일 ) |
| x_afcstuff | 24h | 1건 | 경과 24h ( 1.0일 ) |
| skysports · guardian | 120h · 192h | 0건 | 21일 내 임계 초과 없음 |
| 합계 | | **14건** | 평균 0.7건/일 |

억제를 완전히 없애도 도배가 아니다.
`x_ornstein` 이 죽은 뒤로는 5일째에 처음 알리고 그 뒤 이틀에 한 번꼴로 상기시킨다.

## 5. 설계 — goal.com 수집 중단의 반영

goal.com 은 수집을 중단한다 ( 사용자 판단 2026-08-14 ).
**제거 자체는 이 설계의 안건이 아니다** — 소스 정책이고 별도 PR 로 다룬다 ( 공저자 다중 귀속 세션이 연다 ).
여기서는 감시 대상에서 빠진다는 사실과, 이 설계가 같은 파일을 건드리므로 알아야 할 순서만 적는다.

### 5.1. 수집 중단 소스는 신선도 감시에서 명시적으로 빼야 한다

**이 절이 이 설계에서 goal 을 다루는 이유다.**
수집을 어떤 방식으로 끊느냐에 따라 신선도 알림이 영원히 울릴 수 있다.

- `enabled: false` 로 끊으면 `load_sources` 가 걸러 감시 루프에서 자동으로 빠진다 ( `score.py:6` ).
`football_london` 이 2026-07-30 에 정확히 그렇게 `source_freshness` 에서 사라진 것을 이력으로 확인했다 ( 47행에서 끊김 ).
- **그러나 goal 은 `enabled: false` 를 쓸 수 없다** ( 5.2절 ).
표시 설정까지 함께 사라져 기존 171건이 깨지기 때문이다.
- 대신 쓰는 `collect: false` 는 `load_sources` 가 안 본다.
그것이 표시를 지키는 이유인데, **같은 이유로 goal 이 감시 대상에 그대로 남는다**.

```
run.py:379   records = evaluate_freshness({sid: wm.get(sid) for sid in sources}, ...)
                                                             ^^^^^^^ load_sources 결과
```

수집이 멈추면 `MAX(fetched_at)` 이 영영 안 움직인다.
→ 경과가 무한히 자라 4.2절의 재알림이 48시간마다 영원히 울린다.
→ 지금 코드에서도 터진다 — 수집을 안 하니 후보가 0 이라 현재 억제의 발송 조건에 오히려 매 회차 걸린다.

**처방은 `freshness_hours: 0` 을 함께 주는 것이다.**
이미 있는 감시 제외 장치이고 ( `quality.py:66-67` · `arsenal_official` 이 쓴다 ) 코드 변경 없이 판정 루프에서 빠진다.

```yaml
- source_id: goal
  collect: false
  freshness_hours: 0    # 수집 중단 소스 — 신선도 감시 제외
```

**규칙으로 남긴다 — 수집을 끊는 소스에는 `freshness_hours: 0` 을 함께 준다.**
`enabled: false` 로 끊는 경우에는 불필요하지만, 두 방식이 공존하므로 함께 주는 편이 안전하다.

### 5.1.1. 나머지 두 알림은 어떻게 걸리는가

수집 중단 소스는 수집 계열 알림 셋에 각각 다르게 걸린다.
공저자 세션이 운영 DB 를 읽어 확인한 값이다 ( 쓰기 없음 ).

| 알림 | 걸리는가 | 이유 |
| --- | --- | --- |
| 신선도 ( 이 설계 ) | **걸린다** — 48시간마다 영원히 | 대상이 `load_sources` 결과라 `collect: false` 가 안 걸러진다 |
| 수집량 이상 | 안 걸린다 | goal 최근 12회차 평균 0.75 건으로 `min_baseline` 3.0 미만이라 판정 전에 건너뛴다 ( `quality.py:39-40` ) |
| 후보 절벽 | **한 번 걸린다** | 「직전에 있었는데 이번에 0」 전이만 잡는다 ( `quality.py:95-96` ) |

수집량 이상은 대상 소스를 `sources` 가 아니라 오늘 계수와 지난 12회차 이력의 합집합에서 만든다 ( `quality.py:32` ).
그래서 끊은 뒤에도 12회차 동안 이력으로 남아 급감 판정 대상이 되는 구조인데, goal 은 회차당 1건도 안 들어오는 소스라 기준선에 못 미친다.

후보 절벽은 **막지 않는다.**
그 알림은 「직전 회차까지 살아 있었다」 를 근거로 삼는 설계라 의도적으로 끈 소스도 한 번은 알리는 것이 맞다.
대신 **배포 직후 한 번 온다는 것을 미리 공지한다** — 안 알리면 사고로 읽힌다.

goal 은 4.3 시뮬레이션에서 알림 0건이었다.
임계표에서 빼도 총계 14건이 그대로다.

### 5.2. `enabled` 는 수집과 표시를 함께 끄는 하나의 스위치다

**`enabled: false` 로는 goal 을 끊을 수 없다.**
공저자 다중 귀속 세션이 세 가지를 실제로 넣고 렌더해 확인했다.

| 시험한 것 | 달라지는 파일 | 결과 |
| --- | --- | --- |
| `enabled: false` 만 | 481장 | 칩이 `Goal.com` → `goal` |
| `enabled: false` + 언론사 별칭 | 488장 | 칩 그대로 깨짐 — 별칭이 이 자리에 안 걸린다 |
| 위 + `articles.outlet` 채움 | 189장 | 칩은 살아나나 **공신력이 미등재로 떨어지고 기사 본문이 사라진다** |

원인은 하나의 키가 두 가지를 정하는 것이다.

```
adapters/factory.py:17   if not s.get("enabled", True): continue   ← 수집
score.py:6               ... if s.get("enabled", True)             ← 표시 · 공신력 · 본문 등급
```

- **칩** — `outlet_display` 는 저장된 `articles.outlet` → 소스 설정 → 소스 이름 순으로 떨어진다 ( `render.py:163-184` ).
언론사 사전의 별칭은 X 소스 경로에서만 쓰이므로 `medium: newspaper` 인 goal 에는 안 걸린다.
- **본문** — `serving_mode` 는 소스 설정에서 못 찾으면 `excerpt` 로 떨어진다 ( `render.py:711-713` ).
goal 은 `serving: full` 이라 소스가 사라지면 **171건이 제목만 남은 껍데기가 된다.**

**`football_london` 선례가 안전했던 것은 저장된 기사가 0건이어서다.**
표시할 것이 없으면 표시 설정이 사라져도 드러나지 않는다.
goal 은 171건이 남아 있어 조건이 다르다.
**선례를 옮겨 쓸 때는 그 선례가 통했던 조건이 지금도 성립하는지 본다.**

**처방은 수집 스위치를 표시에서 떼는 것이다** ( 사용자 판단 2026-08-14 · 수단은 렌더 실측으로 두 번 고쳐 정했다 ).

```yaml
- source_id: goal
  enabled: true         # 표시 설정 유지
  collect: false        # 수집만 중단 (신규 키)
  freshness_hours: 0    # 5.1절 — 감시 제외
```

`adapters/factory.py` 가 `enabled` 와 함께 `collect` 도 보고 건너뛴다 ( 한 줄 ).
`load_sources` 는 `collect` 를 안 보므로 표시 설정이 그대로 남는다.

- **화면 변화 0장 · 기존 171건 온전 · 새 goal 기사만 안 들어온다.**
- **기존 171건은 유지한다.**
`articles.outlet` 소급은 하지 않는다.

**나중에 기존 기사까지 내리기로 하면** `football_london` 선례를 따른다 ( 스펙 2026-07-29 §4.6 — `enabled: false` + DB 행 삭제 ).
그때 화면 비용은 아래와 같다 ( 공저자 세션이 실제 서빙 코드로 렌더해 잰 값 · 2026-08-14 ).

| | 기사 페이지 | 선수 페이지 | 선수 페이지 안의 기사 |
| --- | --- | --- | --- |
| 수집만 중단 · 기존 유지 | 변화 없음 | 변화 없음 | 변화 없음 |
| 기존까지 제거 | 171장 소멸 | **0장 소멸** | 30명이 합계 179건 잃음 |

goal.com 도메인 URL 을 다른 소스가 가진 행은 1건뿐이라 애그리게이터 복구 경로는 사실상 없다.

### 5.3. 같은 파일을 건드리는 순서

이 설계의 PR 1 은 `config/sources.yaml` 에서 3절 표의 소스들만 건드린다.
**goal 블록 전체는 별도 PR 이 소유한다** — `collect` · `freshness_hours: 0` 둘 다 그쪽이 넣는다.
goal 은 이 설계의 임계표에서 빠져 있어 손댈 값이 없다.
같은 파일의 다른 줄이라 충돌은 예상되지 않으나, 나중에 머지되는 쪽이 rebase 한다.

### 5.4. 같은 이름의 손실 지표가 잣대마다 다른 값을 낸다

이 회차에서 실제로 밟은 함정이다.
**DB 계수를 화면 손실로 옮겨 적었다가 정정했다.**

| 잣대 | 값 | 무엇을 답하나 |
| --- | --- | --- |
| goal 만 있는 소식 ( 선수 · ±1일 창 ) | 77개 | 소식이 얼마나 없어지는가 |
| 비언급 귀속이 전부 goal 인 확정 선수 ( DB 계수 ) | 3 ~ 4명 | DB 에서 그 선수의 근거가 goal 뿐인가 |
| **선수 페이지 소멸 수 ( 렌더 계산 )** | **0장** | **화면에서 무엇이 사라지는가** |

**세 번째가 화면을 말하는 유일한 잣대다.**
앞의 둘은 DB 계수이고 화면 손실이 아니다.
페이지가 생기는 조건은 귀속만이 아니라 `load_page_players` 의 선수 술어를 함께 통과하는 것이라, DB 계수에 걸린 선수들은 애초에 페이지가 없었다.
실제 서빙 코드로 goal 행을 빼고 렌더하면 선수 페이지가 51 → 51 로 그대로다.

기사 수도 171 ( 공저자 세션 ) 과 175 ( 이 설계 ) 로 다른데 사본 조회 시각 차이다.
**설명할 때 잣대를 함께 적고, 서로 다른 잣대의 값을 한 문장에 섞지 않는다.**

## 6. 설계 — 알림 메시지 다시 쓰기

### 6.1. 원칙 넷

지금 문안은 숫자를 던지고 그것이 무엇을 센 값인지 안 적는다.
아래 넷을 세 알림 ( 신선도 · 후보 절벽 · 수집량 이상 ) 에 공통으로 적용한다.

- 소스 이름을 제목에 올린다.
- 숫자마다 그것이 무엇을 센 값인지 적는다.
- 「그래서 어떤 상태인가」 와 「무엇을 하나」 를 나눈다.
- 설정에 있는 사실 ( 검색 키워드 · 적용 임계 ) 은 알림이 직접 싣는다.

### 6.2. 후보 절벽 알림 — fmkorea 실물

지금 문안의 문제는 셋이다.

- 「최근 5회: 12 → 12 → 12 → 12 → 0」 이 무엇을 센 값인지 안 적혀 있다.
후보 건수 ( 검색으로 찾은 글 · 중복 포함 ) 이지 저장된 글 수가 아니다.
- 「회차는 실패로 끝나지 않음 ( success_rate 1 )」 은 맥락이 빠졌다.
하려던 말은 「어댑터가 예외를 안 던져 실패 알림이 따로 안 갔다」 이고, 그 뜻이 문장에 없다.
- 검색 키워드가 안 나온다.
「검색 실패 4건」 의 4가 무엇인지 알려면 설정 파일을 열어야 한다.

개정안이다.

```
🚨 fmkorea 수집 0건 — 검색이 전부 막혔습니다

이번 회차에 fmkorea 에서 글을 하나도 가져오지 못했습니다.

▸ 무슨 일이 있었나
   - 검색 키워드 4개가 전부 실패했습니다
     · "아스날" (제목)          · "de roche" (제목·본문)
     · "온스테인" (제목·본문)   · "아르테타 이적 시장" (제목·본문)
   - 응답: HTTP 430 4건 — fmkorea 의 자동 수집 차단입니다
▸ 평소와 비교
   - 검색으로 찾은 글: 이번 0건 (직전 4회차는 12 · 12 · 12 · 12건)
   - 「찾은 글」 은 중복을 포함한 검색 결과 수이고, 저장된 글 수가 아닙니다
▸ 지금 어떤 상태인가
   - 이 회차에 새 fmkorea 글이 없습니다. 다음 회차에 풀리면 놓치는 글은 없습니다
     (검색이 최근 글을 매번 다시 훑기 때문입니다)
   - 파이프라인은 오류 없이 끝났습니다 — 어댑터가 예외를 던지지 않아
     실패 알림은 따로 가지 않았습니다
▸ 무엇을 하나
   - 지금은 조치하지 않습니다. 차단은 보통 저절로 풀립니다
   - 확인할 때 fmkorea 에 직접 접속하지 말고 다음 회차 로그를 보십시오
   - 회차가 계속 0이면 런북 (제목 클릭) 의 절차를 따릅니다
```

### 6.3. 신선도 알림

억제가 사라지므로 필드에 「경로 정상 생략 N」 이 없어진다.
후보 계수는 진단 재료로 필드 안에 들어간다.

```
🕰️ 신선도 경고 — David Ornstein (X) 이 12.6일째 조용합니다

── 얼마나 오래됐나
   - 291h 경과 (이 소스의 임계 120h)
   - 마지막 수집: 13일 전 (2026년 8월 1일 오후 9:03)
── 수집 경로는 살아 있나
   - 이번 회차 후보 5건 · 신규 0건 — 경로는 응답하나 새 글이 없습니다
     (후보 0건이었다면 셀렉터 · 쿠키를 의심할 자리입니다)
── 다음 알림
   - 48시간 더 지나면 다시 알립니다
```

`ADAPTER_HINTS` 는 후보 0건일 때만 붙이는 현재 규칙을 유지한다.

### 6.4. 수집량 이상 알림 — 무조건 힌트를 걷어낸다

`build_anomaly_alert` 는 지금 drop 이면 `ADAPTER_HINTS` 를, spike 면 `SPIKE_HINT` 를 근거 없이 붙인다.
같은 함정으로 SLO-5 를 두 번 고쳤다 ( #169 · #174 ).

- drop — `candidate_counts` 를 넘겨받아 후보 0건일 때만 어댑터 힌트를 붙인다.
- spike — `SPIKE_HINT` ( 「중복 유입 · 파싱 회귀 의심」 ) 를 뺀다.
대신 「후보 N건 중 신규 M건」 을 관측 사실로 적고 판단은 숫자에 맡긴다.
`build_cliff_alert` 가 이미 채택한 원칙이다.

2.5절 라이브 검증에서 「Arsenal invite offers for Martinelli and Nwaneri」 가 ④ 에서 탈락했다.
