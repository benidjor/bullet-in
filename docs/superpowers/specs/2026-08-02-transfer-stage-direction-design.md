# 영입 단계 재분류 · 이적 방향 축 설계

2026-08-02 브레인스토밍 확정본.
콘텐츠 신뢰성 감사 (`docs/superpowers/2026-07-28-content-trust-audit-handoff.md` §3 · §3.5) 가 실측한 두 문제
— 재현 오분류 110건 (배포판 461건의 24%) 과 방출 축 부재 (방출 어휘 기사 16건이 기타 · 루머 · 합의 · 관심으로 흩어짐)
— 를 해소하는 설계다.
BBC 가십 단계 롤업 트랙 (세션 메모리 bbc-gossip-stage-rollup-track) 은 이 스펙에 편입해 함께 종결한다.
이 트랙이 끝나야 선수 페이지 (#144 · draft 보류) 가 재개된다 (§8).

## 1. 배경

- 재현 오분류 110건: 현행 프롬프트로 두 번 재분류하면 두 번 다 같은 값이 나오는데 저장값과 다른 기사들이다.
  분류 패스가 `transfer_stage IS NULL` 인 행만 다루므로, 프롬프트가 개선돼도 (#147 등) 기존 기사는 옛 판정을 유지한 것이 원인이다.
- 소스별로는 BBC 가십이 49% 로 압도적이다.
  각종 단신을 모은 라운드업 한 글에 단계 하나를 붙이는 것 자체가 구조적으로 무리이기 때문이다.
  guardian 0% · bbc_sport 8% 로, 라운드업이 아닌 소스는 같은 입력으로도 낮다.
- 방출 축 부재: 현행 8종 단계 (rumour ~ official · other) 가 전부 영입 관점이라
  "트로사르, 베식타스 완전 이적…아스날 떠난다" 같은 방출 기사가 영입 뉘앙스로 읽히거나 기타로 흩어진다.
- 표시 · 저장 불일치: `serve/render.py` 의 `filter_stage()` 가 bbc_gossip 을 화면에서만 루머로 고정해,
  DB 에는 쓰이지 않는 LLM 분류값 30건이 쌓여 있다 (실제로 이 불일치로 오진 사고가 있었다).

## 3. 데이터 모델

`articles` 에 방향 컬럼 하나를 추가한다 (`storage/schema.sql` 멱등 스타일 · `ensure_schema()` 가 자동 적용).

```sql
ALTER TABLE articles ADD COLUMN IF NOT EXISTS transfer_direction VARCHAR(8);
```

| 값 | 의미 |
| --- | --- |
| `in` | 아스날로 오는 이적 (임대 영입 포함) |
| `out` | 아스날에서 나가는 이적 (임대 방출 포함) |
| `none` | 방향 없음 — 이적 무관 기사 · 다주제 라운드업 |
| `NULL` | 미분류 |

- 단계와 방향은 직교한다 — 방출도 루머 → 협상 → 합의 → 오피셜의 같은 수명주기를 밟으므로,
  단계 enum 에 방향 값을 섞지 않고 (`departure` · `out_agreed` 류 배제) 컬럼을 분리한다.
- `other` + `out` 조합을 허용한다 (예: "선수 15명 방출 확정" — 단계 불명 방출 기사).
- 미분류 판별은 현행 `transfer_stage IS NULL` 하나로 충분하다.
  방향은 단계와 같은 분류 패스에서 함께 채워지므로 별도 NULL 검사를 두지 않는다.
- `players` · `article_players` 는 무변경 (읽기만).
  선수 단위 방향 · 임대 해상도는 `players.transfer_status` 가 이미 들고 있다.
- 방향 정의는 "기사 주체 구단 기준 in / out" 으로 서술하되 현재 구현은 아스날 고정이다.
  멀티 클럽 확장 (첼시 · 토트넘 등 · 사용자 의향 2026-08-01) 시 이 정의가 일반화 지점이다.

## 4. 분류 규칙

### 4.1. 규칙 경로 — `rule_stage()` 확장

시그니처를 (stage, direction) 반환으로 넓힌다.
소스별 정책이 두 형태로 갈린다.

| 소스 | stage | direction | 근거 |
| --- | --- | --- | --- |
| arsenal_official | official (규칙 고정 · 현행) | LLM 판정 | 공홈에도 영입 · 방출 (임대 포함) 오피셜이 다 올라오므로 방향은 실재하는 값이다 |
| bbc_gossip | rumour (규칙 고정 · 신설) | none (규칙 고정) | 다주제 라운드업은 대표 단계도 대표 방향도 성립하지 않는다 |
| 그 외 | LLM 판정 | LLM 판정 | |

- bbc_gossip 행은 LLM 분류에서 완전히 빠진다 (호출 감소).
- arsenal_official 행은 분류 배치에 포함하되 stage 응답은 버리고 규칙 값을 쓰며 direction 만 취한다.
- 저장까지 규칙화하므로 표시 계층과 저장 계층이 일치하게 된다 (§5).

### 4.2. LLM 경로 — 분류 프롬프트 확장

`classify_stage_rows` 의 출력에 direction 필드를 추가한다 (stage 와 한 호출 · 입력은 현행대로 제목 + 한국어 3줄 요약).

- 방향 정의: 아스날로 오는 이적 = in · 아스날에서 나가는 이적 = out · 이적 무관 = none.
  임대 영입도 in · 임대 방출도 out 으로 새긴다.
- 혼합 기사 규칙: 제목이 내세우는 주된 이적의 방향 하나를 따르고, 요약에 살아남은 부수 언급 (예: 영입 기사 끝의 "방출 작업도 진행 중" 한 줄) 은 무시한다.
  부수 언급은 대개 제목에 없고 3줄 요약에서도 밀려나므로, 입력 단계에서 이미 주된 주제만 남는 경우가 많다.
  제목이 두 이적을 병기하는 수준의 진짜 대등 혼합 (실측 한 자릿수) 만 out 우선으로 판정한다.
  — out 우선의 근거: 방출은 희소 축 (실측 16건) 이라 놓치는 손실이 다수 축인 영입보다 크다.
  both 값 신설은 방향 필터가 생길 때 재검토한다 (§9).
- 검증: {in, out, none} 밖 응답은 none 으로 강등한다 (`normalize` 와 동일 패턴).
  모호하면 none 으로 떨어져 오판 대신 무표시가 된다 (헤드라인-온리 기사의 안전판).
- 저장 경로 (`set_stage`) 는 (stage, direction) 을 함께 쓰도록 확장한다.

## 5. 서빙 — 표시 무변경 · 내부 정리 1건

이 트랙은 화면에 보이는 것을 바꾸지 않는다.
서빙 계열 필드 침범은 아래 내부 정리 하나뿐이며, 화면 결과는 불변이다.

- `serve/render.py` `filter_stage()` 의 `bbc_gossip → rumour` 하드코딩 분기를 제거하고 저장값을 그대로 쓴다.
  저장이 규칙 경로로 rumour 를 보장하게 되므로 화면은 동일하고, 화면 · DB 오진의 원천이 사라진다.
- 순서 제약: 이 제거는 소급 배치 (§6) 가 기존 가십 행을 rumour 로 통일한 뒤에만 유효하다.
  구현 순서를 "규칙 확장 → 배치 수렴 → 하드코딩 제거" 로 고정한다.
- 방출 배지 접두 ("방출 · 이적 합의" 류) 는 채택하지 않는다.
  단계 라벨 (이적 합의 · 협상 중 · 오피셜 등) 은 방향 중립 표현이고, 방향 정보는 헤드라인이 이미 담고 있어 중복이다.
  방출 모아보기 수요가 생기면 그때 배지 · 사이드바 필터를 한 묶음으로 설계한다 (§9).
- #186 "아스날 링크 선수" 라벨 판별 (`run.py` SERVING_SELECT_SQL 의 `transfer_status='in_link'`) 은 확장하지 않는다.
  그 라벨은 "아스날 소속이 아닌데 영입 링크로 수집된 선수" 표시라, 현재 스쿼드인 방출 대상 (out_link) 에 붙이면 의미가 어긋난다.

## 6. 소급 재분류 배치

런북 `docs/runbook/2026-06-30-transfer-stage-classification-ops.md` 3절 절차를 재사용한다.
오분류 110건 해소와 방향 축 전건 부여를 한 번에 겸한다 (방향은 어차피 전건에 새로 매겨야 하므로 부분 재분류의 절약분이 없다).

1. 사전 덤프: 전건의 `content_hash` · `transfer_stage` 를 백업한다.
   되돌릴 수 없으므로 필수다.
2. `UPDATE articles SET transfer_stage = NULL` — 전건.
3. 다음 정기 회차의 분류 패스가 규칙 경로 (§4.1) 를 먼저 적용하고, 나머지를 현행 프롬프트 + 방향 축으로 재분류한다.
   arsenal_official 행도 배치에 포함돼 direction 을 받는다.
4. 수렴 확인: `transfer_stage IS NULL` 0건 · `transfer_direction` 전건 부여 · bbc_gossip 전행 rumour.

### 6.1. 비용 산정 (무료 티어 아님 — Tier 1 선불)

- 대상: 배포판 461건 중 bbc_gossip 약 52건은 규칙 경로라 LLM 제외
  → 약 409건 ÷ 배치 20건 ≈ 21회 호출 · 1회성.
- 근거: 운영 실측 월 약 ₩700 은 하루 8회 × 30일 = 240회차 (회차마다 분류보다 무거운 번역 · 요약 포함) 를 포함한 값이다.
  분류 전용 21회 호출은 그 1회차 미만의 부하로, 수십 원 미만이다.
- 속도: 429 (약 15 RPM) 기준으로도 1~2 사이클 내 수렴한다.
  2026-07-19 에 201건을 1패스로 수렴시킨 실적이 있다.
- 잔존 노이즈: 모델 흔들림 43건 (9%) 은 재분류로도 값이 오갈 수 있다.
  수용한다 (재현 오분류와 달리 계통 오류가 아니다).

## 7. 검증

- 단위 테스트: `rule_stage` 확장 (가십 · 공홈 · 기타 분기) · direction 정규화 (밖 값 none 강등) · 저장 경로 (stage + direction 동시 기록).
- 배치 후 재측정: 감사 스크립트 (인수인계 §6.2) 를 재실행해 재현 불일치율을 잰다.
  목표는 가십이 규칙 경로로 빠진 뒤 모델 흔들림 수준 (약 9%) 수렴이다.
- 방출 스팟 체크: 방출 어휘 16건 (§3.5 실측 목록) 의 direction 이 out 으로 부여됐는지 확인한다.
- 화면 불변 확인: render 하드코딩 제거 전후로 가십 카드의 배지 · 필터 건수가 동일한지 대조한다.

## 8. #144 (선수 페이지) 재개 조건

본 스펙 구현 PR 머지 · VM 반영 후, 소급 재분류 배치가 수렴
(`transfer_stage` NULL 0건 · `transfer_direction` 전건 부여 · bbc_gossip 전행 rumour)

스펙 머지만으로는 재개하지 않는다 — #144 의 보류 사유가 "오염된 단계 데이터 위에 타임라인을 지을 수 없다" 이므로, 데이터가 실제로 깨끗해진 사실을 조건으로 삼는다.
