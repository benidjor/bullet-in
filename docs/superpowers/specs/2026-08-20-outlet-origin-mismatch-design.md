# 저장된 언론사명이 원문 도메인과 어긋나는 자리 — 설계 (2026-08-20)

## 1. 배경

언론사 표기 통일 설계 (2026-08-20) 가 같은 매체의 여러 표기를 하나로 접는 처방을 확정했다.
그러면서 성격이 다른 넷을 범위 밖으로 넘겼다.
표기가 갈린 것이 아니라 **저장된 매체명이 그 기사의 원문 도메인과 아예 다른** 행이다.

그 문서 §2.3 이 이렇게 적어 두었다.

> 손으로 고친 셋도 근본 해결이 아니다.
> 같은 사이트의 기사가 다시 들어오면 또 잘못 붙는다.

이 설계가 그 근본 자리를 다룬다.
원인 추정은 「fmkorea 게시자가 말머리에 적은 매체명을 그대로 믿는다」 였다.

## 2. 실측 — 추정이 기각됐다

### 2.1. 측정 조건

| 항목 | 값 |
| --- | --- |
| 대상 | 운영 MariaDB `articles` · `source_id='fmkorea'` 235건 · 2026-08-20 조회 |
| 잣대 | `articles.outlet` 원시 저장값과 `articles.url` 의 호스트를 전수 교차 |
| 범위 | 도메인 48개 |

**저장값을 그대로 셌다.**
렌더 결과가 아니고 `outlet_display` 를 거치지도 않았다.

### 2.2. 어긋나는 것은 4건뿐이다

235건 중 **231건은 말머리와 도메인이 맞는다.**
어긋나는 것은 4건 · 1.7% 이고 그 넷이 서로 다른 고장이다.

| 저장값 | 원문 URL | 무슨 일인가 | 말머리가 틀렸나 |
| --- | --- | --- | --- |
| `A BOLA` | `t.co/Iv790raKn3` | 단축 주소를 안 풀고 저장했다 | 아니다 |
| 「메일」 | `pressreader.com/uk/the-mail-on-sunday/…` | 전재 사이트라 도메인이 매체가 아니다 | 아니다 |
| 「빌트」 | `transfermarkt.de/-bild-quot-hsv-amp-vieira-…` | 2차 인용 — 읽은 매체와 원 취재원이 다르다 | 아니다 |
| 「헤코르드」 | `ojogo.pt/…/jorge-jesus-…` | 게시자가 매체를 잘못 적은 것으로 보인다 | 그렇다 |

**뒤의 두 건은 답이 URL 문자열에 그대로 적혀 있었다.**
pressreader 경로에 `the-mail-on-sunday` 가, transfermarkt 슬러그에 `bild-quot` 이 박혀 있다.
원문을 열 필요가 없었다.

### 2.3. 「게시자를 믿어서 틀렸다」 가 아니다

넷 중 셋은 말머리가 맞고 도메인이 틀리거나 매체를 안 알려 준다.
게시자 입력이 실제로 틀린 것은 **1건**이다.

**따라서 원인 추정을 폐기한다.**
`parse_bracket` 의 `OUTLET_MAP` 은 이 넷 중 어느 것도 만들지 않았다.
그 표에는 「빌트」 · 「헤코르드」 · 「메일」 · `A BOLA` 가 아예 없다.
넷 다 말머리 원문이 그대로 지나간 값이다.

## 3. 도메인으로 덮어쓰면 지금보다 나빠진다

「도메인이 더 믿을 만하니 어긋나면 도메인을 쓴다」 가 자연스러운 처방으로 보인다.
실측에 대 보면 그렇지 않다.

| 저장값 | 도메인으로 덮어쓰면 | 판정 |
| --- | --- | --- |
| 「메일」 | `PressReader` | **나빠진다** — 전재 사이트가 매체명이 된다 |
| 「빌트」 | `Transfermarkt` | **나빠진다** — 중계한 곳이 취재한 곳의 자리를 가져간다 |
| `A BOLA` | 판정 불가 | 단축 주소라 도메인이 아무것도 안 알려 준다 |
| 「헤코르드」 | `O Jogo` | 좋아진다 |

**4건 중 1건에서만 맞는다.**
자동으로 한쪽을 택하는 규칙은 이 데이터에서 손해다.

## 4. 처방 — 갈래마다 다르게 다룬다

### 4.1. 단축 주소 — 최종 URL 을 저장한다 (유일한 코드 수정)

`fmkorea.py` 는 이미 리다이렉트를 따라가고 있다.

```python
def _client(self):
    return httpx.AsyncClient(..., follow_redirects=True, ...)

ro = await c.get(orig)        # ro.url 에 최종 주소가 들어 있다
...
out.append(RawItem(..., url=orig, ...))   # 그런데 요청 전 주소를 저장한다
```

원문 fetch 가 성공한 경우에 한해 `str(ro.url)` 을 저장 URL 로 쓴다.
**새 요청을 더하지 않는다** — 이미 받아 둔 응답에서 값을 꺼내는 것뿐이다.

적용 범위는 무료 경로 전체다.
페이월 경로는 `PAYWALLED_OUTLETS = {"The Athletic"}` 하나뿐이고 그 경로는 원문을 안 받으므로 해당이 없다.

fetch 가 실패하면 최종 주소를 모르므로 지금처럼 `orig` 를 저장한다.
**단축 주소가 남는 경우가 없어지지는 않는다** — 줄어들 뿐이다.

### 4.2. 전재 · 2차 인용 · 게시자 오기 — 값을 안 고친다

**전재 사이트 (「메일」)** — 말머리가 맞다.
도메인 판정을 붙이면 틀린 값이 된다.

**2차 인용 (「빌트」)** — 우리가 읽은 매체는 Transfermarkt 이고 취재한 곳은 Bild 다.
`outlet` 한 칸에 두 계층이 안 들어간다.
**원 취재원을 남긴다 (사용자 결정 2026-08-20)** — 독자에게 「Bild 보도」 가 「Transfermarkt 보도」 보다 쓸모 있다.
칼럼을 늘리는 선택지는 기사 1건에 스키마 · 파이프라인 · 화면이 다 따라오므로 택하지 않았다.

**게시자 오기 (「헤코르드」)** — 1건이다.
표본 1건으로 자동 판정 규칙을 만들지 않는다.

**이 1건은 2026-08-20 에 사용자 지시로 `O Jogo` 로 고쳤다** (백업 `articles_backup_20260820_105149_ojogo_fix.sql` · `outlet` 한 컬럼만 · 남은 「헤코르드」 행 0).
**그래서 이 갈래의 표본이 0 이 됐다.**
수집 쪽 자리는 그대로여서 같은 일이 다시 날 수 있는데, 이제는 셀 데이터조차 없다.
**§4.3 의 관측이 이 갈래에서는 유일한 재발 감지 수단이다.**

### 4.3. 대신 말머리와 도메인을 짝으로 남긴다

fmkorea 항목마다 `INFO` 로 한 줄 남긴다.

```
fmkorea 매체명 outlet=%s domain=%s url=%s
```

**어긋났는지를 판정하지 않는다 — 짝을 그대로 적는다.**
판정하려면 「이 도메인의 진짜 매체는 무엇인가」 를 아는 사전이 있어야 한다.
그런데 이 설계의 넷 중 셋이 그런 사전에 절대 안 들어가는 도메인이다 (`pressreader.com` 은 전재 사이트 · `transfermarkt.de` 는 2차 인용 · `t.co` 는 단축 주소).
사전을 두면 **가장 알고 싶은 세 유형을 구조적으로 못 본다.**

짝을 그대로 남기면 사전이 필요 없다.
계수는 나중에 저널에서 낸다.

```bash
journalctl -u <유닛> | grep 'fmkorea 매체명' | sed 's/.*outlet=//' | sort | uniq -c
```

**줄 수는 문제가 안 된다** — 회차당 fmkorea 신규 기사 몇 건이고 넉 달 누적이 235건이다.

**값을 바꾸지 않는다.**
이 줄은 판정이 아니라 계수를 만들려고 두는 것이다.
지금 1.7% 로는 규칙을 만들 근거가 없다.
짝이 쌓여야 다음 사람이 세어 보고 판단할 수 있다.

**같은 계수를 DB 로도 낼 수 있다** — `outlet` 과 `url` 이 둘 다 저장돼 있어 §2.1 의 교차 계수를 아무 때나 다시 돌리면 된다.
로그가 더해 주는 것은 **저장 전에 보인다는 점**과 **버려진 항목까지 남는다는 점**이다.

## 5. 왜 관측이 필요한가 — 발견 경로가 방금 하나 사라졌다

이 어긋남은 지금까지 **사용자 눈검수로만** 발견됐다.
그 검수는 화면을 본다.

언론사 표기 통일 구현이 「메일」 을 `Daily Mail` 로 접었다 (배치 8 줄 1 · 2026-08-20 관측).
접기는 이름으로 동작해서 도메인별로 갈라 접을 수단이 없다.
그래서 **pressreader 전재 1건도 화면에서는 `Daily Mail` 로 보인다.**
저장값은 「메일」 인 채 그대로 남는다.

**화면은 이제 이 어긋남을 안 보여 준다.**
관측을 안 달면 다음에 같은 일이 나도 아무도 모른다.

## 6. `content_hash` 가 함께 움직인다

`content_hash` 는 `제목 | canonical_url(url)` 의 SHA-256 이다.
`articles.url` 에는 UNIQUE 가 걸려 있다.
저장 URL 이 바뀌면 해시도 바뀐다.

**중복 판정은 좋아진다.**
지금은 같은 기사가 단축 주소로 한 번 · 실주소로 한 번 들어오면 키가 달라 두 행이 된다.
최종 URL 로 통일하면 그 쌍이 하나로 붙는다.

**기존 t.co 행 1건은 소급하지 않는다.**
`article_players` 가 `content_hash` 를 키로 잡고 있다.
해시를 고치면 그 기사의 선수 귀속이 고아가 된다.
얻는 것은 링크 한 건의 모양뿐이고 t.co 는 지금도 정상 리다이렉트한다.
**남는 잔여물로 적어 둔다** — 다음 사람이 t.co 행을 보고 코드가 안 고쳐졌다고 읽지 않게 한다.

## 7. 검증

**불변 조건은 「말머리 ↔ 도메인 불일치가 로그에 남는다」 이다.**
어긋남 건수는 유입에 따라 움직이므로 기준선으로 넘기지 않는다.

```
① 단위 테스트 — 리다이렉트를 흉내 낸 응답에서 최종 URL 이 RawItem.url 이 되는지
② 단위 테스트 — fetch 실패 시 요청 전 주소가 그대로 남는지
③ 단위 테스트 — 항목마다 말머리 · 도메인 짝이 로그에 남는지
④ 라이브 — 어댑터 단독 fetch 로 회차 하나를 돌려 로그 줄을 눈으로 확인
```

**저장값은 한 건도 안 바뀌어야 한다.**
이 변경은 URL 과 로그만 건드리고 `outlet` 을 안 만진다.

## 8. 이 트랙이 안 하는 것

- **저장값 넷의 소급 정정** — 넷 중 셋은 지금 값이 맞다.
「헤코르드」 1건은 사용자 지시로 이미 고쳤다 (§4.2) — 코드가 아니라 사람이 정한 1행 수정이다.
- **판정 규칙** — 관측이 먼저다.
- **`A BOLA` · 「빌트」 의 등재** — 저장값이 어긋난 상태로 등재하면 틀린 이름이 굳는다 (단독 매체 등재 판단의 범위).
「헤코르드」 는 `O Jogo` 로 고쳐졌으므로 그 제약에서 빠진다.
- **`OUTLET_MAP` 개정** — 이 넷과 무관한 것이 실측으로 밝혀졌다.

## 9. 남기는 구멍

**2차 인용은 계층이 둘인데 칸이 하나다.**
지금은 1건이라 원 취재원을 남기는 것으로 덮었다.
`outlet` 에 「우리가 읽은 곳」 과 「취재한 곳」 이 섞여 들어가 있다는 사실 자체는 안 없어진다.
이 유형이 늘면 칸을 나누는 판단이 다시 온다.

**관측 로그는 알려 주지 않고 쌓아 두기만 한다.**
어긋남을 자동으로 짚어 주는 줄이 아니므로 사람이 세러 가지 않으면 아무 일도 일어나지 않는다.
이것은 의도한 절충이다 — 짚어 주게 만들려면 사전이 필요하고 사전을 두면 이 설계의 넷 중 셋을 못 본다 (§4.3).
**세러 가는 것을 기억에 맡기지 않으려면 신선도 알림 같은 정기 신호에 얹어야 한다.**
**그것은 이 트랙의 범위 밖이다.**
