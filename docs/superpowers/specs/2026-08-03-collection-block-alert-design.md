# 수집 경로 차단 알림 설계

2026-08-03 브레인스토밍 확정본.
fmkorea 가 하루 다섯 번 막혀도 Discord 알림이 한 건도 오지 않고 사람이 저널을 읽어야 알게 되는 감시 공백을 메우는 설계다.
세션 메모리 `collection-block-alert-gap` 이 진단한 세 경로 미성립을 전제로 하고, 실측 기준값은 `fmkorea-430-not-batch-caused` 를 따른다.

## 1. 배경

### 1.1. 왜 알림이 오지 않았나

세 알림 경로가 전부 조건 미성립이라 침묵.

- **실패 알림** — 어댑터가 430 을 경고 로그 + 그 키워드 스킵으로 흡수해 회차가 `success_rate 1.0` · 종료 코드 0 으로 끝남.
systemd 관점에서 성공이라 `bullet-in-fail-notify` 가 발화할 이유가 없음.
- **신선도 알림 (SLO-5)** — fmkorea 는 override 가 없어 전역 임계 48시간 적용.
차단이 대개 3시간 안에 풀려 임계 근처에도 못 감.
- **수집량 이상탐지 (SLO-6)** — 최근 12회차 신규 적재 평균 0.58 로 `min_baseline` 3.0 미만이라 계산 자체가 스킵.

### 1.2. 재료는 이미 있음

차단을 감지할 신호가 이미 기록되고 있으나 알림 조건으로 쓰이지 않던 상태.

- **소스별 후보 계수** — `run.py` 가 매 회차 계산해 `pipeline_runs.candidate_counts` (JSON) 에 적재 중 (#169 · #174).
- **어댑터 검색 실패 계수** — `adapters/fmkorea.py` 의 `search_failures` 가 실패한 키워드 검색 수를 이미 셈.
- **회차 이력 조회 패턴** — SLO-6 이 `pipeline_runs` 최근 12행을 읽는 코드가 그대로 있음.

### 1.3. 실측 기준값

전 기간 (2026-07-26 – 08-03) 차단 비율.

| 구간 | 표본 | 430 | 비율 |
| --- | --- | --- | --- |
| 정기 회차 | 68 | 13 | 19.1% |
| 워치리스트 배치 | 5 | 3 | 60.0% |

- 2026-08-03 하루만 보면 회차 8회 중 2회 (06 · 15시) · 배치 4회 중 3회 (07:32 · 13:34 · 19:34) 가 430.
- 같은 날 Discord 알림은 0건이고 매번 사람이 저널을 읽어 발견.

## 2. 확정 결정 요약

| 안건 | 결정 |
| --- | --- |
| 발화 정책 | 매 발생 즉시 (A안) · 알림용 상태 저장 없음 |
| 절벽 판정 기준 | 상태가 아니라 전이 — 직전 회차 후보 1건 이상 → 이번 회차 0건 |
| 판정 재료 | `pipeline_runs.candidate_counts` 직전 1행 (이력이 곧 상태) |
| 감지 방식 | 후보 계수로 감지 + 어댑터 실패 코드를 사실로 덧붙임 (3안) |
| 배치 전멸 조건 | 검색 실패 수 = 슬라이스 인원 (부분 실패는 제외) |
| 알림 문구 | 관측 수치만 · 원인 추정 문구 (`ADAPTER_HINTS`) 미사용 |
| 채널 분리 | 이번 트랙 범위 밖 — 발화량 실측 후 재판단 |
| 서빙 · 분류 필드 | 무변경 (읽기만) |

## 3. 감지 규칙

### 3.1. 후보 절벽 — 정기 회차

판정은 `quality.py` 순수 함수 하나로 처리.

```python
def candidate_cliffs(today: dict[str, int], previous: dict[str, int]) -> list[str]:
    """직전 회차에 후보가 있었는데 이번에 0 이 된 소스 (전이만 — 계속 0 은 제외)."""
    return sorted(sid for sid, n in previous.items() if n > 0 and today.get(sid, 0) == 0)
```

- **전이로 잡는 이유** — 상태 (`후보 == 0`) 로 잡으면 이미 죽어 있는 소스가 매 회차 발화.
실측 16회차 (08-02 00시 – 08-03 21시) 에서 `arsenal_official` 은 16회 전부 후보 0 이라 하루 8건이 도배됨.
- **직전 1행만 보는 이유** — 직전 회차에 후보가 있었다는 사실 자체가 "직전까지 살아 있었다" 의 증거라 추가 이력 조건이 불필요.
- **연속 차단이 도배되지 않는 이유** — 두 번째 회차부터는 직전도 0 이라 전이가 성립하지 않음.
매 발생 즉시 발화 (A안) 를 유지하면서도 같은 차단이 반복 발화하지 않음.
- **이력 없음 처리** — `pipeline_runs` 직전 행이 없으면 (첫 회차) 판정하지 않음.
- **신규 소스 처리** — 직전 회차에 키가 없으면 0 으로 읽혀 전이가 성립하지 않음.
- **표시용 이력은 별도** — 알림 본문의 최근 추이 줄을 채우려고 최근 5행을 함께 읽음.
판정에는 직전 1행만 쓰고 나머지 4행은 표시 전용.

발송 위치는 후보 계수 로깅 직후로, 공홈 커버리지 감시 바로 옆.

- **앞쪽에 두는 이유** — 번역 · 분류 · 렌더를 기다리지 않고 차단 사실이 바로 나감.
- **직전 행 조회 시점** — 이번 회차 행은 파이프라인 마지막에 적재되므로, 이 시점의 `pipeline_runs` 최신 행이 곧 직전 회차.
- **`success_rate` 계산 가능 시점** — 어댑터 수와 `errors` 가 `gather_all` 직후 이미 확정돼 알림 본문에 쓸 수 있음.

같은 규칙을 실측 16회차에 적용한 결과.

| 소스 | 후보 계수 범위 | 후보 0 회차 | 발화 |
| --- | --- | --- | --- |
| bbc_gossip | 25 고정 | 0 | 0건 |
| goal | 7 – 16 | 0 | 0건 |
| guardian | 8 고정 | 0 | 0건 |
| skysports | 5 – 6 | 0 | 0건 |
| bbc_sport | 3 – 4 | 0 | 0건 |
| x_ornstein | 4 고정 | 0 | 0건 |
| x_afcstuff | 1 – 7 | 0 | 0건 |
| fmkorea | 9 – 13 | 4 | 4건 |
| arsenal_official | 후보 없음 | 16 | 0건 |

- 이틀에 4건 (하루 약 2건) 이고, 죽은 지 오래인 `arsenal_official` 은 조용함.

### 3.2. 배치 전멸 — 워치리스트

- **조건** — `adapter.search_failures` 가 슬라이스 인원 수와 같고 슬라이스가 비어 있지 않을 때.
- **부분 실패 제외** — 실측 3회 모두 10 / 10 전멸이고, 부분 실패는 관측된 적 없음.
- **스킵된 배치 제외** — 터널 미접속 · 60분 접촉 가드로 조기 종료한 배치는 검색 자체를 하지 않아 대상 아님.
- **이력 비교 없음** — 배치는 `pipeline_runs` 에 행을 남기지 않아 전이 판정 재료가 없음.
실측 60% × 하루 4회 → 하루 약 2.4건.

## 4. 실패 사유 계수

`adapters/fmkorea.py` 의 `_discover` 가 이미 실패마다 `search_failures` 를 올리는 자리에서 사유도 함께 셈.

- **저장 형태** — `search_failure_codes` 에 HTTP 상태 코드를 키로, 연결 오류는 `"error"` 키로 집계.
- **수집 동작 무변경** — 세는 항목만 늘고 요청 · 스킵 · 커서 규칙은 그대로.
- **회차 쪽 전달 경로** — `run.py` 가 어댑터 객체에서 꺼냄.
공홈 커버리지 감시가 `a.coverage` 를 읽는 방식과 같음.
- **계수 없는 어댑터** — 해당 줄을 알림에서 생략할 뿐 판정에는 영향 없음.

## 5. 알림 문구

원인을 만들어내지 않고 관측한 수치만 적는 것이 이 트랙의 핵심 제약.
같은 함정으로 SLO-5 를 두 번 고쳤다 (#169 · #174).

### 5.1. 후보 절벽

```
🚨 수집 후보 절벽 — 소스 1건
직전 회차까지 후보가 있던 소스가 이번 회차에 0건이 되었습니다.

fmkorea 축구 소식통 (fmkorea)
- 직전 회차 10건 → 이번 회차 0건
- 최근 5회: 10 → 10 → 0 → 10 → 0 (이번)
- 검색 실패 4건 — HTTP 430 4건
- 회차 자체는 정상 종료 (success_rate 1.0)

회차: run 3259230a
```

### 5.2. 배치 전멸

```
🚨 워치리스트 배치 전멸 — 검색 10명 전원 실패
검색한 선수 전원의 검색이 실패해 적재가 0건입니다.
커서는 전진하지 않아 다음 배치가 같은 슬라이스를 다시 검색합니다.

- 검색 10명 · 실패 10건 — HTTP 430 10건
- 마지막 fmkorea 접촉: 2026-08-03 19:34 KST
```

### 5.3. 금지 표현

- **`ADAPTER_HINTS` 미사용** — 기존 힌트는 fmkorea 에 `검색 URL 변경 · 429 차단` 을 붙이는데, 실제 응답은 430 이고 후보 0 의 원인은 알림 시점에 알 수 없음.
- **해석 문구 미사용** — 신선도 알림의 `수집 끊김 의심` 은 후보 0 과 stale 이 겹친 상태라 근거가 있으나, 절벽 알림은 단독 회차의 사실만 가짐.
- **실패 코드는 추정이 아님** — HTTP 430 은 서버가 돌려준 응답 코드라 관측 사실로 적을 수 있음.

## 6. 실패 격리

- **회차** — 알림 발송 실패가 파이프라인을 멈추지 않게 감쌈 (`ops` 뷰 생성과 같은 방식).
- **배치** — 알림 발송 뒤에도 커서 전진 규칙 · 접촉 스탬프 기록이 그대로 동작.
- **웹훅 미설정** — `send_alert` 가 이미 경고 로그로 떨어뜨리므로 추가 처리 불필요.

## 7. 테스트

판정 함수와 문구 빌더를 나눠 덮음.

- **절벽 판정** — 실측에서 뽑은 세 경우.
  - fmkorea 가 10 에서 0 으로 떨어지는 전이 (발화).
  - `arsenal_official` 처럼 직전도 이번도 0 인 소스 (침묵).
  - 직전 행이 없는 첫 회차 (침묵).
- **배치 전멸 판정** — 전멸 (발화) · 부분 실패 (침묵) · 슬라이스 0명 (침묵).
- **문구 빌더** — 원인 추정 문구가 본문에 들어가지 않는 것을 검증.
- **실패 사유 계수** — 430 응답과 연결 오류가 각각 집계되는 것을 검증.

## 9. 범위 밖

- **채널 분리** — 알림 성격별 Discord 채널 분리는 발화량을 며칠 받아본 뒤 판단.
`send_alert` 가 웹훅 환경변수 하나만 읽는 구조라 나중에 붙여도 비용이 같음.
- **`arsenal_official` 후보 0 상시** — 7월 24일 이후 후보가 잡히지 않는 별건.
이 설계는 전이만 보므로 발화하지 않고, 복구는 별도 트랙 몫.
- **최신 소식 날짜 묶음** — 오늘 들어온 기사가 기존 묶음에 합류해 화면 상단 날짜가 어제로 보이는 현상은 `serve/render.py` 소유라 이 트랙에서 다루지 않음.
- **430 자체의 회피** — 접촉 간격 · 빈도 조정은 이미 종결된 판단이라 재론하지 않음 (`fmkorea-430-not-batch-caused`).

## 10. VM 반영

- 코드만 바뀌므로 systemd 유닛 · `.env` 변경 없음.
- 선수 페이지 세션이 살아 있는 동안에는 VM 에서 `git pull` · 사이트 재렌더 · 배포를 하지 않음.
- 반영이 필요한 시점에 사용자에게 알리고 지시를 받아 진행.
