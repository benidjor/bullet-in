# 선수 페이지 서빙 개선 · 진행 단계 사다리

2026-08-04 대화 확정본.
선수 페이지의 `단계 흐름` 이 기사 수만큼 길어지는 문제와, 그 옆에 같이 쌓여 있던 화면 문제 넷을 한 번에 닫는 설계다.
구현은 별도 세션 — 이 문서는 스펙까지다.

설계 자체는 2026-08-04 에 사용자와 합의를 끝냈고 이 문서는 그것을 옮긴 것이다.
새로 더한 것은 구현이 딛고 설 코드 사실 (§7) 과 그 확인 과정에서 드러난 설계 구멍 2건 (§6) 이다.

2026-08-05 에 운영 데이터 사본으로 화면을 확인하면서 대표 선정 규칙 한 가지가 추가로 정해졌다.
오피셜 줄은 공홈 기사 중 마지막 공지를 대표로 쓴다 (§4.2).
같은 날 §4.4 실측값도 그 사본으로 다시 쟀다.

## 1. 배경

- **타임라인이 기사 수를 따라 길어진다.**
`stage_timeline()` 은 단계가 직전 기사와 달라질 때마다 노드를 하나 만든다.
2026-08-05 실측으로 레안드로 트로사르가 13줄 · 브루노 기마랑이스가 77줄이다.
- **길어진 줄의 대부분이 낮은 공신력 기사다.**
같은 사건을 여러 매체가 며칠에 걸쳐 다르게 쓰면 그 시차가 그대로 단계 오르내림으로 보인다.
원인 분해는 `docs/troubleshooting/2026-08-04-player-timeline-zigzag-has-four-causes.md` 에 있다.
- **사다리는 그중 보도 시차 (원인 D) 를 표시 정책으로 흡수한다.**
분류 오류 (원인 A) 는 선수별 단계 재추출 트랙이 따로 맡고 이 스펙 범위 밖이다.
- **함께 묶은 나머지 넷은 사다리와 무관한 화면 문제다.**
카드 높이가 들쭉날쭉한 것 · 기사가 전량 한 번에 쏟아지는 것 · 구역 제목이 사다리와 어긋나는 것 · 단계 순위가 두 곳에 서로 다르게 있는 것이다.

## 4. 묶음 1 — 진행 단계 사다리

### 4.1. 순위 정합 (선행)

단계 순위가 두 곳에 있고 서로 다르다.

| 위치 | 순서 |
| --- | --- |
| `render._STAGE_DISPLAY_GROUPS` (화면 · 실제로 그려짐) | 오피셜 · 이적 합의 · **협상 중** · 개인 합의 · 관심 · 루머 |
| `transfer_stage.SIDEBAR_STAGES` (저장 계층) | 오피셜 · 이적 합의 · **메디컬** · 개인 합의 · **협상 중** · 관심 · 루머 |

**화면 쪽 순서를 정답으로 삼아 `SIDEBAR_STAGES` 를 맞춘다.**
사용자가 확정한 `루머 → 관심 → 개인 합의 → 협상 중 (+ 메디컬) → 이적 합의 → 오피셜` 이 곧 화면 쪽 순서다.
`medical` 은 `협상 중` 묶음의 짝이므로 `negotiating` 바로 뒤에 둔다.

바뀐 뒤의 목록은 다음과 같다.

```python
SIDEBAR_STAGES = [
    ("official", "오피셜", "s-off"),
    ("agreed", "이적 합의", "s-agree"),
    ("negotiating", "협상 중", "s-talk"),
    ("medical", "메디컬", "s-med"),
    ("personal_terms", "개인 합의", "s-personal"),
    ("interest", "관심", "s-interest"),
    ("rumour", "루머", "s-rum"),
]
```

**사이드바 화면은 안 바뀐다.**
사이드바가 그리는 것은 `_STAGE_DISPLAY_GROUPS` 이고 지금도 그 순서로 나온다.
이 목록의 순서가 화면을 좌우한 적은 한 번도 없으며, 그 사실은 소비처 전수 확인으로 확정했다 (§7.1).

### 4.2. 사다리 규칙

`stage_timeline()` 이 하던 전이 판정을 묶음별 대표 선정으로 바꾼다.

- **묶음 기준은 화면 묶음 6종이다.**
저장 단계로 묶으면 `협상 중` 이 `negotiating` · `medical` 두 줄로 갈라진다.
트로사르가 저장 단계로는 6종인데 화면에서 5줄이 되는 이유가 이것이다.
- **대표는 공신력 높은 순**이다 (`articles.tier` 가 작을수록 높음).
`tier` 가 없는 행은 가장 낮은 공신력으로 취급한다 (`pick_representative()` 의 `99.0` 선례와 같음).
- **공신력이 같으면 오피셜만 가장 늦은 기사** 를 뽑고 나머지 다섯 묶음은 가장 이른 기사를 뽑는다.
공홈은 합의 때 한 번 · 확정 때 한 번 올리므로 (`docs/runbook/2026-06-30-transfer-stage-classification-ops.md`) 마지막 공지가 그 선수의 현재 상태에 가장 가깝다.
나머지 묶음에서 이른 기사를 쓰는 것은 그 단계가 처음 보도된 시점을 보여 주기 위해서다.
- 입력이 오래된 것부터 정렬돼 있으므로, 오피셜 묶음만 뒤집어 넣고 양쪽 다 안정 선택 (`min`) 으로 처리한다.
- **2026-08-05 확정** — 트로사르의 공홈 기사가 07-14 `이적 합의 완료` · 07-16 `이적 확정` 둘인데, 이른 것을 쓰면 최종 확정 기사가 건수 안으로 숨는다.
지금 데이터에서 공홈 기사가 둘 이상인 선수는 트로사르뿐이지만 (다섯 명 중 넷은 1건), 이적이 끝날 때마다 같은 상황이 생긴다.
- **정렬은 진행 단계 순**이고 오피셜이 위다.
`_STAGE_DISPLAY_GROUPS` 를 그대로 훑어 그 묶음에 기사가 있을 때만 줄을 만든다.
- **`other` · 빈 값은 줄도 건수도 만들지 않는다.**
현행 `stage_timeline()` 의 `is_displayable()` 조건을 그대로 유지한다.
- **각 줄의 건수는 그 묶음의 전체 건수**이고, 대표 말고도 더 있을 때 (`2건 이상`) 만 `같은 단계 N건` 으로 표시한다.
머리 건수 · 사이드바 건수와 같은 셈법을 쓰려는 것이며, 대표를 뺀 수를 적으면 두 숫자가 어긋난다.

의사코드는 다음과 같다.

```python
def stage_ladder(entries: list[dict]) -> list[dict]:
    """진행 단계 사다리 — 표시 묶음마다 대표 기사 하나.
    입력은 오래된 것부터 정렬된 [{"row", "stage"}], 출력은 오피셜이 앞이다."""
    group_of = {e: label for label, enums in _STAGE_DISPLAY_GROUPS for e in enums}
    buckets: dict[str, list[dict]] = {}
    for e in entries:
        if not _stage.is_displayable(e.get("stage")):
            continue
        buckets.setdefault(group_of[e["stage"]], []).append(e)

    def cred(e):                       # 공신력 (tier 작을수록 높음) · 미상은 최하
        t = e["row"].get("tier")
        return float(t) if t is not None else 99.0

    out = []
    for label, _ in _STAGE_DISPLAY_GROUPS:
        b = buckets.get(label)
        if not b:
            continue
        # 오피셜은 마지막 공지가 현재 상태다 — 뒤집어 넣어 동률에서 늦은 기사가 이기게 한다.
        seq = list(reversed(b)) if label == "오피셜" else b
        rep = min(seq, key=cred)       # 안정 선택 — 동률이면 seq 순서상 첫 기사
        out.append({"row": rep["row"], "stage": rep["stage"], "count": len(b)})
    return out
```

### 4.3. 화면

줄마다 담는 것은 **단계 배지 · 날짜 · 제목 링크 · 언론사 · 공신력 · `같은 단계 N건`** 이다.

- 공신력은 독자 라벨 (`_reader_tier`) 로만 적는다.
내부 tier 숫자는 화면에 내보내지 않는다 (UI 스펙 §7.1).
- 배지는 지금처럼 `display_stage()` 가 만든다.
`medical` 대표가 뽑혀도 배지 글자는 `협상 중` 이라 묶음 이름과 어긋나지 않는다.
- 노드 반복 · CSS 클래스 (`.timeline` · `.tlnode` · `.tldate` · `.tltitle` · `.tlsrc` · `.tlmore`) 는 그대로 쓴다.
바뀌는 것은 `이후 N건` 이 `같은 단계 N건` 이 되는 것과 공신력 한 칸이 느는 것뿐이다.
- **공신력은 언론사 칸 (`.tlsrc`) 안에 이어 붙인다.**
관련 보도 항목 (`_cards.html.j2` 의 `relitem` 매크로) 이 이미 `언론사 · 공신력` 을 한 칸에 넣는 방식을 쓰고 있어 그것을 따른다.
새 CSS 클래스를 만들지 않는다.

### 4.5. 날짜 역전은 받아들인다

§4.4 표의 날짜가 위에서 아래로 07-16 · 07-14 · 06-13 · 07-05 · 07-14 순으로 오르내린다.
맨 아래 `루머 (07-14)` 가 그 위 `협상 중 (06-13)` 보다 나중 기사다.

- **대표 선정 규칙을 바꿔도 안 없어진다.**
공식 발표 뒤에도 BBC 같은 상위 매체가 계속 보도하는데, `official` 이 공홈 전용이라 그 기사들이 전부 `이적 합의` 로 들어오기 때문이다.
낮은 단계에서도 마찬가지다 — 이적이 끝난 뒤에도 가십 · 집계 계정이 계속 쓰면 그 기사들이 `루머` 로 쌓인다.
- **사다리는 시간축이 아니라 진행 단계 축**이므로 역전 자체가 규칙 위반이 아니다.
구역 제목을 `진행 단계` 로 바꾸는 것 (§5.3) 이 이 성격을 화면에서 선언하는 몫을 맡는다.
- **뿌리는 오피셜의 의미 문제**다.
`official` 을 구단 공지 전용으로 둘 것인지는 별도 안건으로 빼 두었고 이 스펙 범위 밖이다 (§9).
그 안건을 나중에 풀면 사다리는 저절로 좋아진다.

## 5. 묶음 2 — 카드 높이 정렬 · 10개 더보기 · 제목 변경

### 5.1. 카드 높이 정렬

- **실측한 원인** — 트로사르 페이지 21개 카드 중 썸네일은 21개 전부 있는데 요약문은 11개에만 있다.
요약문은 공신력 하 · 최하 (tier 3 · 4) 기사에서 마크업 자체가 빠지도록 돼 있다 (`show_summary()`).
- **컨테이너에 `flatlist` 가 빠져 있다.**
선수 페이지 목록은 `daylist plist` 라 `align-items:start` 로 그려지고, 전체 기사 페이지가 쓰는 `flatlist` (`align-items:stretch`) 가 없다.
그래서 같은 행의 두 카드가 서로 다른 높이로 끝나고 구분선이 어긋난다.
- **조치는 선수 페이지 목록에 `flatlist` 를 붙이는 것 하나다.**
같은 행의 블록 높이가 맞춰져 구분선이 행 단위로 정렬된다.
- **요약문 2줄 자르기는 이미 적용돼 있다.**
새로 할 일이 없다는 확인이며 경위는 §6.1 에 적었다.

### 5.2. 기사 10개 단위 더보기

- 처음에 **10건**만 보이고 아래에 `더보기 · 남은 N건` 버튼을 둔다.
- 누를 때마다 10건씩 늘리고, 다 펼쳐지면 버튼 글자가 `접기` 로 바뀐다.
- `접기` 를 누르면 다시 10건으로 돌아가고 구역 머리로 스크롤한다 (`latestCollapse()` 와 같은 마무리).
- 버튼의 생김새는 기존 `.latestmore` 클래스를 그대로 쓴다.

동작 자체는 새로 쓴다.
최신 소식 · 전체 기사의 더보기는 **날짜 그룹 단위 · 7일 창** 이라 건수 단위와 셈법이 다르다.
재사용하는 것은 버튼 클래스 · 글자 문법 (`… 더보기 · 남은 N건` ↔ `접기`) · 토글 배선 방식이다.

DOM 계약은 다음과 같이 둔다.

- 서버가 11번째 블록부터 `pl-extra` 클래스를 붙이고, 버튼은 남은 건수를 글자에 담아 낸다.
- CSS 는 `.block.pl-extra{display:none}` 한 줄이다.
- 스크립트는 노출 건수 `shown` 을 들고 있다가 클릭마다 10을 더하고, 매번 블록마다 `pl-extra` 를 다시 계산해 붙인다.
- 새 클래스 이름은 `.latest` 계열 (`latestcut` · `dg-extra` · `wcut`) 과 겹치지 않게 둔다.

**필터 스크립트와 충돌하지 않는다.**
선수 페이지에는 사이드바가 없어 `applyFilters()` 가 아예 배선되지 않으며 (§7.2), 그래서 카드의 인라인 `style.display` 를 건드리는 경로가 없다.
클래스로 숨겨도 필터가 되살리거나 덮어쓰지 않는다.

**스크립트가 없으면 10건만 보인다.**
기존 `.latestmore` 버튼도 같은 성질이라 새로 생기는 제약이 아니다.

### 5.3. 제목 변경

구역 제목 `단계 흐름` 을 **`진행 단계`** 로 바꾼다.
사다리는 시간축이 아니라 진행 단계 축이므로 제목이 그것을 선언해야 한다.

**묶음 2 에 넣은 이유** — 문자열 한 줄이라 사다리 구현을 기다릴 필요가 없다.
묶음 2 만 먼저 나가면 잠깐 동안 제목이 `진행 단계` 인데 내용은 전이형 타임라인인 상태가 된다.
전이형도 진행 단계를 보여 주는 것은 맞으므로 그 사이 화면이 거짓말을 하지는 않는다.

## 6. 설계 구멍 2건

확정 설계를 코드에 대 보는 과정에서 드러난 것이다.
결정을 바꾸는 것이 아니라 구현이 걸려 넘어질 자리를 미리 적는다.

### 6.1. 요약문 2줄 자르기는 이미 돼 있다

확정 5 는 카드 높이 정렬의 조치를 `flatlist` 부착과 요약문 2줄 자르기 둘로 잡았다.
그런데 `.item .dek` 에 2줄 자르기가 이미 걸려 있다.

```css
.item .dek{font-size:13.5px;color:var(--mut);line-height:1.5;margin:0 0 7px;
  display:-webkit-box;-webkit-line-clamp:2;-webkit-box-orient:vertical;overflow:hidden}
```

UI 개편 (#121 · 2026-07-23) 때 들어간 전역 규칙이고 선수 페이지 카드에도 그대로 적용된다.
즉 요약문 **길이** 차이는 이미 없고, 남아 있는 것은 요약문의 **유무** 차이 (21개 중 11개) 다.
유무 차이는 자르기로 없앨 수 있는 성질이 아니며, 같은 행의 높이를 맞춰 구분선을 정렬하는 `flatlist` 가 그 몫을 맡는다.

**따라서 묶음 2 의 이 항목에서 실제로 할 일은 `flatlist` 부착 하나다.**

### 6.2. 현재 단계 배지는 사다리 꼭대기가 아니다

머리의 현재 단계와 선수 색인의 단계 배지는 같은 값을 쓴다.

```python
"stage": timeline[0]["stage"] if timeline else None
```

전이형 타임라인은 최신 노드가 앞이라 이 값이 **시간축 최신 단계**를 뜻했다.
사다리는 오피셜을 앞에 두므로, 같은 자리를 그대로 두면 값의 뜻이 **가장 진행된 단계**로 바뀐다.

2026-08-05 실측에서 다섯 명이 전부 달라졌다.

| 선수 | 지금 배지 | 사다리 첫 줄을 그대로 읽으면 |
| --- | --- | --- |
| 브루노 기마랑이스 | 관심 | 이적 합의 |
| 모건 로저스 | 관심 | 이적 합의 |
| 훌리안 알바레스 | 루머 | 협상 중 |
| 레안드로 트로사르 | 이적 합의 | 오피셜 |
| 크리스토스 촐리스 | 이적 합의 | 오피셜 |

기마랑이스는 최근 보도가 08-05 `관심` 인데 배지가 `이적 합의` 로 올라간다.
08-04 에 합의 임박 기사가 한 번 있었다는 것만으로 현재 상태를 잘못 말하게 된다.

**현재 단계는 시간축 최신값이라는 뜻을 유지한다.**
사다리와 별개로 마지막 기사의 단계를 따로 뽑아 이 자리에 넣는다.
기존 스펙이 정한 "머리의 현재 단계는 최신 노드 값" 의 취지가 시간축 최신이었으므로, 뜻을 바꾸지 않고 계산 경로만 사다리에서 떼어 내는 것이다.

색인 배지도 같은 필드를 읽으므로 여기서 함께 지켜진다.

## 7. 확인한 코드 사실

구현이 딛고 설 지반이다.
주석만 읽고 세 번 오진한 기록이 있어 (`docs/troubleshooting/2026-08-04-called-design-a-defect-without-reading-it.md`) 이번에는 소비처를 직접 확인했다.

### 7.1. `SIDEBAR_STAGES` 순서의 소비처

| 소비처 | 순서가 동작에 영향을 주나 |
| --- | --- |
| `_LABEL` · `_CSS` 사전 | 아니오 — 조회용 |
| `STAGE_ENUMS` → `VALID_STAGES` | 아니오 — 집합 |
| `env.globals["stages"]` | 아니오 — 템플릿에서 아무도 안 읽음 |
| `facet_counts()` 의 `stage_counts` | 아니오 — 사이드바는 `stage_groups` 를 그림 |
| `_STAGE_DISPLAY_GROUPS` | 예 — 화면에 그려지는 것은 이것뿐 |
| 사다리 (신규) | 예 — 진행 단계 순 정렬의 기준 |

**분류 프롬프트는 이 목록에서 단계 값을 읽지 않는다.**
`TRANSLATE_PROMPT` · `PARAPHRASE_PROMPT` · `EXTRACT_PLAYERS_PROMPT` 는 단계 값을 본문에 직접 적어 두고, 동기화는 테스트가 지킨다.
그래서 순서를 바꿔도 분류 동작에는 영향이 없다.

### 7.2. 선수 페이지에서 필터 스크립트는 배선되지 않는다

- `_layout.html.j2` 는 `solo` 일 때 `aside.side` 를 아예 렌더하지 않고, 선수 페이지는 `solo=True` 로 그려진다.
- `app.js` 의 배선 조건이 `items.length && side` 라, 사이드바가 없는 선수 페이지에서는 `applyFilters()` · `sortBlocks()` · `hideEmpty()` 가 한 번도 실행되지 않는다.
- 이 조건은 회귀 테스트로 고정돼 있다 (`test_serve_players.py` 의 `"items.length && side" in js`).
- 선수 페이지는 `.daylist` 가 있으면서 사이드바가 없는 유일한 페이지다.

### 7.3. 카드 · 목록 컨테이너

- 선수 페이지 목록은 `<div class="daylist plist">` 이고, 카드마다 `<div class="block">` 이 감싼다.
구분선 (`border-bottom`) 은 `.block` 에 있으므로 높이를 맞출 대상도 `.block` 이다.
- `.daylist{align-items:start}` · `.daylist.flatlist{align-items:stretch}` 이고, 후자는 전체 기사 페이지가 이미 쓴다.
- 카드 매크로는 선수 페이지에서 `show_all=True` 로 불려 기타 단계 기본 숨김 (인라인 `style="display:none"`) 이 걸리지 않는다.
즉 더보기가 클래스로 숨기는 것과 부딪히는 인라인 스타일이 없다.

### 7.4. 기존 더보기 버튼

- `.latestmore` 는 `all.html.j2` · `index.html.j2` 가 쓰고, 스크립트는 `latestReveal()` · `latestCollapse()` 로 **날짜 그룹 7일 창**을 연다.
- 버튼 글자는 남은 양이 있으면 `… 더보기 · N개 날짜`, 없으면 `접기` 다.
- 클릭 배선은 `latestMore.onclick = () => latestHiddenCount() ? latestReveal() : latestCollapse()` 한 줄이다.
- `latestWrap` 은 `.latest` 를 찾는데 선수 페이지에는 없으므로, 선수 페이지 더보기는 이 코드와 겹치지 않는 별도 블록이 된다.

## 8. 검증

### 8.1. 단위 테스트

- **사다리** — 묶음별 대표 하나 · 진행 단계 순 · 건수.
- **묶음 기준** — `negotiating` 과 `medical` 이 한 줄로 합쳐지는지.
- **대표 선정** — 공신력 높은 기사가 뽑히는지 · `tier` 가 없는 행이 최하로 밀리는지.
- **동률 방향** — 오피셜 묶음은 늦은 기사가, 나머지 다섯 묶음은 이른 기사가 뽑히는지.
공홈 기사 둘을 넣고 뒤엣것이 대표가 되는 케이스를 따로 둔다.
- **제외** — `other` · 빈 값이 줄도 건수도 만들지 않는지.
- **현재 단계** — 오피셜 기사가 섞여 있어도 머리 배지가 시간축 최신 단계인지 (§6.2 회귀 방어).
- **순위 정합** — `SIDEBAR_STAGES` 순서 검증 테스트를 새 순서로 갱신 (`test_transfer_stage.py`).
- **더보기 계약** — `player.html.j2` · `style.css` · `app.js` 가 같은 클래스 이름을 공유하는지 (기존 `.plfold` 계약 테스트와 같은 방식).
- `stage_timeline()` 의 전이 판정 테스트 넷은 사다리 테스트로 대체된다.

### 8.2. 로컬 렌더 실측

- 트로사르 페이지가 §4.4 표와 같은 5줄인지 — 날짜 · 언론사 · 건수까지 대조한다.
오피셜 줄이 07-16 `이적 확정` 이어야 한다.
- 기마랑이스 · 촐리스 · 로저스 · 알바레스가 §4.4 표의 줄 수인지.
- 카드 구분선이 행 단위로 맞는지.
- 기사 목록이 10건에서 끊기고 더보기가 10건씩 여는지 · 다 펼친 뒤 접기가 되는지.
- 선수 색인의 단계 배지가 바뀌지 않았는지 — §6.2 표의 왼쪽 값이 그대로 나와야 한다.
- 실측 데이터가 필요하면 운영 DB 를 복제해 쓴다 (`docs/runbook/2026-07-22-mockup-rerender-from-vm.md`).
로컬 `bulletin` 은 스키마가 낡아 선수 페이지가 렌더되지 않는다.

### 8.3. 배포 후 확인

- 코드 PR 은 머지 · VM 반영 · 첫 회차 확인까지가 한 묶음이다 (`docs/runbook/2026-07-20-vm-cohost-bootstrap.md` §6.1).
- 이 스펙의 변경은 스키마를 건드리지 않으므로 `ensure_schema` 선행이 필요 없다.
- 자산 (`style.css` · `app.js`) 이 바뀌므로 재렌더만으로는 반영되지 않는다 — 배포 경로를 함께 확인한다.

## 9. 남는 리스크

**사다리는 잘못 분류된 기사도 대표로 뽑는다.**

트로사르의 `medical` 후보 (07-14 · Goal) 는 "아스날, 레안드로 트로사르 베식타스 이적 합의 완료" 라는 제목을 달고 메디컬로 분류돼 있다.
§4.4 에서는 같은 묶음의 `negotiating` 후보가 더 일러 대표 자리를 가져가지만, 묶음에 기사가 그것 하나뿐이었다면 그대로 대표가 됐다.
화면에 드러나는 오류가 13줄에서 1줄로 줄 뿐 사라지지는 않는다.

**선수별 단계 재추출은 여전히 필요하다.**
사다리는 잘못된 단계를 가려 주는 것이 아니라 반복 노출을 줄이는 것이며, 값 자체를 고치는 것은 재추출 트랙의 몫이다.

## 10. 범위 밖

- **선수별 단계 재추출** — 별도 트랙 (`docs/troubleshooting/2026-08-03-player-stage-not-grounded-in-article.md`).
- **오피셜을 구단 공지 뜻으로 다시 정하는 안건** — 별도 안건.
단계 정의 재설계와 전건 재분류가 따른다.
- **적록색약 배지 보강** — 배지 글자가 이미 뜻을 나르므로 WCAG 1.4.1 은 충족한다.
선택 사항이며 이번에 하지 않는다.
