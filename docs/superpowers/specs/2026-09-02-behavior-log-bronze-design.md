# 사이트 방문자의 행동 기록을 우리 레이크하우스로 들이는 설계 (2026-09-02)

화면에서 무엇이 눌렸는지는 2026-08-23 부터 이미 기록되고 있다.
그 기록은 구글 애널리틱스로 흘러가 BigQuery 에 하루 한 덩어리씩 쌓이는데, 우리 파이프라인은 그것을 한 번도 읽은 적이 없다.
이 설계는 그 기록을 우리 Iceberg 레이크하우스로 옮겨 기사 데이터와 나란히 놓는다.

지금 gold 3모델은 전부 우리가 수집한 것을 우리가 다시 세는 내부 지표다.
방문자의 행동이 들어오면 「어떤 매체 · 어떤 이적 단계 · 어떤 기자 등급이 실제로 읽히는가」 라는 바깥 신호가 처음 생긴다.

## 1. 착수 전 실측

설계를 정하기 전에 값 여섯을 쟀다.
재는 과정에서 착수 입력에 적혀 있던 전제 하나가 뒤집혔고, 설계를 가르는 사실이 넷 더 나왔다.

### 1.1. 보관 기간은 시한이 아니었다

착수 입력은 「구글 애널리틱스의 보관 기간이 지나면 원자료가 사라진다」 를 복사의 근거로 적어 두었다.
이 내보내기에는 해당하지 않는다.

| 확인한 것 | 값 |
| --- | --- |
| 데이터셋 기본 테이블 만료 | 설정 없음 |
| `events_20260901` 테이블 만료 | 설정 없음 |
| BigQuery 샌드박스의 60일 강제 만료 | 해당 없음 (만료가 안 걸려 있다는 사실 자체가 증거) |

구글 애널리틱스 화면의 보관 설정은 그 도구 안의 탐색 보고서에 걸리는 값이고, BigQuery 로 내보낸 테이블에는 걸리지 않는다.
그러므로 이 안건에는 마감일이 없다.
값어치의 본체인 「바깥 신호」 는 만료 여부와 무관하므로 그대로 남는다.

### 1.2. 규모와 도착 시각

| 항목 | 실측 |
| --- | --- |
| 내보내기 | `bullet-in-analytics.analytics_551139164` · `asia-northeast3` |
| 쌓인 날짜 | 6일 (`20260824` · `20260828` 에서 `20260901`) |
| 전체 | 13,035행 |
| 하루 규모 | `events_20260901` 이 821행 · 832,978 바이트 |
| 도착 시각 | 다음 날 09:44 에서 10:28 KST |
| 도착 뒤 변경 | 없음 (생성 시각과 최종 수정 시각이 같다) |

날짜가 6일인데 창은 9일이다.
`20260825` 에서 `20260827` 은 공개 전이라 방문이 없었고, 구글 애널리틱스는 이벤트가 0인 날의 테이블을 만들지 않는다.

### 1.4. 조인 열쇠의 결측은 무작위가 아니다

착수 입력은 `card_hash` 가 클릭의 74% 에만 있어 「조인하면 4분의 1이 조용히 사라진다」 고 적었다.
표면별로 갈라 보니 사라지는 것이 아니라 기사 카드가 아닌 클릭이었다.

| 표면 | 건수 | 정체 | `card_hash` | 고칠 수 있나 |
| --- | --- | --- | --- | --- |
| `item` | 432 | 기사 카드 | 전량 있음 | 정상 |
| `mitem` | 88 | 홈의 매칭 갈래 항목 | 없음 | 그렇다 |
| `pcard` | 48 | 선수 카드 | 없음 | 아니다 (기사가 아니다) |
| `relitem` | 15 | 없어진 옛 마크업 | 없음 | 해당 없음 |
| `tltitle` | 4 | 선수 페이지 타임라인 제목 | 없음 | 그렇다 |

`mitem` 과 `tltitle` 은 주소에 `content_hash` 를 이미 갖고 있는데 `data-hash` 속성이 없다.
계측이 `card.dataset.hash` 를 읽으므로 빈 값이 된다.
템플릿 두 줄이면 92건이 살아난다.

`relitem` 은 템플릿에 주석으로만 남은 옛 마크업이다.
행동 기록은 과거 배포본의 흔적을 담는다는 뜻이고, 그래서 표면 값의 목록을 코드에 박아서는 안 된다.

### 1.5. 같은 행동이 두 번 도착한다

우리 계측 이벤트 4,007건에서 `bi_cid` · `bi_ts` · `event_name` 이 같은 행이 51건 겹친다.
겹친 행들은 클라이언트 · 클라이언트 시각 · 페이지가 모두 같고 구글 애널리틱스의 수집 시각만 다르다.
같은 행동이 두 번 도착한 것이다.

그래서 `user_pseudo_id` 와 수집 시각을 키로 삼으면 안 된다.
같은 행동이 다른 시각으로 오므로 겹침을 못 잡는다.
`bi_cid` 는 4,007건 전량에 있어 자연키 노릇을 한다.

### 1.6. 밖으로 나가는 데이터 요금

착수 입력이 「안 쟀다」 고 넘긴 항목이다.

| 항목 | 값 |
| --- | --- |
| 적용 SKU | `BigQuery: Network Data Transfer Out Internet Premium within Asia` |
| 단가 | 165.99 KRW/GiB · 무료 구간 없음 |
| 하루 응답 (압축 없음) | 11,815,192 바이트 |
| 하루 응답 (gzip) | 228,728 바이트 |
| 월 환산 | 6.7 MiB |
| 월 요금 | 약 1.1원 |

응답이 51배로 압축된다.
구글 애널리틱스의 JSON 은 빈 칸이 끝없이 반복되는 구조라 그렇다.
읽는 라이브러리가 gzip 을 기본으로 요청하므로 실제로 나가는 것은 압축된 쪽이다.

### 2.1. 범위를 집계까지 늘린 이유 (2026-09-03 개정)

처음에는 범위를 평탄화까지로 잘랐고 근거는 표본이 적다는 것이었다.
그 판단에서 두 가지를 섞었다.

| | 표본이 필요한가 |
| --- | --- |
| 집계 모델을 만드는 것 | 아니다 · 3건이든 3만건이든 모델은 같다 |
| 그 수치로 제품 결정을 내리는 것 | 그렇다 |

이 저장소가 안건을 재는 기준은 「스택 이름이 아니라 끝맺음」 이다.
같은 기준을 대면 「bronze 에 넣었다」 는 끝맺음이 아니고, 원자료에서 바로 쓸 수 있는 표까지 이어져야 한다.
팩트와 디멘션을 나누고 조인 키를 설계한 흔적이 남는 것도 평탄화 테이블 하나를 두는 것과 값어치가 다르다.

**그래서 gold 까지 만들되 수치를 읽는 일은 미룬다.**
집계 모델에 표본 수 컬럼 (`n_clicks`) 을 함께 두어 표본이 적다는 사실을 드러낸다.
읽는 사람이 3건짜리 칸을 보고 스스로 판단하게 하는 편이, 모델을 안 만들고 기다리는 것보다 낫다.

**화면도 이번에 만든다 (2026-09-03 재개정).**
처음에는 「빈 차트가 나온다」 를 이유로 화면을 미뤘는데, 그 문장을 재 보지 않고 적었다.
공개일을 빼고 세어 보니 매체별 상위가 31 · 31 · 29 · 25 · 24건이고 단계와 기자 등급을 교차해도 65 · 49 · 40 · 39건이다.
두 자릿수 막대가 여러 개 서므로 화면이 성립하고, `n_clicks` 를 함께 보이면 초기 자료를 정직하게 다룬 화면이 된다.

**아래 조건은 「수치를 근거로 제품을 바꿔도 되는 시점」 이다.**
파이프라인을 완성하거나 화면을 만드는 조건이 아니다 — 그 둘은 표본과 무관하게 지금 끝낼 수 있다.

| 조건 | 값 |
| --- | --- |
| 공개일 (2026-08-29) 을 표본에서 뺀다 | 그날 하루가 전체의 58% 라 평균을 왜곡한다 |
| 클릭 500건 이상 | 매체별로 갈랐을 때 상위 매체에 30건쯤 모이는 선 |
| 어림 | 공개일 뒤 하루 34에서 128클릭이라 2에서 4주 |

## 3. 만드는 것

### 3.1. 네임스페이스를 하나 더 판다

지금 카탈로그에는 `mart_history` 하나뿐이고 그 안에 운영 마트의 이력 테이블 여섯이 있다.
행동 기록은 성격이 달라 같은 이름 아래 두면 이름과 내용이 어긋난다.

```
카탈로그 bullet-in-lakehouse-prod
├── mart_history          운영 마트의 이력 (지금 있는 것 · 그대로 둔다)
└── behavior              행동 기록 (새로 판다)
    ├── ga4_events        원본
    └── ga4_events_flat   평탄화
```

나중에 Mongo `raw_items` 가 들어올 때도 자기 네임스페이스를 갖게 된다.

### 3.2. `behavior.ga4_events` — bronze

BigQuery 가 준 31컬럼을 그대로 옮긴다.
`event_params` 배열도 `device` · `geo` · `traffic_source` 중첩 레코드도 손대지 않는다.

겹친 행도 그대로 둔다.
원자료는 도착한 그대로여야 하고, 겹침을 지우는 것은 다음 층의 일이다.

파티션은 `event_date` 를 쓴다.
2θ 의 표들이 적재 날짜로 나뉜 것과 다른데, 구글 애널리틱스는 날짜가 데이터 자체의 축이라 그쪽이 조회에 맞는다.

기존 표들과 같이 `_loaded_at` 과 `_loaded_date` 를 붙인다.
언제 들어온 것인지가 남아야 적재를 되짚을 수 있다.

### 3.3. `behavior.ga4_events_flat` — silver

원본에서 파생한다.
같은 회차 안에서 그 날짜분만 만들어 덧붙이고, 원본과 같은 파티션 · 같은 메타 컬럼을 쓴다.
모양이 마음에 안 들면 통째로 지우고 원본에서 다시 만들 수 있다.

| 하는 일 | 왜 |
| --- | --- |
| 값 합치기 | 파라미터 값이 문자 · 정수 · 실수 네 칸에 나뉘어 있어 하나로 모아야 컬럼이 된다 |
| 겹침 지우기 | `bi_cid` · `bi_ts` · `event_name` 로 접는다 (실측 51건) |
| 타입 정리 | 수집 시각은 마이크로초 정수이고 `bi_ts` 는 문자열이라 둘 다 시각 타입으로 |
| 중첩 축 펴기 | `device.category` · `geo.country` · `traffic_source.source` 등을 컬럼으로 |
| 파생 컬럼 | KST 기준 날짜와 「기사 클릭인가」 판정 |

빈 값은 채우지 않는다.
`card_hash` 가 없다는 것은 기사 카드가 아니라는 뜻이고, 채우면 거짓이 된다.

컬럼은 그 날짜의 원본에 나타난 키 전량으로 세운다.
지금 39개이고 새 키가 나타나면 Iceberg 스키마 진화로 컬럼이 늘어난다.

값은 전부 문자열로 저장한다.
같은 키가 두 타입으로 오는 자리가 실제로 있다 — `session_engaged` 는 문자열 12,231건과 정수 804건, `card_tier` 는 정수 406건과 실수 41건이다.
키마다 타입을 정하려 들면 이런 예외를 손으로 다뤄야 하는데, 문자열로 모으면 그 문제가 사라지고 숫자로 쓸 때만 변환하면 된다.

### 3.4. 적재 흐름

기존 적재가 도는 자리에 한 갈래를 더한다.

1. BigQuery 에서 `events_*` 테이블 목록을 받는다.
2. `behavior.ga4_events` 에 이미 있는 날짜를 뺀다.
3. 남은 날짜가 없으면 아무것도 하지 않는다.
4. 남은 날짜를 오래된 것부터 읽어 원본에 덧붙이고 평탄화본을 만든다.

날짜가 판정 단위라 같은 날을 두 번 넣지 않는다.
처음 돌리면 6일치가 한 번에 들어오고, 그 뒤로는 하루에 한 덩어리씩 들어온다.
도착이 늦어 못 집은 회차가 있어도 다음 회차가 같은 판정으로 집어 온다.

### 3.5. `behavior` 아래 gold — star schema

평탄화 테이블 하나에서 팩트와 디멘션을 나눈다.
디멘션 둘은 이미 Iceberg 에 있으므로 새로 만들지 않고 참조한다.

| 표 | 무엇 | 어디서 |
| --- | --- | --- |
| `fact_card_click` | 클릭 한 건이 한 행 · 측정값은 건수와 표본 수 | `ga4_events_flat` 에서 |
| `dim_article` | 매체 · 등급 · 이적 단계 · 기자 · 발행 시각 | `mart_history.articles_snapshot` |
| `dim_player` | 선수 이름 · 상태 · 갈래 | `mart_history.players_snapshot` |
| `dim_date` | 날짜 · 요일 · 공개일 이후 며칠째 | 날짜에서 생성 |

표면 (`card_surface`) 은 값이 다섯뿐이라 별도 표를 만들지 않고 팩트에 그대로 둔다.

**팩트에 표본 수를 함께 싣는다.**
집계 결과에 `n_clicks` 가 붙어 있으면 읽는 사람이 3건짜리 칸과 300건짜리 칸을 가른다.
표본이 적다는 사실을 숨기지 않는 것이, 표본이 쌓일 때까지 모델을 안 만드는 것보다 낫다.

**엔진은 아직 안 정했다.**
파이썬으로 만들지, DuckDB 로 Iceberg 를 읽어 만들지가 남았다.
게이트가 이미 DuckDB 를 쓰는데 거기에 얹으면 배포를 막는 자리에 위험을 더한다 (안건 2ν).
구현 계획에서 정한다.

### 3.6. 권한

적재를 도는 서비스 계정은 `bullet-in-lakehouse` 프로젝트의 것이고, 읽을 데이터는 `bullet-in-analytics` 프로젝트에 있다.
프로젝트를 건너 읽을 권한을 붙여야 한다.

| 역할 | 어느 프로젝트에 |
| --- | --- |
| `roles/bigquery.dataViewer` | `bullet-in-analytics` |
| `roles/bigquery.jobUser` | `bullet-in-analytics` |

### 3.7. 선수 카드에 식별자를 심는다

선수 카드 클릭 48건이 어느 선수의 것인지 모르는 채로 쌓였다.
기사 카드의 `mitem` 과 같은 모양이다.
주소에는 이미 값이 있는데 계측이 읽는 속성이 없다.

```
<a class="pcard" href="player/{{ e.slug }}.html">                          지금
<a class="pcard" href="player/{{ e.slug }}.html" data-slug="{{ e.slug }}"> 고치면
```

계측 코드는 `card_slug` 를 한 줄 더 읽는다.
그러면 그 시점부터 선수 카드 클릭이 `dim_player` 와 이어진다.

**이미 쌓인 48건은 되살릴 수 없다.**
클릭이 일어난 페이지가 선수 페이지가 아니라 홈이나 목록이어서 주소에도 선수 정보가 없다.

### 3.8. 행동 지표 페이지

집계 결과를 보여 줄 자리를 새 도구 없이 만든다.

`run.py` 가 이미 `write_ops` 로 운영 뷰 (`ops.html`) 를 만들고 있고, 같은 방식으로 페이지를 하나 더 그린다.
외부 대시보드 도구를 붙이는 길도 있지만 우리 집계 결과가 Iceberg 에 있어 오히려 왕복이 생긴다.

| 무엇을 그리나 | 축 |
| --- | --- |
| 어떤 매체가 읽히나 | `card_outlet` 별 클릭 · 표본 수 병기 |
| 어떤 이적 단계가 읽히나 | `card_stage` 별 |
| 우리가 매긴 기자 등급이 맞나 | `card_tier` 별 · 등급이 높을수록 더 눌리는지 |
| 어떤 화면에서 눌리나 | `card_surface` 별 |

**표본 수를 숫자 옆에 늘 붙인다.**
공개일 하루가 전체의 58% 라 그날을 뺀 값과 포함한 값이 다르고, 어느 쪽을 보고 있는지 화면에 적는다.

### 3.9. 이 안건의 크기

| 회차 | 내용 |
| --- | --- |
| 1 | 계획서 · 프로젝트를 건너 읽는 권한 · 중첩 커밋 검증 · bronze 적재 |
| 2 | silver 평탄화 · gold star schema |
| 3 | 행동 지표 페이지 · 배포 |

세 회차로 본다.
처음 어림이 1에서 1.5세션이었는데 그때는 범위가 평탄화까지였다.

## 5. 이번 범위 밖

- **`relitem` 15건.**
  없어진 마크업이라 고칠 대상이 없다.
- **쌓여 있는 `pcard` 48건.**
  선수 카드에 식별자를 심는 것은 이번에 한다 (위 3.7).
  다만 이미 쌓인 48건은 그 값이 없어 되살릴 수 없다.
- **기존 `dbt/models/gold/` 3모델.**
  한 글자도 건드리지 않는다.

## 6. 위험

| 위험 | 어떻게 다루나 |
| --- | --- |
| 프로젝트를 건너 읽는 권한이 안 붙는 것 | 구현의 첫 태스크로 두어 다른 코드를 쓰기 전에 막힌다 |
| 중첩 구조 커밋이 실패하는 것 | 실패하면 원본만 평탄화된 형태로 받아 넣는 쪽으로 돌린다 |
| 스키마가 매 적재마다 자라는 것 | 새 키는 드물다 · 남은 스냅샷 수를 이미 로그에 남기고 있어 `metadata.json` 이 커지면 보인다 |
| 적재 실패가 기존 이력 적재를 죽이는 것 | 갈래를 나누어 이 부분이 실패해도 앞의 적재는 끝나게 한다 |
| 겹친 두 행이 다른 날짜 테이블로 갈라지는 것 | 자정 근처에서만 생길 수 있고 겹침을 날짜 안에서 접으므로 그때는 두 건이 남는다 · 규모가 51건 중 극소수라 이번에는 다루지 않는다 |
| 표본 편중을 잊고 수치를 읽는 것 | 팩트에 `n_clicks` 를 실어 표본 수가 결과에 늘 함께 보이게 한다 · 화면은 만들지 않는다 |
| 집계 엔진이 dbt 게이트에 위험을 더하는 것 | 게이트는 배포를 막는 자리다 · DuckDB 에 얹을지 파이썬으로 만들지는 구현 계획에서 가른다 (안건 2ν) |
