# 아스날 공식 소스 사이트맵 재시도와 「가려진 실패」 관측 설계 (2026-10-05)

## 1. 배경 — 무엇이 일어났나

### 1.1. 증상

2026-10-05 03:00 KST 실행의 수집 현황 화면에서 SLO-2 (실행 성공률 · 최근 30회 평균) 가 98.8% 로 목표 (99% 이상) 아래였다.
직전 12:00 UTC 화면은 99.2% 였다.

최근 30회 가운데 3회에서 아스날 공식 소스 (`arsenal_official`) 하나만 실패했다.
수집 소스가 8개라 그 실행들의 성공률은 7 ÷ 8 = 0.875 다.

```
(27 × 1.0 + 3 × 0.875) ÷ 30 = 0.9875 → 화면 표기 98.8%
```

| 실행 (UTC) | 오류 |
| --- | --- |
| 2026-10-03 15:00 | `ReadTimeout` |
| 2026-10-03 18:00 | `ReadTimeout` |
| 2026-10-04 15:00 | `ReadTimeout` |

이 실패에는 Discord 알림이 하나도 없었다.
공식 소스는 신선도 감시에서 빠져 있어 (`freshness_hours: 0` · `quality.py` 의 감시 제외), 수집 자체가 실패해도 끊김 알림이 나가지 않는다.
재집계를 하다 SLO-2 값을 보고서야 알았다.

### 1.2. 실패 지점 — 사이트맵 요청

`adapters/arsenal_api.py` 는 먼저 사이트맵 (`https://www.arsenal.com/sitemaps/articles/1/sitemap.xml`) 을 받아 최근 48시간 기사를 고르고, 기사마다 GraphQL (`GetArticle`) 로 본문을 받는다.

- 기사별 GraphQL 요청의 HTTP 오류 (시간 초과 포함) 는 기사 단위로 잡혀 그 기사만 건너뛴다.
- 사이트맵 요청의 오류만 밖으로 나가 그 실행의 소스 오류가 된다 (`raise_for_status` · 시간 제한 20초).

그래서 소스 전체를 실패시킨 `ReadTimeout` 은 사이트맵 요청에서 난 것이다.
실패한 10-04 15:00 UTC 실행의 수집 로그에는 사이트맵 응답 줄이 없다.
정상 실행 (10-04 12:00 · 18:00 UTC) 에서는 시작 뒤 2 ~ 3초 안에 사이트맵 응답 줄이 찍혔다.

### 1.3. 이력 (운영 DB `pipeline_runs` · 읽기 전용 · 2026-10-05)

첫 라이브 실행부터 627회 가운데 공식 소스 오류는 8회이고, 전부 사이트맵 요청이었다.

| 실행 (UTC) | 오류 |
| --- | --- |
| 2026-09-06 12:00 | `ReadTimeout` |
| 2026-09-22 15:00 | `ReadTimeout` |
| 2026-09-23 00:00 | `503 Service Unavailable` (사이트맵 주소) |
| 2026-09-26 06:00 | `404 Not Found` (사이트맵 주소) |
| 2026-09-30 06:00 | `503 Service Unavailable` (사이트맵 주소) |
| 2026-10-03 15:00 | `ReadTimeout` |

9월 6일에 처음 나타났고, 최근 이틀에 세 번으로 잦아졌다.
실패한 바로 다음 실행은 매번 정상이었다.

### 1.4. 우리 쪽 원인이 아니라고 본 근거

| 확인 | 결과 |
| --- | --- |
| 같은 순간 다른 소스 | 10-04 15:00 UTC 실행에서 BBC · Sky Sports · The Guardian 요청은 1 ~ 2초 안에 정상 응답 |
| 코드 변경 | 어댑터는 2026-08-12 (#263) 뒤로 바뀌지 않았다 · 첫 실패는 그 뒤 25일째 |
| 지금 재현 | VM 에서 한 번 받으면 0.07초 · 200 · 452 KB · URL 2,000개 |
| 응답 헤더 | `last-modified` 가 실행 시각과 무관 (17:54:30 등) · `cache-control: public, max-age=300, s-maxage=31536000` |

아스날 공홈 서버가 가끔 20초를 넘기거나 일시적으로 503 · 404 를 돌려준다고 본다.
서버 안에서 왜 느려지는지는 우리 쪽에서 볼 수 없어 모른다.
「정각에 캐시가 비어 느려진다」 는 가설은 헤더로 보아 근거가 약해 채택하지 않았다.

### 1.5. 이 설계가 푸는 것과 못 푸는 것

외부 서버의 근본 원인은 고칠 수 없다.
이 설계는 일시적 장애를 견디게 하고, 견딘 횟수를 숨기지 않게 한다.

이미 30회 창에 들어간 실패 셋은 이 설계로 지워지지 않는다.
SLO-2 는 실패가 창 밖으로 빠질 때 회복된다 (§6).

## 2. 재시도

### 2.1. 규칙

사이트맵 요청 한 곳만 바꾼다.
기사별 GraphQL 요청은 지금처럼 기사 단위로 건너뛴다.

| 첫 시도 응답 | 지금 | 바꾼 뒤 |
| --- | --- | --- |
| 시간 초과 · 연결 오류 (`httpx.TransportError` 계열) | 즉시 소스 실패 | 10초 뒤 1회 재시도 · 또 실패하면 소스 실패 |
| 5xx | 즉시 소스 실패 | 10초 뒤 1회 재시도 · 또 실패하면 소스 실패 |
| 4xx (404 등) | 즉시 소스 실패 | 그대로 즉시 실패 |
| 정상 | 성공 | 성공 |

404 를 재시도하지 않는 이유는, 주소가 바뀐 구조적 신호일 수 있어 재시도로 덮으면 발견이 늦어지기 때문이다.

### 2.2. 값

| 값 | 정한 값 | 이유 |
| --- | --- | --- |
| 재시도 횟수 | 1회 | 장애 길이를 모르는 상태에서 실행을 길게 붙잡지 않는다 |
| 기다리는 시간 | 10초 | 짧은 순간 장애를 넘기되 이 소스의 최악 소요를 50초 (20 + 10 + 20) 로 묶는다 |
| 시간 제한 | 20초 그대로 | 늘리면 「느림」 만 구제하고 503 · 404 는 그대로다 |

소스들은 병렬로 받으므로 이 소스가 50초 걸려도 다른 소스는 영향이 없다.
실행 전체 제한 (30분) 과도 거리가 멀다.

## 3. 기록 — 재시도가 가린 실패를 셀 수 있게

재시도가 들어가면 서버가 느려도 실패로 잡히지 않아 SLO-2 가 좋아 보인다.
그래서 재시도한 횟수와 결과를 남긴다.

### 3.1. 수집 단계 기록

어댑터의 `funnel` 속성에 아래 키를 남긴다.
`run.adapter_funnels` 가 모아 `pipeline_runs.fetch_detail.funnels.arsenal_official` 로 실행마다 저장한다.

| 키 | 값 |
| --- | --- |
| `sitemap_attempts` | 1 또는 2 |
| `sitemap_sec` | 사이트맵 받기에 걸린 시간 (재시도 대기 포함 · 소수 첫째 자리) |
| `sitemap_first_error` | 첫 시도가 실패했으면 사유 (`ReadTimeout` · `503` 등) · 아니면 없음 |

사이트맵이 끝내 실패해도 기록은 남긴다 (예외를 내기 전에 `funnel` 을 채운다).

공식 소스는 신선도 감시에서 빠져 있어 (§1.1), 이 기록이 SLO-5 판정에 들어가지 않는다.
수집 현황 화면의 「수집 단계」 칸도 신선도 감시 소스만 그리므로 바뀌지 않는다.

### 3.2. 로그

| 시점 | 수준 | 문구 |
| --- | --- | --- |
| 매 실행 | INFO | 「사이트맵 N.N초 · 시도 N」 |
| 첫 시도 실패로 재시도할 때 | WARNING | 「사이트맵 1차 실패 (사유) — 10초 뒤 재시도」 |

로그는 Airflow 수집 태스크 로그에 남는다.
정본은 §3.1 의 DB 기록이다.

### 3.3. 손으로 셀 때

```sql
SELECT started_at,
       JSON_VALUE(fetch_detail, '$.funnels.arsenal_official.sitemap_attempts')    AS attempts,
       JSON_VALUE(fetch_detail, '$.funnels.arsenal_official.sitemap_first_error') AS first_error,
       JSON_VALUE(fetch_detail, '$.errors.arsenal_official')                      AS final_error
FROM pipeline_runs
WHERE JSON_VALUE(fetch_detail, '$.funnels.arsenal_official.sitemap_attempts') = 2
ORDER BY started_at DESC LIMIT 30;
```

`attempts` 가 2 이고 `final_error` 가 비어 있으면 재시도가 가린 실패다.

## 4. 읽는 자리 — 수집 현황 화면과 알림

기록만 하고 아무도 읽지 않으면 신호가 아니다.
그래서 읽는 자리를 둘 둔다.

### 4.1. 수집 현황 화면 (SLO 표 아래 한 줄)

SLO 표 아래 해설 줄에 한 줄을 더한다.

> SLO-2 최근 30회 가운데 사이트맵 재시도로 구한 실행은 N회다.

- N 은 SLO-2 와 같은 창 (최근 30회 · `RECENT_RUNS`) 에서 `sitemap_attempts` 가 2 이고 공식 소스 오류가 없는 실행 수다.
- 0회여도 줄을 그린다 (값이 없는 것과 0 을 구별).
- 기록 키가 아직 없는 옛 실행은 세지 않는다.

SLO-2 숫자 바로 아래에 있어, 숫자가 좋아 보여도 무엇이 가려졌는지 같은 화면에서 읽힌다.

### 4.2. Discord 알림 (경향 채널)

할 일이 있는 경우에만 보낸다.

| 경우 | 알림 | 이유 |
| --- | --- | --- |
| 재시도로 구함 | 없음 | 서비스는 정상이고 받는 사람이 할 일이 없다 · 화면 한 줄에서 센다 |
| 재시도까지 실패 | 1건 | 그 실행에서 공식 기사 수집이 0 이고 SLO-2 에 잡힌다 · 원인 확인 |
| 404 (재시도 안 함) | 1건 | 주소가 바뀌었을 수 있다 · 구조 변화 확인 |

채널은 경향 (`CHANNEL_TREND`) 이다.
외부 서버의 일시 장애는 우리가 고칠 수 없고 다음 실행에서 대개 풀린다.

알림에는 SLO-2 여유를 함께 싣는다.
받는 사람이 「이번 실패로 SLO-2 가 미달이 되는가」 를 바로 판단하게 하기 위해서다.

```
⚠️ 공식 소스 사이트맵 수집 실패 — 이번 실행 공식 기사 0건
사유: ReadTimeout → 재시도도 ReadTimeout
SLO-2 여유: 최근 30회 중 소스 실패 3회 (2회까지 충족)
실행: 10-05 03:00 (UTC 10-04 18:00)
```

- 「소스 실패」 는 SLO-2 와 같은 창에서 성공률이 1 보다 작은 실행 수다 (공식 소스에 한정하지 않음).
- 「2회까지 충족」 은 지금 소스 수 (8) 와 목표 (99%) 에서 계산한다 · 소스 수가 바뀌면 같이 바뀐다.
- 「실행」 칸은 알림 공통 함수 `notify.run_label` 을 쓴다 (#525).

## 5. 시험

### 5.1. 단위 테스트

HTTP 는 기존 어댑터 테스트처럼 `respx` 로 흉내 내고, 재시도 대기는 테스트에서 0초로 바꾼다.

| 대상 | 경우 | 기대 |
| --- | --- | --- |
| 어댑터 | 정상 | 시도 1 · 결과 그대로 · `sitemap_first_error` 없음 |
| 어댑터 | 시간 초과 → 성공 | 시도 2 · 기사 수집됨 · 첫 실패 사유 `ReadTimeout` |
| 어댑터 | 503 → 성공 | 시도 2 · 첫 실패 사유 `503` |
| 어댑터 | 404 | 재시도 없이 예외 · 시도 1 기록 |
| 어댑터 | 시간 초과 → 시간 초과 | 예외 (지금처럼 소스 오류) · 시도 2 기록 |
| 화면 | 최근 30회 중 재시도 구함 2회 · 재시도 실패 1회 · 기록 없는 옛 행 | 「N회」 = 2 |
| 화면 | 재시도 0회 | 「0회」 줄이 그려짐 |
| 알림 | 재시도까지 실패 · 404 | 경향 채널 · 사유 · SLO-2 여유 · 실행 칸 |
| 알림 | 재시도로 구함 | 알림 없음 |

### 5.2. 머지 전 확인

공식 소스 어댑터 하나만 실제로 한 번 `fetch()` 해 `funnel` 이 `sitemap_attempts: 1` 로 채워지는지 본다.
접속은 한 번이고 출력은 파일로 받는다.

## 6. SLO-2 와의 관계

### 6.1. 이미 창에 들어간 실패

이 설계를 머지해도 10-03 · 10-04 의 실패 셋은 30회 창에 남는다.
새 실패가 없다면 이렇게 회복된다.

| 실패 | 창에서 빠지는 첫 실행 (UTC) | KST | 그 실행의 SLO-2 |
| --- | --- | --- | --- |
| 10-03 15:00 | 10-07 09:00 | 10-07 18:00 | 99.2% |
| 10-03 18:00 | 10-07 12:00 | 10-07 21:00 | 99.6% |
| 10-04 15:00 | 10-08 09:00 | 10-08 18:00 | 100% |

30회 창은 현재 실행과 그 앞 87시간 (29 × 3시간) 이다.

### 6.2. 수동 실행으로 창을 당기지 않는다

손으로 실행을 여러 번 더 돌리면 「최근 30회」 가 빨리 채워져 실패가 일찍 창 밖으로 밀려난다.
측정 대상을 조작해 지표를 맞추는 일이라 하지 않는다.

### 6.3. 범위 밖으로 둔 SLO-2 의 문제

- **창 길이** — 2026-07-14 수집 현황 화면 설계는 「30회 = 하루 4회 스케줄 기준 약 일주일」 로 정했다. 2026-07-20 스케줄이 하루 8회가 되면서 30회는 약 3.7일이 됐다. 창을 시간 (7일) 으로 다시 정할지는 이번 결과와 떼어 별도 안건에서 정한다.
- **목표 99% 의 근거** — 2026-05-27 최초 설계에서 운영 데이터 없이 정한 값이다. 첫 라이브부터 627회 평균은 99.44% 다.

## 7. 범위 밖

- 다른 소스의 재시도 (지금 문제는 공식 소스 사이트맵뿐)
- 시간 제한 늘리기 · 재시도 2회 이상
- 공식 소스를 신선도 감시에 넣기 (이벤트 구동 소스라 감시 제외를 유지 · 수집 실패는 §4.2 알림이 맡음)
- 사이트맵 대신 다른 발견 경로 찾기
