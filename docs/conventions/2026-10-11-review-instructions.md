# 서브에이전트 구현 · 리뷰 지시에 붙이는 문구

계획서를 서브에이전트에게 맡겨 구현할 때 (Subagent-driven development) 구현 지시와 리뷰 지시에 그대로 붙이는 문구의 정본이다.
문구를 고칠 때는 이 문서만 고친다.
지시를 쓸 때마다 손으로 옮겨 적으면 몇 줄씩 빠지기 때문이다.

## 1. 왜 있나

CLAUDE.md 의 행동 가이드라인 (Karpathy 4원칙) 은 처음부터 있었다.
2026-10-07 에 6월부터의 커밋 · 메모리 · 트러블슈팅을 원칙별로 다시 읽었더니 원칙 1 (가정 · 확인하지 않은 단정) 이 매 기간 가장 많이 어겨졌다.
원칙 3 (수술적 변경) 도 「부분」 판정을 벗어나지 못했다.

규칙을 글로 더 적는 방식으로는 재발이 멈추지 않았다.
멈춘 것은 검사기를 만든 경우뿐이었다 (PR 본문 섹션 이탈 8건 → `check-pr-format.py` · 문서 서식 → PostToolUse 훅).
그래서 이 문서는 두 가지를 함께 둔다.

| 종류 | 무엇 | 강제 수준 |
| --- | --- | --- |
| 기계 검사 | 계획서 · 스펙 절 검사기 · 범위 검사 (§5) | 자동 또는 실행 시점 고정 |
| 지시 문구 | 구현 · 리뷰 지시에 붙이는 줄 (§2 · §3) | 리뷰어가 읽어야 작동 |

## 2. 구현 지시에 붙이는 원칙 줄

구현 서브에이전트에게 주는 지시의 머리에 아래를 그대로 붙인다.

```markdown
## 작업 원칙 (CLAUDE.md 행동 가이드라인 · Karpathy 4원칙)

- **생각 먼저** — 가정을 적는다. 계획서와 코드가 다르면 고치지 말고 멈춰서 보고한다.
- **단순함** — 계획서에 없는 기능 · 설정 · 추상화를 더하지 않는다.
- **수술적 변경** — 작업의 Files 목록 밖 파일을 고치지 않는다. 인접 코드 · 주석 · 서식을 「개선」 하지 않는다. 넣을 만한 것은 보고만 한다.
- **목표 주도** — 실패하는 테스트를 먼저 보고 통과시킨다. 「통과했다」 는 실행한 명령의 출력으로 보고한다.
- **근거** — 보고 · 커밋 · 주석의 숫자와 사실은 실행한 명령이나 읽은 파일에 닿아야 한다. 닿지 않으면 「추정」 이라고 쓴다. 「없다」 · 「0건」 에는 찾은 범위를 붙인다.
```

## 3. 리뷰 지시에 붙이는 문구

작업 리뷰와 최종 리뷰 지시에 아래를 그대로 붙인다.
세 항목 모두 리뷰어가 따로 찾아야 하는 것이고, 테스트 통과로는 드러나지 않는다.

```markdown
## 반드시 찾을 것 (CLAUDE.md 행동 가이드라인)

1. **근거 없는 단정** — 보고 · 커밋 메시지 · 주석 · 문서의 숫자와 사실마다 그것을 낸 명령이나 파일이 있는지 본다. 없으면 Important 로 올린다 (「추정」 표시가 있으면 제외).
2. **요청 밖 변경** — 계획서의 Files 목록 밖 파일 · 설계에 없는 동작 · 설정 추가는 Important 다. 좋은 변경이어도 고치라고 하지 말고 「넣지 말고 보고」 로 적는다.
3. **기대값 다시 세기** — 테스트의 정답 값과 보고의 수치를 계획서에서 베끼지 말고, 지표 정의와 픽스처 · 실측 데이터로 직접 다시 센다. 다르면 어느 쪽이 맞는지 근거와 함께 적는다.
```

3번이 있는 이유는 계획서의 기대값이 테스트 정답으로 들어가면 구현 · 테스트 · 리뷰가 같은 값을 보고 함께 통과하기 때문이다.

## 4. Minor 지적의 처리 (2026-10-11 결정)

| 지적 | 처리 |
| --- | --- |
| 설계 안의 Minor | 고친다 · 묻지 않는다 |
| 설계 밖의 Minor | 고치지 않는다 · 마지막 보고에 목록으로 올리고 사용자가 정한다 |

설계 안은 계획서 · 스펙이 정한 동작과 파일 안에서 끝나는 수정이다.
이름 · 오타 · 주석 · 테스트 보강이 여기에 든다.
설계 밖은 계획서에 없는 동작 · 파일 · 설정을 더하거나 바꾸는 수정이다.

## 5. 기계 검사

| 검사 | 언제 | 무엇 |
| --- | --- | --- |
| `.claude/hooks/check-plan-sections.py` | 계획서 · 스펙을 Write · Edit 로 저장할 때 (훅) · PR 의 CI | 계획서의 「작업 원칙」 · 「가정과 확인」 · 「더 단순한 꼴과 버린 이유」 절과 Task 별 `**Files:**` 블록 · 스펙의 「가정과 확인」 · 「더 단순한 꼴과 버린 이유」 절 · 표의 빈 칸 |
| `.claude/tools/check-plan-scope.py --plan <계획서>` | 최종 리뷰 전 · PR 생성 전 (손으로 실행) | 브랜치에서 바뀐 파일 가운데 계획서 Files 목록에 없는 것 |

절 검사기는 파일 이름 날짜가 2026-10-12 이후인 문서에만 훅 · CI 로 걸린다.
그 전 문서는 경로를 손으로 주면 검사한다.
Bash 로 쓴 파일은 PostToolUse 훅이 보지 못하므로 CI 단계가 함께 있다.

범위 검사에서 「범위 밖」 이 나오면 고치기 전에 둘 중 하나로 정한다.
계획서가 빠뜨린 파일이면 계획서 Files 목록을 고친다.
요청 밖 변경이면 되돌리고 보고한다.

## 6. 이 문서가 못 하는 것

- 지시 문구는 리뷰어가 따라야 작동한다 · 따랐는지는 리뷰 결과를 읽어야 안다
- 절 검사기는 표의 칸이 비지 않았다는 것만 본다 · 적은 확인 방법이 실제로 돌았는지는 보지 않는다
- 범위 검사는 파일 단위로만 본다 · 목록 안 파일 속의 설계 밖 변경은 §3 의 2번 리뷰 몫이다
- 대화 답변의 숫자 · 사실에 근거를 붙이는 규칙은 기계로 강제할 수 없다
