# 반환형 변경이 문서 속 스니펫을 조용히 무력화 (2026-08-02)

이적 방향 축 (PR #194) 이 두 함수의 반환형을 넓히면서, 런북과 감사 문서에 실려 있던 스니펫 두 개가 옛 계약 위에 남았다.
2026-07-19 에 기록한 스니펫 드리프트 (`2026-07-19-runbook-snippet-logic-drift.md`) 의 재발이지만 고장 방식이 다르다.
그때는 분기가 빠진 것이라 결과가 틀렸고, 이번에는 **조회 대상이 0건이 되어 아무 문제가 없다고 보고**하는 형태였다.

## 1. 무엇이 바뀌었나

- `transfer_stage.rule_stage(source_id)` — 단일 값 (`"official"` 또는 `None`) → 쌍 (`("official", None)` · `("rumour", "none")` · `(None, None)`).
- `enrich.classify_stage_rows(...)` — `content_hash → stage` → `content_hash → (stage, direction)`.

두 함수 모두 파이프라인 코드에서는 같은 PR 안에서 호출부를 함께 고쳤다.
문제는 코드가 아니라 문서에 사본으로 실려 있던 호출부였다.

## 2. 증상 — 두 스니펫이 각각 다르게 고장났다

**① enrich 전용 런북 §3 의 분류 블록** — 잘못된 값을 쓴다.

```python
for h, s in classify_stage_rows(staged, client, GEMINI_MODEL).items():
    mart.set_stage(h, s)          # s 가 이제 (stage, direction) 튜플이다
```

- 튜플이 `transfer_stage` 컬럼에 그대로 바인딩된다.
- `rule_stage` 분기가 없어 공홈 행이 LLM 판정을 받고, official 은 프롬프트에서 제외돼 있으므로 오피셜이 유실된다.

**② 감사 스크립트 §6.2 의 대상 필터** — 아무 것도 검사하지 않으면서 성공처럼 보인다.

```python
target = [r for r in rows if not transfer_stage.rule_stage(r["source_id"])]
```

- 튜플은 `(None, None)` 이어도 참이므로 `not` 이 항상 거짓이 된다.
- `target` 이 빈 리스트가 되고, 스크립트는 `흔들림 0 · 재현 불일치 0 / 공통 0` 을 출력한다.
- 이 출력은 "오분류가 없다" 로 읽힌다 — 실제로는 한 건도 재분류해 보지 않았다.
- 같은 스크립트의 비교부 (`runA[h] != runB[h]`) 도 튜플끼리 비교하게 돼, 방향이 흔들린 건이 단계 흔들림으로 집계된다.

## 3. 어떻게 발견했나

- 소급 재분류를 실행하는 운영 게이트에서 이 절차들을 실제로 쓰려고 읽다가 발견했다.
- 즉 발견 경로가 리뷰가 아니라 **실행 직전 통독** 이었다 — 코드 리뷰는 문서 속 사본을 검사 범위로 보지 않았다.
- 감사 스크립트는 그대로 돌렸다면 오류 없이 "문제 없음" 을 출력했을 것이고, 그 숫자로 트랙을 종결했을 수 있다.

## 4. 예방 규칙

- **공개 함수의 반환형을 바꾸면 문서부터 grep 한다** — 호출부 수정은 인터프리터가 강제하지만, 문서 사본은 아무도 강제하지 않는다.

```bash
# 반환형을 넓혔다면 그 함수를 인용하는 문서를 모두 찾는다
grep -rn "rule_stage\|classify_stage_rows" docs/
```

- **건수 0 은 성공 신호가 아니라 의심 신호로 다룬다** — 감사 · 검증 스크립트가 "대상 0건" 을 내면 통과가 아니라 필터를 먼저 의심한다.
- 스니펫이 파이프라인의 어느 블록을 미러하는지 문장으로 적는다 (2026-07-19 규칙 유지).
이번 정정에서 런북 §3 블록에 "run.py 분류 패스와 같은 형태를 유지한다" 를 명시했다.
- 진리값 판정 (`if x` · `not x`) 은 반환형이 넓어질 때 가장 먼저 깨지는 표현이다.
`is None` 처럼 값을 특정해 비교하면 같은 변경에서 조용히 뒤집히지 않는다.
