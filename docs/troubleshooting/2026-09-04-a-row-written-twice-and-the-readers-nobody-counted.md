# 행을 두 번에 나눠 적었더니 세지 않은 독자가 셋 나왔다 (2026-09-04)

회차를 Airflow 로 옮기는 첫 PR (#461 · 안건 2ε 계획서 태스크 1에서 3) 에서 회차 행 (`pipeline_runs`) 의 쓰기 시점을 바꿨다.
종전에는 회차 끝에 한 번 삽입했고, 이제는 `collect` 가 끝날 때 삽입하고 `publish` 가 끝날 때 `finished_at` · `duration_sec` 을 채운다 (스펙 §5.3).
스펙은 이 변경이 흔드는 자리를 둘 (절벽 판정 · SLO-6 이력) 로 셌는데 실제로는 다섯이었다.
셋은 코드 리뷰 (태스크 리뷰 하나 · 최종 리뷰 하나) 가 잡았고 구현자의 잘못은 하나도 없었다.
셋 다 계획서를 그대로 옮긴 결과였다.

## 1. 증상 (머지됐다면 이렇게 보였을 것)

### 1.1. 같은 회차를 다시 돌리면 마지막 문장에서 죽는다

1. `collect` 를 같은 `run_id` 로 다시 돌린다 (Airflow 에서 태스크를 clear 하거나 사람이 `--stage collect --run-id <같은 값>` 을 친다).
2. 수집 · 원본 저장 · 마트 upsert 가 전부 다시 돌고 마지막 문장인 회차 행 INSERT 가 `Duplicate entry` 로 죽는다.
   `run_id` 가 기본 키라서다.
3. 가장 비싼 일을 다 한 뒤 가장 싼 한 줄에서 실패한다.

### 1.2. 웨어하우스에 끝나지 않은 회차가 영원히 남는다

1. 회차는 매시 정각 (UTC 3시간 간격) 에 시작하고 상한이 30분이다.
2. 웨어하우스 적재 타이머는 같은 시각의 20분 뒤에 돈다.
3. 회차가 20분을 넘기면 적재가 `collect` 와 `publish` 사이에 들어와 `finished_at` 이 빈 행을 복사한다.
4. 적재는 `started_at` 워터마크로 새 행만 덧붙이고 한 번 복사한 행은 다시 안 본다.
   그 회차는 웨어하우스에 영원히 「끝나지 않은 회차」 로 남는다.

### 1.3. 회차 하나가 중간에 죽으면 운영 화면이 나흘 멈춘다

1. `enrich` 나 `publish` 에서 예외가 나거나 유닛이 시간 상한으로 죽는다.
2. 종전엔 행이 아예 없었는데 이제는 `duration_sec` 이 빈 행이 남는다.
3. 운영 화면 집계 (`MartStore.ops_snapshot`) 는 최근 30회차를 조건 없이 읽고, 렌더 (`serve/render.py`) 가 `sum(r["duration_sec"] for r in runs)` 을 한다.
4. `None` 을 더하다 `TypeError` 가 나고 `write_ops` 는 예외를 삼키고 회차를 계속 보낸다.
5. 그 행이 30회차 창 안에 있는 동안 (하루 8회차라 약 나흘) `ops.html` 은 갱신되지 않는다.
   판정기가 옛 코드로 롤백해도 옛 렌더가 같은 `sum` 이라 풀리지 않는다.

## 2. 원인

스펙 §5.3 은 「따라 고치는 것 둘」 이라고 적었다.
절벽 판정과 SLO-6 이력 조회다.
둘 다 `run.py` 안에 있는 독자라 스펙을 쓰면서 눈에 들어왔다.

그 행을 읽는 곳은 `run.py` 밖에도 있었다.

| 독자 | 어디 | 스펙이 셌나 | 무엇이 깨졌나 |
| --- | --- | --- | --- |
| 절벽 판정 | `run.py` `CANDIDATE_HISTORY_SQL` | 예 | 삽입이 뒤에 오므로 그대로라고 봤는데, 삽입이 upsert 가 되자 재실행이 자기 행을 직전 회차로 읽게 됐다 |
| SLO-6 이력 | `run.py` `VOLUME_HISTORY_SQL` | 예 | 자기 `run_id` 제외 조건 한 줄 |
| 운영 화면 | `storage/mariadb.py` `ops_snapshot` | 아니오 | 미완 행을 합산해 `TypeError` |
| 웨어하우스 적재 | `warehouse.py` `load_ops` | 아니오 | `started_at` 워터마크가 미완 행을 영구 복사 |
| 재실행 | `run.py` `RUN_INSERT_SQL` | 아니오 | 기본 키 충돌 |

「이 값을 쓰는 곳」 을 grep 으로 세지 않고 기억으로 셌다.
`pipeline_runs` 를 문자열로 찾으면 다섯 파일이 나온다.
그 검색은 30초짜리였고 스펙을 쓴 뒤 다섯 시간이 지나서야 리뷰어가 대신 했다.

## 3. 고친 것

전부 PR #461 안에서 고쳤다.

- **재실행** — 회차 행 삽입을 `INSERT … ON DUPLICATE KEY UPDATE` 로 바꿨다.
  값 열 열하나만 갱신하고 `finished_at` · `duration_sec` 은 건드리지 않는다.
  원본 저장은 중복을 건너뛰고 마트는 이미 upsert 라 이 한 줄이 `collect` 의 유일한 비멱등 자리였다.
- **절벽 판정** — `CANDIDATE_HISTORY_SQL` 에 `run_id <> :rid` 를 붙였다.
  SLO-6 이력과 같은 처방이다.
- **웨어하우스** — `OPS_SOURCES` 의 `pipeline_runs` 워터마크 열을 `started_at` 에서 `finished_at` 으로 바꿨다.
  한 토큰이다.
  `finished_at` 은 `started_at` 보다 늦고 회차는 겹치지 않으므로 전환 시 중복도 유실도 없다.
  끝내 못 끝난 회차는 복사되지 않는데, 지금까지도 그런 회차는 행 자체가 없었다.
- **운영 화면** — `ops_snapshot` 의 회차 조회에 `WHERE finished_at IS NOT NULL` 을 붙였다.
  렌더 쪽에서 `None` 을 빼는 대안도 있었지만 「운영 화면의 회차 = 마감된 회차」 가 뜻에 맞아 SQL 쪽을 골랐다.

스펙 §5.3 의 「따라 고치는 것」 은 이 문서와 같은 PR 에서 넷으로 고쳤다.

## 4. 남은 것

- 이 전환 전에 마감 안 된 채 웨어하우스에 복사된 행이 있었다면, 마감된 뒤 `finished_at` 워터마크로 한 번 더 복사돼 `ops_pipeline_runs` 에 같은 `run_id` 가 둘 남을 수 있다.
  회차가 3시간 간격이라 실제로는 드물다.
  PR B 뒤 첫 적재 로그에서 센다.
- 재실행된 `collect` 는 `started_at` 도 갱신한다.
  판정이 명시한 결과이고 회차 이력의 순서에는 영향이 없다.

## 5. 교훈

행의 쓰기 시점을 바꾸는 설계는 그 행을 읽는 곳과 복사하는 곳을 전부 세고 나서 적는다.
세는 도구는 기억이 아니라 grep 이다.
「따라 고치는 것 둘」 처럼 개수를 적었으면 그 개수가 검색 결과와 같은지 한 번 대 본다.

같은 병을 앞서 한 번 앓았다.
뒤 층이 앞 층의 진행에 얹히면 앞 층이 먼저 끝나는 순간 조용히 멈춘다는 것 (2026-09-03 · 행동 로그 적재 · 세션 메모리 `each-layer-needs-its-own-watermark`) 도 「같은 값을 읽는 곳이 하나 더 있었다」 는 이야기다.
