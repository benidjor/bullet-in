# 복구 절차를 찾다가 백업이 하나도 없다는 것을 알았다 (2026-09-01)

안건 우선순위를 다시 재던 회차에서 「이 서비스가 지금 잃고 있는 것」 을 세다가, 운영 DB 를 되살릴 방법을 찾아봤다.
찾은 것이 없었다.

이 문서는 고친 기록이 아니라 **없다는 것을 확인한 기록**이다.
고치는 일은 별도 안건으로 넘겼다.

## 1. 무엇을 찾았고 어디까지 찾았나

「없다」 를 말하려면 찾은 범위를 함께 적어야 한다.

| 찾은 곳 | 찾은 말 | 결과 |
| --- | --- | --- |
| `src/` 전체 | `mysqldump` · `mongodump` · `restore` | 0건 |
| `infra/` 전체 (systemd 유닛 · 배포 스크립트 포함) | 같음 | 0건 |
| `docs/runbook/` 66편 | 같음 · 「백업」 | 운영 DB 백업 절차 0편 |

grep 에 셋이 걸렸지만 전부 다른 것이었다.

- `src/bullet_in/hash_snapshot.py` 와 `src/bullet_in/backup_orphans.py` 가 `~/backups/` 에 남기는 JSON 둘
   → 특정 조사용 1회성 산출물이고 DB 백업이 아니다
- `src/bullet_in/enrich.py` 의 번역 지시문에 든 「back-up」
   → 축구 용어다

## 2. 그래서 지금 무엇이 어디에 있나

기사 · 선수 명단 · 선수 귀속 · 회차 기록 · 수집 원본이 전부 **VM 한 대의 도커 볼륨 안에만** 있다.

- VM = Oracle Cloud 무료 등급 A1 arm64 (`docs/runbook/2026-07-20-vm-cohost-bootstrap.md`)
- 그 VM 은 다른 서비스와 함께 쓰고 있다 (동거)
- MariaDB 와 MongoDB 둘 다 `docker compose` 로 그 위에서 돈다

복제본도 스냅샷도 내보내기도 없다.
볼륨이 날아가면 되돌릴 방법이 없다.

## 3. 왜 지금까지 안 보였나

**「무엇을 하는 절차」 는 66편이 있는데 「무엇이 없는지」 를 세는 절차가 없다.**

런북은 전부 하려는 일이 있을 때 펴는 문서다.
백업은 하려는 일이 생기지 않으므로 런북을 펼 계기도 없다.
같은 뿌리의 함정을 이 저장소에 이미 두 번 적어 두었다.

- `docs/troubleshooting/2026-08-15-verification-that-silently-passes.md`
   → 「문제가 없음」 을 확인하는 검사는 검사가 안 돌아도 같은 답을 낸다
- 「없어진 것은 없어지기 전 목록에서 센다」
   → 남아 있는 쪽에서 시작하는 점검은 빠진 것을 구조적으로 못 본다

이번 일은 그 둘의 한 갈래다.
**있는 것을 훑는 점검은 없는 것을 영영 못 찾는다.**

## 4. 다음에 같은 것을 찾는 방법

기능이 아니라 **자산**에서 시작한다.
「이 서비스가 잃으면 못 되돌리는 것이 무엇인가」 를 먼저 적고, 그 각각에 되살릴 경로가 있는지 묻는다.

이번에 적어 본 목록이다.

| 자산 | 잃으면 | 되살릴 경로 |
| --- | --- | --- |
| MariaDB `articles` 외 5표 | 서빙 · 선수 페이지 · 운영 지표가 전부 사라진다 | **없음** |
| MongoDB `raw_items` | 원본이 사라져 재처리 자체가 불가능해진다 | **없음** |
| `.env` · `x_cookies.json` | 수집 · 번역이 멈춘다 | 로컬 맥에 사본이 있다 |
| 코드 · 문서 | — | GitHub |

**코드만 원격에 있고 데이터는 한 곳에 있다.**
이 표를 만들기 전에는 그 비대칭이 안 보였다.

## 5. 남긴 것

- 백업 · 복구를 별도 안건으로 등재했다
- 이 문서는 그 안건의 출발점이다 — 무엇을 백업 대상으로 볼지는 위 4절의 표에서 시작한다
