# 재시도가 거꾸로 돌 뻔한 자리 — Airflow 설계 회차의 함정 셋 (2026-09-04)

회차를 Airflow 로 옮기는 설계 (스펙 `docs/superpowers/specs/2026-09-04-airflow-migration-design.md` · 안건 2ε) 를 쓰는 동안 세 번 틀렸다.
셋 다 코드 전에 잡혔지만 하나는 계획서까지 살아남았으면 게이트 재시도가 원하는 것과 정반대로 돌았을 것이다.
나머지 둘은 안건 표와 옛 설계 문서의 문장을 관측으로 취급한 것이다.

## 1. 재시도를 「건너뜀」 에 붙이려다 방향이 뒤집혔다

### 1.1. 증상 (계획서까지 갔다면 이렇게 보였을 것)

1. dbt 게이트가 세그폴트로 죽고 종료 코드 `3` 을 낸다 (안건 2ν · 비결정적).
2. 게이트 태스크의 `skip_on_exit_code=3` 이 그것을 「건너뜀」 으로 찍는다.
3. 건너뜀은 재시도되지 않으므로 같은 회차 안의 두 번째 시도는 없다.
   세그폴트 재시도가 이 전환의 가장 구체적인 서비스 이득이었는데 그것이 사라진다.
4. 반대로 게이트 위반 (`1`) 은 「실패」 라 `retries=1` 이 한 번 더 돌린다.
   같은 마트를 같은 규칙으로 다시 검사하므로 결과는 같고 1분을 더 쓰고 같은 자리에서 실패한다.
5. 화면에는 「게이트 2회 시도 후 실패」 가 남아 위반이 일시적 장애처럼 읽힌다.

### 1.2. 원인

스펙 초안이 §6.2 에 「재시도가 먼저다 · 첫 시도가 3 이면 한 번 더 돌고 두 번째도 3 이면 그때 건너뜀이 된다」 고 적었다.
`skip_on_exit_code` 와 `retries` 를 순서가 있는 두 단계로 상상했는데, Airflow 에서 둘은 다른 상태에 붙는다.
`retries` 는 실패에만 붙고 건너뜀은 종료 상태라 그 뒤가 없다.
상태 어휘 셋 (성공 · 실패 · 건너뜀) 을 스펙 2026-09-03 §8 의 세 갈래 (통과 · 위반 · 급사) 에 하나씩 대응시킨 것은 맞았고 재시도가 그 어휘의 어느 칸에 붙는지를 안 봤다.

### 1.3. 고친 것

급사 재시도를 Airflow 가 아니라 게이트 단계 안으로 옮겼다.
`run_gate` 가 dbt 를 돌린 뒤 신호 종료 (`returncode < 0`) 일 때만 한 번 더 돌리고 두 번째도 신호 종료면 그때 `3` 을 낸다.
위반은 첫 시도에서 `1` 로 끝난다.
게이트 태스크의 Airflow 재시도는 0 이다.

덤이 하나 생겼다.
재시도가 단계 안에 있으니 systemd 로 되돌린 상태에서도 같은 재시도가 산다.

### 1.4. 잡힌 자리

스펙을 쓴 직후의 자체 점검 (자리표시 · 모순 · 범위 · 중의) 에서 잡혔다.
§3.2 표의 재시도 칸과 §6.2 본문이 서로 다른 말을 하고 있었다.

## 2. 안건 표의 「이미 멱등이고 단계 재개가 된다」 는 절반이었다

### 2.1. 무엇이 틀렸나

안건 표 2ε 행은 「`run.py` 의 각 단계가 이미 DB 에 무엇이 남았나를 묻는다 · 즉 이미 멱등이고 단계 재개가 된다 · 태스크로 쪼개도 상태를 XCom 으로 넘길 필요가 없다」 고 적혀 있었다.
번역 · 분류 · 말투 백필은 그 말이 맞다.
수집 단계의 값 여덟 (원본 목록 · 후보 계수 · 수집 소요 · 시작 시각 · 어댑터 퍼널 · 오류 목록 · 적재 통계 · 신규 건수) 은 그렇지 않다.
메모리로 회차 끝까지 흘러 SLO-6 이상탐지 · 신선도 알림 · 운영 화면 · 회차 행 기록에 쓰인다.

### 2.2. 어떻게 잡았나

`run.py` 본체 356줄을 읽고 값 이름 여덟이 어느 줄에서 쓰이는지 grep 했다.
전부 수집 직후 (248에서 305줄) 에 만들어져 회차 끝 (494에서 560줄) 에서 소비됐다.

### 2.3. 고친 것

설계에 「회차 행의 두 단계 기록」 절을 뒀다.
`collect` 가 끝날 때 회차 행 (`pipeline_runs`) 을 삽입하며 오류 목록과 퍼널을 JSON 열 `fetch_detail` 에 담고 `publish` 가 `run_id` 로 그 행을 읽는다.
SLO-6 의 이력 조회는 자기 행을 제외하는 조건 한 줄이 붙는다.
XCom 을 안 쓰는 이유는 값이 회차 행에 있어야 단계 함수가 Airflow 없이도 같은 길로 값을 받기 때문이다.

## 3. 옛 기각 근거는 그때의 입력값이었다

### 3.1. 무엇이 틀렸나

2026-07-20 설계 §2.2 는 Airflow standalone 을 「하루 4회 회차를 위해 상시 약 1GB 를 지불한다 · 동거 채택 사유 (메모리 절약) 와 역행」 으로 기각했다.
이 문장을 그대로 착수 입력으로 읽으면 전환은 처음부터 막힌다.

### 3.2. 어떻게 잡았나

VM 을 쟀다.
2026-09-04 02시대에 23Gi 중 available 11Gi · 디스크 22G 여유 · load 0.4 에서 0.9 였다.
「상시 1GB」 는 지금도 맞는 값이지만 그것이 아까웠던 것은 7월의 여유 기준이다.
기각의 결론이 아니라 기각의 입력값이 바뀌어 있었다.

### 3.3. 고친 것

스펙 §1.3 에 실측 표를 두고 「그때의 여유와 지금의 11Gi 는 다른 값이고 그 근거는 더 이상 성립하지 않는다」 고 적었다.
돈은 0원 그대로라는 것도 같은 자리에 적었다.

## 4. 재발 방지 규율

- **오케스트레이터의 재시도는 상태에 붙는다.**
  「어떤 종료를 어떤 상태로 옮기나」 를 정한 뒤에는 「그 상태에 재시도가 붙나」 를 따로 본다.
  건너뜀 · 성공에는 재시도가 없다.
- **선택적 재시도 (이 경우만 한 번 더) 는 단계 안에서 한다.**
  오케스트레이터의 재시도는 「실패면 전부」 라 조건을 못 단다.
  조건이 있는 재시도는 코드가 맡고 오케스트레이터는 그 결과만 받는다.
- **「이미 멱등」 이라는 문장은 값 이름으로 센다.**
  단계를 쪼개기 전에 앞 단계에서 만든 값이 뒤 단계 어디서 쓰이는지를 grep 으로 표로 만든다.
  DB 를 다시 묻는 단계와 메모리로 받는 단계가 한 함수 안에 섞여 있을 수 있다.
- **옛 기각을 인용할 때는 그 기각의 입력값을 다시 잰다.**
  결론 (「기각」) 이 아니라 근거의 수치 (여유 메모리 · 비용 · 빈도) 가 지금도 같은지를 본다.
