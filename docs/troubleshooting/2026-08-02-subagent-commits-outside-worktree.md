# 서브에이전트가 지정 워크트리 밖 main 에 커밋 (2026-08-02)

워치리스트 구현 (PR #191) 을 태스크마다 서브에이전트에게 맡겨 진행하던 중,
첫 태스크의 구현 서브에이전트가 지시받은 워크트리가 아니라 메인 체크아웃에서 작업하고 main 브랜치에 직접 커밋했다.
같은 사고가 2026-07-15 에도 있었고, 이번에 디스패치 문구를 게이트 형태로 바꾼 뒤로는 나머지 7개 태스크에서 재발이 없었다.
그 확인 절차와 복구 · 재발 방지 문구를 기록한다.

## 1. 증상

- 서브에이전트가 "작업 완료 · 커밋 0635c2a" 로 보고했는데, 워크트리 브랜치의 HEAD 는 그대로였다.
- 보고에 적힌 산출물 경로가 워크트리가 아니라 메인 체크아웃 아래를 가리켰다.
- 메인 체크아웃에서 `git log` 를 확인하니 main 브랜치 위에 해당 커밋이 올라가 있었다.

## 2. 원인

- 디스패치 프롬프트에 "Work from: <워크트리 경로>" 한 줄만 있었다.
- 서브에이전트 셸의 기본 작업 디렉토리는 메인 체크아웃이라, 이 한 줄을 놓치면 모든 파일 편집과 git 명령이 메인 체크아웃에서 실행된다.
- 위치 지정이 서술 (읽고 따라야 하는 문장) 에 그쳤고, 어기면 실패하는 검증 게이트가 없었다.

## 3. 복구

순서가 중요하다 — 커밋을 먼저 워크트리로 옮긴 뒤에 main 을 되돌린다.

```bash
# 1) 워크트리에서 사고 커밋을 가져온다 (객체 저장소 공유라 SHA 로 바로 가능)
cd <워크트리> && git cherry-pick 0635c2a

# 2) 메인 체크아웃의 main 을 사고 직전 커밋으로 되돌린다
cd <메인 체크아웃> && git reset --hard <사고 직전 SHA>

# 3) 워크트리 밖에 쓰인 부속 산출물 (보고 파일 등) 을 워크트리로 옮긴다
```

- 이번 사고는 push 전에 발견해 로컬 reset 으로 끝났다.
push 된 뒤라면 되돌리는 비용이 훨씬 크므로 (`docs/conventions` 의 force-push 금지), 커밋 보고를 받으면 곧바로 확인해야 한다.

## 4. 재발 방지 — 디스패치 가드 3요소

이후 모든 디스패치에 아래 3요소를 넣었고, 같은 세션의 나머지 7개 태스크에서는 같은 사고가 다시 나지 않았다.

1. **경로 명시 + 금지 명시**
— 워크트리 절대 경로를 적고, 메인 체크아웃 경로를 "절대 건드리지 말 것" 으로 함께 적는다.
경로 하나만 주면 놓치지만, 금지 대상까지 짝으로 주면 두 경로가 대비돼 눈에 들어온다.
2. **커밋 전 자기검증 게이트**
— "커밋 전에 `git rev-parse --show-toplevel && git branch --show-current` 를 실행해 워크트리 경로와 브랜치명이 맞는지 확인하고, 다르면 멈추고 BLOCKED 로 보고하라" 를 지시에 넣는다.
서술이 아니라 어기면 실패하는 절차로 만든다.
3. **컨트롤러 즉시 검증**
— 서브에이전트가 커밋 SHA 를 보고하면, 다음 일을 시작하기 전에 워크트리에서 그 SHA 가 자기 브랜치 tip 인지 확인한다.
이번 사고도 이 확인에서 잡혔다.

## 5. 자기검증 게이트가 통과했는데도 재발했다 (2026-08-03)

§4 의 3요소를 전부 넣고 시작한 회차에서 첫 태스크가 또 메인 체크아웃에 커밋했다.
게이트 2 (커밋 전 자기검증) 가 **실행됐고 통과까지 했는데** 사고가 났다.

### 5.1. 무엇이 다르게 났나

- 서브에이전트가 `git branch --show-current` 를 실행했고 결과는 워크트리 브랜치였다.
- 그런데 같은 보고에 `git commit` 출력이 `[main 38346a4]` 로 찍혀 있었다.
- 두 명령이 서로 다른 디렉터리에서 실행된 것이다.

### 5.2. 원인 — 확인 시점과 커밋 시점의 위치가 다르다

셸의 작업 디렉터리는 도구 호출 사이에 유지되지만, 중간에 다른 경로로 옮겨 가면 그대로 남는다.
그래서 확인 명령이 워크트리에서 돌고 커밋 명령이 메인 체크아웃에서 도는 조합이 성립한다.

**게이트 2 는 위치를 "확인" 할 뿐 "고정" 하지 않는다.**
확인과 커밋 사이에 위치가 바뀌면 아무것도 막지 못한다.

### 5.3. 조치 — 위치에 의존하지 않게 만든다

모든 git 명령에 `-C` 로 경로를 박는다.
셸이 어디에 있든 결과가 같아지므로 위치 드리프트 자체가 무의미해진다.

```bash
git -C <워크트리 절대경로> add <파일>
git -C <워크트리 절대경로> commit -F - <<'EOF'
...
EOF
git -C <워크트리 절대경로> show --stat HEAD
```

함께 넣은 것 두 가지다.

- 커밋 출력의 대괄호 안 브랜치명을 눈으로 확인하고, `[main ...]` 이면 **스스로 되돌리려 하지 말고** BLOCKED 로 보고하라고 지시한다.
- 파일 읽기 · 쓰기와 테스트 실행에도 워크트리 절대경로를 쓰게 한다.

이후 같은 회차의 태스크 9개와 수정 라운드 전부에서 재발이 없었다.

### 5.4. 복구는 이번엔 §3 을 그대로 쓸 수 없었다

§3 의 2단계 (`git reset --hard` 로 main 되돌리기) 를 실행하지 못했다.
메인 체크아웃에 다른 트랙의 미커밋 파일이 12개 있었기 때문이다.

- 워크트리로 체리픽만 하고 (§3 의 1단계) main 의 사고 커밋은 그대로 두었다.
- 그 커밋은 push 되지 않았고, 로컬 `main` 은 이미 `origin/main` 과 갈라져 정리 대상이었으므로 함께 사라진다.
- **복구 전에 메인 체크아웃의 작업 트리 상태를 먼저 본다** — 남의 미커밋 작업이 있으면 `reset --hard` 는 선택지가 아니다.

## 6. 교훈

- 위치 · 브랜치처럼 어기면 복구 비용이 큰 지시는 서술이 아니라 검증 가능한 게이트로 준다.
- **그 게이트가 "확인" 형태면 확인 이후를 보장하지 못한다** — 명령 자체가 위치에 의존하지 않게 바꾸는 편이 확실하다.
- 서브에이전트의 "완료" 보고는 검증 전까지 미확인 주장으로 다룬다 — 커밋 위치 확인은 보고 직후 한 줄이면 된다.
- 보고와 실물이 어긋난 사례도 있었다 (고치지 않은 파일을 고쳤다고 적음).
커밋 stat 을 직접 대조하면 잡힌다.
