# 눈으로 구분 안 되는 문자가 옮겨 적히다 뭉개진다 (2026-08-03)

계획서에 코드 전문을 적어 두고 구현을 서브에이전트에 맡긴 회차에서, 같은 유형의 사고가 세 번 났다.
셋 다 화면에서 구별되지 않는 문자가 옮겨 적히는 과정에 다른 문자로 바뀐 것이고, 셋 다 전체 테스트가 통과하는 채로 기능이 꺼져 있었다.

## 1. 무엇이 뭉개지나

곧은따옴표와 굽은따옴표는 대부분의 편집기 글꼴에서 거의 같아 보인다.

| 문자 | 코드포인트 | 이름 |
| --- | --- | --- |
| `"` | U+0022 | 곧은 큰따옴표 |
| `“` | U+201C | 왼쪽 굽은 큰따옴표 |
| `”` | U+201D | 오른쪽 굽은 큰따옴표 |

같은 위험이 있는 것이 더 있다.
붙임표 계열 (`-` U+002D · `–` U+2013 · `—` U+2014) 과 말줄임표 (`...` 대 `…` U+2026) 와 줄바꿈 없는 공백 (U+00A0) 이다.

## 2. 실제로 난 사고 셋

### 2.1. 인용 검사 정규식이 곧은따옴표만 보게 됐다

인용문이 재작성에서 훼손됐는지 대조하는 정규식을 새로 넣는 작업이었다.
계획서의 원본은 여는 자리 · 안쪽 제외 집합 · 닫는 자리에 굽은따옴표를 담고 있었는데, 커밋된 코드에서는 그 자리가 전부 U+0022 로 바뀌어 있었다.

- 결과 — 굽은따옴표로 인용된 발화를 아예 수집하지 못했다.
한국어 게시글과 언어 모델 산출물이 흔히 쓰는 형태라 이 검사가 겨냥한 주요 대상이 통째로 빠졌다.
- **테스트 픽스처도 같이 뭉개졌다.** 두 형태를 다 잡는지 고정하려던 테스트가 두 인용 모두 곧은따옴표를 쓰게 되어, 결함을 가린 채 통과했다.
- 그 시점 전체 스위트는 886개가 전부 통과였다.

### 2.2. 고치면서 문자 집합을 필요 이상으로 넓혔다

앞의 사고를 고치라고 지시했더니 세 자리를 모두 `["“”]` 합집합으로 통일했다.
원본은 여는 자리와 닫는 자리를 구분하고 있었다.

- 겉보기에는 더 관대해 보이지만 실제로는 손해다.
짝이 어긋난 따옴표가 하나 섞이면 **진짜 인용을 놓치고 인용이 아닌 것을 잡는다.**

```
입력: “첫 발화입니다” 중간 텍스트입니다 ” 그리고 “둘째 발화입니다”

합집합    : ['첫 발화입니다', '그리고']          ← 둘째 발화 누락 · '그리고' 오검출
원본 구분 : ['첫 발화입니다', '둘째 발화입니다']  ← 정확
```

- 기전 — 짝 없는 닫는 따옴표가 여는 자리로 인정돼 뒤따르는 여는 따옴표를 닫는 자리로 잡아먹고, 그 바람에 둘째 인용의 여는 따옴표가 소비된다.

### 2.3. 범위 밖 정규식을 "고치려다" 깨뜨렸다

앞의 두 사고 뒤에 "따옴표 문자는 눈으로 구분되지 않으니 주의하라" 고 경고했더니, 다음 작업자가 그 경고를 **자기 범위 밖의 따옴표까지 손보라는 뜻으로 받아들였다.**

- 대상은 문장 분할 정규식 `_SENT_END_RE` 였고 원본에는 아무 문제가 없었다.
그 줄의 U+201D 가 U+0022 로 바뀌었다.
- 결과 — 닫는 굽은따옴표로 끝나는 문장이 분할되지 않는다.

```
_split_sentences('그는 말했다.” 그리고 떠났다.')
깨진 상태 : ['그는 말했다.” 그리고 떠났다.']
원본      : ['그는 말했다.”', '그리고 떠났다.']
```

- 파급 — 400자 넘는 문단을 문장 경계에서 다시 쪼개는 기능이 조용히 멈춘다.
인용으로 끝나는 문단이 많은 기사에서 문단이 안 쪼개진 채 저장된다.
- 보고에는 "따옴표 문제를 해결했다" 는 취지로 적혀 있었다.
고친 것이 아니라 깨뜨린 것이었고, 작업자는 그것을 몰랐다.

## 3. 왜 테스트가 못 잡나

**구현과 테스트가 같은 손을 거치면 같은 방식으로 뭉개진다.**
검사 대상과 검사 기준이 함께 틀어지므로 단언은 그대로 성립한다.

- 2.1 에서 실제로 그랬다.
- 2.3 은 그 문자를 다루는 테스트가 아예 없어서 통과했다.

전체 스위트가 초록불이라는 사실은 이 유형에 대해 아무 정보도 주지 않는다.

## 4. 어떻게 잡았나

두 가지가 실제로 작동했다.

- **코드포인트를 직접 찍는다.** 리뷰 지시에 "정규식과 픽스처의 따옴표가 어떤 코드포인트인지 바이트 단위로 대조하라" 를 넣자 2.1 과 2.2 가 잡혔다.

```bash
uv run python -c "
from bullet_in.fidelity import _QUOTE_RE
print([hex(ord(c)) for c in _QUOTE_RE.pattern])
"
```

- **원본과 대조한다.** 범위 밖 변경 (2.3) 은 분기점의 파일과 비교해야 드러난다.

```bash
git show origin/main:src/bullet_in/enrich.py | grep "_SENT_END_RE = "
grep "_SENT_END_RE = " src/bullet_in/enrich.py
```

## 5. 예방

### 5.1. 특수 문자는 이스케이프로 쓴다

리터럴 문자는 옮겨 적을 때마다 뭉개질 기회가 생긴다.
파이썬 정규식에서는 원시 문자열을 벗고 유니코드 이스케이프를 쓰면 구조적으로 불가능해진다.

```python
_QUOTE_RE = re.compile('["“]([^"“”]{4,}?)["”]')
```

정규식 안에 백슬래시가 없으면 원시 문자열일 이유가 없다.

### 5.2. 되돌릴 때는 타이핑하지 말고 치환한다

깨진 문자를 손으로 되돌리면 같은 실수가 반복된다.
이스케이프로 지정한 치환 스크립트를 주는 편이 안전하다.

```python
import pathlib
p = pathlib.Path('src/bullet_in/enrich.py')
s = p.read_text(encoding='utf-8')
bad  = '[.!?\u2026]["' + '"' + "\\'\u300f\u300d]?"
good = '[.!?\u2026]["\u201d' + "\\'\u300f\u300d]?"
assert bad in s
p.write_text(s.replace(bad, good), encoding='utf-8')
```

### 5.3. 범위 밖 문자는 건드리지 말라고 명시한다

"문자에 주의하라" 는 경고는 2.3 처럼 반대로 해석될 수 있다.
지시에 두 가지를 함께 적는다.

- 네가 만질 곳은 지정된 곳뿐이다.
- 다른 곳의 문자가 이상해 보여도 고치지 말고 보고하라.

### 5.4. 두 형태를 모두 덮는 테스트를 요구한다

한쪽 형태만 덮으면 반대쪽이 조용히 깨져도 모른다.
곧은따옴표 입력과 굽은따옴표 입력을 각각 통과시키는 테스트를 따로 둔다.

### 5.5. 리뷰 지시에 코드포인트 대조를 넣는다

이 유형은 diff 를 눈으로 읽어서는 잡히지 않는다.
리뷰어에게 "코드포인트로 확인하라" 를 명시하지 않으면 통과한다.
