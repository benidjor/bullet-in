# 같은 커밋을 다시 배포하면 옛 표지로 판정이 통과한다 (2026-09-04)

배포 자동화의 첫 라이브 리허설에서 「✅ 코드 반영 완료」 알림 두 장의 `run` 이 같은 값이었다.
두 번째 판정기가 받은 라이브 표지는 첫 배포의 것이었는데, 커밋이 같아서 첫 시도에 통과했다.
판정은 틀리지 않았지만 알림의 `run_id` 가 「이 회차」 가 아니었다.

## 1. 증상

2026-09-03 밤의 리허설 순서다.

1. 22:09 회차 손 시작 → 전진 `651f837 → 0388c64` → 22:12:37 배포 완료 → 22:12:58 판정 「반영 완료」 (`run 0f589a09`).
2. 수동 `rollback` → `unblock` → 22:13 회차 손 시작 → 같은 커밋 `0388c64` 로 다시 전진.
3. 22:15:59 배포 완료 → 같은 초에 판정기가 `build.json` 을 한 번 받고 「반영 완료」 (`run 0f589a09`).

두 번째 회차의 `run_id` 는 `675f4186` 이었다.
그 뒤 손으로 다시 받으니 라이브 표지는 `675f4186` 으로 바뀌어 있었다.

## 2. 원인

판정기는 라이브 `build.json` 의 `commit` 을 상태 파일의 `current` 와 대조한다 (스펙 §6.1).
배포 직후 최상위 도메인은 잠깐 옛 배포본을 돌려준다.
그래서 20초 간격으로 3회까지 다시 받게 돼 있다.

새 커밋을 반영하는 보통 경로에서는 옛 표지의 `commit` 이 다르므로 거부되고 다시 받는다.
첫 회차가 실제로 그랬다 (22:12:38 불일치 → 22:12:58 일치).

같은 커밋을 다시 배포하는 경로 (롤백 → `unblock` → 재전진) 에서는 옛 표지의 `commit` 도 같다.
판정기는 그것을 「일치」 로 읽고 첫 시도에 끝낸다.
알림에 실린 `run` 은 판정 순간 라이브에 있던 것, 즉 직전 배포의 것이다.

## 3. 해결

판정을 엄격하게 하지 않았다.
`run_id` 까지 대조하면 전파가 재시도 창 (3회 × 20초) 을 넘길 때 헛 「표지 불일치」 사고 알림이 난다.
이 경로는 같은 커밋 재배포에서만 드러나고 그때도 코드는 맞게 반영돼 있다.

대신 알림이 두 값을 나란히 싣게 했다 (PR #456).

- 「이 회차」 의 `run_id` 는 라이브가 아니라 로컬 `site/build.json` 에서 읽는다.
  그 파일은 이 회차의 `run.py` 가 쓴 것이다.
- 「회차」 필드에 `run <로컬> · 라이브 표지 run <라이브>` 로 적는다.
  둘이 다르면 라이브가 아직 전파 전이라는 뜻이고 사람이 그것을 알림에서 본다.

2026-09-04 01:48 · 01:51 의 알림에서는 둘이 같았다 (`e69f166b` · `8d06a454`).

## 4. 예방

- **대조 키에 같은 값이 두 번 나올 수 있으면 「일치」 는 「최신」 이 아니다.**
  캐시 앞에서 무엇이 최신인지 가르려면 배포마다 달라지는 값 (`run_id` · `rendered_at`) 이 필요하다.
- 그 값으로 판정을 엄격하게 할지는 전파 시간의 분포를 잰 뒤 정한다.
  지금 관측은 「배포 완료 0초 뒤 옛 것 · 20초 뒤 새 것」 둘뿐이다.
- 알림에는 「무엇을 받았나」 를 그대로 싣는다.
  판정이 틀리지 않았어도 사람이 헷갈리는 자리는 값 하나로 풀린다.
