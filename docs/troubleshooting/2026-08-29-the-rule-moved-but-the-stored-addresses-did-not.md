# 주소를 접는 규칙만 넓히고 저장된 주소는 그대로 뒀다 (2026-08-29)

트윗 역추적 (안건 σ) 이 페이월 기사를 어떻게 버리는지 재려다가, 그 옆에서 다른 것이 나왔다.
**저장된 기사 936건 중 156건의 주소가 지금 규칙으로 다시 접으면 다른 값이 된다.**
그리고 그 가운데 32건은 이미 같은 기사가 두 행으로 서 있다.

## 1. 무엇이 어긋나 있나

중복 판정은 `dedup.classify` 가 하고, 그것이 받는 목록은 `MartStore.seen_map()` 이다.

```python
def seen_map(self):
    rows = c.execute(text("SELECT url,content_hash,revision,source_id, ... FROM articles"))
    return {u: (h, rev, sid, int(lv)) for u, h, rev, sid, lv in rows}
```

**키가 저장된 주소 문자열 그대로다.**
새로 들어온 기사는 `canonical_url()` 을 통과한 주소로 조회되므로, 저장값이 옛 모양이면 그 행은 조회에 안 걸린다.
같은 기사가 다시 오면 **없는 것으로 보고 새 행을 만든다.**

2026-08-28 에 주소 정규화가 넓어졌다 (PR #366 · BBC 호스트 · 스카이 섹션 번호 · Athletic 슬러그 · 추적 인자 셋).
규칙은 넓어졌는데 **이미 저장돼 있던 주소는 옛 모양으로 남았다.**

```
저장 URL ≠ canonical_url(저장 URL)          156행 / 936행
  www.nytimes.com   108
  www.skysports.com  46
  www.bbc.co.uk       2
```

**언제 생겼는지도 갈렸다 (2026-08-29 추가).**
지운 17행이 전부 **#366 배포 직후 첫 회차부터** 만들어졌다.
즉 안건 ρ 가 「합쳐질 묶음 0」 으로 닫힌 그날, 다음 회차부터 다시 쌓이기 시작했다.

```
UTC 08-28 09:04  = KST 08-28 18:04   ← #366 배포 (18:03 회차) 바로 다음
UTC 08-28 13:31  = KST 08-28 22:31
UTC 08-28 16:33  = KST 08-29 01:33
UTC 08-28 21:03  = KST 08-29 06:03
```

**이 판정이 한 번 뒤집혔던 이유는 시간대다.**
`articles.created_at` 은 UTC 인데 (`SELECT NOW()` 로 확인) 그것을 KST 회차 시각과 그대로 견주고
「배포보다 앞서 생겼으니 배포 탓이 아니다」 라고 적었다.
+9 를 하니 전부 배포 뒤였다.
이 저장소는 그 함정을 이미 적어 뒀다 — 메모리 `vm-manual-ops-gotchas` 의 「UTC 로 적힌 시각을 회차와 견줄 때는 +9 를 해서 본다」 다.
**목록에 있다는 것과 그 순간 떠올린다는 것은 다르다.**

## 2. 화면에 이미 나와 있다

지금 규칙으로 접으면 한 키가 되는 묶음이 **16개 · 행 32개**다.
32행 전부 `title_ko` 가 채워져 있다
— 번역까지 끝난 행이라 렌더 입력에서 걸러지지 않는다.

```
https://www.nytimes.com/athletic/7526325/2026/08/21
   d4d1209c fmkorea 귀속 9 · 69c45b29 fmkorea 귀속 10
https://www.skysports.com/football/news/13576278
   02a632a5 skysports 귀속 4 · 36a4f6c9 skysports 귀속 11
```

소스별로는 fmkorea 24 · x_ornstein 4 · skysports 4 다.
합칠 때 옮겨야 할 선수 귀속은 최대 70건이다 (`article_players` 는 PK 가 `(content_hash, player_id)` 라 그 복합키로 센다).

**「두 모양이 다 들어온다」 가 원인이다.**
The Athletic 은 슬러그가 붙은 주소와 날짜까지만 있는 주소를 둘 다 내보낸다.
게시자가 어느 쪽을 붙일지는 우리가 못 정한다.
정규화는 그 둘을 접으라고 들어온 규칙이다.
그런데 접을 대상 가운데 **먼저 저장된 쪽**이 옛 모양이면 규칙이 닿지 않는다.

## 3. 이것이 다음 작업을 가른다

안건 σ 의 페이월 갈래는 트윗 주소를 기사 주소로 바꾸는 일이다.
바꾼 주소는 `canonical_url` 을 지나 짧은 모양이 되는데, 짝이 되는 fmkorea 행이 긴 모양으로 저장돼 있으면 **합쳐지는 대신 세 번째 행이 생긴다.**

같은 `classify` 를 두 잣대로 돌려 봤다 (저널 전 구간에서 페이월로 버려진 기사 14건).

| 잣대 | 합쳐짐 | 새 행 |
| --- | --- | --- |
| 지금 (저장 URL 그대로) | 6 | 8 |
| 재정규화 뒤 | **12** | 2 |

**재정규화를 먼저 하면 σ 의 효과가 두 배가 된다.**
순서를 뒤집으면 σ 가 중복을 줄이는 대신 늘린다.

## 4. 재는 법

두 줄이면 된다.
운영 DB 에 붙어 **제품이 쓰는 함수 그대로** 부른다.

```python
from bullet_in.canonical import canonical_url
drift = [r for r in rows if canonical_url(r["url"]) != r["url"]]

groups = defaultdict(list)
for r in rows:
    groups[canonical_url(r["url"])].append(r)
dup = {k: v for k, v in groups.items() if len(v) > 1}
```

**앞 줄이 「규칙이 안 닿는 행」 이고 뒤 줄이 「이미 두 행인 것」 이다.**
뒤 줄만 세면 아직 짝이 안 온 140행을 못 본다 — 그 행들은 짝이 오는 날 새 행을 만든다.

## 5. 규율

**정규화 규칙을 바꾸는 배포에는 저장값 재계산이 함께 들어간다.**
흡수 설계 (`docs/superpowers/specs/2026-08-14-tweet-article-absorption-design.md` §4.1) 에 그렇게 적혀 있다
— 「`canonical_url` 을 바꾸면 저장된 URL 과 새로 계산한 키가 어긋난다」.
적혀 있는데도 한 배포에서 병합만 들어갔다.

**병합과 재계산은 다른 일이다.**
병합은 **이미 충돌한** 묶음을 지운다 (16묶음).
재계산은 **아직 충돌하지 않은** 행까지 규칙 안으로 들여놓는다 (140행).
병합만 하면 다음 회차에 같은 묶음이 다시 생긴다.

**「묶음 0」 은 종결 신호가 아니다.**
병합 직후에는 언제나 0 이 나온다 — 방금 지웠기 때문이다.
닫혔는지는 **드리프트 행 수**로 본다.
그 수가 0 이 아니면 아직 열려 있다.

**주소를 손으로 고치지 않는다 — `migrate_url_identity` 를 쓴다.**
`UPDATE articles SET url = …` 만 돌리면 그 자리에서는 아무 일도 안 나고, **다음 회차가 해시를 갈면서** 귀속과 번역이 함께 떨어져 나간다 (§8).
그 배치는 주소 · 해시 · 참조 둘을 한 트랜잭션에서 함께 옮긴다.

**합쳐진 테이블에서 「합쳐질 것이 있었나」 를 묻지 않는다.**
병합이 증거를 지운다 — 물어야 할 곳은 Mongo `raw_items` 와 소급 직전 백업이다 (§7).

## 6. 재계산을 못 하는 자리가 하나 있다 (2026-08-29 추가)

**스카이 섹션 번호를 지운 주소는 기사에 못 간다.**
두 주소를 실제로 받아 봤다.

```
https://www.skysports.com/football/news/11670/13562252  → 기사
https://www.skysports.com/football/news/13562252        → 축구 섹션 첫 화면
```

그래서 재계산에서 스카이 46행을 뺐고, **그 대가가 90분 만에 나왔다.**
다음 정기 회차가 스카이 두 행을 **지우기 전과 같은 `content_hash` 로 그대로** 되살렸다.
재계산이 들어간 Athletic 쪽은 한 행도 안 되살아났다.

**한 값이 두 역할을 지고 있는 것이 본체다.**
`url` 컬럼이 중복 판정 키이면서 동시에 화면의 「원문 기사 보기」 주소다.
정규화는 키로는 맞고 주소로는 틀린 값을 만든다.
어느 쪽으로 두어도 손해다.

| 두는 법 | 잃는 것 |
| --- | --- |
| 규칙 유지 · 재계산 안 함 | 신선한 스카이 기사가 회차마다 두 행이 된다 |
| 규칙 유지 · 재계산 함 | 46행의 원문 링크가 축구 섹션 첫 화면으로 간다 |
| 규칙 제거 | 스카이가 섹션을 바꿔 다시 실은 기사가 두 행이 된다 |

**대상을 셀 때 축을 밝힌다.**
46 은 **호스트** 가 스카이인 행이다 — `source_id` 로 가르면 skysports 34 · fmkorea 12 다 (게시자가 전재한 것).
축을 안 적으면 대상이 4분의 3 으로 잡힌다.

## 7. 규칙을 걷어냈고, 그 판단의 근거 하나가 틀렸다 (2026-08-29 정정)

규칙은 `news` · `live-blog` 둘 다에서 걷어냈다 (PR #380).
근거로 **「규칙이 막아 준 실물은 0건」** 을 적었는데 **그 계수가 틀렸다.**

**틀린 이유는 잰 자리다.**
`articles` 를 기사 번호로 묶어 세었는데, 그 테이블은 **안건 ρ 의 소급이 이미 그 쌍들을 합쳐 없앤 뒤**였다.
합쳐진 자리에서 「합쳐질 것이 있었나」 를 물은 셈이라 답이 언제나 0 이다.

**증거는 두 군데에 남아 있었다.**

```
Mongo raw_items — 스카이 원본 67건 중 섹션 없는 주소 0건
                  같은 기사가 두 섹션으로 수집된 것 5종 / 49종
ρ 소급 직전 백업 — 그 5종이 그때 전부 두 행이었다 (47종 중 5종)
```

**스카이는 섹션 없는 주소를 준 적이 없다.**
`articles` 에 있던 섹션 없는 주소는 전부 우리가 만든 것이었다 — 규칙이 깎았거나, ρ 의 소급이 합치며 깎인 값을 남겼거나.

**그래서 두 손해가 다 실재한다.**

- 규칙을 두면 새 스카이 기사마다 원문 링크가 죽는다 (배포 뒤 적재된 4건이 4건 다).
- 규칙을 빼면 스카이가 섹션을 바꿔 다시 실은 기사가 두 행이 된다 (규칙 없던 구간 실적 47종 중 5종).

지금은 링크를 살리는 쪽을 택했다 — 죽은 링크는 못 쓰게 되는 것이고 중복은 항목이 둘 보이는 것이라 무게가 다르다.
**본래 해법은 키와 표시 주소를 나누는 것**이고 안건 2ζ 로 열어 두었다.

**착수할 때 첫 일은 실제 중복 발생률을 규칙 제거 이후 회차들에서 다시 재는 것이다.**
지금 가진 값은 과거 실적 하한 하나뿐이다 — 같은 기사를 두 번 이상 수집해야 섹션이 갈린 것이 보이므로, 한 번만 수집된 기사는 갈렸어도 안 보인다.

## 8. 해시가 갈리면 번역도 지워진다 (2026-08-29 추가)

`article_players` · `players.first_seen` · 상세 페이지 파일명 말고 **한 자리가 더 있다.**

```sql
title_ko = IF(articles.content_hash = VALUES(content_hash), articles.title_ko, NULL),
-- summary_ko · summary3_ko · body_ko 도 같은 꼴
```

해시가 달라지면 번역 4필드가 NULL 이 되고 그 기사는 다음 패스에서 다시 번역된다.
**Gemini 호출이 따라붙는다.**

2026-08-29 04:35 에 주소 110행을 손으로 고친 뒤 06:02 회차가 8행의 해시를 갈았고, 그 8건이 다시 번역됐다.
그 작업을 **「과금 0」 으로 보고했는데 틀렸다** — 배치 자체는 0 이지만 그 뒤 회차가 비용을 냈다.

**`migrate_url_identity` 는 이 자리도 막는다.**
upsert 를 안 타고 `UPDATE` 로 해시를 미리 맞추므로, 다음 수집 때 `IF()` 조건이 참이 되어 번역이 지켜진다.
107행에 적용한 뒤 두 회차를 지나 번역을 잃은 행은 0 이었다.

**옆 작업이 남의 잠재 결함을 앞당겨 터뜨린다.**
그날 재번역된 기사 하나에서 표기 사전의 짝 누락이 게이트에 걸렸다.
그 결함은 원래 새 기사가 들어와야 드러났을 것인데, 주소 정정이 재번역을 불러 앞당겼다.
**병렬로 도는 작업 중 주소나 원문 제목을 만지는 것이 있는지 먼저 묻는다.**

### 8.1. 방아쇠는 주소만이 아니다 (2026-08-29 18:02 회차)

해시는 **원문 제목**도 재료로 쓴다 — `sha256(원문 제목 | canonical_url(url))`.
그래서 **아무도 주소를 안 건드려도 제목이 달라지면 같은 일이 난다.**

18:02 정기 회차가 afcstuff 트윗 행 하나를 그렇게 갈았다.

```
INFO 잔여 페이지 1건 삭제 (DB 에서 빠진 기사)
INFO 잔여 페이지 삭제 목록 1-1 09f700c8….html
```

- 같은 트윗 주소에 **새 해시로 행이 다시 섰다** (`09f700c8` → `1a21f0d6`).
- 옛 해시의 귀속 1건이 고아가 됐고 번역 4필드가 지워져 재번역 큐에 들어갔다.
- **사람이 한 일이 없다** — 그 행은 이 회차의 신원 이전 107행에 안 들어 있었다 (09:29 · 17:43 두 스냅샷에 같은 해시로 있었다).
- 트윗을 다시 긁는 과정에서 본문 텍스트가 달라진 것이 방아쇠다.

**그래서 이 문서의 경고를 「주소를 고칠 때」 로만 읽으면 안 된다.**
`title_original` 을 바꾸는 백필 · 파서 개정 · 소스 쪽 텍스트 변경이 전부 같은 자리를 건드린다.

**이 줄을 쓸 수 있었던 것은 PR #377 덕이다** — 그 전에는 「1건 삭제」 만 남아 무엇이 사라졌는지 물을 수 없었다.
**개수만 남기는 로그는 원인을 못 잇는다.**
