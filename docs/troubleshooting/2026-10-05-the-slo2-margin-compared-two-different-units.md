# SLO-2 여유 셈이 서로 다른 단위를 비교했고, 계획서 검증과 작업 리뷰가 못 봤다 (2026-10-05)

- **영역**: 공식 소스 사이트맵 실패 알림 (`run.slo2_margin`) / 계획 · 리뷰 절차
- **관련 안건**: 3γ 공홈사이트맵장애
- **고친 것**: #528 의 최종 리뷰 수정 커밋 (`2176cc3`) · 사이트맵 재시도 설계 §4.2 문장 정정
- **남은 일**: 없음

## 1. 증상

사이트맵이 재시도까지 실패하면 경향 채널로 알림을 보내고, 받는 사람이 「이번 실패로 SLO-2 가 미달이 되는가」 를 바로 판단하도록 SLO-2 여유를 싣는다.
알림 문구는 「최근 30회 중 소스 실패 N회 (M회까지 충족)」 이다.

설계 원안 (§4.2) 과 계획서는 두 값을 이렇게 셌다.

| 값 | 원안의 셈 | 단위 |
| --- | --- | --- |
| N (소스 실패) | 최근 30회 가운데 성공률이 1 보다 작은 실행 수 | 실행 |
| M (충족 한도) | 30 × (1 − 0.99) × 소스 8 = 2.4 → 2 | 소스 하나가 실패한 실행 |

한 실행에 소스 하나만 실패하면 두 단위가 같다.
한 실행에 소스 둘이 실패하면 어긋난다.

예를 들어 소스 둘씩 실패한 실행 (성공률 0.75) 이 2번이면 알림은 「2회 (2회까지 충족)」 이다.
실제 평균은 (28 + 2 × 0.75) ÷ 30 = 0.983 으로 미달이다.
창이 30회보다 짧을 때도 한도를 30회 기준으로 계산했다.

## 2. 누가 잡았나

| 단계 | 결과 |
| --- | --- |
| 계획서 dry run (코드를 그대로 적용해 전체 테스트) | 통과 · 「도는가」 만 본다 |
| 작업 2 리뷰 | 통과 · 리뷰 요청에 「SLO-2 여유 셈과 창」 을 짚어 두었는데도 「설계 예시와 같은 2 가 나온다」 로 확인했다 |
| 최종 브랜치 리뷰 | 잡았다 · 「N 과 M 의 단위가 다르다」 · 계획 · 설계 쪽 결함으로 분류 |

작업 리뷰가 놓친 이유는 셈을 SLO-2 의 정의 (평균 성공률) 가 아니라 설계 문서의 예시와 대조했기 때문이다.
설계의 단순화를 그대로 물려받은 예시와 맞으니 통과로 읽혔다.
계획서의 테스트도 그 단순화를 정답으로 박아 두었다 (`slo2_margin([1.0, 0.875], 0.875, 8) == (2, 2, 3)` · 3회 중 2회 실패를 「충족」 으로).

## 3. 고친 것

N 을 실패한 소스 수의 합으로 셌다.

```python
window = [current_rate, *previous_rates[:RECENT_RUNS - 1]]
failed = round(sum(1 - r for r in window) * n_sources)                  # 소스 실패 단위
allowed = math.floor(round(len(window) * (1 - SLO2_TARGET) * n_sources, 6))
```

한 실행에 소스 하나만 실패하는 평소에는 원안과 값이 같다.
설계 §4.2 의 「소스 실패」 정의도 같은 PR 에서 고쳤다.
테스트에는 소스 둘씩 실패한 실행 둘 (`(4, 2, 30)`) 을 더했다.

## 4. 교훈

- **지표에서 파생한 값은 지표의 정의로 검산한다.** 설계 문서의 예시와 대조하면 설계의 단순화까지 함께 통과한다.
- **계획서의 기대값은 주장이다.** 테스트가 그 값을 정답으로 박으면 dry run 과 테스트 통과가 그 주장을 증명하는 것처럼 보인다.
- **최종 리뷰는 가장 강한 모델로 따로 받는다.** 이번에는 작업 리뷰 셋이 모두 통과한 뒤 최종 리뷰만 잡았다.
