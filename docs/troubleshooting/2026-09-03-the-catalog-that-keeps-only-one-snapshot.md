# 스냅샷을 하나만 남기는 카탈로그 (2026-09-03)

변경 이력 레이크하우스의 첫 유지보수 (11:44 KST) 를 검증하다가, 카탈로그가 이전 스냅샷을 커밋 즉시 걷어낸다는 것을 알았다.
컴팩션은 열 표 전부 성공했는데 갈아 끼우기 전의 데이터 파일이 GCS 에 그대로 남아 버킷이 하루 만에 2.6배가 됐다.
설계와 런북이 기대던 전제 하나가 무효가 됐고, 고아 파일을 우리가 직접 지우는 단계가 생겼다.

## 1. 무엇이 이상했나

유지보수 뒤 `python -m bullet_in.warehouse show` 는 열 표 모두 파일 1개 · 스냅샷 1개라고 했다.
그런데 `articles_changes` 는 그때까지 커밋을 여덟 번 했다 (첫 적재 뒤 변경분 append 일곱 번).
표준 Iceberg 라면 스냅샷이 여덟 개 있어야 하고, 우리 만료 (`expire`) 는 7일 넘은 것만 걷어낸다.

표를 열어 보니 이렇다.

```
snapshots: 1  ·  snapshot-log: 8  ·  metadata-log: 5  ·  last-sequence-number: 8
properties: write.metadata.delete-after-commit.enabled=true · write.metadata.previous-versions-max=5 · write.parquet.compression-codec=zstd
```

`snapshot-log` 가 커밋 여덟 번을 기억하는데 `snapshots` 목록에는 현재 것 하나뿐이다.
우리는 스냅샷 만료 속성을 건 적이 없다.

## 2. 누가 걷어내나

유지보수가 돌기 전 (11:24 KST) 에 이미 하나였으므로 우리 `expire` 가 한 일이 아니다.
남는 것은 카탈로그다.
운영 카탈로그는 Google 의 Lakehouse (BigLake) metastore 이고 Iceberg REST 프로토콜로 붙는다.
커밋 응답에 실려 오는 메타데이터에서 이전 스냅샷이 빠져 있으니 서버 쪽이 걷어낸다.

Google 의 REST 카탈로그 문서 (퀵스타트 · 제한 사항) 에서 스냅샷 보존 정책 · 타임 트래블 · 메타데이터 크기 한도를 설명하는 문장은 찾지 못했다.
**이유는 문서로 확인하지 못했고 동작만 관측했다.**

## 3. 무엇이 바뀌나

전제 셋이 갈린다.

| 전제 | 전 | 후 |
| --- | --- | --- |
| `metadata.json` 1 MB 한도 | 스냅샷당 약 1,015 바이트가 쌓여 약 124일에 커밋 실패 | 스냅샷이 안 쌓이므로 성립하지 않는다 |
| 스냅샷 만료 단계 | 하루 1회 7일 넘은 것을 걷어낸다 | 늘 「1개에서 1개로」 다 · 해롭지 않아 코드는 둔다 |
| 타임 트래블 · 롤백 | 옛 스냅샷으로 표를 되돌릴 수 있다 | 못 쓴다 |

셋째는 설계에 구멍을 내지 않는다.
이력은 스냅샷이 아니라 데이터 행 (변경분 표 + 날짜별 전량 스냅샷 파티션) 에 두기로 설계했기 때문이다.
잃은 것은 「잘못 덮어쓴 것을 되돌리는 안전망」 하나이고, 필요하면 버킷의 객체 버전 관리가 값싼 대안이다.

## 4. 진짜 문제는 고아 파일이다

표준 Iceberg 의 스냅샷 만료는 두 일을 한 번에 한다.
옛 목록 (스냅샷) 을 지우고, 그 목록만 가리키던 데이터 파일도 함께 지운다.
이 카탈로그는 앞 절반만 하고 뒤 절반을 안 한다.

그래서 컴팩션이 파일 여덟 개를 읽어 한 개로 다시 쓰면, 옛 여덟 개는 아무 목록에도 걸리지 않은 채 GCS 에 남는다.
gold 두 표는 회차마다 `overwrite` 라 같은 일이 하루 여덟 번 일어난다.

| 표 | 표가 가리키는 파일 | GCS 의 parquet |
| --- | --- | --- |
| `articles_changes` | 1 | 9 |
| `ga4_events` · `ga4_events_flat` | 1 | 7 씩 |
| `fact_card_click` · `dim_date` | 1 | 5 씩 |
| 나머지 여섯 | 1 | 3 씩 |

버킷 전체가 8,865,742 에서 23,001,079 바이트가 됐다.
부피보다 상한이 없다는 것이 문제다.
컴팩션이 읽기만 좋게 하고 저장은 나쁘게 하는 반쪽이 된다.

PyIceberg 0.11.1 에는 고아 정리가 없다.
`table.maintenance` 에는 `expire_snapshots` 하나뿐이고, 다른 엔진의 `remove_orphan_files` 가 기대는 스냅샷 만료도 여기서는 걸릴 것이 없다.

## 5. 어떻게 고쳤나

유지보수에 고아 청소 단계 (`sweep_orphans`) 를 두었다 (PR #449).

1. 현재 스냅샷을 스캔해 살아 있는 파일 집합을 먼저 받는다.
2. 표 위치 아래 `data/` 객체를 나열한다.
3. 집합에 없으면서 생긴 지 3일 넘은 것만 지운다.

3일은 Apache Iceberg 의 `remove_orphan_files` 기본값과 같다.
Iceberg 는 데이터 파일을 먼저 쓰고 목록을 나중에 갱신하므로, 「목록에 없다」 가 「버려도 된다」 와 같은 말이 아니다.
살아 있는 집합을 나열보다 먼저 받는 순서도 같은 이유다.
순서를 바꾸면 그 사이에 커밋된 새 파일이 고아로 보인다.

나열과 삭제는 pyarrow 파일시스템으로 한다.
운영 표의 FileIO 가 이미 `PyArrowFileIO` 라 읽는 눈과 지우는 손이 같은 경로 표기를 본다.
`gs://` 와 `file://` 을 같은 API 로 다루니 로컬 카탈로그 테스트가 같은 코드를 지난다.
다만 pyarrow 의 URI 파서는 ASCII 밖 문자가 든 경로를 못 읽어서 (테스트 임시 경로에 한글 테스트 이름이 들어간다) `file://` 은 로컬 파일시스템에 직접 붙였다.

배포 뒤 수동 유지보수에서 열 표 전부 「고아 청소 — data/ 객체 N · 살아 있는 것 1 · 3일 안 된 것 N−1 · 지움 0」 이 나왔다.
오늘 고아는 전부 3일 안이라 실제 첫 삭제는 2026-09-05 유지보수부터다.

## 6. 다음에 같은 자리를 만나면

- **관리형 카탈로그의 동작은 문서보다 표를 열어 재는 편이 빠르다.** `snapshots` 와 `snapshot-log` 의 길이 차이 하나가 답이었다.
- **한 절차에 묶인 두 일이 갈라지면 빠진 절반을 찾는다.** 「목록 지우기」 와 「파일 지우기」 가 그것이다.
- **버킷을 `show` 로 재지 말고 나열로 잰다.** `show` 는 표가 가리키는 파일만 세고, 고아는 표 밖에 있다.
