# 새 필드로 판정 기준을 바꿀 때 값이 비어 있는 구간이 화면을 바꾼다 (2026-08-12)

선수 페이지의 기사 선별 기준을 `article_players.stage` 에서 새 필드 `role` 로 옮기면서 (PR #251) 겪은 설계 결함이다.
값을 만드는 쪽이 다른 회차에 있어 배포 시점에는 새 필드가 비어 있었는데, 그 구간의 동작을 잘못 정해 **배포 즉시 화면이 나빠질 뻔했다.**
태스크 리뷰에서 잡혀 배포 전에 고쳤다.

## 1. 무엇이 문제였나

바꾸려던 것은 한 줄이다.

- 옛 규칙: `stage != 'other'` 인 귀속만 목록에 올린다.
- 새 규칙: `role != 'mention'` 인 귀속만 목록에 올린다.

`role` 은 추출이 채우는데 그 프롬프트 문안은 다른 트랙 소유라 이 브랜치가 건드리지 않았다.
따라서 배포 시점에는 2,168행 전부가 미기입이다.

미기입을 어떻게 읽을지가 남았고, 초안은 **미기입 = 주역**으로 정했다.
언급으로 읽으면 모든 선수 페이지가 사라지므로 반대편을 고른 것이다.

여기까지는 그럴듯하지만 결과가 정반대였다.

- 옛 규칙은 단계가 `other` 인 귀속 588건을 **빼고** 있었다.
- 새 규칙은 미기입을 주역으로 읽으므로 **아무것도 빼지 않는다** (`None != 'mention'` 은 항상 참).
- 즉 배포 순간 숨어 있던 588건이 전부 선수 페이지에 올라온다.
- 귀속이 전부 `other` 라 그때까지 페이지가 없던 선수 4명도 페이지를 갖는다.

값이 채워지는 것은 다른 트랙의 적용 회차이므로, 그때까지 며칠 동안 화면이 **개선 전보다 나쁜 상태**로 운영된다.

## 2. 스펙이 스스로 모순이었다

같은 스펙에 배포 판정 기준을 이렇게 적어 두었다.

> 배포 후 판정 기준은 무변화 확인이다 — 역할이 비어 있으므로 페이지가 지금과 같아야 하고, 달라지면 미기입 해석이 잘못된 것이다.

**통과할 수 없는 기준이었다.**
미기입을 주역으로 읽는 한 화면은 반드시 바뀐다.

더 나쁜 것은 그 모순을 **테스트가 증명하고 있었다**는 점이다.
"값이 채워지기 전에는 화면이 유지되는지" 를 검증한다고 주석을 단 테스트가, 실제로는 단계 `other` 인 기사가 새로 포함되는 것 (건수 1 → 2) 을 확인하고 있었다.
주석과 단언이 반대를 말하는데 테스트는 통과하므로 자동 검사로는 걸리지 않는다.

## 3. 어떻게 잡혔나

태스크 리뷰가 잡았다.
리뷰 지시에 "이 브랜치에는 값을 만드는 코드가 없으므로 운영에서는 전 행이 미기입이다.
그 상태에서 화면이 지금과 같아야 한다는 요구가 코드로 지켜지는지 확인하라" 는 항목을 **명명된 위험**으로 넣은 것이 주효했다.

리뷰어는 그 항목을 트레이스하다 테스트 자체가 반증이라는 것을 찾아냈다.
지시가 없었다면 "코드가 브리프대로 구현됐다" 로 통과했을 것이다 — 실제로 구현은 브리프를 정확히 따랐고, 틀린 것은 브리프였다.

## 4. 해법 — 전환 규칙

값이 있는 행과 없는 행을 다른 규칙으로 판정한다.

```python
paired = [(by_hash[l["content_hash"]], l["stage"]) for l in p["links"]
          if l["content_hash"] in by_hash and (
              l["stage"] != _stage.OTHER if l.get("role") not in ROLES
              else l["role"] != MENTION)]
```

- 역할이 있으면 역할로 판정한다 (단계는 보지 않는다).
- 역할이 미기입이거나 어휘 밖이면 **옛 규칙으로 판정한다.**

배포 시점에는 전 행이 미기입이라 옛 규칙이 그대로 돌아 화면이 바뀌지 않고, 값이 채워지는 행부터 하나씩 새 규칙으로 넘어간다.
모델이 값을 빠뜨린 행도 종전 동작을 유지한다.

**"두 조건을 함께 걸지 않는다" 는 결정과 충돌하지 않는다** — 역할이 있는 행에서는 단계를 보지 않는다.
단계 조건은 값이 없는 행에만 적용되는 임시 경로이고, 백필이 끝나면 걷어내는 후속 작업으로 등재했다.

## 5. 검증 방법 — 빈 값 상태에서 집합을 대조한다

전환 규칙이 실제로 무변화인지는 **역할을 하나도 채우지 않은 운영 사본**에서 확인했다.

- 새 코드로 만든 (선수, 기사) 쌍 집합과 옛 규칙 (`stage != 'other'`) 으로 계산한 집합을 대조.
- 결과: **806쌍 대 806쌍 · 차집합 0건.**

이 검사가 배포 판정 기준을 비로소 성립시켰다.
배포 후 실측도 일치했다 — 첫 정기 회차에서 선수 페이지 54개 유지 · 사라진 페이지 0 · **기사 건수 감소 0건** (증가 6페이지는 신규 수집분).

## 6. 규칙을 바꾸면 옛 문구가 남는다

전환 규칙으로 개정한 뒤 브랜치 전체 리뷰에서 Important 2건이 나왔는데 **둘 다 같은 유형**이었다.

- 정본 스펙의 다른 절에 개정 전 규칙 ("미기입은 자연히 주역이 된다") 이 그대로 남아 있었다.
- 값을 만드는 함수의 docstring 이 존재하지 않는 안전망 ("미기입은 주역으로 읽혀 기사가 사라지지 않는다") 을 단언하고 있었다.

코드는 맞는데 문서가 코드보다 오래된 규칙을 말하는 상태다.
그대로 두면 다음 작업자가 **정상 동작을 결함으로 오진하고 되돌린다.**

리뷰어는 "주역" 이라는 낱말이 등장하는 12곳을 전수 확인해 3곳을 찾았다 (계획서에 남은 것은 이력 보존 문서라 제외).
**회차 중간에 규칙이 바뀌면 옛 규칙의 표현을 검색어로 잡아 전수 훑는 것이 필요하다.**

## 7. 일반화 — 새 필드가 기존 판정을 대체할 때

- **값이 채워지기 전 구간의 동작을 설계에 명시한다.** "기본값을 무엇으로 읽을 것인가" 가 아니라 "그 기본값이 옛 규칙과 같은 결과를 내는가" 를 묻는다.
- **판정 기준을 스펙에 적었으면 그 기준으로 설계를 한 번 대 본다.** 이번 결함은 스펙 안에서 두 절이 서로 모순이었고, 그것만 대조했어도 잡혔다.
- **리뷰 지시에 "값이 비어 있는 상태" 를 명명된 위험으로 넣는다.** 구현이 브리프를 정확히 따르면 브리프의 결함은 리뷰에서만 잡힌다.
- **테스트 주석과 단언이 같은 것을 말하는지 본다.** 주석이 의도를, 단언이 반대를 말해도 테스트는 통과한다.
- **규칙 개정 후에는 옛 규칙의 표현으로 전수 검색한다.**
