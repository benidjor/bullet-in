# 되돌리기 도구가 자기 자신을 지우는 자리 (2026-09-04)

배포 자동화 (안건 2β) 의 계획서는 머지 뒤 라이브 리허설을 「상태 파일에 직전 커밋을 `previous` 로 넣고 수동 `rollback` 을 친다」 로 적어 두었다.
그 직전 커밋에는 되돌리기 도구 `bullet_in.deploy` 가 없다.
리허설 첫 명령이 자동화를 통째로 멈추는 순서였고, 코드 리뷰가 아니라 브랜치 전체 리뷰가 잡았다.

## 1. 증상 (일어났다면 이렇게 보였을 것)

리허설 순서대로 치면 이렇게 된다.

1. `rollback` 이 `git reset --hard <previous>` 로 소스 트리를 직전 커밋으로 되돌린다.
2. 그 커밋에는 `src/bullet_in/deploy.py` 가 없다.
3. 다음 명령 `unblock` 이 「No module named bullet_in.deploy」 로 죽는다.
4. 설치된 유닛의 `advance` (`ExecStartPre=-` 라 무시된다) 와 `judge` (`ExecStopPost=-` 라 무시된다) 도 같은 오류로 못 돈다.
5. 어느 회차도 다시 전진하지 못하고, 손으로 `git pull` 을 치는 것만이 복구 경로다.

알림은 하나도 안 온다.
`rollback` 의 사고 알림은 되돌리기 전에 나가고, 그 뒤의 실패는 전부 유닛의 `-` 표기가 삼킨다.

## 2. 원인

도구가 자기 자신이 생기기 전 상태로 소스 트리를 되돌렸다.

이 저장소는 편집 설치다 (`pyproject.toml` 의 `hatchling` · `packages = ["src/bullet_in"]`).
`.venv` 안에 모듈의 복사본이 없고 소스 트리가 곧 import 대상이라, 트리를 되돌리면 모듈이 같이 사라진다.

계획서는 「알려진 정상 쌍 P · N 에 대해 `rollback` 을 친다」 고만 적었다.
P 가 정상 커밋인지는 물었지만 P 에 도구가 있는지는 묻지 않았다.
작업 단위로 나눠 한 리뷰 여섯은 각자의 diff 만 봤으므로 이 순서를 볼 자리가 없었다.

## 3. 해결

리허설 순서를 바꿨다.

- 상태 파일의 씨앗은 `previous` 도 머지 커밋 `M` 으로 둔다.
  되돌릴 곳이 도구가 있는 커밋이 된다.
- 후속 문서 PR 을 하나 머지한다 (이 문서가 실린 PR 이 그것이다).
  다음 회차가 그 커밋 `M2` 를 첫 자동 전진으로 집어 오고, 판정 뒤 상태 파일은 `previous: M · current: M2` 가 된다.
- 그 다음에 수동 `rollback` 을 친다.
  `M` 으로 되돌아가고 `M` 에는 도구가 있다.
- `unblock M2` 뒤 회차를 손으로 시작하면 전진 · 판정 성공 경로가 한 번 더 돈다.

계획서 태스크 7 의 Step 4에서 6 을 이 순서로 고쳤고, 새 런북 §6 에 「도구를 들여온 커밋보다 앞으로 되돌리지 않는다」 를 적었다.

## 4. 예방

- **되돌리기 · 마이그레이션 · 정리 도구는 자기 자신이 생기기 전 상태로 갈 수 없다.**
  그 경계 앞에서는 도구 밖의 경로 (손으로 치는 `git pull` · SQL) 가 유일하고, 런북이 그 경계를 적어야 한다.
- 도구의 리허설은 도구를 들여온 커밋을 `previous` 로 두고 한다.
  즉 도구 PR 이 머지되고 배포된 뒤, 후속 커밋 하나가 올라간 다음이 첫 리허설 시점이다.
- 코드가 다 맞아도 절차가 틀릴 수 있다.
  브랜치 전체 리뷰에 「이 절차를 순서대로 치면 어느 시점에 무엇이 사라지나」 를 질문으로 넣는다.
