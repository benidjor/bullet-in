# fmkorea 의 430 은 장애가 아니라 회차마다 다시 던지는 동전이었다 (2026-10-03)

- **영역**: 수집 / fmkorea 검색 어댑터 / SLO-5
- **관련 안건**: 2ι 맥 의존 수집
- **고친 곳**: 이 문서와 같은 PR · `docs/superpowers/specs/2026-10-02-slo5-broken-source-signal-design.md` §8
- **남은 일**: 24시간을 넘는 차단에서 글을 잃는지 (아직 관측된 적 없음)

## 1. 증상

SLO-5 끊김 신호 (#515) 를 배포한 다음 날인 2026-10-02 18:01 KST 에 끊김 알림이 왔다.

> 🔌 수집 끊김 — fmkorea 축구 소식통 · 검색어 5개 모두 실패 (430) · 2회 연속

21시 회차도 같았고 수집 현황 화면의 SLO-5 는 「끊긴 소스 2」 가 됐다.
fmkorea 수집이 멈춘 사고로 보였다.

그런데 다음 회차 (10-03 00:00) 에 검색 5개가 모두 정상으로 돌아왔다.

## 2. 처음 세운 가설과 그것이 틀린 이유

### 2.1. 맥 터널이 끊겼다

VM 의 IP 는 fmkorea 에 430 으로 막혀 있다 (`docs/runbook/2026-07-13-fmkorea-search-adapter-ops.md` 「rate-limit」 절 · 안건 2ι).
그래서 정기 회차의 fmkorea 요청은 맥의 역터널 (`FMKOREA_PROXY`) 을 거쳐 맥 회선으로 나간다.

터널이 끊기면 연결 오류가 나야 한다.
어댑터는 `proxy=self.proxy` 로 고정돼 있어 VM IP 로 바로 나가는 대체 경로가 없다.
로그에는 연결 오류가 0건이고 430 만 있었으므로, 요청은 맥 회선으로 fmkorea 에 닿은 뒤 막혔다.

### 2.2. 우리 쪽 추가 요청이 차단을 불렀다

같은 맥 회선을 쓰는 작업이 둘 더 있다.
VM 의 워치리스트 타이머와 맥의 보충 작업 (15분마다 · 마지막 접촉 3시간 가드) 이다.

10-02 의 시각을 나란히 놓아 보면 둘 다 계기가 아니었다.

| 시각 (KST) | 회차 | 워치리스트 |
| --- | --- | --- |
| 04:32 | — | 정상 |
| 09:00 | 전부 430 | 실행 없음 |
| 12:00 | 정상 | 실행 없음 |
| 15:00 · 18:00 · 21:00 | 전부 430 | 실행 없음 |
| 19:33 | — | 전부 430 (이미 막힌 뒤) |
| 22:30 | — | 정상 |
| 00:00 | 정상 | — |

보충 작업은 430 을 받아도 접촉 스탬프를 남기므로 (`collect_fmkorea.py` 161행), 차단 중에도 3시간에 한 번만 요청한다.

### 2.3. 수 시간 이어지는 차단이다

연속 차단 (09-14 21:00 부터 09-15 12:00 까지 6회) 을 보고 처음에는 「몇 시간씩 걸렸다 풀렸다 한다」 고 적었다.
직전 회차 상태별로 다음 회차의 차단 확률을 세어 보니 이 설명은 틀렸다 (§3.2).

## 3. 실제로 일어나는 일

Airflow 회차 로그 (2026-09-04 부터 10-03 00:00 까지 228회차) 를 파일 단위로 열어 회차마다 검색 요청 줄 (`search.php`) 과 그 응답 코드를 셌다.

### 3.1. 매일 있던 일이다

| 셈 | 값 |
| --- | --- |
| 검색 요청 수 | 228회차 모두 5건 · 재시도 0 |
| 5건 모두 430 | 101회 (44%) |
| 430 0건 | 127회 |
| 일부만 430 | 0회 |

날짜별로는 하루 8회 가운데 1회에서 6회까지 날마다 있었다.
10-02 은 특별한 날이 아니었다.
새로 생긴 것은 차단이 아니라 차단을 읽는 판정 (#515) 이다.

### 3.2. 이어지지 않는다

| 직전 회차 | 다음 회차가 막힌 비율 |
| --- | --- |
| 막힘 | 44 / 101 (44%) |
| 정상 | 56 / 126 (44%) |

두 값이 같다.
차단은 회차마다 독립적으로 약 44% 확률로 걸리고 직전 회차와 상관이 없다.
연속 6회도 이 확률이면 한 달에 한 번쯤 우연히 나오는 길이다.

시간대 편향도 약하다 (09시 17% · 18시 20% · 나머지 40% 에서 62%).
정상 회차의 fmkorea 요청 수는 늘 20건 안팎 (검색 5 · 글 15) 이라, 요청량과 차단의 관계는 이 자료로 가려낼 수 없다.

### 3.3. 글을 잃지 않는다

손실은 차단이 풀린 첫 성공 회차가 상한 (`max_posts` 15) 에 걸리거나, 검색 1페이지가 차단 기간을 덮지 못할 때 생긴다.
회차마다 요청한 글 번호를 모아 차단 뒤 첫 성공 회차가 직전 성공 회차와 같은 글을 몇 건 다시 봤는지 셌다.
한 건이라도 겹치면 그 사이 공백은 1페이지 안에 들어 있었다는 뜻이다.

| 직전 연속 차단 | 성공 회차 수 | 겹침 0 인 회차 | 겹침 중앙값 |
| --- | --- | --- | --- |
| 0회 | 70 | 0 | 15 |
| 1회 | 35 | 0 | 14 |
| 2회 · 3회 | 14 | 0 | 12 |
| 4회 · 5회 | 6 | 0 | 13 · 14 |
| 6회 (18시간) | 1 | 0 | 11 |

후보는 늘 11에서 14건이었고 상한 15에 닿은 회차는 없었다.
피해는 지연뿐이다.

## 4. 고친 것

2회 연속 규칙이 이 상태를 한 달에 스무 번 넘게 「끊김」 으로 알리게 되므로, 무응답 사유를 하나 더 나눴다 (설계 문서 §8).

- **새 사유 `blocked`** — 검색 전부 실패이고 실패 코드가 430 뿐일 때
- **끊김 기준** — 연속 무응답이 모두 `blocked` 이면 8회 (24시간) · 다른 사유가 섞이면 2회 그대로
- **화면** — 「차단 N회 (430)」 · 「응답 없음 N회」

우연한 알림이 몇 달에 한 번으로 줄면서 (아래쪽 경계) 손실 없이 관측된 18시간을 크게 벗어나지 않는 (위쪽 경계) 값은 7 과 8 이고, 우연한 알림이 더 적고 「하루」 로 읽히는 8 을 골랐다.
240 × (1 − p) × pᴺ 로 계산하면 8회 연속이 우연히 생기는 일은 약 5개월에 한 번이다.

## 5. 배운 것

### 5.1. 연속 관측은 지속성의 증거가 아니다

6회 연속 차단은 「오래 가는 차단」 처럼 보였지만 독립적인 44% 사건도 한 달이면 그만큼 이어지는 때가 나온다.
지속성은 직전 회차의 상태별로 다음 회차의 확률을 나눠 재야 한다.

### 5.2. 과거 이력 대입은 기록이 있는 소스만 본다

#515 를 머지하기 전에 과거 이력으로 규칙을 시험했지만 fmkorea 의 수집 단계 기록은 그 PR 이 처음 만들었다.
같은 정보는 회차 로그 (`fmkorea 검색 HTTP 430`) 에 원래 있었다.
새 판정을 대입할 때는 소스마다 「대입할 재료가 어디에 있는가」 를 먼저 물어야 한다.

### 5.3. 알림 기준은 받은 사람이 할 일이 있는지로 정한다

같은 무응답이라도 430 은 기다리면 풀리고, 연결 오류는 맥을 깨워야 하고, 검색 결과 0 은 어댑터를 고쳐야 한다.
사유를 기록하고 있었으므로 (#517 의 실패 코드) 사유별로 기준을 나누는 데 드는 비용은 작았다.
