# 머지된 PR 브랜치에 push 한 커밋이 사라진다 (2026-08-03)

문서 PR 을 올린 뒤 보강 커밋을 같은 브랜치에 push 했는데, 그 사이 PR 이 머지돼 두 번 다 main 에 들어가지 않았다.
그 결과 계약 정정을 머지했다고 믿은 런북이 **몇 시간 동안 구식인 채로 main 에 남아 있었다** — 그대로 실행하면 모든 기사의 단계가 깨지는 스니펫이다.

## 1. 증상

- `#199` 에 올린 런북 §2 백필 스니펫 정정 (`ac2d31c`) 이 main 에 없었다.
- `#204` 에 올린 방향 기준 한계 기록 (`b21344d`) 도 같은 이유로 누락됐다.
- 둘 다 push 는 성공했고 (`1bef853..ac2d31c`), 오류도 경고도 없었다.
- 뒤늦게 main 의 런북을 직접 열어 보고서야 옛 내용이 그대로인 것을 확인했다.

## 2. 원인

- squash merge 는 머지 시점의 브랜치를 한 커밋으로 눌러 담고 PR 을 닫는다.
그 뒤 같은 브랜치에 push 해도 닫힌 PR 은 다시 열리지 않고, main 도 그대로다.
- 이 저장소는 **PR 생성과 머지가 분리돼 있다** (세션은 생성까지 · 머지는 사용자).
그래서 "PR 을 올린 뒤 보강" 이라는 흔한 흐름이 머지 시점과 겹치기 쉽다.
- 특히 위험한 조합은 **여러 PR 을 연달아 올리는 세션**이다 — 앞 PR 이 이미 머지됐는지 확인하지 않고 브랜치를 재사용하게 된다.

## 3. 왜 자체 점검에서도 못 잡았나

세션 종료 전 "미반영 커밋이 있는지" 를 아래로 확인하려 했는데, 이 검사는 squash 저장소에서 **항상 거짓 양성**을 낸다.

```bash
git log --oneline origin/main..<branch>   # squash 후에도 항상 커밋이 남아 보인다
```

- squash 는 새 SHA 를 만들므로 원래 브랜치 커밋은 영원히 main 의 조상이 되지 않는다.
- 실제로 이 검사를 42개 브랜치에 돌리니 대부분이 "미반영" 으로 나왔고, 진짜 누락 2건이 그 잡음에 묻혔다.
- 파일 단위 비교 (`git diff origin/main...<branch>`) 도 쓸 수 없다 — 이후 PR 들이 같은 파일을 더 고쳐 정상적으로 달라지기 때문이다.

## 4. 조치

- 누락된 커밋을 `origin/main` 에서 딴 새 브랜치로 옮겨 새 PR (`#205`) 로 다시 올렸다.
- cherry-pick 중 이미 squash 로 반영된 커밋은 빈 변경이 되어 멈춘다 — `git cherry-pick --skip` 으로 넘기고 나머지만 적용한다.

## 5. 예방

- **보강 전에 PR 상태를 확인한다.**

```bash
gh pr view <번호> --json state -q .state    # MERGED 면 같은 브랜치에 push 하지 않는다
```

- **MERGED 면 새 브랜치 · 새 PR 로 올린다.** 브랜치 재사용은 조용히 유실된다.
- **반영 확인은 커밋이 아니라 내용으로 한다.** 변경마다 고유한 표지를 골라 main 에서 직접 찾는다.

```bash
git show origin/main:<파일> | grep -c "<그 변경에만 있는 문구>"   # 0 이면 미반영
```

- 세션 종료 전 점검은 이 표지 확인으로 대신한다 — 코드는 함수 · 상수 이름, 문서는 새로 쓴 문장이 표지가 된다.
