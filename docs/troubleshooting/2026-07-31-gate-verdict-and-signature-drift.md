# 게이트 판정을 뒤집은 기록과 시그니처 확장이 만든 조용한 드리프트 (2026-07-31)

재번역 큐 무한 루프를 고치다가 세 가지가 드러났다.
한 기사의 게이트 판정을 원문만 보고 정했더니 저장소에 이미 있던 실측 기록이 그 판정을 뒤집었다.
검출기에 인자를 하나 더하자 문서에 적힌 조사 스니펫이 파이프라인과 다르게 판정하기 시작했다.
종착 상태를 로그로만 남기자 사후에 조회할 길이 사라졌다.

공통점은 **바꾼 자리에서는 아무 문제도 안 보인다**는 것이다.
셋 다 코드가 정상 동작하고 테스트도 통과한다.

## 1. 원문만 읽고 내린 판정을 저장소 기록이 뒤집었다

### 1.1. 증상

게이트가 발화한 다섯 건을 오탐과 정탐으로 분류하는 중이었다.
`7341690b` 는 원문 제목이 아래와 같다.

```
With Arteta's Backing: Liverpool Compete Strongly to Snatch Target of Chelsea, Arsenal and United
```

제목 맨 앞에 아르테타가 나오니 기사의 주체로 읽었다.
번역이 그를 빠뜨린 것은 결함이라고 판정했다.

### 1.2. 반박

`docs/superpowers/plans/2026-07-22-classification-relevance-track.md` 에 2026-07-23 진단이 남아 있었다.

> `7341690b` 의 좋은 번역 ("아스날 · 첼시 · 맨유 노리는 알렉스 스콧, 리버풀 영입전 가세") 이 **`인명 누락:Arteta` 게이트에 결정적으로 걸림** (1 ~ 3 회 FLAGGED · 5 회는 Arteta 억지 삽입한 어색한 제목으로만 PASS).

Gemini 로 재번역을 다섯 번 돌려 본 결과다.
원제의 아르테타는 "아르테타가 원하는 선수" 라는 배경 설명이고 기사의 주인공은 알렉스 스콧이다.
번역이 그를 뺀 것은 정당한 축약이었다.
게이트가 문제 삼은 쪽이 틀렸다.

### 1.3. 교차 확인 — 화면에 남은 값이 그 진단의 산출물이다

기록만으로 끝내지 않고 라이브 DB 를 봤다.

```
7341690b 의 title_ko = 아르테타의 주목을 받는 알렉스 스콧, 리버풀·첼시·맨유와 영입 경쟁
```

기록이 말한 "Arteta 억지 삽입한 어색한 제목" 이 그대로 저장돼 서빙되고 있었다.
**과거 진단의 결론이 현재 데이터에 물증으로 남아 있는 경우가 있다** — 기록과 DB 를 함께 보면 기록의 신뢰도까지 같이 확인된다.

### 1.4. 판정이 바뀌자 표본이 바뀌었다

| | 정정 전 | 정정 후 |
| --- | --- | --- |
| 인명 축 발화 5건 | 오탐 3 · 정탐 1 · 판정 불가 1 | 오탐 4 · 정탐 0 · 판정 불가 1 |
| 현행 코드 유효 표본 | 오탐 1 · 정탐 1 | 오탐 2 · 정탐 0 |

이 표본이 종착 상태를 무엇으로 할지 (번역 채택 · 영문 유지) 정하는 근거였다.
결론은 바뀌지 않았지만 근거의 강도가 달라졌다.

### 1.5. 재발 방지

게이트 발화를 오탐 · 정탐으로 분류하기 전에 아래를 검색한다.

```bash
grep -rn "<content_hash 앞 8자>" docs/
grep -rln "게이트\|오탐\|환각" docs/superpowers/plans/ docs/superpowers/specs/
```

원문 제목의 문면만으로는 인명이 주체인지 배경인지 가릴 수 없다.
실제로 재번역을 돌려 본 기록이 있으면 그쪽이 강한 근거다.

## 2. 기본값을 준 새 인자가 문서 스니펫에서 조용히 다르게 판정한다

### 2.1. 무엇을 바꿨나

`detect_title_mistranslation` 에 네 번째 인자 `source_text` 를 더했다.
기본값 `""` 을 준 이유는 기존 호출 다섯 곳을 한꺼번에 고치지 않기 위해서였다.

```python
def detect_title_mistranslation(title_ko, title_original, name_map, source_text=""):
```

### 2.2. 증상

`docs/runbook/2026-07-19-translation-quality-gates-ops.md` §5 의 전수 스윕 스니펫이 세 인자로 호출하고 있었다.
기본값이 있으니 예외도 경고도 나지 않는다.
그런데 컨텍스트가 제목뿐이라 **본문에만 풀네임이 있는 행을 파이프라인은 검사하고 스윕은 면제한다.**

실측으로 갈라지는 것을 확인했다.

```
detect_title_mistranslation("아스날, 수비수 계약 임박", "White nears new Arsenal deal",
                            {"화이트": "White"})
  -> []                       # 3인자 · 스윕이 보던 결과
동일 입력 + source_text="Ben White is closing in on fresh terms."
  -> ['인명 누락:White']       # 4인자 · 파이프라인이 보는 결과
```

조사 도구와 운영 코드가 같은 행을 다르게 본다.
스윕으로 "깨끗하다" 는 결론을 내면 그 결론이 틀린다.

### 2.3. 왜 늦게 발견됐나

단위 테스트는 함수를 직접 부르므로 인자를 명시한다.
파이프라인 호출부는 배선 테스트가 잡는다.
**문서 안의 코드 블록만 아무도 실행하지 않는다.**

### 2.4. 재발 방지

검출기 · 저장 함수의 시그니처를 바꾸면 `docs/` 안의 호출까지 함께 찾는다.

```bash
grep -rn "detect_title_mistranslation\|finalize_translation" docs/ src/ tests/
```

`docs/superpowers/plans/` · `specs/` 아래 과거 문서는 역사 기록이므로 고치지 않는다.
런북은 다르다 — 사람이 복사해 실행하는 절차라 코드와 같이 움직여야 한다.

이번에는 `finalize_translation` 의 반환값도 네 개에서 다섯 개로 늘렸는데, 그쪽은 `*` 전개가 즉시 깨지므로 오히려 안전했다.
**조용히 통과하는 변경이 즉시 깨지는 변경보다 위험하다.**

## 3. 종착을 로그로만 남기면 DB 조회 경로가 사라진다

### 3.1. 무엇이 바뀌었나

전에는 게이트가 끝내 못 푼 행이 `title_ko` 를 비운 채 남았다.
그래서 운영자가 SQL 한 줄로 찾을 수 있었다.

```sql
SELECT * FROM articles WHERE title_ko IS NULL AND summary_ko IS NOT NULL;
```

이번에 종착을 "번역 제목 채택 + 경고 로그" 로 바꿨다.
루프는 멈췄지만 **채택된 행이 DB 에서 정상 행과 구별되지 않는다.**
남는 것은 journal 의 WARNING 한 줄뿐인데 journal 은 보존 기간이 지나면 사라진다.

### 3.2. 무엇이 비어 있었나

설계는 "경고 로그와 런북 §5 수동 정정 절차가 그 뒤를 받는다" 고 적었다.
그런데 §5 스윕 스니펫이 `detect_title_hallucination` 을 import 하지 않았다.

- 역방향 오역 (원문 인명이 번역에서 소실) — 스윕이 잡음
- 정방향 환각 (번역에 원문에 없는 인명이 생김) — **스윕이 안 잡음**

채택 종착으로 새로 서빙될 수 있는 것이 정방향 환각인데, 그것을 사후에 찾을 경로가 0 이었다.
스윕에 이 축을 더해 메웠다.

### 3.3. 교훈

DB 상태를 로그로 바꾸는 변경은 관측을 함께 설계해야 한다.

- 바꾸기 전에 물어볼 것 : **이 상태를 나중에 어떻게 다시 찾는가.**
- journal 은 보존 기간이 있다.
전수 스윕처럼 데이터에서 다시 계산하는 경로가 있으면 그쪽이 오래 간다.
- 스윕이 파이프라인의 모든 축을 도는지 확인한다.
축을 하나 빼먹으면 그 축의 사후 발견이 통째로 없어진다.
