# 「JSON 없음」 으로 108 실행 동안 실패한 번역은 입력 차단이었다 (2026-10-20)

- **영역**: 번역 (`enrich`) · Gemini 응답 처리
- **관련 PR**: #545 (입력 차단 기사는 다시 시도하지 않고 확인요청 채널에 알림) · #369 (실행 안 재시도)
- **고친 것**: 입력 차단을 먼저 알아보고 그 기사를 포기로 표시 · 확인요청 채널 알림 · 이 문서
- **남은 일**: 재작성 · 제목만 생성 · 선수 추출 경로에는 같은 확인이 없다 (지금까지 그 경로에서 차단 사례는 확인된 바 없음)

## 1. 증상

fmkorea 로 들어온 기사 한 건이 실행마다 번역에 실패했다.
FourFourTwo 의 「every notable Manchester City signing of the 115 charges era」 를 옮긴 글이다 (`content_hash` 앞 8자리 `92f0bae9` · 2026-10-06 01:42 UTC 적재).

enrich 로그에는 실행마다 같은 줄이 남았다.

```
WARNING Gemini 응답 파싱 실패, 스킵 content_hash=92f0bae9… 사유=JSON 없음 시도=3
```

- **기간**: 2026-10-06 03:00 UTC 실행부터 10-19 15:00 UTC 실행까지 108 실행 연속
- **호출**: 실행마다 3번 (실행 안 재시도 · #369) · 모두 약 324번 (추정 · 실행당 3번으로 셈)
- **화면**: 번역되지 않아 사이트에 한 번도 실리지 않았다

같은 기간 다른 기사의 번역 파싱 실패는 16건이었고, 그중 15건은 실행 안 2번째 시도에서 살아났다.
끝까지 실패한 것은 이 한 건뿐이었다.

## 2. 「JSON 없음」 이 원인을 가렸다

「JSON 없음」 은 응답 글자에 `{` 가 하나도 없을 때 붙는 이름이다.

```python
# src/bullet_in/enrich.py — _parse_full
m = re.search(r"\{.*\}", text or "", re.DOTALL)
if not m:
    # 여는 괄호만 있으면 응답이 닫히기 전에 끊긴 것이다 (출력 토큰 상한).
    return None, ("응답 잘림" if "{" in (text or "") else "JSON 없음"), []
```

이 이름은 응답 글자의 모양만 보고 붙는다.
그래서 「모델이 형식을 어겼다」 와 「모델이 아예 답하지 않았다」 를 가르지 못한다.
처음에는 둘 다 가설로 놓고 데이터로 좁혔다.

| 확인 | 결과 | 남는 가설 |
| --- | --- | --- |
| 응답이 출력 상한에서 잘렸나 | 아니다 · 잘렸다면 `{` 가 남아 「응답 잘림」 이 붙는다 | |
| 본문이 길어서인가 | 아니다 · 본문 7,900자 이상 기사 61건 중 60건은 번역됐다 | |
| 모델이 응답을 비웠나 | 로그로는 알 수 없다 · 코드가 응답의 종료 사유를 남기지 않는다 | 빈 응답 (차단) |

## 3. 원인 — 입력 단계 차단

운영 번역 경로와 같은 입력으로 Gemini 를 한 번 불러 응답 전체를 남겼다 (2026-10-20 · 사용자 승인 · 운영 DB 쓰기 없음).

- **입력**: `_MODES["translate"]` 프롬프트에 그 기사의 제목 · 본문 · 확정 링크 명단을 넣은 11,919자
- **설정**: `gemini-3.1-flash-lite` · `max_output_tokens` 8192 · `response_mime_type` JSON (운영과 같음)

| 응답 항목 | 값 |
| --- | --- |
| `prompt_feedback.block_reason` | `PROHIBITED_CONTENT` |
| 응답 후보 | 0개 |
| 응답 글자 | 빈 문자열 |
| 입력 토큰 | 3,725 |
| 우리 코드의 분류 | 「JSON 없음」 |

모델이 답을 만들다 실패한 것이 아니라, **입력을 받는 단계에서 거부**했다.
같은 입력이면 매번 같은 판정이라 몇 번을 다시 불러도 풀리지 않는다.
본문의 어느 부분이 걸렸는지는 응답이 알려 주지 않는다.

#369 의 실행 안 재시도는 「파싱 실패는 일시적이다」 를 전제로 만들었다.
일시적 실패에는 맞는 전제였지만 (16건 중 15건 회복), 이 건처럼 매번 똑같이 실패하는 경우에는 같은 호출을 실행마다 되풀이했다.
실행 사이에는 시도 횟수를 세는 장치도 없었다.

## 4. 해결 (#545)

- **먼저 차단을 본다** — `enrich_rows` 가 응답 글자를 해석하기 전에 `prompt_feedback.block_reason` 을 확인한다
  → 차단이면 같은 실행 안에서도 다시 부르지 않고 「Gemini 입력 차단, 번역 포기」 경고를 남긴다
- **포기를 저장한다** — `articles.enrich_blocked` 칼럼에 차단 사유를 남기고, `rows_missing_translation` 이 이 칸에 값이 있는 기사를 고르지 않는다
  → 실행끼리는 상태를 공유하지 않으므로, 실행 안에서만 멈추면 3시간 뒤 다음 실행이 같은 기사를 다시 고른다
- **사람이 한 번 보게 한다** — 「확인요청」 채널에 「🚫 번역 차단 — N건」 을 보낸다 · 표시한 뒤에는 다시 고르지 않으므로 알림은 기사마다 한 번

배포 뒤 첫 실행 (2026-10-19 18:00 UTC) 에서 확인했다.

- enrich 로그: 「Gemini 입력 차단, 번역 포기 content_hash=92f0bae9… 사유=PROHIBITED_CONTENT」 1줄 · 파싱 실패 줄 0
- 알림: 「알림 발송: review — 🚫 번역 차단 — 1건」 · 확인요청 채널에 도착 (사용자 화면 확인)
- 운영 DB: 그 기사의 `enrich_blocked = PROHIBITED_CONTENT`

차단이 풀린 뒤 다시 번역하려면 `UPDATE articles SET enrich_blocked = NULL WHERE content_hash = …` 로 표시를 지운다.

## 5. 예방

- **실패를 분류할 때는 응답 글자 밖의 신호를 먼저 본다** — 차단 사유 (`prompt_feedback`) · 종료 사유 (`finish_reason`) 가 있으면 글자 모양보다 앞선다
- **재시도 장치에는 포기 조건을 짝으로 둔다** — 「다시 부르면 나아질 실패인가」 를 가르지 않으면 늘 실패하는 입력이 호출을 계속 쓴다
- **로그의 사유 이름을 원인으로 읽지 않는다** — 「JSON 없음」 은 증상의 이름이다
