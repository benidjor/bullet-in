# 잣대가 틀렸던 자리 셋 — 워크트리 테스트 · Airflow 메모리 · pkill (2026-09-04)

안건 2ε 구현 첫 회차 (PR #461) 에서 잰 값 셋이 실물과 달랐다.
셋 다 데이터가 아니라 재는 도구가 틀렸고, 셋 다 「값이 이상하다」 가 아니라 「값이 그럴듯하다」 로 나와서 한 번 더 봐야 잡혔다.

## 1. 워크트리에서 돌린 전체 테스트가 「4 failed」 를 냈다

### 1.1. 증상

1. 워크트리 브랜치의 마지막 태스크를 끝내고 전체 테스트를 돌렸다.
   명령은 `uv run --project <워크트리> --extra dev pytest -q` 였다.
2. `4 failed, 1666 passed` 가 나왔다.
   떨어진 넷은 전부 `tests/integration/test_pipeline_runs_insert.py` 였다.
3. 같은 파일만 워크트리 안에서 다시 돌리니 `5 passed` 였다.

### 1.2. 원인

`--project` 는 가상환경만 고정한다.
pytest 가 어느 테스트 파일을 모을지는 셸의 현재 디렉터리가 정한다.

직전에 규약 문서를 읽느라 `cd <저장소>` 를 쳤고 셸이 메인 체크아웃에 서 있었다.
그래서 메인의 옛 테스트 파일이 워크트리 venv 에 편집 설치된 새 코드를 import 했다.
옛 통합 테스트 넷은 회차 행 INSERT 에 `dur` 파라미터를 넘기는데 새 SQL 상수엔 그 이름이 없다.

신호는 수집된 테스트 수였다.
`4 + 1666 + 1 = 1671` 은 메인 기준선 (1,670 통과 + 1 skip) 과 같은 수이고 워크트리는 1,689 를 모아야 했다.

### 1.3. 처방

- 전체 테스트는 `cd <워크트리> && uv run --project . --extra dev pytest -q` 로 돌린다.
- 결과를 읽기 전에 수집 수를 본다.
  기준선과 같은 수가 나오면 잘못된 트리를 잰 것이다.
- 세션 공통 규율 (메모리 `standing-session-rules` §3) 에 이 줄을 더했다.

앞서 반대 방향의 사고가 있었다.
셸 작업 디렉터리가 되돌아가 옛 브랜치 코드를 읽은 일 (CLAUDE.md 「병렬 세션 · 워크트리」) 이다.
그 처방이 `--project` 고정이었는데, 고정되는 것이 venv 뿐이라는 것을 이번에 알았다.

## 2. Airflow 상주 메모리가 4.7 GB 로 나왔다

### 2.1. 증상

1. 계획서 태스크 0 대로 VM 의 일회 venv 에 Airflow 3.3.1 을 깔고 스케줄러 · dag-processor · api-server 를 60초 띄웠다.
2. 계획서의 명령 (`ps -o rss= … | awk '{s+=$1}'`) 이 `TOTAL_MB 4755` 를 냈다.
   문턱은 1,500 MB 였다.
3. 명령줄에 실험 디렉터리 이름이 든 프로세스만 거르니 `304 MB` 였다.
   둘 다 틀렸다.

### 2.2. 원인

스케줄러가 기본 `parallelism=32` 로 워커 32개를 fork 한다.
fork 된 자식은 부모와 페이지를 공유하는데 RSS 는 공유 페이지를 프로세스마다 다시 센다.
131 MB 짜리 워커 32개가 전부 같은 페이지를 가리키고 있었다.

명령줄로 거른 값은 반대로 워커를 놓쳤다.
워커는 제목이 `airflow worker` 로 바뀌어 실험 디렉터리 이름이 명령줄에 없다.

### 2.3. 처방

`/proc/<pid>/smaps_rollup` 의 `Pss` 를 세 부모의 자손 전체에 합산한다.
PSS 는 공유 페이지를 공유하는 프로세스 수로 나눠 세므로 이런 트리에서 유일하게 맞는 잣대다.

```bash
# 세 부모 (S · D · A) 의 자손을 pgrep -P 로 모은 뒤
for p in $all; do
  pss=$((pss + $(awk '/^Pss:/{print $2}' /proc/$p/smaps_rollup)))
done
echo "PSS_MB=$((pss/1024))"
```

| 설정 | 프로세스 | PSS | RSS 합 |
| --- | --- | --- | --- |
| 기본 (`parallelism=32`) | 36 | 643 MB | 4,746 MB |
| 스펙 §4.1 (`parallelism=2`) | 6 | 509 MB | 904 MB |

스펙 §1.3 에 적을 값은 509 MB 다.
SQLite 기준이라 Postgres 컨테이너 몫은 따로 더한다.

## 3. `pkill -f` 가 ssh 세션을 끊었다

### 3.1. 증상

실험 뒤 정리 명령 `ssh … 'pkill -f af-probe/venv; rm -rf /tmp/af-probe'` 가 종료 코드 255 로 끝났다.
`rm` 은 돌지 않았다.

### 3.2. 원인

`pkill -f` 는 전체 명령줄에서 패턴을 찾는다.
그 패턴은 ssh 가 원격에서 띄운 셸의 명령줄에도 그대로 들어 있다.
셸이 자기 자신을 죽였다.

### 3.3. 처방

```bash
for p in $(pgrep -f "af-probe/venv/bin"); do [ "$p" != "$$" ] && kill $p; done
```

패턴을 실행 파일 경로처럼 셸 명령줄엔 없을 문자열로 좁히고, 그래도 `$$` 를 뺀다.

## 4. 공통점

셋 다 결과가 「말이 되는 숫자」 였다.
`4 failed` 는 실패한 테스트 이름까지 있었고, 4.7 GB 는 워커 32개면 그럴 법했고, 255 는 ssh 가 흔히 내는 코드다.
잣대를 의심한 계기는 셋 다 「두 번째 잣대가 다른 값을 냈다」 였다.
값 하나가 결정을 가르는 자리 (문턱 · 통과 여부) 에서는 잣대를 둘 대 본다.
