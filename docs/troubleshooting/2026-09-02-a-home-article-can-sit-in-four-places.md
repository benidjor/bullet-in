# 홈에서 기사가 놓이는 자리는 넷인데 둘만 세고 결론을 냈다 (2026-09-02)

홈 시간순 개편 (PR #421) 을 검증하면서 **「홈 어디에도 없는 기사 9건」** 이라고 판정했다.
실제로는 0건이었다.

수치는 다 실측이었고 **세는 범위가 좁았다.**
같은 회차에서 같은 실수를 두 번 했다.

앞선 사례 `2026-08-28-we-measured-one-screen-and-talked-about-another.md` 는
「마크업에 있는 것과 화면에 그려지는 것이 다르다」 는 층을 다룬다.
이 문서는 그다음 층이다 — **화면 안에서도 기사가 놓일 수 있는 자리가 여럿이다.**

## 1. 자리가 넷이다

홈 한 장에서 기사가 실릴 수 있는 곳은 이렇다.

| 자리 | 무엇 | 어디서 만드나 |
| --- | --- | --- |
| 날짜 묶음의 카드 | 그날의 대표 기사 | `render_index` 의 블록 |
| 카드 안의 줄 | 같은 소식을 전한 나머지 기사 | 블록의 `same` |
| 가십 구역 | 공신력 최하 등급 전부 | `render_index` 의 `gossip` |
| 화면 맨 위 머리기사 | 히어로 한 장 · 주요 소식 네 줄 | `pick_top_stories` |

여기에 **숨김 카드**를 더해야 그날 전체와 맞는다.
단계가 「기타」 인 기사는 카드가 만들어지되 `display:none` 으로 감춰진다.

## 2. 첫 번째 오판 — 앞의 둘만 셌다

계수 도구가 날짜 묶음만 훑고 가십 구역과 머리기사를 안 봤다.

```
2026-09-01     카드 11  줄 7  합 18     그날 전체 27     차이 9
```

그래서 「9건이 어디에도 없다」 는 결론이 나왔다.
실제로는 그 9건이 가십 3 · 머리기사 1 · 숨김 카드 5 로 전부 **홈 한 장 안에** 있었다.

숨김 카드 5 는 화면에 그려지지 않는다.
그래도 「사라진 기사」 와는 다르다 — 필터를 걸면 나오고, 그날 전체를 셀 때 이 자리를 빼면 수가 안 맞는다.
**「화면에 보이는가」 와 「홈 문서에 실려 있는가」 는 다른 질문이고, 둘을 같은 문장에서 쓰면 안 된다.**

**바뀐 잣대** — 「카드 + 줄 + 가십 + 머리기사 + 숨김 카드 = 그날 전체」 로 세니 모든 날짜에서 차이가 0 이었다.

## 3. 두 번째 오판 — 표에서 한 항목을 빠뜨렸다

PR 본문의 비교표를 이렇게 적었다.

| 항목 | 기존 화면 | 새 화면 |
| --- | --- | --- |
| 화면에 보이는 카드 | 83장 | 299장 |
| 버튼을 눌러야 나오는 보도 | 373건 | 0건 |
| 카드 안에 붙은 줄 | 0건 | 115건 |

읽는 사람이 더해 보면 `83 + 373 = 456` 과 `299 + 115 = 414` 로 **42가 안 맞는다.**
문체 점검이 「이 42를 독자가 스스로 설명할 수 없다」 고 짚어서 드러났다.

빠진 것은 **숨김 카드**였고, 30장에서 72장으로 42건 늘어 있었다.
기존에 접혀 있던 「기타」 단계 기사가 새 설계에서 낱개 카드로 만들어지되 여전히 숨겨지기 때문이다.

항목을 다 채우면 양쪽이 정확히 떨어진다.

```
기존 화면: 카드 83 + 숨김 30 + 접힌 보도 373 + 가십 434 + 머리기사 5 = 925
새 화면:   카드 299 + 숨김 72 + 줄 115 + 가십 434 + 머리기사 5 = 925
```

## 4. 다시 세다가 다른 도구의 결함을 찾았다

숫자가 안 맞자 「내 도구가 틀렸을 것」 을 의심해 HTML 파서로 다시 셌다.
**표에 쓴 수치는 전부 맞았고 표가 항목을 빠뜨린 것이었다.**

다만 그 과정에서 **다른** 도구 하나가 실제로 틀린 값을 내고 있었다는 것을 발견했다.

```python
# 이렇게 자르면 .* 가 파일 끝까지 먹는다
latest = re.search(r'<div class="latest[^"]*">(.*)', home, re.S).group(1)
```

`latest` 구역만 자르려던 것인데 가십 구역과 푸터까지 들어와,
그 안의 카드를 세면 실제보다 크게 나온다 (옛 화면에서 83 이어야 할 것이 552 로 나왔다).

**정규식으로는 중첩된 `<div>` 를 닫을 수 없다.**
`BeautifulSoup` 로 바꾸니 양쪽 화면 모두 합계가 서빙 행 수와 정확히 일치했다.

이 값은 다행히 PR 에 쓰지 않았지만, 썼다면 검산이 어긋난 채 게시됐을 것이다.

## 5. 무엇을 남기나

- **화면을 셀 때는 「이 화면에서 기사가 놓일 수 있는 자리를 다 적었는가」 를 먼저 묻는다.**
   → 홈은 넷 + 숨김 카드이고, 둘만 세면 나머지가 「사라진 기사」 로 보고된다
- **비교표는 독자가 더해 볼 수 있게 만든다.**
   → 항목을 빠뜨리면 읽는 사람이 그 차이를 설명할 수 없고, 그것이 곧 표의 결함이다
- **합계가 알려진 값과 떨어지는지 검산한다.**
   → 여기서는 서빙 행 수 (925) 가 그 값이었고, 두 화면 모두 정확히 떨어지는 것이 확인 근거가 됐다
- **HTML 을 셀 때 중첩 태그를 정규식으로 자르지 않는다.**
   → 파서를 쓰면 이 종류의 오차가 아예 안 생긴다
