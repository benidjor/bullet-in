# 사전에 한 줄 더했더니 그 뒤에 오는 검사의 입력이 바뀌었다 (2026-08-29)

표기 교정 사전 (`config/glossary.yaml`) 을 늘리는 일을 「화면 문자열만 바꾸는 것」 으로 보고 시작했다.
아니었다.
**후처리 치환은 그 뒤에 오는 검사의 입력**이고, 사전을 늘리면 게이트가 보는 텍스트 자체가 달라진다.

안건 υ (표기 흔들림) 회차에서 이 자리를 세 번 밟았다.
셋이 같은 뿌리인데 드러난 방식이 달라 함께 적는다.

## 1. 순서가 먼저다 — 치환이 게이트보다 앞에 있다

`enrich.finalize_translation` 안의 순서다.

```
enrich.py:429   v = apply_glossary(v, glossary)          ← 번역 4필드를 고친다
enrich.py:448   club_suspects = detect_club_injection(v, src_text, club_map)
```

`detect_club_injection` 은 「번역문에 나온 구단명이 원문에 근거가 있는가」 를 본다.
근거 경로가 둘이다.

- **ko 경로** — 원문에 같은 별칭 목록의 다른 한글 표기가 있는가 (`_ko_present(src, k2)`).
- **en 경로** — 원문에 영문 별칭이 단어 경계로 있는가.

**사전은 번역문만 통일하고 원문은 그대로 둔다.**
그래서 한국어 원문인 fmkorea 기사에서 ko 경로의 근거가 끊긴다.

## 2. 실측 — 사전만 늘리면 오탐이 는다

구단 표기 11종을 사전에 넣고 서빙 전량에 대 봤다.

```
사전만 더함                                    구단 주입 의심 27 → 45
club_map 에 원문 쪽 표기 11키를 함께 등재       → 29
```

늘어난 18건 대부분이 fmkorea 였다.
원문이 「브렌트포드」 로 적은 기사에서 번역문만 「브렌트퍼드」 로 바뀌자 근거가 사라졌다.

`config/club_map.yaml` 에는 이럴 때 쓰는 **규칙 ④** 가 이미 있다.
같은 구단의 한글 표기 여럿을 각각 등재하고 **별칭 목록을 똑같이 맞춰 준다**.
그러면 두 표기가 한 묶음이 되어 원문 쪽 표기도 근거로 인정된다.

**「에버턴 · 에버튼」 이 그 형태로 이미 들어 있었다.**
규칙도 선례도 있었는데 새 항목에 적용하지 않은 것이 이 사고의 전부다.

## 3. 오탐이 공짜가 아니다

구단 의심이 잡히면 `title_ko` 가 `None` 이 되어 재번역 큐에 들어간다 (첫 진입 기준).

- 그 기사는 **한 회차 동안 제목 없이 선다.**
- 다음 회차에 제미나이 호출이 한 번 더 든다 (안건 ξ 요금 축과 같은 자리).
- 재시도 경로에서는 제목을 채택하고 경고만 남기므로 **한 회차로 끝난다.**

실측 1건 (`4ef0373f`) 의 모습이다.

```
원문에 '베식타시': 1 · '베식타스': 0 · 'Besiktas': 0
번역:  … 레안드로 트로사르를 베식타스로 떠나보냈다 …
결과:  title_ko = None
```

### 3.1. 이 구멍이 그때 발화한 이유는 옆 작업이었다

처음에 「배포 뒤 첫 회차가 내 부작용을 잡았다」 로 적었다.
맞지만 절반이다.
**그 기사가 하필 그 회차에 다시 번역된 이유는 내 축이 아니었다.**

같은 날 병렬 세션이 주소 110행을 손으로 고쳤다 (`UPDATE ... SET url`).
그 뒤 회차가 재수집하면서 upsert 가 이렇게 움직였다.

```
content_hash=VALUES(content_hash)                                    ← 해시가 갈린다
title_ko=IF(articles.content_hash=VALUES(content_hash), …, NULL)     ← 번역이 지워진다
```

- 확인한 것 — 그 기사의 `url` 이 `nytimes.com/athletic/…` 이고 (재정규화 대상 도메인),
옛 해시 `8efa3723` 은 지금 없으며 `fetched_at` 이 그 회차다.
- **기전은 병렬 세션이 짚었고 위 세 값은 내가 확인했다.**

그래서 사슬이 넷이다.

1. 옆 작업이 주소를 고친다 (해시 이관 없이).
2. 회차가 재수집하며 해시를 갈고 **번역 4필드를 NULL 로 지운다.**
3. 그 기사가 다시 번역되며 **새 사전이 걸린다.**
4. `club_map` 짝이 없어 게이트가 오탐한다.

**구멍은 원래 잠재였다.** 새 베식타스 기사가 들어와야 드러났을 자리다.
**옆 작업이 그것을 앞당겨 발화시켰다.**

이것이 「배포 뒤 첫 회차를 자기 축으로 읽어라」 의 이유를 하나 더 준다
— 내 변경이 안 건드린 기사도 남의 작업 때문에 내 코드 경로를 지날 수 있다.

## 4. 계약 테스트가 자기 사각지대에 걸렸다

이 회차에서 계약 테스트를 한 번 좁혀 썼다.

```python
for wrong in set(glossary) & set(clubs):
    ...  # 정규형이 등재됐고 별칭 목록이 같은가
```

그리고 「계약을 고정했다」 고 적었다.
**그 검사가 못 보는 자리가 바로 다음 버그였다.**

- 이 루프는 **이미 `club_map` 에 있는 키만** 돈다.
- 「구단으로 수렴하는데 원문 쪽 표기가 `club_map` 에 아예 없는」 항목은 교집합에 안 들어 **검사 대상이 아니다.**
- `베식타시` 가 정확히 그 갈래였다.

발견한 것은 테스트가 아니라 **배포 뒤 첫 회차의 저널**이었다.

넓힌 방향은 이렇다.

```python
for wrong, right in glossary.items():
    if right in clubs:
        assert wrong in clubs      # 원문 쪽 표기도 등재돼 있는가
        assert clubs[wrong] == clubs[right]
```

전량 대조로 같은 구멍이 2건 나왔다 (`베식타시` · `베식타슈`).
**둘 중 하나는 이 회차 전부터 있던 것**이라, 새 사전 항목만 훑었으면 못 찾았다.

## 5. 사전의 소비자는 셋이다 — 셋 다 대 봐야 한다

`docs/troubleshooting/2026-07-15-credibility-registry-curation-traps.md` 의 함정 ④ 는
`credibility.yaml` 별칭이 두 조회에 걸린다고 적었다.
같은 질문을 glossary 에 던지면 소비자가 셋이다.

| 소비자 | 무엇을 바꾸나 | 확인 결과 |
| --- | --- | --- |
| `enrich.apply_glossary` | 기사 4필드 (화면에 나가는 글) | 본체 · 전량 측정 대상 |
| `roster.normalize_pairs` | 추출된 `ko` (후보 등재 이름) | 라벨만 · **귀속은 안 바뀐다** |
| `credibility.resolve_tier` | — | **안 탄다** (`credibility.py` 에 glossary 참조 0) |

- **귀속이 안 바뀌는 이유** — `record_article_players` 의 매칭은 접힌 라틴 `full_name` 과 성이다.
`ko` 는 매칭에 안 쓰이고 `insert_candidate(ko_candidate=...)` 로만 간다.
- **역할 판정도 안 깨진다** — `decide_role` 은 한글 키로도 맞추는데 `_name_keys` 가
**모델 표기 (사전 적용 뒤) 와 명단 표기를 둘 다** 키에 넣는다.
게다가 기사 본문과 `pair["ko"]` 는 같은 사전 객체로 함께 정규화되므로 구조적으로 어긋날 수 없다.
- **등급 경로를 안 타는 것이 핵심이다.**
함정 ④ 의 위험 (「짧은 별칭 × 강한 등급」) 은 `credibility.yaml` 을 건드릴 때 생긴다.
**사전을 늘리는 것과 별칭을 늘리는 것은 위험이 다르다.**

## 6. 규율

- **사전에 구단 표기를 더하면 `club_map` 짝을 같은 PR 에서 함께 넣는다** (규칙 ④ · 별칭 목록 동일).
- **사전을 늘린 뒤 게이트 계수를 함께 잰다.**
전후 비교는 총량이 아니라 **어느 기사에서 늘고 줄었는지**로 본다.
- **늘어난 의심을 전부 오탐으로 읽지 않는다.**
이번에 남은 둘은 게이트가 원래 못 보던 진짜 주입이었다 (afcstuff 트윗이 원문에 없는 뇌르고르의 소속 구단을 지어냈다).
- **배포 뒤 첫 회차의 저널을 자기 축으로 직접 읽는다.**
이 건은 병렬 세션이 알려준 「회차 성공 · 오류 0」 안에 들어 있었다.
`success_rate` 1.0 이 내 축의 WARNING 까지 말해 주지는 않는다.
- **새 검사를 넣을 때는 무엇을 빼서 실패시켜 봤는지 남긴다.**
「없음」 을 확인하는 검사는 안 돌아도 「없음」 을 낸다.
