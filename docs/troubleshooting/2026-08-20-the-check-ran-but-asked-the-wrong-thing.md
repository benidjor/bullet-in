# 검사는 돌았는데 묻는 대상이 달랐다 — 기준선 · 인자 · 입력 출처 (2026-08-20)

한 회차에서 세 번 밟았다.
셋 다 **검사가 정상 종료했고 답도 정확했다.**
틀린 것은 검사가 아니라 **무엇에 대고 물었는가** 였다.

기존 문서 `2026-08-15-verification-that-silently-passes.md` 는 「검사가 안 돌아도 「없음」 이 나온다」 를 다룬다.
**이번 셋은 성격이 다르다** — 검사는 돌았고 답도 맞는데 질문이 달랐다.
그래서 증상도 다르다.
앞쪽은 조용히 통과하고 이번 셋은 **그럴듯한 값**을 낸다.

## 1. 사례 1 — 유실 점검을 내 브랜치에 걸었다

### 1.1. 증상

세션 마무리 점검이 0 을 냈고 「푸시 유실 없음」 으로 보고했다.

```bash
git log --oneline origin/worktree-outlet-origin..HEAD | wc -l
# → 0
```

실제로는 정정 커밋 하나가 `main` 에 없었다.
PR 이 그 커밋을 만들기 **세 시간 반 전에** 머지돼 있었다 (머지 01:44 UTC · 커밋 05:18 UTC).

### 1.2. 원인

그 검사가 답하는 질문은 **「내가 푸시했는가」** 다.
알아야 하는 질문은 **「`main` 에 들어갔는가」** 였다.

푸시는 다 했으므로 0 이 맞는 답이다.
**맞는 검사를 엉뚱한 기준선에 걸었다.**

### 1.3. 확인 방법 — 파일 내용으로 판정한다

```bash
git fetch origin
git show origin/main:<파일> | grep -c "<내가 넣은 문구>"   # 0 이면 유실
```

### 1.4. 곁들여 — squash 에서는 커밋 목록이 양방향으로 못 쓰인다

같은 브랜치에서 두 검사를 나란히 돌리면 서로 반대를 말한다.

| 검사 | 머지 직후 값 | 뜻 |
| --- | --- | --- |
| `git log origin/main..HEAD` | 1 | squash 라 커밋이 `main` 의 조상이 아니다 — 유실이 아니다 |
| `git diff origin/main HEAD --stat` | 0 | 내용은 전부 반영됐다 |

유실이 실제로 났을 때는 방향이 정반대였다 (목록 0 · 내용 누락).
**커밋 목록은 거짓 양성도 거짓 음성도 낸다.**

## 2. 사례 2 — 렌더를 흉내 내며 인자를 빠뜨렸다

### 2.1. 증상

설정을 바꾸면 화면이 어떻게 달라지는지 미리 재려고 `outlet_display` 를 직접 불렀다.
사이드바 언론사 항목이 **내 계산 49종 · 실제 렌더 48종**으로 갈렸다.

원인을 「회차가 기사를 들여와 항목이 늘었다」 로 붙였는데 그것도 틀렸다.

### 2.2. 원인

```python
outlet_display(row, sources, outlet_dir=d)                    # 내가 부른 것 — 49종
outlet_display(row, sources, directory=jd, outlet_dir=d)      # write_site 가 부르는 것 — 48종
```

`directory` 를 안 넘기면 X 소스 행이 **인용 기자 소속으로 접히는 경로를 못 타고** 소스 폴백 (`display_name`) 으로 떨어진다.
그래서 `David Ornstein (X)` 이라는 없던 항목이 하나 생겼다.

### 2.3. 왜 오래 안 드러났나

**전후 양쪽을 같은 (틀린) 호출로 쟀기 때문이다.**
그 항목이 양쪽에 다 있어 상쇄됐고 **델타 예고는 전부 맞았다** (16종 1대1 교체 · `Marca` 11 · `afcstuff` 190 → 189 이 회차 실측과 일치).

**「델타는 맞고 절대값은 틀린」 상태는 델타만 보는 한 영원히 안 드러난다.**

### 2.4. 처방

**함수를 손으로 불러 렌더를 흉내 낼 때는 인자 목록을 호출부와 1:1 로 맞춘다.**
`outlet_display` 는 `directory` (기자 소속 접기) 와 `outlet_dir` (표기 · 조직 계정 접기) 를 둘 다 받는다.
하나만 빠져도 없던 표시명이 생긴다.
호출부는 `run.py` 의 `write_site(...)` 다.

## 3. 사례 3 — 서빙 필터의 명단을 설정에서 읽었다

### 3.1. 증상

같은 재현에서 서빙 필터를 돌렸더니 **숨김 26건 · 항목 46종**이 나왔고 세 매체가 필터에서 빠지는 것처럼 보였다.
운영 로그의 실제 값은 **숨김 20건**이었다.

### 3.2. 원인

`player_names` 를 `config/sources.yaml` 에서 읽었다.
실제로는 **운영 DB 명단**에서 온다.

```python
adapters = build_adapters(cfg, fmkorea_player_names=pstore.confirmed_ko_names())   # run.py
```

설정에는 그 목록이 없어 이름 매칭이 통째로 빠졌고 **조용히 과잉 필터**가 됐다.
DB 명단으로 바꾸니 숨김 20 · 통과 784행으로 운영 로그와 정확히 붙었다.

### 3.3. 처방

**파이프라인을 재현할 때는 입력의 출처를 코드에서 확인한다.**
설정 파일에 같은 이름의 키가 있어도 실행 경로가 그것을 안 쓸 수 있다.

## 4. 세 사례의 공통 모양

**검사가 안 돈 것도 아니고 틀린 것도 아니다.**
셋 다 정상 종료했고 자기 질문에는 정확히 답했다.

| 사례 | 물어야 했던 것 | 실제로 물은 것 |
| --- | --- | --- |
| 기준선 | `main` 에 들어갔는가 | 내가 푸시했는가 |
| 인자 | 렌더가 무엇을 보여 주는가 | 인자 하나를 뺀 함수가 무엇을 내는가 |
| 입력 출처 | 운영이 무엇을 거르는가 | 설정만 준 필터가 무엇을 거르는가 |

**그래서 결과가 「없음」 이 아니라 「그럴듯한 값」 으로 나온다.**
대놓고 틀린 값이면 측정 코드를 먼저 보는데, 자릿수가 맞으면 데이터를 의심하게 된다 (`2026-08-14-suspect-the-yardstick-not-the-data.md` 와 같은 뿌리다).

### 4.1. 측정이 틀어지는 축은 셋이다

같은 날 다른 두 문서가 나머지 두 축을 다룬다.
**셋을 나란히 두면 틀린 값을 만났을 때 어디부터 볼지가 갈린다.**

| 무엇이 틀렸나 | 물음 | 정본 |
| --- | --- | --- |
| **층** | 어느 계층에서 잰 값인가 | `2026-08-20-rendered-values-are-not-raw-data.md` |
| **빈도** | 얼마나 자주 재고 있었나 | `2026-08-20-gap-samples-contain-our-own-downtime.md` |
| **대상** | 무엇을 대고 물었나 | **이 문서** |

**층이 맞아도 관측이 성기면 틀리고, 층과 빈도가 맞아도 대상이 어긋나면 틀린다.**
세 축은 서로를 못 덮는다.

## 5. 어떻게 알아채는가

- **값을 남에게 보낼 때 잣대를 함께 적는다.**
이 회차에 병렬 세션과 서로 여섯 번 값을 바로잡았고 **넷은 반박이 아니라 한쪽이 자기 값을 먼저 의심해서** 열렸다.
숫자만 보내면 받는 쪽이 자기 잣대의 값으로 옮겨 적고 그 위에 원인까지 붙인다 — 실제로 그렇게 오류가 서로에게 퍼질 뻔했다.
- **절대값을 한 번은 다른 방법으로 낸다.**
델타만 대조하면 상쇄되는 오류를 못 본다.
- **양방향으로 센다.**
「항목에는 있는데 카드에 없는 것」 과 「카드에는 있는데 항목이 없는 것」 을 둘 다 본다 — 한쪽에서 출발하는 검사는 반대쪽 결손을 구조적으로 못 본다.

**같은 회차에 병렬 세션도 같은 모양을 밟았다** (`git log` 에 리비전을 둘 넘겨 엉뚱한 커밋 본문을 자신 있게 받았다).
경위는 세션 메모리 `verification-that-silently-passes` 에 있다.
