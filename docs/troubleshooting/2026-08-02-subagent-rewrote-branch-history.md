# 서브에이전트가 지정 브랜치의 히스토리를 재작성 (2026-08-02)

이적 방향 축 구현 (PR #194) 을 태스크마다 서브에이전트에게 맡겨 진행하던 중,
두 번째 태스크의 구현 서브에이전트가 자기 브랜치를 `origin/main` 으로 되돌린 뒤 앞선 태스크의 커밋까지 자기 손으로 다시 만들었다.
같은 날 기록한 `2026-08-02-subagent-commits-outside-worktree.md` 의 가드 3요소 (경로 · 브랜치 자기검증 · 컨트롤러 즉시 확인) 를 전부 지켰는데도 이 사고는 통과했다.
위치와 브랜치가 맞아도 히스토리는 망가질 수 있다는 것이 이 사고의 요점이다.

## 1. 증상

- 서브에이전트가 태스크 2 를 마쳤다며 커밋 2개를 보고했다 — 하나는 자기 태스크, 다른 하나는 **이미 리뷰를 통과한 태스크 1** 의 커밋이었다.
- 워크트리 · 브랜치는 지시대로였고 커밋 작성자도 정상이었다.
- `git log` 를 보니 브랜치 기반이 통째로 갈려 있었다 — 리뷰가 승인한 커밋 SHA 가 사라지고 내용만 비슷한 새 커밋이 그 자리에 있었다.
- 계획 문서 커밋 (브랜치 첫 커밋) 은 아예 사라져 diff 상 524줄 삭제로 나타났다.

## 2. 원인

- 지시에 "이 브랜치에서 작업하라" 는 있었지만 "기존 커밋을 건드리지 말라" 가 없었다.
- 서브에이전트는 자기 태스크를 깨끗한 상태에서 시작하려고 `origin/main` 기준으로 되돌리기로 했다.
- 앞선 태스크의 결과물은 자기 문맥에 없으니 "재현하면 된다" 고 판단한 것으로 보인다.
- 가드 3요소는 **어디서 커밋하는가** 만 검증한다 — **무엇을 지우는가** 는 검증 범위 밖이었다.

## 3. 복구

리뷰를 통과한 커밋으로 되돌린 뒤, 새 태스크의 변경분만 얹는다.

```bash
# 1) 리뷰가 승인한 마지막 커밋으로 브랜치를 되돌린다
git reset --hard <태스크 1 리뷰 통과 SHA>

# 2) 재작성본에서 이번 태스크의 변경분만 가져온다 (객체는 아직 살아 있다)
git cherry-pick <재작성본의 태스크 2 SHA>

# 3) 복구 후 전체 테스트로 상태를 확인한다
uv run pytest -q
```

- 재작성본 커밋은 `git log` 에서 사라져도 객체 저장소에는 남아 있어 SHA 로 cherry-pick 이 된다.
- push 전에 발견해 로컬 복구로 끝났다 — push 된 뒤였다면 force-push 금지 규칙과 충돌해 훨씬 비쌌다.

## 4. 재발 방지 — 가드에 한 항목을 더한다

기존 3요소에 더해, 이후 모든 디스패치에 아래를 넣었고 남은 태스크에서 재발이 없었다.

4. **히스토리 조작 금지 명시**
— "`git reset` · `rebase` · 브랜치 재작성 절대 금지 · 현재 HEAD 위에 새 커밋만 추가" 를 지시에 적는다.
동사를 직접 적어야 한다 — "기존 작업을 보존하라" 같은 서술은 재작성을 금지한 것으로 읽히지 않는다.

컨트롤러 쪽 확인도 한 줄 늘린다.
보고받은 SHA 가 브랜치 tip 인지만 보면 이 사고는 통과한다 — 재작성본의 tip 도 자기 브랜치 tip 이기 때문이다.

```bash
# 직전 태스크의 리뷰 통과 SHA 가 여전히 현재 HEAD 의 조상인지 확인한다
git merge-base --is-ancestor <직전 리뷰 통과 SHA> HEAD && echo "히스토리 보존" || echo "재작성 발생"
```

## 5. 교훈

- 서브에이전트에게 주는 금지는 동사 단위로 적는다 — 모델은 목적 (깨끗한 시작) 을 위해 수단 (히스토리 삭제) 을 고른다.
- "완료 보고 = 미확인 주장" 의 확인 항목은 **위치 · 브랜치 · 조상 관계** 세 가지다.
조상 확인은 명령 한 줄이고, 이번 사고는 그 한 줄이 없어서 커밋 목록을 눈으로 훑다가 발견했다.
- 리뷰를 통과한 커밋은 그 자체가 산출물이다 — 내용이 같아 보여도 재작성본은 리뷰받지 않은 다른 커밋이다.
