# fmkorea 접촉 예산과 검색 도달 범위 (2026-07-30)

fmkorea 본문 백필을 라이브에서 돌리다 세 가지를 잘못 짚었다.
430 의 성격 · 백필이 못 닿는 이유 · 원문 재수집 가능성이다.
세 번 다 표본이 좁은 상태에서 원인을 단정했고, 넓은 데이터가 그때마다 반박했다.

이 문서는 그 반박 과정을 남긴다.
같은 작업을 다시 할 때 어디서 멈춰 무엇을 먼저 재야 하는지가 요지다.

## 1. 430 은 시각 패턴이 아니라 누적 접촉량이다

### 1.1. 하루치로 본 그림 (틀렸다)

7월 30일 정기 회차만 보면 03시와 15시 (KST) 두 회차가 검색 첫 요청부터 430 이었고 나머지 여섯 회차는 18요청을 전부 통과했다.
"매일 같은 시각에 막힌다" 고 결론했다.

### 1.2. 5일치로 본 그림 (맞다)

7월 26일부터 30일까지 정기 회차 36회를 세니 실패는 7회 (약 19%) 였고 **실패 시각이 날마다 달랐다**.

| 날짜 | 430 발생 회차 |
| --- | --- |
| 7/26 | 06시 · 09시 |
| 7/27 | 없음 |
| 7/28 | 21시 |
| 7/29 | 06시 · 09시 |
| 7/30 | 03시 · 15시 |

어제는 03시와 15시가 멀쩡했다.
고정 시각 패턴이 아니라 확률적 실패다.

실패가 인접 회차에 붙는 경향은 있다 (7/26 과 7/29 모두 06시 + 09시 연속).
한 번 걸리면 3~6시간 지속되는 것으로 보이나 7/30 은 두 실패가 떨어져 있어 항상은 아니다.

### 1.3. 확률을 올리는 것은 최근 접촉량이다

같은 날 백필을 돌린 기록이다.

| 시각 (KST) | 실행 | 검색 | 글 fetch | 직전 16분 누적 |
| --- | --- | --- | --- | --- |
| 12:03 | 정기 회차 | 3회 200 | **14회 200** | 0 (3시간 쉼) |
| 16:20 | 백필 `--pages 3` | 9회 200 | 2회 **430** | 0 |
| 16:35 | 백필 `--pages 1` | 3회 200 | **2회 200** | 11 |
| 16:36 | 백필 `--pages 1` | 3회 200 | 7회 **430** | 16 |
| 19:00 | 백필 `--pages 1` | 3회 200 | **7회 200** | 0 (2.5시간 쉼) |

정기 회차는 **한 번에 18요청을 다 통과**시킨다.
백필은 3요청짜리도 막혔다.
차이는 회차당 요청 수가 아니라 **최근 누적 접촉량**이다.
16분에 26요청을 몰아 쓰자 예산이 소진됐고, 2.5시간 쉬자 완전히 복구됐다.

`--force` 로 3시간 가드를 세 번 연속 우회한 것이 직접 원인이었다.
가드는 정확히 이것을 막으려고 있는 장치다.

### 1.4. 원인을 단정했다가 반박당한 기록

`--pages 3` 이 실패하고 `--pages 1` 이 성공한 한 쌍을 보고 "검색 요청 볼륨이 원인" 이라고 단정했다.
1분 뒤 같은 `--pages 1` 실행이 글 7건 전부 430 으로 반박했다.
표본 한 쌍으로 인과를 정하면 이렇게 된다.

### 1.5. 그래서 이렇게 한다

- **직전 회차 로그를 먼저 읽는다** — 접촉 0회로 현재 상태를 알 수 있다.

```bash
sudo journalctl -u bullet-in --since "21:00" | grep "fmkorea.com/search" | grep -c "200 OK"
```

직전 회차 검색이 200 이면 예산이 정상이고, 430 이면 다음 회차를 기다린다.
"3시간 기다린다" 가 아니라 "직전 회차가 성공했는지 보고 판단한다" 가 맞다.

- **실패 비용을 `--limit` 으로 묶는다** — 첫 확인은 대상 1건으로 한다.
- **실패해도 DB 는 안전하다** — 멱등 설계라 fetch 실패 행은 건드리지 않는다.
29건 대상 실행에서 7건 전부 430 이었으나 DB 무변경으로 확인됐다.

## 2. 백필이 못 닿는 이유는 도달 범위이고, 기사 날짜와 무관하다

### 2.1. 게시글 주소가 저장되지 않는다

본문을 받으려면 fmkorea 게시글 주소가 필요한데 DB 에 없다 (저장된 `url` 은 언론사 원문 주소다).
그래서 저장된 제목으로 검색해 같은 제목의 글을 찾는다.
검색은 키워드별 최근 20개만 돌려주므로 그보다 오래 전에 올라간 글은 주소를 알 수 없다.

**"접근 금지" 가 아니라 "주소 미상" 이다.**
게시글은 지금도 공개 상태로 존재한다.

### 2.2. 기사 날짜로 추정하면 틀린다

`--pages 1` 로 29건을 조회했을 때 주소를 찾은 것은 7건이었다.
그런데 07-28 텔레그래프 기사는 못 찾고 07-24 BeSoccer 기사는 찾았다.

`published_at` 은 **기사 발행일**이고 검색 결과 순서는 **fmkorea 게시 시각**이다.
게시자가 며칠 전 기사를 나중에 퍼오면 순서가 뒤집힌다.
실제 기준은 fmkorea 글 번호이고, 찾은 7건은 `10122685477` ~ `10143225983` 구간에 있었다.

### 2.3. 수집용 고정 키워드가 진짜 제약이었다

못 찾은 22건을 "검색 도달 범위 밖" 으로 판정했는데, 이것도 정확하지 않았다.
백필은 수집용 고정 키워드 세 개 (`아스날` · `"de roche"` · `온스테인`) 로만 검색하고 있었다.
제목에서 뽑은 검색어로는 바로 나온다 — `에미레이츠` · `노팅엄` · `타임즈 기마랑이스` · `비사커 첼시` 로 각각 대상 글이 검색됐다.

백필은 찾을 제목을 이미 알고 있으므로 수집용 키워드를 재사용할 이유가 없었다.
`--by-title` 경로를 추가했다 (PR #162).

**검색어 도출 규칙도 접촉 없이 검증할 수 있었다.**
사람이 브라우저로 성공시킨 검색어 4건이 곧 실측이므로, 도출 규칙이 그 검색어를 만들어내는지 대조하면 된다.
초기 규칙 (최장 토큰) 은 2/4 만 재현했다 — 게시자가 띄어쓰기를 붙여 써서 (`어떻게아스날을` · `우스만디오망데영입`) 최장 토큰이 검색되지 않는 덩어리를 골랐다.
첫 토큰 계열 후보를 추가해 4/4 가 됐다.

## 3. 언론사 원문 재수집은 실제로 0/22 다

남은 22건의 원문 주소를 파이프라인과 같은 경로 (`httpx` + `extract_article_body`) 로 재보니 본문을 받은 것이 하나도 없었다.
스펙의 "26건 중 1건만 성공" 을 다른 표본으로 재현한 것이다.

| 사유 | 건수 | 매체 |
| --- | --- | --- |
| 403 차단 | 7 | The Telegraph 5 · 아스 · 하늘운동 |
| 406 차단 | 9 | BeSoccer 전량 |
| 200 이지만 본문 0자 | 5 | The Times 2 (페이월) · Daily Mail · A BOLA · barcabuzz |

BeSoccer 는 페이월이 없는 사이트인데도 406 으로 전량 차단이다.
"페이월이 없으니 받을 수 있다" 는 추정은 통하지 않는다.

### 3.1. 저장된 원문 주소가 기사가 아닌 경우가 있다

`200 이지만 본문 0자` 5건 중 둘은 주소 자체가 잘못됐다.

- Daily Mail 행 — `dailymail.com/profile-201/tom-collomosse.html` (기자 프로필 페이지)
- A BOLA 행 — `https://t.co/Iv790raKn3` (t.co 단축 링크)

수집기가 게시글 본문의 **첫 URL** 을 원문으로 채택하는데, 게시자가 기사 대신 다른 주소를 붙이면 그것이 저장된다.
독자에게 보여 주는 '원문 보기' 링크도 엉뚱한 곳을 가리킨다.
`content_hash` 가 `canonical_url` 기반이라 중복 판정에 영향이 있을 수 있다 (미확인).

## 4. HTTP 200 이 온전한 본문을 보장하지 않는다

같은 게시글의 본문 길이가 두 실행에서 달랐다.

```
16:35 드라이런 → 923자
19:00 실행     → 2019자   (같은 글 10143225983 · 둘 다 HTTP 200)
```

앞 실행이 부분 렌더나 인터스티셜을 받았을 가능성이 있으나 원인은 확인하지 않았다.
길이 기준 게이트를 도입할 때 이 변동을 감안해야 한다.
