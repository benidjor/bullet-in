# 백업을 잴 잣대를 대상이 아닌 데서 뽑을 뻔했다 (2026-09-01)

백업 · 복구 경로를 만들면서 (#412) 무엇을 기준으로 삼을지를 세 번 엉뚱한 데서 가져올 뻔했다.
셋 중 둘은 코드가 그대로 돌면서 조용히 틀렸을 자리이고, 하나는 백업 유닛이 매일 죽어 시끄럽게 틀렸을 자리다.
시끄러운 쪽도 안전한 것은 아니다.
경보를 보고 손대기 전까지는 「백업이 있다」 고 믿게 된다.

**공통 뿌리는 하나다.**
재려는 대상이 아닌 다른 곳에서 기준값을 가져왔다.
하나는 다른 시점의 DB 에서, 하나는 실물 대신 짐작에서, 하나는 담긴 것 대신 담은 그릇에서 가져왔다.

## 1. 세 번의 실수를 한 표로

| 재려던 것 | 잘못 잡은 잣대 | 바로잡은 잣대 | 그대로 뒀으면 |
| --- | --- | --- | --- |
| 백업에 담긴 행 수 | 지금 운영 DB 에 다시 질의 | 덤프 파일 안의 INSERT 를 셈 | 회차가 끼는 날마다 멀쩡한 백업이 실패로 찍힘 |
| mongodump 의 출력 형식 | 짐작한 문자열 | VM 에서 받아 적은 실제 출력 | 백업 유닛이 매일 실패 |
| 데이터 부피 | 도커 볼륨 크기 | 논리 덤프 크기 | 실제의 185배로 보고 설계 판단이 통째로 뒤틀림 |

## 2. 검증 기준값을 대상과 다른 시점에서 뽑았다

백업마다 `manifest.json` 을 함께 올린다.
복구가 제대로 됐는지는 되살린 DB 를 이 매니페스트와 대조해서 판정한다.
그러니 매니페스트의 행 수가 이 검증의 유일한 기준이다.

**처음 쓴 코드는 그 행 수를 운영 DB 에 다시 물어서 채웠다.**

```python
dump_mariadb(sql)          # 덤프를 뜬다
dump_mongo(archive)
rows, docs = observed_counts()   # 지금 DB 에 다시 묻는다   ← 여기가 문제
```

덤프는 `--single-transaction` 이라 시작 시점의 스냅샷이다.
`observed_counts()` 는 그보다 나중의 DB 를 본다.
수집 회차는 3시간마다 돌고 한 회차가 기사 몇 건을 넣으므로, 덤프를 뜨는 사이에 회차가 끼면 두 값이 갈린다.

**그러면 백업 자체는 멀쩡한데 복구 대조가 실패로 끝난다.**
검증 장치가 스스로 거짓 경보를 내는 구조다.
게다가 이 거짓 경보는 회차가 겹친 날에만 나오므로 재현이 어렵다.

### 바로잡은 방법

기준값을 산출물에서 뽑는다.

- 표별 행 수는 덤프 파일의 `INSERT INTO ...` 를 센다
   → 그래서 `mariadb-dump` 에 `--skip-extended-insert` 를 준다 (행마다 INSERT 가 한 줄씩 나온다)
- `raw_items` 건수는 mongodump 이 stderr 에 남기는 값을 읽는다

행마다 한 줄씩 쓰면 파일이 커지는데, 압축 뒤 차이는 0.2% 에 그쳤다 (2,287,679 → 2,291,503 바이트).

**규칙**: 검증 기준이 되는 값은 검증 대상과 같은 순간 · 같은 출처에서 뽑는다.

## 3. 출력 형식을 실물 대신 짐작에서 뽑았다

위 고침 때문에 mongodump 의 stderr 를 파싱하게 됐는데, 그 정규식을 짐작으로 썼다.

```python
re.search(rf"done dumping {MONGO_DB}\.{MONGO_COLLECTION} \((\d+) document", stderr)
```

VM 에서 실제로 돌려 보니 이랬다.

```
2026-08-31T20:29:52.226+0000	done dumping `bulletin.raw_items` (1634 documents)
```

**이름이 백틱에 싸여 있다.**
짐작으로 쓴 정규식은 아무것도 못 읽고, 못 읽으면 `raise SystemExit` 으로 끝나는 자리라 백업 유닛이 매일 실패했을 것이다.

실패가 Discord 로 오니 언젠가는 알았겠지만, 그때까지 「백업이 있다」 고 믿는 며칠이 생긴다.
**확인 비용은 `ssh` 한 번이었다.**

회귀 테스트의 입력을 VM 출력 원문으로 바꿔 두었고, 백틱이 없는 형태도 함께 받도록 고쳤다.

## 4. 담긴 것 대신 담은 그릇을 쟀다

백업 설계를 시작할 때 가장 먼저 물은 것이 「얼마나 큰가」 였다.
`docker system df -v` 가 준 값은 이랬다.

| 대상 | 볼륨 | 실제 데이터 |
| --- | --- | --- |
| `bullet-in_maria_data` | 207.4 MB | 논리 덤프 gzip 2,291,503 바이트 |
| `bullet-in_mongo_data` | 531.7 MB | 논리 덤프 gzip 1,734,975 바이트 |

몽고는 볼륨이 531.7 MB 인데 그 안에 든 데이터는 3.4 MB 다.
이 3.4 MB 는 `listDatabases` 가 주는 압축 전 크기이고, 표의 1,734,975 바이트는 그것을 gzip 으로 눌러 담은 아카이브다.
어느 잣대로 재도 볼륨 크기와는 두 자릿수 차이가 난다.
나머지는 WiredTiger 가 미리 잡아 둔 파일과 저널이다.

**볼륨 값을 그대로 믿었으면 1회분을 739 MB 로 보고 설계를 짰을 것이다.**
그 수치대로면 매일 백업하는 것만으로 무료 한도가 빠듯하고, 세대 보관은 엄두를 못 내서 「주 1회로 줄이자」 가 답으로 나왔을 것이다.
실제 값은 4.0 MB 라서 하루 1회 · 세대 셋을 다 넣고도 무료 한도의 12% 만 쓴다.

**부피가 제약이 아니라는 것을 알고 나서야 선택지가 넓어졌다.**
이것이 「부피부터 재고 나머지를 정한다」 가 옳았던 이유다.

## 5. 덤으로 — 권한을 뺀 대가로 생긴 조건

이 셋과 뿌리는 다르지만 같은 작업에서 나왔으니 함께 적어 둔다.

VM 의 서비스 계정에 삭제 권한을 안 줬다 (`roles/storage.objectCreator` + `roles/storage.objectViewer`).
두 역할의 권한 목록에 `storage.objects.delete` 가 없다는 것은 `gcloud iam roles describe` 로 확인했다.
지우는 일은 GCS 수명주기 규칙이 하므로 VM 이 통째로 털려도 과거 백업이 남는다.

**그런데 `objectCreator` 는 덮어쓰기도 못 한다.**
이것도 추론으로 두지 않고 같은 서비스 계정으로 같은 이름을 두 번 올려 봤다.

```
1회차: 올림
RESULT: 덮어쓰기 거부 — 업로드 실패 403
"message": "bullet-in-backup@bullet-in-backup.iam.gserviceaccount.com
            does not have storage.objects.delete access to ..."
```

덮어쓰기가 `storage.objects.delete` 를 요구하기 때문이다 (시험 삼아 올린 객체는 확인 뒤 지웠다).

그래서 객체 이름에 초 단위 타임스탬프를 넣은 것이 취향이 아니라 필수 조건이 됐다.
**이름 규칙을 「날짜만」 으로 단순화하면 같은 날 두 번째 백업이 이 403 으로 죽는다.**
나중에 이름 규칙을 손대는 사람이 이것이 권한과 얽혀 있다는 것을 모르면 이유를 못 찾는다.
