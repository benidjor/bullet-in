# 모든 수치를 다시 잰 리뷰 (2026-09-03)

행동 기록 편입 (PR #443에서 #447) 을 한 세션이 회차 안에서 낸 답이 계속 달라져, 별도 세션이 코드와 수치를 처음부터 다시 쟀다.
수치는 전부 재현됐고, 코드에서 확정 결함 둘이 나왔으며, 브리핑에 없던 운영 사고 하나를 저널에서 찾았다.
그리고 리뷰가 낸 수정 하나는 배포 뒤에야 틀린 것으로 드러났다.

## 1. 답이 계속 바뀐 이유

같은 값이 회차 안에서 두세 번 바뀌었다.
독립 잣대로 다시 재니 마지막 값이 맞았고, 바뀐 이유는 셋으로 갈렸다.

| 이유 | 사례 |
| --- | --- |
| 세상이 움직였다 | 원자료 문서 1,698 → 1,701 → 1,702 (재는 사이에 회차가 돈다) · 마트 1,010 → 1,020 |
| 잣대가 달랐다 | 3.2 MiB 는 압축 후 디스크 (`storageSize`) · 5.05 MiB 는 BSON (`size`) · 688 은 뺄셈 · 819 는 집합 차 |
| 스스로 정정했다 | 「1,185건 유실」 은 순차 처리 가정의 과장 · 실제 454 |

셋 중 진짜 오류는 셋째 하나였다.
재측정 값을 남길 때 시각과 잣대 이름을 함께 적어 두면 다음 사람이 「틀렸다」 와 「바뀌었다」 를 가를 수 있다.

## 2. 독립 잣대

같은 자료를 다른 길로 셌다.

- **bronze 13,035 · 접힘 51 · 팩트 577 · 공개일 306 · 등급 축 일곱 칸** — BigQuery 에서 창 함수로 (`event_date` · `bi_cid` · `bi_ts` · `event_name` 으로 접고 `event_timestamp` 를 KST 로 바꿔 공개일을 뺐다)
- **기사 분모 1,010** — VM 의 집계 파일 `state/behavior_metrics.json` 의 축 합
- **원자료 819 · 137 · 454 · 369** — VM 에서 Mongo 와 MariaDB 를 함께 읽어 해시 집합 차와 삽입 순서 역행을 셌다
- **테스트 1,615** — 로컬 실행

전부 브리핑과 같았다.
독립 잣대가 같은 값을 내면 그 값은 믿을 수 있고, 다르면 어느 잣대가 좁았는지부터 본다.

## 3. 코드에서 확정된 결함 둘

### 3.1. 「(없음)」 52 는 등급 없는 기사가 아니었다

행동 지표 화면의 등급 · 단계 · 매체 세 축에 「(없음)」 이 똑같이 52 였다.
값이 축마다 다르면 자료의 결측이고, 축과 무관하게 같으면 계측 쪽 결측이다.
화면 축과 대조하니 주요 소식 (`mitem` 24) · 선수 카드 (`pcard` 26) · 타임라인 제목 (`tltitle` 2) 의 합이 정확히 52 였다.
그 셋은 카드에 `data-hash` 만 있고 `data-stage` · `data-tier` · `data-outlet` 이 없었다.

템플릿 둘에 속성 셋을 더하고 화면에 「(없음)」 의 뜻을 한 문단 적었다 (PR #448).

### 3.2. 행동 갈래가 실패해도 알림이 없었다

`run_load` 가 행동 기록 적재 넷을 한 `try/except` 로 감싸고 경고만 남겼다.
유닛이 0 으로 끝나니 `OnFailure=` 가 안 뜨고 집계 파일이 조용히 낡는다.
마트 이력 적재는 그 앞에서 이미 끝나 있으므로, 로깅 뒤 다시 던지게 했다.
알림 경로를 새로 만들지 않고 이미 있는 것을 되살린 한 줄이다.

## 4. 리뷰가 낸 수정 하나가 틀렸다

PR #448 본문에 「이미 쌓인 클릭 26건도 기사 해시로 마트에서 단계 · 등급을 채워 센다」 고 썼다.
집계에 해시 기준 채움을 넣었으니 옛 클릭도 살아나리라고 봤다.

배포 뒤 화면의 「(없음)」 은 세 축 모두 52 그대로였다.
BigQuery 로 재니 9월 1일까지의 주요 소식 · 타임라인 · 선수 카드 클릭은 **`card_hash` 가 전부 빈 값**이었다.
해시를 싣는 PR #437 이 9월 2일 밤에 들어갔으니 그 전 클릭에는 채움이 걸릴 열쇠가 없다.

채움 코드는 #437 과 #448 배포 사이의 클릭에만 뜻이 있고, 그 뒤로는 템플릿이 속성을 직접 실어 필요가 없다.
PR 에 정정 댓글을 달았다.
**채움을 짜기 전에 열쇠가 자료에 있는지를 세야 했다.**
장치의 논리로 자료를 단정한 것이 원인이고, 확인은 질의 하나였다.

## 5. 브리핑에 없던 사고를 저널에서 찾았다

회차 목록을 하루치로 훑다가 03:03 KST 회차가 `Failed with result 'exit-code'` 로 끝난 줄을 봤다.
dbt 게이트가 `gold_slo_rollup` (29개 중 23번째) 에서 종료코드 -11 로 죽어 배포가 50분 서 있었고, 03:56 수동 회차가 풀었다.
같은 자리에서 죽은 세 번째 관측이고 VM 에서는 두 번째다.

구현 세션은 03:56 회차 뒤 저널을 `--since '10 min ago'` 로만 봐서 50분 전 실패가 창 밖이었다.
자기 행동이 만든 창만 보면 그 앞의 실패를 놓친다.
회차 목록 (`Starting` · `Finished` · `Failed`) 을 하루치로 먼저 보는 것이 순서다.

이 관측으로 「VM 은 아직 두 번째 차단 전」 이라던 코어 덤프 유예 근거가 사라졌다.
회차 유닛에 `LimitCORE=infinity` 를 넣었고 (PR #448), VM 에 `systemd-coredump` 를 깔아 시험 세그폴트가 잡히는 것까지 확인했다 (17:08 KST).
다음에 게이트가 -11 로 죽으면 `coredumpctl info -1` 부터 연다.

## 6. 다음에 같은 자리를 만나면

- **같은 자료를 다른 길로 센다.** 층마다 하나씩 독립 잣대를 두면 브리핑을 믿을지 말지가 아니라 어느 값이 맞는지를 말할 수 있다.
- **한 값이 여러 축에서 똑같이 비면 계측을 의심한다.** 자료의 결측은 축마다 다르게 빈다.
- **수정이 살릴 대상이 실제로 있는지 먼저 센다.** 「이 열쇠로 채운다」 앞에 「그 열쇠가 그 행에 있나」 가 온다.
- **저널은 회차 목록부터 하루치로 본다.** 그다음에 시각을 좁힌다.
