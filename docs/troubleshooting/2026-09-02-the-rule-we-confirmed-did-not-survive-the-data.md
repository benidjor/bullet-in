# 확정한 규칙이 운영 데이터를 만나 뒤집혔다 (2026-09-02)

결말 카드를 되살리는 일 (안건 2π) 은 설계가 이미 끝나 있었다.
규칙 셋을 확정했고 운영 14묶음을 손으로 갈라 「결말이 서야 할 것 11 · 서면 안 될 것 3」 까지 정해 둔 뒤였다.
구현만 남은 작업이었는데 **그중 한 조건이 실제 데이터 앞에서 그 판정 셋을 뒤집었다.**

## 1. 뒤집힌 조건

확정된 규칙은 이랬다.

```
후보 = 다른 구단 관점 기사  또는  무산
채택 ① = 무산이면 면제 · 아니면 단계가 대표 이상
채택 ② = 결말보다 나중에 나온 진행 단계 기사가 그 묶음에 없을 것
```

②는 「이적시장 마감까지 협상이 계속되니 무산을 확정으로 보기 어렵다」 는 지적에서 나왔다.
근거도 실물이었다.
알바레스는 2026-08-29 에 무산이 났다가 이틀 뒤 되살아났고 09-01 에 다시 무산됐다.

문자 그대로 구현하니 **결말이 서야 한다고 판정해 둔 묶음 셋에서 결말이 사라졌다.**
규칙이 걸러야 할 것은 서면 안 될 둘 (넬슨 · 기마랑이스) 뿐이었다.

## 2. 왜 세게 걸렸나

판정 안쪽을 묶음별로 찍어 보니 원인이 하나였다.

**「무산 뒤에 온 기사」 가 서로 다른 두 가지인데 저장된 단계가 같다.**

| 뒤에 온 기사 | 실제 의미 | `transfer_stage` |
| --- | --- | --- |
| 알바레스 「영입에 150m 유로 투입 준비」 | 이야기가 되살아남 | `interest` |
| 비니시우스 「영입 불발된 아스날, 대체 자원 물색 나서」 | 무산을 확인 | `interest` |
| 크루피 「영입 고려했으나 부상으로 보류」 | 무산을 확인 | `interest` |

②는 이 둘을 못 가르고 뒤 기사가 있다는 사실만 본다.
그래서 이미 끝난 이야기의 결말이 함께 사라졌다
— 비니시우스 (레알 마드리드와 재계약) 와 크루피 (부상으로 일단락) 다.

로저스도 함께 사라졌는데 이유가 조금 다르다.
첼시행이 확정된 지 네 시간 뒤에 「아스날, 모건 로저스 영입 근접」 이 들어와 있었다
— 내용상 앞선 소식이 시각상 뒤에 온 것이라 단계가 `negotiating` 으로 저장돼 있다.

②가 막으려던 알바레스는 ② 없이도 옳게 나온다.
묶음이 최신순이라 09-01 무산이 먼저 잡히기 때문이다.
②가 실제로 값어치를 내는 구간은 「무산 뒤 되살아났고 아직 다시 무산되지 않은」 중간뿐인데,
그 구간을 가리키는 신호가 무산 확인 기사와 구분되지 않는다.

## 3. 저울이 한쪽으로 기울어 있었다

이런 판정은 두 종류의 오류를 맞바꾸는 일이라 「정확한 규칙」 이 없다.
다만 이번에는 두 오류가 대칭이 아니었다.

- ②를 빼서 틀리면 (끝난 줄 알았는데 되살아남) **다음 회차의 새 보도가 카드를 바꿔 준다**
- ②를 넣어서 틀리면 (끝났는데 안 보임) **이미 끝난 이야기라 새 보도가 안 들어오고 영영 화면에 안 나온다**

「되살아남을 안 따진다」 로 결정해 ②를 뺐다.
설계에 있던 조건을 왜 안 넣었는지는 `ending_card` 독스트링에 적어 두었다
— 안 적으면 다음 사람이 설계 기록만 보고 되돌린다.

## 4. 재는 도구가 두 번 흔들렸다

### 4.1. 대상이 움직이고 있었다

같은 판정을 두 번 돌렸는데 결말 카드 수가 갈렸다.
처음에는 도구를 의심했으나 원인은 대상이었다.

워치리스트 회차가 22:35 에 기사 2건을 적재했고 그 단계 부여는 다음 정규 회차에 붙는다.
두 실행 사이에 서빙 행이 918에서 920으로 늘어 있었다.

**행과 기준 시각을 한 번 떠서 파일에 고정한 뒤에야 네 판정을 서로 비교할 수 있게 됐다.**
런북 스니펫의 `assert blank == 0` 이 이것을 잡아 주었다
— 그 가드가 없던 두 번째 스크립트는 조용히 지나갔다.

고정한 920행에 판정 넷을 각각 댄 결과는 이렇다.

```
옛 판정              11   현재 배포본의 규칙 (다른 구단 관점만)
② 없음               10   이번에 택한 것
② 를 협상 중 이상으로   9
② 를 문자 그대로        7
```

### 4.2. 두 계수가 다른 것을 세고 있었다

파이썬으로 센 결말 카드는 10개, 브라우저로 센 것은 7개였다.

둘 다 맞는 값이었다.

- 파이썬 = 결말 카드가 **붙은** 묶음
- 브라우저 = 대표와 결말이 **나란히 보이는** 묶음
- 차이 3 = 대표가 주요 소식과 겹쳐 숨겨지고 (`band_dup`) 결말만 보이는 묶음

이름을 안 갈랐으면 「3개가 사라졌다」 는 틀린 보고가 나갔을 것이다.

## 5. 화면을 눈으로 봐서만 잡힌 결함

수가 맞고 테스트도 통과한 뒤 화면을 열었더니 **같은 기사가 두 자리에 서 있었다.**
왼쪽에 낱개 카드로, 오른쪽 묶음의 결말 카드로 각각 한 장씩 3건이었다.

`promote_recent` 는 꺼낸 기사를 관련 보도와 기사 목록에서 빼 주는데 `b["ending"]` 은 안 건드린다.
결말 카드가 2026-08-23 부터 안 그려졌고 승격은 08-27 에 들어왔으므로
**두 코드가 함께 돈 적이 한 번도 없었다.**
되살리는 순간 처음 만나는 조합이었다.

이 셋을 고치면서 결말 카드 수가 3장 줄었다.
설계 단계의 예측이 「13에서 12로」 였는데 실측이 11에서 10이 된 것은 이 셋과, 그 사이 새로 생긴 묶음 하나 때문이다.
**변화의 내용 — 넬슨 · 기마랑이스가 빠지고 크루피가 들어온다 — 은 예측 그대로였다.**
