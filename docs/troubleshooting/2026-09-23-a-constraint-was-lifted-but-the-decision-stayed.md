# 제약이 풀린 뒤에도 결정은 그대로 남았다 (2026-09-23)

- **영역**: README / 라이브 화면 캡처 / 결정의 수명
- **관련 문서**: `docs/runbook/2026-09-06-capturing-live-screens-for-the-readme.md` §4.2 · 세션 메모리 `deferred-by-a-constraint-needs-revisiting`

## 1. 증상

사용자가 물었다.
「README 에 왜 전체 기사 화면 이미지를 넣었지. 홈 화면 캡처가 낫지 않나.」

확인해 보니 첫 이미지는 방문자가 실제로 처음 보는 화면이 아니었고, 캡처 설명에는 **보여 주지 않는 화면을 말로만 설명하는 문장**이 남아 있었다.

> 홈 화면은 대표 기사와 주요 소식을 신문 레이아웃으로 배치합니다.

## 2. 원인 — 제약은 풀렸는데 결정이 안 따라왔다

이력을 따라가면 전체 기사 캡처는 PR #58 부터 README 의 대표 이미지였고 다섯 번 손대는 동안 바뀌지 않았다.

중간에 **의식적인 판단이 한 번 있었다.**
2026-09-06 개편 (#473) 에서 홈을 찍으려 했지만 대표 기사 사진이 헤드리스에서 막혀 자리가 비었고, 그래서 홈 대신 `all.html` 을 골랐다.
촬영 런북 §4.2 에 그 사유가 적혀 있었다.

그런데 **#501 에서 그 제약이 풀렸다.**
원인이 응답 헤더의 어긋남 (`.webp` 파일명에 `content-type: image/jpeg` · `nosniff`) 이라는 것을 밝히고 촬영용 중계 코드를 런북에 넣었다.

문제는 제약을 푼 그 PR 이 **「그래서 이제 무엇을 되돌아봐야 하는가」 를 남기지 않은 것**이다.
런북에는 여전히 「그래서 README 첫 캡처는 홈 대신 `all.html` 로 찍었다」 가 현재형으로 남아 있었다.

## 3. 처방

- **첫 캡처를 홈으로 교체** — 중계로 대표 기사 사진을 채워 촬영 (1180 × 1425 · 582 KB · `naturalWidth` 1200 으로 확인)
- **전체 기사 캡처는 3.3 절로 이동** — facet 과 갈래별 건수를 설명하는 자리로
- **런북 §4.2 를 과거형으로** — 홈을 뺀 판단이 2026-09-06 시점의 것임을 명시하고 이번 촬영 설정을 기록

## 4. 배운 것

- **제약 때문에 포기한 것은 제약을 푸는 PR 에 함께 적는다.**
원인과 해법만 적으면 포기했던 결정은 그대로 남는다.
이번에는 사용자가 짚을 때까지 남아 있었다.
- **런북에 적힌 판단은 시점을 붙여 둔다.**
「그래서 A 대신 B 로 했다」 가 현재형으로 적혀 있으면 조건이 바뀐 뒤에도 규칙처럼 읽힌다.

## 5. 곁다리 — `full_page` 가 뷰포트 높이로 늘어난다

홈을 찍을 때 `full_page=True` 인데도 결과가 1500px 으로 나왔다.
뷰포트 높이를 1500 으로 잡아 둔 탓이다.
`full_page` 는 콘텐츠 높이와 뷰포트 높이 중 **큰 쪽**을 쓰므로, 실제 페이지 (1425px) 보다 큰 뷰포트를 주면 아래에 빈 띠가 붙는다.
`document.body.scrollHeight` 를 먼저 재고 그보다 낮은 뷰포트로 다시 찍는다.
