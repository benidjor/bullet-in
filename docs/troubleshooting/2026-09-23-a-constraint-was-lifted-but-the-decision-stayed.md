# 제약이 풀린 뒤에도 결정은 그대로 남았고 바꿀지는 산수가 정했다 (2026-09-23)

- **영역**: README / 라이브 화면 캡처 / 결정의 수명
- **관련 문서**: `docs/runbook/2026-09-06-capturing-live-screens-for-the-readme.md` §4.2 · 세션 메모리 `deferred-by-a-constraint-needs-revisiting`

## 1. 증상

사용자가 물었다.
「README 에 왜 전체 기사 화면 이미지를 넣었지. 홈 화면 캡처가 낫지 않나.」

확인해 보니 첫 이미지는 방문자가 실제로 처음 닿는 화면이 아니었고, 캡처 설명에는 **보여 주지 않는 화면을 말로만 설명하는 문장**이 남아 있었다.

> 홈 화면은 대표 기사와 주요 소식을 신문 레이아웃으로 배치합니다.

## 2. 원인 — 제약은 풀렸는데 결정이 안 따라왔다

이력을 따라가면 전체 기사 캡처는 PR #58 부터 README 의 대표 이미지였고 다섯 번 손대는 동안 그대로 유지됐다.

중간에 **의식적인 판단이 한 번 있었다.**
2026-09-06 개편 (#473) 에서 홈을 찍으려 했지만 대표 기사 사진이 헤드리스에서 막혀 자리가 비었고, 그래서 홈 대신 `all.html` 을 골랐다.
촬영 런북 §4.2 에 그 사유가 적혀 있었다.

그런데 **#501 에서 그 제약이 풀렸다.**
원인이 응답 헤더의 어긋남 (`.webp` 파일명에 `content-type: image/jpeg` · `nosniff`) 이라는 것을 밝히고 촬영용 중계 코드를 런북에 넣었다.

문제는 제약을 푼 그 PR 이 **「그래서 이제 무엇을 되돌아봐야 하는가」 를 남기지 않은 것**이다.
런북에는 여전히 「그래서 README 첫 캡처는 홈 대신 `all.html` 로 찍었다」 가 현재형으로 서 있었다.

## 3. 처방

- **첫 캡처를 홈으로 교체** — 중계로 대표 기사 사진을 채워 촬영 (1180 × 1425 · 572 KB · `naturalWidth` 1200 으로 확인)
- **전체 기사 캡처는 3.3 절로 이동** — facet 과 갈래별 건수를 설명하는 자리로
- **런북 §4.2 를 과거형으로** — 홈을 뺀 판단이 2026-09-06 시점의 것임을 명시하고 이번 촬영 설정을 기록

## 4. 덱은 왜 안 바꿨나 — 말이 아니라 산수로 갈렸다

이어서 「포트폴리오에도 전체 기사 화면이 있는데 그것도 바꿀까」 라는 물음이 왔다.
말로는 양쪽이 다 그럴듯했다.

갈린 지점은 **덱이 캡처를 잘라 쓴다는 사실**이었다.
그 장은 캡처를 `height:332px` 상자에 `overflow:hidden` 으로 넣고 위쪽만 보여 준다.
그리고 그 장의 본문이 캡처에 요구하는 것은 하나다 — **왼쪽 facet 사이드바가 보일 것** (「오른쪽 캡처 참조」 라고 본문이 직접 가리킨다).

두 이미지의 세로 비율이 달라 같은 상자에 들어오는 범위가 크게 달라진다.

| 캡처 | 원본 | 세로 / 가로 | 332px 상자에 들어오는 범위 | facet 사이드바 |
| --- | --- | --- | --- | --- |
| 전체 기사 | 2360 × 1800 | 0.76 | 위 56 에서 71% | 영입 단계 8칸 + 공신력 대부분 |
| 홈 | 1180 × 1425 | 1.21 | 위 약 40% (약 563px) | 보이지 않음 |

홈은 위 563px 이 헤더 · 대표 기사 사진 · 대표 기사 제목 · 주요 소식 네 건이다.
facet 레일은 대표 기사 아래 y 약 550 부터 시작하므로 **증거로 걸어 둔 사이드바가 한 칸도 안 보인다.**

그래서 덱은 그대로 두었다.

## 5. 배운 것

- **제약 때문에 포기한 것은 제약을 푸는 PR 에 함께 적는다.**
원인과 해법만 적으면 포기했던 결정은 그대로 남는다.
이번에는 사용자가 짚을 때까지 남아 있었다.
- **런북에 적힌 판단은 시점을 붙여 둔다.**
「그래서 A 대신 B 로 했다」 가 현재형으로 서 있으면 조건이 바뀐 뒤에도 규칙처럼 읽힌다.
- **같은 캡처라도 문서마다 답하는 질문이 다르다.**
README 첫 이미지가 답하는 질문은 「이게 뭐하는 서비스인가」 이고, 덱의 그 장이 답하는 질문은 「명단 파일 하나가 필터를 움직인다는 주장이 사실인가」 다.
한쪽을 바꿨다고 다른 쪽을 맞출 이유가 없다.
- **잘라 쓰는 이미지를 바꿀 때는 무엇이 잘려 나가는지 먼저 잰다.**
세로 비율과 상자 높이를 대입하는 계산 한 번이 논증보다 빨리 답을 냈다.

## 6. 곁다리 — `full_page` 가 뷰포트 높이로 늘어난다

홈을 찍을 때 `full_page=True` 인데도 결과가 1500px 으로 나왔다.
뷰포트 높이를 1500 으로 잡아 둔 탓이다.
`full_page` 는 콘텐츠 높이와 뷰포트 높이 중 **큰 쪽**을 쓰므로, 실제 페이지 (1425px) 보다 큰 뷰포트를 주면 아래에 빈 띠가 붙는다.
`document.body.scrollHeight` 를 먼저 재고 그보다 낮은 뷰포트로 다시 찍는다.
