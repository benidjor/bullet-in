# 정의를 안 읽고 설계를 결함으로 지목했다 (2026-08-04)

선수 페이지 화면이 이상해 보이는 원인을 찾다가, 같은 세션에서 **의도된 설계를 세 번 결함으로 보고했다.**
세 번 다 사용자가 정정했고, 세 번 다 정의가 이미 어딘가에 적혀 있었다.

기록해 두는 이유는 실수 자체보다 **세 사례의 구조가 같기 때문**이다.
화면에서 이상해 보이는 값을 만나면 코드부터 읽게 되는데, 코드는 "왜 그렇게 정했는지" 를 말해 주지 않는다.

## 사례 1 — 주석이 실제 소비처를 가리키지 않았다

`transfer_stage.py` 의 상수에 이렇게 적혀 있다.

```python
# (enum, 한국어 라벨, css 클래스) — 사이드바 표시 순서 (위 → 아래, 진행 단계 높은 순)
SIDEBAR_STAGES = [official, agreed, medical, personal_terms, negotiating, interest, rumour]
```

이 순서가 실제 사이드바와 달라서 "순서가 정의와 어긋난다" 고 보고했다.

**틀렸다.**
사이드바는 이 목록을 쓰지 않는다.
화면에 그려지는 것은 `serve/render.py` 의 `_STAGE_DISPLAY_GROUPS` 이고, 그쪽은 `negotiating` 과 `medical` 을 `협상 중` 하나로 묶는다.

소비처를 전수로 확인한 결과다.

| 소비처 | 순서가 화면에 보이나 |
| --- | --- |
| `_LABEL` · `_CSS` 사전 | 아니오 — 조회용이라 순서 무관 |
| `STAGE_ENUMS` → `VALID_STAGES` | 아니오 — 집합이라 순서 무관 |
| `env.globals["stages"]` | 아니오 — 템플릿에서 아무도 쓰지 않는다 |
| `facets["stage"]` | 아니오 — 템플릿에서 쓰지 않는다 |
| `_STAGE_DISPLAY_GROUPS` | **예 — 이것만 그려진다** |

즉 `SIDEBAR_STAGES` 의 순서는 화면에 아무 영향이 없고, 주석만 사실과 달랐다.
그 주석을 읽고 "화면 순서를 정의하는 목록" 이라고 믿은 것이 오진의 출발점이다.

이 문서를 쓰면서 주석을 실제 역할로 고쳤다.

## 사례 2 — 도메인 이유를 모른 채 병합을 결함으로 봤다

배지 표시 사전이 `medical` 을 `negotiating` 과 같은 `협상 중` 으로 보여 준다.
저장 순서에서는 `medical` 이 더 진행된 단계라, 타임라인에서 `이적 합의 → 협상 중` 이라는 역행처럼 보인다.

"필터 항목을 줄이려던 묶음이 배지에까지 잘못 재사용됐다" 고 보고했다.

**틀렸다.**
사용자가 설명한 실제 이유는 다르다.

> 메디컬 보도가 나오는 기사도 있고 안 나오는 기사도 있다.

메디컬은 보도 자체가 들쭉날쭉해서 진행 이정표로 쓸 수 없다.
그래서 별도 단계로 세우지 않고 협상 중에 합친 것이다.
코드 주석에도 "medical 은 건수가 적어 협상 중에 합친다" 로 결과만 적혀 있어, 그 판단의 근거는 코드에 없었다.

## 사례 3 — 런북에 정의와 불변량이 다 있었다

공홈 기사 여섯 건 중 하나가 `아스날 트로사르, 베식타스 이적 합의 완료` 인데 `오피셜` 배지를 달고 있었다.
합의 소식에 오피셜이 붙은 것으로 보여 "소스 규칙이 무조건 오피셜을 준다" 고 보고했다.

**틀렸다.**
`docs/runbook/2026-06-30-transfer-stage-classification-ops.md` 가 이미 이렇게 정하고 있다.

> - **규칙 경로만 official 을 생성한다.** `rule_stage(source_id)` 는 공홈 행에만 `official` 을 부여한다.
> - **LLM enum 에서 official 이 제거됐다.** 공홈이 아닌 소스는 구조적으로 official 이 될 수 없다.
> - **공홈이면 조건 없이 덮어쓴다.**

같은 문서에 불변량 진단 SQL 까지 있다 — 공홈 기사인데 `official` 이 아닌 귀속은 항상 0이어야 한다.

이 프로젝트에서 `official` 은 **이적 완료가 아니라 구단 공식 발표**다.
공홈은 합의 때 한 번 · 확정 때 한 번 올리므로 오피셜이 여러 번 나오는 것이 정상 동작이다.
내 기준 ("오피셜 = 이적 확정") 을 들이대고 결함이라 부른 것이다.

## 세 사례의 공통 구조

1. 화면에서 값이 이상해 보인다.
2. 코드를 읽는다.
3. 코드가 왜 그런지는 안 적혀 있으므로 **내 상식으로 빈칸을 채운다.**
4. 그 상식과 다른 동작을 결함으로 보고한다.
5. 정의 문서나 도메인 지식이 그 설계를 정당화한다.

## 재발 방지

**화면 이상의 원인을 지목하기 전에 두 가지를 먼저 한다.**

- **그 값의 정의가 어디에 적혀 있는지 찾는다.**
`docs/runbook/` 과 `docs/superpowers/specs/` 를 그 값 이름으로 검색한다.
이 프로젝트는 분류 값의 정의를 런북에 두고 불변량까지 적어 두는 편이다.
- **주석이 아니라 실제 소비처를 확인한다.**
`git grep <상수명> -- src/ tests/` 로 전수를 보고, 템플릿까지 훑는다.
주석은 코드가 바뀌어도 따라오지 않는다.

**도메인 판단이 섞인 값은 실측으로 검증되지 않는다.**
단계 순서를 이 저장소 데이터로 실증하려 했는데, `personal_terms` 여덟 건 중 진짜는 한 건뿐이라 무엇을 재도 의미가 없었다.
이런 값은 사용자에게 묻는 것이 더 정확하고 빠르다.
