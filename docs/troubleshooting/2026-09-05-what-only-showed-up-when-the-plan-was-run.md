# 계획서 코드를 돌려 봐야 나온 결함 셋 (2026-09-05)

안건 2φ PR 1 (행동 지표 화면 · #469) 은 계획서에 코드와 테스트 전문이 있어 구현자가 옮겨 적기만 하면 되는 회차였다.
그런데 옮겨 적은 코드에서 실물과 어긋난 자리가 열한 곳 나왔고, 그 가운데 셋은 단위 테스트를 다 통과한 뒤에야 드러났다.
셋 다 「부분 테스트로는 안 보이는」 유형이라 따로 적어 둔다.
열한 곳 전부는 계획서 `docs/superpowers/plans/2026-09-05-dashboard-behavior-screen.md` 의 「실행 중 정정 (2026-09-05)」 절에 있다.

## 1. Jinja 가 CSS 의 `{#` 를 주석 시작으로 읽었다

**증상** — 뷰모델만 재는 테스트 넷은 통과했는데, 템플릿을 실제로 렌더하는 테스트가 돌자 화면의 스타일이 통째로 사라지고 `</style>` 뒤까지 삼켜졌다.

**원인** — 목업 v2.8 의 CSS 에 `@media (prefers-reduced-motion:reduce){#tip{transition:none}}` 이 있다.
여기서 `{#` 는 CSS 로는 「블록 시작 + id 선택자」 이지만 Jinja 로는 주석 시작 기호다.
Jinja 는 `#}` 가 나올 때까지를 주석으로 버리므로, 그 뒤의 스타일과 태그가 출력에서 빠졌다.
같은 계획서의 `_overview` 는 항목 넷 가운데 둘을 2-튜플로 돌려주는데 템플릿은 `for lab, txt, subs` 로 셋을 풀어 `ValueError` 가 났다.

**해결** — `_dash.html.j2` 의 `<style>` 블록을 `{% raw %}` 와 `{% endraw %}` 로 감쌌다.
그 블록 안에는 실행돼야 할 Jinja 식이 없어서 잃는 것이 없다.
`_overview` 의 두 항목에는 셋째 원소 `[]` 를 붙였다.

**예방** — 템플릿에 CSS 나 JS 를 인라인으로 넣을 때는 `{#` · `{{` · `{%` 가 글자 그대로 나오는지 먼저 grep 하고, `<style>` · `<script>` 는 `{% raw %}` 로 감싸는 것을 기본으로 둔다.
템플릿을 옮겨 적는 태스크는 `-k` 로 고른 부분 테스트로 끝내지 말고, 실제 렌더를 부르는 테스트 한 번을 통과 조건에 넣는다.

## 2. pyiceberg 는 없는 컬럼을 고르면 예외를 낸다

**증상** — 계획서의 `_scan_rows` 가 silver 표에서 `event_name` · `user_pseudo_id` · `event_date_kst` · `page_location` 넷만 골라 읽는데, 통합 테스트에서 `ValueError: Could not find column: 'page_location'` 이 났다.

**원인** — pyiceberg 0.11.1 의 `table.scan(selected_fields=…)` 는 스키마에 없는 이름이 하나라도 있으면 예외를 낸다 (착수 전 대조에서 직접 확인했다).
silver `ga4_events_flat` 의 스키마는 날마다 관측된 이벤트 파라미터에서 만들어지므로 (`flat_schema`), 어떤 컬럼은 아직 없을 수 있다.
테스트 픽스처 `fake_ga4` 는 `bi_cid` 파라미터만 실어 `page_location` 컬럼이 없었다.

**해결** — 요청한 컬럼을 표 스키마에 있는 이름으로 좁혀 읽고, 빠진 이름은 `WARNING` 으로 남긴다.
없는 컬럼은 행에서도 빠지므로 소비자는 `.get` 으로 읽는다.
경고를 남기는 이유는 운영에서 `page_location` 이 빠지면 페이지 집계가 전부 「(없음)」 으로 조용히 무너지기 때문이다.

**예방** — 스키마가 관측값에서 자라는 표를 읽을 때는 「컬럼이 있다」 를 전제하지 않는다.
무해한 값을 돌려주는 실패 경로는 로그부터 남긴다.

## 3. 합산하기 전에 목록을 잘랐다

**증상** — 단위 테스트는 다 통과했는데, 리뷰어가 기준값 7행 (fmkorea 참조 비율) 이 잘린 목록 위에서 계산된다는 것을 짚었다.

**원인** — `agg_daily` 가 유입 목록을 사용자 수 상위 10 으로 자른 뒤 JSON 에 실었고, `baseline_lines` 와 화면 인사이트는 그 목록에서 `fmkorea` 가 들어간 호스트를 전부 더한다.
11위 이하의 fmkorea 호스트가 있으면 아무 신호 없이 빠진다.
기준값 재현 창 (7일) 에서는 fmkorea 호스트가 상위를 차지해 값이 맞았으므로 재현으로도 안 잡혔다.

**해결** — 집계는 목록을 자르지 않고, 화면 뷰모델이 표시할 때만 7 로 자른다.
같은 리뷰에서 히트맵 두 벌에 `start=LAUNCH_DATE` 가 빠져 스펙 §3.1 의 창 「공개 뒤 전체」 와 어긋난 것도 함께 고쳤다.

**예방** — 잘라서 저장한 값 위에서 합계 · 비율을 내지 않는다.
자르기는 표시 층의 일이다.

## 4. 공통 교훈

셋 다 계획서 코드 그대로였고, 셋 다 그 태스크의 단위 테스트를 통과했다.
드러난 자리는 각각 렌더 (템플릿을 실제로 호출) · 스캔 (진짜 pyiceberg 를 실행) · 리뷰 (합계의 입력이 어디서 오는지 추적) 였다.
계획서의 코드 전문은 옮겨 적는 비용을 줄이지만 검증 비용은 줄이지 못한다.
스펙이 계획서와 다르면 스펙이 우선한다는 규칙도 이 회차에서 두 번 썼다 (히트맵 창 · 인사이트의 해석 문장 여섯 제거).
