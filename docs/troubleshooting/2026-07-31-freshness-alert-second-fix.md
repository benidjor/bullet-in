# 신선도 경고를 같은 날 두 번 고쳤다 — 문구 수정으로는 소음이 남는다 (2026-07-31)

신선도 경고의 원인 문구 오진 (07-30 진단 §4) 을 고쳐 배포하자,
바로 그 첫 발화가 두 번째 문제를 드러냈다.
문구는 참말이 됐는데 **조치할 수 없는 알림이 매 회차 반복**되는 구조가 그대로였다.
같은 날 발송 조건을 다시 고쳐 닫았고, 그 과정의 확인 실수와 교훈을 남긴다.

## 1. 1차 수정 — 원인 문구를 사실 기반으로 (#169)

- fetch 결과를 소스별로 세서 (후보 계수) 로그와 `pipeline_runs.candidate_counts` 에 남기고,
후보 0건일 때만 어댑터 힌트 (셀렉터 드리프트 등) 를 붙이게 했다.
- 후보가 있으면 "수집 경로 정상 · 신규 없음" 을, fetch 오류면 실제 오류 문구를 적는다.
- 저빈도 소스 guardian · arsenal_official 은 임계를 168h 로 올렸다.

## 2. 확인 실수 — 발송 성공은 로그를 남기지 않는다

- 머지 직후 회차를 보고 "신선도 경고 발화 없음" 이라고 단정했는데, 실제로는 발화한 뒤였다.
- `send_alert` 는 webhook 미설정 · HTTP 오류 · 예외일 때만 WARNING 을 남기고
**성공 발송은 아무 로그도 남기지 않는다**.
- journalctl 에 문구가 없다는 것은 발화하지 않았다는 증거가 아니다.
발화 여부는 디스코드 채널이나 `source_freshness` 의 stale 행으로 확인한다.

## 3. 첫 발화가 드러낸 것 — 참말이지만 조치 불가능한 알림

- 09:03 발화: guardian 192.0h (조정된 임계 168h 를 실제 경과가 넘음) · x_ornstein 96.0h,
둘 다 "이번 회차 후보 N건 — 수집 경로 정상 · 신규 없음".
- 문구는 정확해졌지만 받은 사람이 할 일이 없고, 신규 기사가 날 때까지
하루 8회 같은 알림이 반복된다 — 알림 피로는 이 트랙의 원래 출발점이었다.
- 원인: 07-30 진단의 처방 "후보는 있으나 전부 중복 = 정상 (알릴 필요 없음)" 을
문구 조건부화로만 반영하고 **발송 조건에는 반영하지 않았다**.

## 4. 2차 수정 — 조치 신호일 때만 발송 (#174)

- `freshness_alert_targets`: stale 중 후보 0건 (수집 끊김 의심) 또는 fetch 오류만 알림 대상.
- 경로 정상 stale 은 필드에서 빼고, 다른 조치 신호로 발화할 때 설명의
"경로 정상 생략 N" 계수로만 남긴다 (stale 총수는 설명에 유지 — 정보 소실 없음).
- 검증: 09:03 발화와 같은 입력이면 발송 자체가 없다.
12:06 판정 (stale = x_ornstein 뿐 · 후보 3건) 에서 무발화 확인.

## 5. 알림 수정과 소스의 실체는 별개 작업이다 — guardian

- 알림이 조용해져도 guardian 의 8일 무신규는 실재하는 제품 문제였다.
- 실측: 6/20 이후 HTML 목록 19건 vs 프리 티어 API 12건 — API 부재 7건 (37%) 에
비니시우스 단독 · Tzolis 영입 발표가 포함, 역방향 부재 0건.
- 같은 날 HTML 어댑터로 전환 (#175) 했고 첫 회차에 신규 3행이 적재됐다.
- 교훈: **경고의 소음을 줄이는 작업과 경고가 가리키던 실체를 고치는 작업을 분리해 둘 다 한다.**
알림을 고치고 끝냈다면 소스 고사는 조용히 계속됐을 것이다.
