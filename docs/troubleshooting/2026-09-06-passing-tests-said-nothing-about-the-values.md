# 테스트를 다 통과한 코드에 값의 오류 넷이 있었다 (2026-09-06)

안건 2φ PR 2 (수집 현황 화면 · #471) 는 계획서에 코드와 테스트 전문이 있었고 실행 전에 그 코드를 그대로 꺼내 한 번 돌려 결함 둘을 미리 고친 회차였다 (절차는 `docs/runbook/2026-09-06-dry-running-a-plan-before-executing-it.md`).
그런데 구현이 끝나고 태스크 리뷰가 돌자 Important 넷이 나왔고 넷 다 테스트 17종을 전부 통과한 코드에 있었다.
넷 다 「값이 화면에 잘못 나온다」 는 유형이고 테스트는 그 값을 묻지 않았다.
dry run 이 잡은 둘과 리뷰가 잡은 넷이 하나도 겹치지 않아서 따로 적어 둔다.
고친 자리는 계획서 `docs/superpowers/plans/2026-09-05-dashboard-ops-screen.md` 의 「실행 중 정정 (2026-09-05 저녁)」 표에 있다.

## 1. 오늘을 하루로 셌다

**증상** — Ingestion Volume 절의 인사이트 「회차가 8회에 못 미친 날은 N일이다」 가 매일 7/8 의 시간 동안 하루를 더 센다.
자정에서 21시 회차가 돌기 전까지 오늘은 늘 8회 미만이기 때문이다.

**원인** — 날짜 목록을 첫 라이브 실행일부터 `now.date()` 까지 만들고 그 안에서 회차 수가 8 미만인 날을 셌다.
마지막 날은 아직 진행 중인데 코드는 그것을 끝난 날과 같은 자리에 놓았다.
테스트 픽스처의 `NOW` 는 회차가 없는 날이었으므로 오늘이 세어지는 경우가 테스트에 없었다.

**해결** — 오늘을 빼고 세고, 문장을 「회차가 있던 날 가운데 … (오늘 제외)」 로 바꿨다.
오늘 회차 하나를 넣은 픽스처로 테스트 하나를 더했다.

**예방** — 「지금까지」 를 세는 집계는 마지막 구간이 완결됐는지 먼저 묻는다.
픽스처의 `now` 는 데이터가 있는 날 안에 두어야 부분 구간이 테스트에 나타난다.

## 2. 회차가 없는 날이 0초로 그려졌다

**증상** — Run Duration 의 p50 선과 p10 에서 p90 밴드가 회차 없는 날마다 0초로 떨어져 골이 생겼다.
6월과 7월 초에는 손으로 돌리던 때라 그런 날이 여럿이다.

**원인** — 백분위 헬퍼가 빈 목록에 0.0 을 돌려주고, 차트 함수 `line_chart` 는 빈 칸 (`None`) 을 받지 못하므로 날짜 축의 모든 날에 값이 있어야 했다.
「값이 없다」 가 「0초 걸렸다」 로 그려진 것이다.
테스트는 회차가 있는 날 셋만 넣어 빈 날이 축에 없었다.

**해결** — p50 · 밴드 · 에러 표시 · 이벤트 표시를 회차가 있던 날만으로 계산하고 라벨도 그 날들만 쓴다.
회차 없는 날이 축에서 빠지는 대신 0 이라는 거짓 값이 사라졌다.

**예방** — 빈 입력에 기본값을 돌려주는 헬퍼가 차트에 들어가면 그 기본값이 「값」 으로 보인다.
없는 날은 그리지 않는 것이 맞고 픽스처에는 값이 없는 구간을 하나 넣어 둔다.

## 3. 등급이 없는 행이 등급 비율의 분모에 들어갔다

**증상** — Credibility Mix 히트맵의 한 열 (한 주) 이 100% 로 안 더해질 수 있었다.

**원인** — `articles.tier` 는 NULL 을 허용하고 주별 구성 쿼리는 그 행도 돌려준다.
뷰모델은 그 행을 주 합계에는 더했지만 등급 행 (`0` 에서 `4`) 어디에도 그리지 않았다.
운영 데이터에는 등급 NULL 이 0건이라 화면에서는 안 보였고, 픽스처에도 없었다.

**해결** — 등급 히트맵의 분모를 등급이 있는 행만으로 따로 세고, 단계 히트맵 (「기타」 칸이 있다) 과 식별률은 전체를 쓴다.
등급 None 행이 든 픽스처로 테스트 하나를 더했다.

**예방** — 비율의 분모와 분자가 같은 집합에서 나오는지 본다.
분자에 나타날 수 없는 행이 분모에 있으면 열 합이 100 아래로 조용히 내려간다.
스냅샷 계약이 「이 값은 None 일 수 있다」 라고 말하면 픽스처에 그 None 을 하나 넣는다.

## 4. 값에서 안 나오는 문장이 픽스처와 모순됐다

**증상** — SLO 절의 인사이트에 「게이트가 막히면 두 행이 ✕ 로 바뀌고 배포가 멈춘다」 가 고정으로 실려 있었다.
같은 파일의 픽스처는 not_null 테스트 하나가 2행 실패한 게이트 결과를 넣었는데 SLO-4 는 ✓ 99.0% 로 나왔다.
문장이 말한 것과 표가 보인 것이 한 화면에서 어긋났다.

**원인** — 문장이 값에서 만들어지지 않고 목업의 설명을 옮겨 적은 것이다.
게이트가 막혀도 두 행이 함께 ✕ 가 되는 것은 아니고 (unique 와 not_null 은 따로 판정된다), 막히면 배포가 안 나가므로 그 화면은 발행되지도 않는다.
스펙 §3.3 은 「값에서 만들 수 있는 문장만 싣는다」 고 정해 두었는데 계획서가 그 규칙을 한 문장에서 놓쳤다.

**해결** — 그 부연을 지우고 본문에 게이트 시각을 넣었다 (「SLO-3 · 4 는 직전 회차 게이트 (09-05 12:02 UTC) 의 값이다」).

**예방** — 인사이트 문장은 f-string 에 값이 들어가는지로 판별한다.
값이 안 들어가는 문장은 설명문 (`.q`) 이나 문서로 옮긴다.

## dry run 이 잡은 둘과 무엇이 다른가

실행 전에 계획서 코드를 그대로 돌린 dry run 은 결함 둘을 잡았다.

| dry run 이 잡은 것 | 어떻게 드러났나 |
| --- | --- |
| 한 화면에 「12주」 와 「13주」 가 섞임 (일수 ÷ 7 과 월요일 수) | 기대 문자열이 다른 테스트가 실패 |
| 통합 픽스처가 `run-000` 을 두 번 넣어 기본 키 충돌 | `IntegrityError` |

둘 다 「형식 · 셈 · 픽스처」 의 오류라 테스트가 실패로 말해 준다.
리뷰가 잡은 넷은 전부 테스트가 통과한 채였고 리뷰어가 화면 값을 손으로 따라가며 「이 날은 아직 안 끝났다」 「이 날은 회차가 없다」 「이 행은 등급이 없다」 「이 문장은 어디서 나오나」 를 물어서 드러났다.

**두 검사는 겹치지 않는다.**
dry run 은 코드가 도는지를 묻고, 리뷰는 값이 맞는지를 묻는다.
계획서에 코드 전문이 있어도 둘 다 필요하고 하나가 깨끗하다고 다른 하나를 줄이면 안 된다.
