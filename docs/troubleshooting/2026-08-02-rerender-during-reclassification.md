# 재분류 중간 창에 재렌더해 빈 페이지를 배포 (2026-08-02)

병렬로 돌던 소급 재분류가 단계 값을 비운 7분 사이에 다른 세션이 사이트를 다시 만들어 배포했다.
그 결과 공개 화면에서 최신 소식 카드가 사라지고 기사 400건이 전부 "기타" 로 집계됐다.
데이터는 멀쩡했고 화면만 낡은 중간 상태였는데, 사용자가 "기사가 전부 없어졌다" 고 물을 때까지 아무도 몰랐다.

## 1. 사고 경위

- **15:42** — 단계 재분류 구현 (#194) 머지.
그 트랙 세션이 곧바로 기존 기사를 전부 다시 분류하는 배치를 VM 에서 시작했다.
이 배치는 대상 행의 `transfer_stage` 를 NULL 로 비운 뒤 다시 채운다.
- **15:46** — 서빙 트랙 세션이 자기 변경 (배지 수정) 을 확인하려고 `git pull` · 재렌더 · 배포를 실행했다.
하필 단계가 비어 있는 때였다.
- 렌더는 단계 없는 행을 전부 "기타" 로 집계했고 최신 소식 구간은 표시할 카드가 없어 비었다.
그 페이지가 그대로 배포됐다.
- **15:49** — 재분류 배치 완료 (459행 · 방향 컬럼 포함).
DB 는 이때부터 정상이었고 화면만 어긋난 채 남았다.

## 2. 원인

두 가지가 겹쳤고 어느 하나만 있었어도 사고는 없었다.

- **pull 이 가져온 커밋의 성격을 확인하지 않았다.**
스키마 · 분류 체계를 바꾸는 커밋이 들어왔으면 "그 트랙이 기존 데이터를 다시 채우는 배치를 지금 돌리고 있나" 를 먼저 물었어야 했다.
자기 변경만 보고 바로 배포했다.
- **렌더 입력을 검증하지 않았다.**
단계가 빈 행이 몇 건인지 세어 보기만 했어도 렌더에 들어가기 전에 멈출 수 있었다.

배포 자체가 급한 일도 아니었다.
그냥 두었으면 다음 정기 회차 (18:00) 가 값이 다 채워진 DB 로 렌더했을 것이고, 공개 화면은 한 번도 깨지지 않았다.

## 3. 복구

배치가 끝난 것을 확인한 뒤 같은 절차로 다시 렌더 · 배포했다.
이때는 아래 가드를 걸고 실행했다.

```python
blank = sum(1 for r in rows if not r["transfer_stage"])
assert blank == 0, f"stage 빈 행 {blank} — 렌더 중단"
```

사이드바 단계 집계가 DB 분포와 일치하는지 · 최신 소식 카드가 돌아왔는지를 확인했다.

## 4. 재발 방지

수동 재렌더 · 배포 절차에 아래 셋을 넣는다 (런북 `2026-07-19-enrich-only-pass.md` §4 에 반영).

1. **배포 전 사전 점검** — `git pull` 로 새 커밋이 들어왔으면 그 트랙이 기존 데이터를 다시 채우고 있는지 확인한다.
`ps aux | grep bullet_in` 로 돌고 있는 배치가 없는지 본다.
2. **렌더 입력 가드** — 단계가 빈 행이 있으면 렌더를 중단한다.
집계 · 표시가 단계에 걸려 있어 빈 값은 곧 잘못된 화면이 된다.
3. **급하지 않으면 자동 회차에 맡긴다** — 정기 회차가 렌더 · 배포까지 하므로, 확인 목적의 수동 배포는 대개 불필요하다.

## 5. 교훈

- 병렬 세션이 있는 동안 공유 자원 (VM · DB · 배포) 을 건드릴 때는 자기 변경이 아니라 **저장소 전체의 진행 상태**를 봐야 한다.
- 기존 데이터를 옮기거나 다시 채우는 작업은 "완료" 와 "진행 중" 사이에 화면이 깨져 보이는 중간 상태가 있다.
그 구간은 짧아서 (이번엔 7분) 우연히 겹치기 쉽다.
- 트랙 현황판의 병렬 규칙 (공유 자원의 대량 호출 · 배포는 시작 전에 알린다) 은 이 사고를 정확히 겨냥하고 있었다.
