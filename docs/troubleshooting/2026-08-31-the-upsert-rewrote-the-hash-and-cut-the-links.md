# 적재가 기사 신원을 갈아 치우고 선수 연결을 끊고 있었다 (2026-08-31)

기사와 선수를 잇는 `article_players` 에 가리키는 기사가 없는 짝이 259쌍 쌓여 있었다.
원인을 코드에서 확정하고 고쳤다.
dbt 품질 게이트를 세운 배포의 첫 회차에서 찾아냈다.

## 1. 증상

`article_players` 의 259쌍이 어느 기사도 안 가리켰다 (기사 76건 몫).
추출 시각은 2026-08-12 부터 2026-08-30 까지 흩어져 있어 한 번의 사고가 아니라 계속 쌓이는 것으로 보였다.

이 부채를 지우고 0에서 시작한 뒤 **한 회차 만에 2쌍이 다시 생겼다.**

```
INFO dbt 게이트 경고 1건 — relationships_stg_article_players_content_hash… 2행
INFO dbt 게이트 통과 — 차단 0 · 경고 1
```

## 2. 처음 세운 가정이 틀렸다

「기사가 지워져서 귀속이 남았다」 고 보았다.
기사를 지우는 코드는 주소 신원 이전 배치 하나뿐인데 그 배치는 회차에서 안 돈다.

실측이 가정을 뒤집었다.

| 재는 것 | 값 |
| --- | --- |
| 기사 총수 | 954 → **956** (늘었다) |
| 고아가 된 귀속 | 알바레스 · 마르티넬리 각 1 |
| 마르티넬리 기사 생성 | 2026-08-30 15:04:50 |
| 그 기사에 귀속이 붙은 시각 | 2026-08-30 15:05:05 |

**그 귀속은 기사가 만들어지고 15초 뒤에 붙었는데 지금 고아이고 기사는 살아 있다.**
삭제 때문이 아니다.

## 3. 원인

`content_hash` 는 원문 제목과 정규화된 주소로 만들어진다.
그래서 원문 제목이 바뀌면 해시도 바뀐다.

`articles` 는 `content_hash` 와 `url` 을 **둘 다 UNIQUE** 로 걸어 두었다.
같은 주소에 다른 해시가 들어오면 `MartStore.upsert` 의 `ON DUPLICATE KEY UPDATE` 가 `url` 로 기존 행을 찾아낸다.
그 구문의 마지막 줄이 이것이었다.

```sql
content_hash=VALUES(content_hash)
```

**기사 행은 살아남고 신원만 새 값으로 갈린다.**
그 해시를 가리키던 `article_players` 는 그 자리에서 전부 고아가 된다.

### 3.1. 절반은 이미 알고 있던 자리다

같은 구문에 이런 줄이 있다.

```sql
title_ko=IF(articles.content_hash=VALUES(content_hash), articles.title_ko, NULL)
```

해시가 달라지면 번역을 지워 다시 만들게 한다.
**번역은 새 신원을 따라가게 만들어 두었는데 선수 귀속은 안 옮겼다.**

## 4. 해시가 갈리는 계기는 트윗 본문이다

고아가 된 둘 다 X 트윗이었다.
같은 트윗이 어떤 회차엔 이렇게, 어떤 회차엔 저렇게 읽히면 원문 제목이 달라지고 해시가 갈린다.

**해시는 두 값 사이를 왕복한다.**
고침을 배포한 뒤 회차에서 갈린 두 기사의 새 해시가 **직전에 고아였던 귀속이 가리키던 바로 그 값**이었다.

```
1a21f0d6… → 09f700c8…   (고아였던 알바레스 귀속의 해시)
551d34fe… → 919c19fb…   (고아였던 마르티넬리 귀속의 해시)
```

그래서 고아 2쌍이 지워진 것이 아니라 **되살아났다** — 기사가 옛 해시로 돌아오자 그 귀속이 다시 유효해졌다.

> **지우기 전에 그 해시가 돌아올 수 있는지 본다.**
> 「남은 2쌍을 지우자」 는 계획을 실행했다면 멀쩡한 귀속을 버릴 뻔했다.

## 5. 고침

`upsert` 는 INSERT 를 실행하기 **전에** 같은 트랜잭션 안에서 그 주소에 저장돼 있던 해시를 조회한다.
해시가 달라졌으면 그 짝의 참조를 먼저 옮긴다.

- **순서를 바꾸면 안 된다** — 행을 먼저 갱신하면 옛 해시를 되찾을 방법이 없다.
- 참조를 옮기는 규칙은 `storage/mariadb.py` 의 `move_hash_refs` 한 곳에 두고 주소 신원 이전 배치가 이 함수를 부른다.
  두 벌로 두면 한쪽만 고쳐진다.
- 같은 선수가 옛 해시와 새 해시 양쪽에 있으면 `UPDATE IGNORE` 가 건너뛰고 뒤이은 `DELETE` 가 옛 행을 지운다.

## 6. 확인

로그만 보면 「안 뜬 것」 이 「코드가 안 돎」 인지 「이번엔 대상이 없었음」 인지 안 갈린다.
그래서 회차 전후로 주소별 해시를 통째로 뽑아 대조했다.

```
INFO 해시가 갈린 기사 2건 — 선수 귀속을 새 해시로 옮김
INFO dbt 게이트 통과 — 차단 0 · 경고 0

기사 수 = 956 → 957
고아 = 2 → 0
해시가 갈린 기사 = 2
```

뽑아서 대조하는 절차는 `docs/runbook/2026-08-31-when-the-dbt-gate-blocks-a-deploy.md` §4 에 있다.

## 7. 남은 것

**해시가 갈리는 것 자체는 안 막았다.**
참조만 안 끊기게 했을 뿐이라 두 가지가 남는다.

- 해시가 갈릴 때마다 번역 네 필드가 NULL 로 밀려 **같은 트윗을 회차마다 다시 번역**한다.
- 상세 페이지 파일명이 해시 기반이라 **그 기사의 주소가 회차마다 바뀐다.**

2026-08-30 트랙은 트윗 펼치기 수정이 이 왕복을 끝낸다고 적었으나 그 예측은 틀렸다.
펼치기는 원문 제목이 260자 이상인 트윗만 손대는데 왕복하는 두 트윗은 75자와 65자다.
**왕복의 원인이 한 갈래가 아니었고 그 수정은 그중 하나만 덮었다.**

## 8. 되짚을 자리

- **부채를 남긴 채 감시를 켜면 새 고장이 소음에 묻힌다.**
  259 위에 쌓였다면 261 이 되는 것을 아무도 못 알아챘다.
  0 에서 시작했기 때문에 2쌍이 곧바로 눈에 띄었다.
- **「고쳤다」 와 「고쳐졌는지 봤다」 는 다른 축이다.**
  하루 전 문서가 이 왕복을 끝냈다고 적어 두었는데 아무도 대 보지 않아 그대로 살아남았다.
- **한 구문 안에서 어떤 참조는 따라가고 어떤 참조는 안 따라갔다.**
  신원이 바뀌는 자리를 고칠 때는 그 신원을 가리키는 곳을 전부 세어야 한다.
