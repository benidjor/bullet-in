# 확정된 설계를 다 만든 뒤에야 방향이 다르다는 것을 알았다 (2026-09-02)

결말 카드를 홈에 되살리는 일은 설계가 이미 끝나 있었다.
규칙 셋이 확정돼 있었고, 운영 데이터에서 결말 카드가 붙는 선수 이야기 14개를 사람이 하나씩 보며 「서야 한다」 11개와 「서면 안 된다」 3개로 갈라 둔 뒤였다.
구현만 남은 작업으로 받아 테스트 10종을 쓰고 화면을 확인한 다음 PR 까지 올렸다.

**그리고 그 PR 은 방향이 달라 닫혔다.**

## 1. 무엇이 어긋났나

설계 기록에는 이렇게 적혀 있었다.

> 결말 카드 (`ending_card`) 는 지금 홈에 안 그려진다 (2026-08-23 결정) 라 함수만 고치면 화면이 안 바뀐다.
> 되살릴 때 배지를 함께 단다.

그대로 만들었다.
대표 카드 아래에 결말 카드 한 장을 더 세우고 행선지 구단 배지를 붙였다.

화면을 본 사용자는 이렇게 말했다.

> 이미지처럼 별도로 기사 밑에 기사를 함께 붙이는 것이 아니라 시간 순서대로 기사가 보여지기를 원했다.
> 결말 부분은 선수 상세 페이지를 눌렀을 때 「진행 단계별 대표 기사」 에서 확인하기 편하게 하려던 것이다.

**「결말을 보여 준다」 는 같았고 「어디에」 가 달랐다.**

## 2. 왜 구현 중에 못 알아챘나

코드를 보면 두 자리가 완전히 갈려 있다.

| 화면 | 함수 | 무엇을 그리나 |
| --- | --- | --- |
| 홈 결말 카드 | `ending_card` | 대표 카드 옆에 한 장 더 |
| 선수 페이지 「진행 단계별 대표 기사」 | `stage_ladder` + `ended_marker` | 단계별 대표 줄 + 무산 종결 줄 |

둘은 서로를 부르지 않는다.
**`ending_card` 를 아무리 고쳐도 선수 페이지는 한 글자도 안 바뀐다.**

설계 기록은 `ending_card` 만 가리켰고 나는 그 이름을 따라갔다.
기록에 **「무엇을 고칠 것인가」 는 있었지만 「왜 그것을 원하는가」 가 없었다.**

목적이 적혀 있었다면 첫 grep 에서 갈렸을 것이다
— 「선수 페이지에서 결말을 보기 편하게」 라고만 했어도 `ending_card` 가 그 페이지와 무관하다는 사실이 바로 걸린다.

## 3. 무엇이 이것을 드러냈나

**목업이다.**

화면을 실제로 렌더해 스크린샷으로 보여 준 순간 어긋남이 드러났다.
그전까지는 테스트 10종이 통과했고 계수도 맞았고 차집합도 설계 예측과 일치했다
— **전부 「내가 만들려던 것」 안에서만 맞는 값이었다.**

## 4. 확인해 보니 진짜 문제는 다른 데 있었다

선수 페이지를 열어 보니 알바레스 페이지의 「진행 단계별 대표 기사」 에 무산 줄이 없었다.
그 선수에게 귀속된 기사 전체에 무산 보도가 11건이나 있는데도 그렇다 (하루치가 아니라 누적이다).

`ended_marker` 가 **명단 뒷받침**을 요구하기 때문이다.
선수 명단 (`players` 표) 의 `transfer_status` 가 종결을 가리켜야만 무산 줄을 그린다는 뜻이다.

```python
b = [e for e in entries if e.get("stage") == "collapsed"]
if not b or transfer_status not in _TERMINAL_BACKING["collapsed"]:
    return None
```

`_TERMINAL_BACKING["collapsed"]` 는 `{"link_dropped", "other_club"}` 인데 알바레스의 `transfer_status` 는 아직 `in_link` 다.
**코드 결함이 아니라 명단 데이터가 보도를 못 따라온 것이다.**

## 5. 이 회차에 잣대가 세 가지로 틀렸다

틀린 종류는 셋이고 실제로 틀린 횟수는 넷이다 — 아래 5.2 를 한 회차에 두 번 밟았다.

### 5.1. 틀린 컬럼을 보고 「0명」 이라고 보고했다

`ended_marker` 가 요구하는 값이 붙은 선수가 몇인지 세면서 `players.status` 를 조회했다.
분포가 `candidate` · `archived` · `confirmed` 뿐이라 **「뒷받침하는 선수 0명」** 이라고 보고했다.

코드가 읽는 것은 `players.transfer_status` 였다.
같은 표에 두 컬럼이 다 있다.
올바른 컬럼으로는 17명이고 가드는 정상 작동한다.

**분포를 다 봤다는 것은 안심할 근거가 못 된다** — 틀린 컬럼의 분포를 다 본 것이기 때문이다.

### 5.2. 숨기는 층이 셋인데 매번 한 층만 봤다

홈 화면에서 결말 카드가 몇 장 서는지를 두 번 틀리게 셌다.

| 놓친 층 | 결과 |
| --- | --- |
| 카드의 `display:none` | 대표 카드가 감춰진 묶음 세 개를 못 셈 (1면에 이미 실린 기사라 아래 목록에서 감춘다 · `band_dup`) |
| 날짜 그룹의 `latestcut` | 「화면에 7」 이 실은 「이전 날짜를 펼치면 7」 이었다 · 첫 화면은 3장 |

**숨기는 층은 셋이다** — 카드 · 블록 · 날짜 그룹.
위 표는 그중 내가 실제로 놓친 둘이고, 블록 층은 이번에 걸리지 않았을 뿐 같은 함정이다.
한 층만 보면 늘 더 크게 센다.

### 5.3. 정렬 축 순서를 잘못 읽고 목업을 그렸다

`pick_representative` 를 「공신력이 앞선다」 로 읽고 그 전제로 목업을 그려 보여 줬다.
정렬 키 튜플의 실제 순서는 이렇다.

```
구단 공식 → 최하 제외 → 아스날 주어 → 최신 날짜 → 본문 → 최신 시각 → 공신력 → 단계
```

축 이름 셋은 뜻이 바로 안 잡히니 풀어 둔다.
「최하 제외」 는 더 높은 등급이 같은 묶음에 있으면 최하 등급을 대표에서 뺀다는 것이고,
「아스날 주어」 는 제목이 「아스날」 로 시작하는 기사를 앞세운다는 것이며,
「본문」 은 트윗처럼 제목뿐인 행보다 본문을 가진 기사를 앞세운다는 것이다.

**공신력은 일곱째다.**
목업에서는 `BBC 01:38` (공신력 최상) 이 대표였는데 실제 코드로는 `Sky Sports 07:00` (공신력 중) 이 대표가 된다.
사용자가 그 목업을 보고 고른 뒤였다.

**독스트링은 처음부터 맞게 적혀 있었다.**
튜플을 눈으로 훑고 「공신력이 앞이겠거니」 하고 넘어간 것이 원인이다
— 그래서 다음부터는 요약이 아니라 **정렬 키를 한 자리씩 세어 본다.**

이것을 잡아낸 것은 문체 점검이다 — 같은 문서 안에서 대표 선정을 세 번 설명했는데 한 곳만 다르다고 짚었다.

## 6. 그래서 무엇을 바꿨나

- **설계 기록에 목적을 적는다** — 「무엇을 고친다」 옆에 「왜 그것을 원하는가」 를 나란히 둔다
   → 이번 기록에는 규칙과 검산 표까지 있었지만 목적이 없어서 그 정교함이 오히려 확신을 줬다
- **화면을 바꾸는 일은 목업을 먼저 보여 준다** — 만든 뒤가 아니라 만들기 전에
   → 절차는 `docs/runbook/2026-09-02-choosing-a-layout-with-real-articles.md`
- **문체 점검을 설계 문서에도 돌린다** — 문체만이 아니라 문서 안의 사실 불일치를 잡는다
