# 「성공률」 이 셋이었고 정작 완주율은 아무도 재지 않았다 (2026-09-11)

소개 자료의 표지 숫자를 갱신하다가 발견했다.
표지에는 「실행 성공률 99.6% · 누적 395회」 가 나란히 있었는데, 99.6% 는 최근 30회 평균이고 395회는 전체 누적이라 두 값의 셈이 달랐다.
그 값을 바로잡으려고 「성공률」 을 다시 세어 보니 이 저장소에는 성공률이라 부를 수 있는 값이 셋이고, 사용자가 실제로 묻는 값 (파이프라인이 끝까지 갔는가) 은 그중에 없었다.

## 1. 증상 — 같은 이름의 값이 셋

수집 현황 화면 (`ops.html`) 과 `pipeline_runs` 표에서 「성공률」 로 읽힐 수 있는 값이 셋이다.

| 값 | 셈 | 2026-09-11 07시 값 |
| --- | --- | --- |
| SLO-2 「Success Rate · 30회」 타일 | 최근 30회의 `success_rate` 평균 | 100.0% |
| `pipeline_runs.success_rate` 전체 평균 | 436행의 평균 | 99.43% |
| 「에러 회차」 | `error_count > 0` 인 회차 수 | 13주 435회 중 21회 |

셋 다 소스 단위 성공을 잰다.
`success_rate` 는 회차마다 「소스 어댑터 중 몇 개가 성공했나」 의 비율이고, `error_count` 는 실패한 어댑터 수다.
에러 회차 21건을 DB 에서 직접 세어 보니 전부 `error_count = 1` 이었다.
소스 하나가 실패한 회차이고 회차 자체는 끝까지 돌았다.

그리고 `pipeline_runs` 에는 완주한 회차만 행이 생긴다.
게이트가 배포를 막았거나 배포 명령이 실패한 회차는 행이 없어 분모에도 들어가지 않는다.
그래서 세 값 어느 것도 「파이프라인이 끝까지 갔는가」 에는 답하지 않는다.

## 2. 완주율은 오케스트레이터 기록으로만 셀 수 있었다

완주는 파이프라인 밖에서 지켜본 기록에만 남는다.
systemd 시절은 저널, Airflow 시절은 실행 목록이다.

```bash
# systemd 시절 (저널이 2026-05-21 부터 남아 있다) — 시작 · 완료 · 실패 수
J() { journalctl -u bullet-in.service --no-pager -q -o short-iso; }
J | grep -c "Starting bullet-in.service"    # 358 (2026-07-20 09:01 KST 부터 09-04 15:04 까지)
J | grep -c "Finished bullet-in.service"    # 354
J | grep -c "Failed with result"            # 4

# Airflow 시절 — run_id 접두어와 상태로 집계
set -a; . ~/airflow/airflow.env; set +a
PYTHONWARNINGS=ignore ~/airflow-venv/bin/airflow dags list-runs bullet_in_cycle -o json \
  | python3 -c "import sys,json; s=sys.stdin.read(); r=json.loads(s[s.index('['):]); \
from collections import Counter; print(Counter((x['run_id'].split('__')[0], x['state']) for x in r))"
# Counter({('scheduled', 'success'): 54, ('manual', 'success'): 5})
```

둘을 합치면 417회 시작에 413회 완주, 99.0% 다.
실패 4건은 전부 뒷단계에서 났다.

| 시각 (KST) | 원인 |
| --- | --- |
| 07-31 21:05 | Cloudflare Pages 배포 명령 (wrangler) 실패 |
| 08-31 21:05 | dbt 품질 게이트, 종료 코드 -11 (세그멘테이션 오류) |
| 09-01 09:03 | dbt 품질 게이트, 종료 코드 -7 |
| 09-03 03:06 | dbt 품질 게이트, 종료 코드 -11 |

넷 중 셋은 안건 2ν 의 관측 셋과 같은 사건이다.
소스 수집 성공률로는 이 넷이 하나도 안 보인다.

06-16 부터 07-19 까지의 회차는 유닛 로그가 없어 완주율 창에서 빠진다.
그래서 `pipeline_runs` 의 436행과 완주율의 417회는 창이 다르다.

## 3. 원인 — 「성공률」 에 셈이 붙어 있지 않았다

- 화면의 타일 이름이 「Success Rate」 뿐이라 무엇의 성공률인지 읽는 사람이 채워 넣는다.
- 표지에는 최근 30회 값을 적고 옆에 누적 회차 수를 붙여 두 셈을 한 줄에 섞었다.
- 완주 여부는 제품 어디에도 지표로 없다.
  judge 태스크가 회차마다 반영 여부를 판정하지만 그 결과를 세는 화면이 없다.

## 4. 처방

- 소개 자료의 표지는 완주율 (413/417 · 07.20 부터 · 09.11 기준) 로 바꾸고, 소스 수집 성공률 99.4% 는 SLO-2 로 따로 적었다.
- 「성공률」 을 적을 때는 단위 (소스 · 회차) · 창 (최근 30회 · 누적) · 분모 (완주한 회차만인가) 셋을 함께 적는다.
- 안건 후보로 남긴다.
  수집 현황 화면에 「완주율 · 최근 N회」 타일을 두면 이 질문에 화면이 답한다.
  데이터원은 Airflow 실행 목록이나 judge 의 판정 기록이고, `pipeline_runs` 로는 셀 수 없다.

## 5. 배운 것

- **같은 이름의 값이 여럿이면 그중 하나가 아니라 셈이 문제다.** 어느 값이 맞느냐를 고르기 전에 각 값의 단위 · 창 · 분모를 적으면 셋이 서로 다른 질문에 답하고 있다는 것이 보인다.
- **완주한 것만 기록하는 표로는 완주율을 못 센다.** 실패한 회차는 그 표에 없으므로 분모는 표 밖 (저널 · 오케스트레이터) 에서 와야 한다.
- **대시보드에 없는 값은 물어봐야 드러난다.** 이번에는 소개 자료를 읽는 사람의 질문 (「초반 단계 성공률을 표시하는 것이 맞나」) 이 그 자리를 짚었다.
