# 검사가 실패했는데 push 와 PR 생성이 실행됐다 (2026-10-08)

- **영역**: 작업 절차 (AI 세션의 셸 실행 · PR 게시)
- **관련 PR**: #538
- **고친 것**: 게시된 PR 본문 교체 · 작업 메모의 잘못된 진단 정정 · 이 문서
- **남은 일**: 없음

## 1. 증상

PR #538 을 게시할 때 세션은 「PR 본문 검사 → push → PR 생성」 을 셸 실행 한 번으로 묶었다.
맨 앞에 `set -euo pipefail` 을 두어 검사가 실패하면 뒤 단계가 실행되지 않게 하려 했다.

검사기 (`.claude/tools/check-pr-format.py --body`) 는 위반 19건을 출력했다.
서술형 종결 4건 · 라벨 없는 불릿 12건 · 범위 물결표 3건이었다.
그런데 push 와 `gh pr create` 가 그대로 실행돼 위반 19건이 남은 본문으로 PR 이 만들어졌다.

같은 날 저장소 밖의 다른 작업에서도 같은 일이 한 번 더 있었다.
치환 스크립트가 개수 검사에 실패해 아무것도 쓰지 않고 끝났는데 같은 실행에 묶인 백업과 빌드가 계속 진행됐다.
쓰인 것이 없어서 피해는 없었다.

## 2. 처음 내린 진단은 틀렸다

세션은 처음에 「검사기가 위반이 있어도 종료 코드 0 을 낸다」 고 판단하고 작업 메모에 그렇게 적었다.
검사기 코드를 읽지 않고 묶음이 멈추지 않았다는 결과만 보고 내린 결론이었다.

코드를 열어 보니 검사기는 위반이 있으면 1 을 돌려준다.

```python
# .claude/tools/check-pr-format.py
    print(f"\n{len(hits)}건 — 이 검사가 안 보는 것은 파일 머리 주석에 있다.")
    return 1 if hits else 0
```

직접 실행해 봐도 결과는 같았다.

```bash
python3 .claude/tools/check-pr-format.py --body 위반본.md > /dev/null; echo $?   # 1
python3 .claude/tools/check-pr-format.py --body 정상본.md > /dev/null; echo $?   # 0
```

## 3. 원인 — 세션의 셸 실행 도구에서 `set -e` 가 듣지 않는다

Claude Code 의 Bash 도구 안에서 `set -e` 를 시험했다.

```bash
set -e; false; echo "이 줄이 보이면 set -e 가 무시된다"
# → 「이 줄이 보이면 set -e 가 무시된다」 가 출력된다
setopt | grep errexit
# → errexit (옵션 자체는 켜져 있다)
```

옵션은 켜지지만 실패한 명령 뒤에도 다음 줄이 실행된다.
별도로 띄운 셸 (`zsh -c 'set -e; false; echo …'`) 안에서는 정상적으로 멈춘다.
도구가 명령을 조건문 안의 `eval` 로 감싸 실행하고, zsh 는 그런 자리에서 `errexit` 를 적용하지 않는 것으로 보인다.
출력에 남은 `(eval):1:` 흔적이 그 근거다.
도구 내부 구현은 확인하지 못했다.

그래서 검사기는 제대로 1 을 돌려줬는데도 묶음이 그 실패를 보지 못했다.

## 4. 해결

- 고친 본문을 `gh pr edit 538 --body-file` 로 교체했다.
- 게시된 본문을 `gh pr view 538 --json body -q .body` 로 다시 받아 검사기에 넣었고 0건을 확인했다.
- 작업 메모의 「검사기가 0 을 낸다」 는 진단을 지우고 위 원인으로 고쳤다.

## 5. 예방

세션이 셸 한 번으로 여러 단계를 묶을 때는 `set -e` 에 기대지 않는다.
아래 세 방법은 이 도구 안에서 실제로 멈춘다는 것을 2026-10-08 에 확인했다.

```bash
python3 .claude/tools/check-pr-format.py --body pr_body.md || exit 1   # 실패하면 여기서 끝
검사 && git push && gh pr create …                                    # 앞이 실패하면 뒤를 건너뜀
zsh -c 'set -euo pipefail; 검사; git push; gh pr create …'              # 별도 셸 안에서는 set -e 가 듣는다
```

게시 뒤에는 GitHub 에 올라간 본문을 다시 받아 한 번 더 검사한다.
로컬 파일을 검사했어도 실제로 올린 것이 그 파일인지는 따로 확인해야 한다.

## 6. 교훈

- 묶음이 멈추지 않았을 때 앞 단계의 종료 코드부터 의심했지만 실제로는 묶는 장치가 고장이었다.
  두 가지를 가르는 비용은 `echo $?` 한 줄이었다.
- 「도구가 이렇게 동작한다」 는 진단은 그 도구의 코드나 실측으로 확인한 뒤에 적는다.
  틀린 진단을 메모에 남기면 다음 세션은 멀쩡한 검사기를 고치는 일부터 시작하게 된다.
