# 덱 문장 셋이 코드와 어긋났고, 메모리에서 옮긴 수 둘은 셈법이 없었다 (2026-09-17)

소개 자료 14 ~ 20장을 두 번째로 검토한 회차다.
문장은 그대로 두고 강조와 낱말만 고치는 일이라 여겼는데, 코드와 어긋난 문장 셋과 근거를 다시 만들 수 없는 수 둘이 나왔다.
둘 다 09-15 의 「그림은 문장을 검증한다」 와 09-06 의 「값은 저장소나 실측에 닿아야 한다」 의 연장이고, 이번에는 그림이 아니라 검토 질문이 어긋남을 드러냈다.

## 1. 문장 셋이 코드와 달랐다

### 1.1. 「불일치면 롤백」 은 코드가 하지 않는 일이다

15장 해결 절에 「게이트 실패, 배포 실패, 불일치면 이전 커밋으로 롤백」 이라 적혀 있었고, 옆 흐름도의 빨간 상자도 「실패 · 불일치 → 롤백」 이었다.
검토 질문 「롤백 알림은 어느 채널로 가나」 에 답하려고 `src/bullet_in/deploy.py` 의 `judge` 를 열었다.
라이브 표지 불일치는 스펙의 F7 「배포는 성공인데 라이브가 안 바뀜」 이고, 코드는 이것을 「코드 탓이 아닐 수 있다」 로 두어 되돌리지 않고 사고 채널에 알리기만 한다.
같은 함수에서 롤백 알림은 `incident=True` 라 사고 채널이고, 리뷰 채널로 가는 것은 「반영 완료」 와 「판정 보류」 뿐이다.
그러니 「불일치면 롤백」 과 「롤백 + 리뷰 채널 알림」 둘 다 틀렸다.

이 문장은 두 번의 통독을 지나갔다.
「실패하면 롤백」 은 자연스러운 문장이라 읽는 사람이 멈추지 않는다.
스펙이 F7 을 따로 떼어 「되돌리지 않음」 으로 둔 이유가 덱에는 없었다.

### 1.2. 「파이프라인 태스크 6」 은 산수였다

흐름도 가운데 상자에 「② 파이프라인 태스크 6」 이라 적혀 있었다.
태스크 8개에서 Advance 와 Judge 를 뺀 수다.
DAG 의 의존 관계 두 줄을 보면 Advance 와 Judge 사이의 직렬 태스크는 collect · enrich · publish · gate · deploy_site 다섯이고, 여덟째 warehouse_load 는 publish 에서 갈라져 병렬로 돈다.
상자 하나가 의존 관계 두 줄을 검증한 셈이다.

### 1.3. 「태스크 8개로 분해」 는 DAG 가 여덟 개로 읽혔다

16장 요약 띠의 「태스크 8개로 분해」 를 사용자가 「DAG 가 8개가 되었다는 뜻인가」 로 읽었다.
DAG 는 하나고 그 안의 태스크가 여덟이다.
「Airflow DAG 내부 태스크 8개로 분해」 로 고쳤다.
틀린 문장은 아니었지만, 도구의 단위 (DAG · 태스크) 를 모르는 독자에게는 두 뜻으로 읽혔다.

## 2. 수 둘은 셈법이 없어 다시 만들 수 없었다

### 2.1. 「판정 18회」

15장과 20장에 「판정 18회 · 롤백 0」 이 「09-06 실측」 이라는 꼬리표와 함께 있었다.
오늘 Airflow 의 judge 태스크 로그 110개에서 「반영 완료」 가 든 run 을 세니 14 였고, 롤백 · 보류 · 불일치는 0 이었다.
09-04 에 Airflow 로 옮긴 뒤의 판정이 09-17 에 14 인데 09-06 에 18 일 수는 없으므로, 09-06 의 18 은 systemd 시절 판정을 함께 센 것으로 보인다.
그러나 그때의 셈법이 메모리에 없어 확인할 길이 없다.
덱에는 오늘 값 14 를 셈법과 함께 적었다.

### 2.2. 「7개 모델」

19장에 co-author 로 적힌 모델이 「7개」 라 되어 있었다.
커밋 메시지의 트레일러에서 모델 이름을 모아 보니 9종이었다.
09-06 의 7 이 어떤 기준이었는지도 기록이 없다.
같은 자리에서 트레일러 대소문자 함정이 하나 더 나왔다.
`Co-Authored-By` 를 대소문자 그대로 세면 282 커밋인데, GitHub 의 squash merge 가 트레일러를 `Co-authored-by` 로 다시 쓰기 때문에 대소문자를 무시해야 592 가 된다.
잣대에서 빠지기 쉬운 자리 목록 (단위 · 층 · 범위 · 낱말 · 시간대 · 타입) 에 대소문자를 더한다.

### 2.3. 「AI 협업 트러블슈팅 18편」 은 기준을 정해 다시 셌다

이 수도 09-06 값이었고 기준이 없었다.
「AI 세션 · subagent · 계획서 · 지시 · co-author 표기 때문에 생긴 문제」 를 기준으로 후보 31편의 첫 문단을 읽어 21편을 골랐다.
09-06 에 쓴 세 편을 빼면 18 이라 그때의 수와 맞는다.
파일명 키워드 grep 도 우연히 21 을 냈지만 구성이 달랐다.
grep 은 제품 프롬프트 문서 넷을 넣고 09-06 의 셋을 빠뜨렸다.
대리 지표로 센 수가 맞아 보여도 목록을 대 봐야 한다.
기준과 목록은 소개 자료 조립 폴더의 리뷰 목록 파일에 적어 두었다.

## 3. 목업과 그림에서 밟은 것

- **목업 머리가 인라인 스타일을 몰랐다.**
  ① ② ③ 앞의 화살표를 지우는 규칙이 덱의 공통 스타일이 아니라 4장 안의 인라인 `<style>` 에 있었다.
  덱에서는 그 규칙이 다른 장으로 새어 나가 정상으로 보였고, 목업에서만 화살표가 찍혔다.
  09-11 의 「인라인 SVG 의 스타일은 문서 전체로 샌다」 와 같은 뿌리다.
  목업 머리에 그 규칙을 보강했다.
- **목업 파일을 조각으로 되돌리며 구분선을 딸려 넣었다.**
  목업은 `</body>` 까지가 한 덩어리라 다음 장의 구분선 주석이 붙어 있다.
  그대로 조각에 넣자 구분선이 겹쳐 조립기가 id 없는 블록에서 멈췄다.
  조립기가 멈춘 덕에 잘못된 덱은 만들어지지 않았다.
  되돌릴 때는 조각 쪽 기준으로 다음 구분선 앞까지만 자른다.
- **SVG 상자가 영역 끝에 닿으면 테두리 바깥 절반이 잘린다.**
  15장 흐름도의 Judge 상자와 빨간 상자의 오른쪽 변이 viewBox 끝 x=560 에 정확히 닿아 있어 오른쪽 테두리만 얇아 보였다.
  겹침 검사기는 글자와 선의 겹침만 보므로 이것을 못 잡는다.
  svg 에 `overflow:visible` 을 주어 풀었다.
- **같은 값이 그림 안에도 있었다.**
  「18편」 이 타일 · 본문 · 도식 세 곳에 있었는데 치환은 두 곳만 잡았다.
  값을 바꿀 때는 SVG 텍스트까지 grep 한다.
- **요약 띠는 낱말 하나에도 접힌다.**
  16장 띠에 「Airflow」 를 넣자 두 줄이 되었고, 「단일 프로세스로 돌던」 으로 바꾸자 또 접혔다.
  띠 높이를 재는 도구를 두고 띠를 고칠 때마다 돌렸다.
- **두 줄을 「+」 로 합쳐도 글자 수가 그대로면 높이가 안 준다.**
  접히는 자리만 바뀌고 낱말 하나가 둘째 줄에 남는다.
  겹치는 낱말 (「파이프라인」 이 두 번) 을 같이 걷어내야 한 줄이 된다.
  한 줄인지는 캡처를 다시 보는 대신 항목 높이 (한 줄 20px) 로 잰다.
