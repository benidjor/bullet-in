# fmkorea 소급 백필 실행 절차 (검색 페이징)

fmkorea 수집이 며칠 끊긴 뒤 (IP 차단 · 터널 장애 등) 놓친 글을 복원할 때 쓴다.
정기 회차는 검색 1페이지만 읽으므로, 공백 기간의 글은 페이지 밖으로 밀려나 다시 닿지 않는다
— 이 절차는 여러 페이지를 읽되 이미 적재된 제목을 배제해 신규분만 받아온다.
첫 실행 (2026-07-25 · 차단 기간 07-19 ~ 07-23 복원) 의 실측을 함께 남긴다.

## 사전 확인

- 맥 릴레이가 살아 있어야 한다 (백필도 프록시를 탄다).
  맥에서 `launchctl list | grep com.bulletin` — tunnel 항목에 PID 가 있으면 1차 통과.
- PID · 포트 확인만으로는 부족하다 — 맥이 잠들었다 깨면 VM 쪽 리스너만 남고 실통신이 죽은 상태가 있다
  (2026-07-25 실측: 선체크 통과 후 "All connection attempts failed").
  실통신은 VM 에서 fmkorea 가 아닌 대상으로 확인한다:
  `curl -s --socks5-hostname 127.0.0.1:1080 https://ifconfig.me` → 주거 IP 가 나와야 정상.
  죽어 있으면 맥에서 `launchctl kickstart -k gui/$(id -u)/com.bulletin.fmkorea-tunnel` 후 재확인.
- 직전 fmkorea 접촉에서 3시간이 지났는지 확인한다 (`~/.bullet-in/fmkorea_last_contact` · DB 워터마크 중 최신).
  감독하에 dry-run → 소규모 → 전체를 연달아 돌리는 것은 한 회차 묶음으로 취급하고 `--force` 로 잇는다.
- 시작 시점은 정기 회차 직후 (KST 0x:02 완료 후 10분 안팎) 로 잡는다
  — 다음 회차까지 약 3시간이 비어 정기 접촉과 겹치지 않고, 배제 집합도 최신이다.
- 단시간 반복 접촉 주의: 2026-07-25 실측에서 dry-run (검색 9요청 · 전부 200) 직후
  몇 분 안에 재실행하자 3요청 전부 430 을 받았다. 한 번 실행했으면 결과를 다 쓰고, 재실행은 충분히 띄운다.

## 키워드 선택

config 키워드는 그대로 쓰지 않는 편이 낫다.
`온스테인` · `"de roche"` 는 본문 포함 검색 (title_content) 이라 타 구단 완결 딜 · 옛 분석 글이 대량 딸려 오고,
라운드로빈 배분이 복원 목표인 글을 뒤로 밀어낸다 (2026-07-25 실측 — 차단 기간 글이 전역 50번대로 밀림).

- 공백 기간 복원: `--keyword 아스날` (제목 검색 3페이지가 약 1주 커버 — 실측 2페이지에 07-18 도달).
- 링크 선수 글 (제목에 아스날 없음): 활성 링크 선수명을 `--keyword` 로 추가.
  완료된 딜의 선수는 넣지 않는다 (새 소속팀 뉴스만 딸려 온다).
  선수 리스트의 시스템화는 워치리스트 트랙 (spec 2026-07-04 §미해결) 소관 — 여기서는 수동 소수만.

## 접촉 예산 (실행 전 계산)

| 단계 | fmkorea 요청 | 비고 |
|---|---|---|
| dry-run | 검색 = 키워드 수 × 페이지 수 | 글 본문 0 · DB 데이터 미기록 |
| `--limit 5` | 검색 + 본문 5 | 원문 사이트 요청 최대 5 별도 |
| 전체 | 검색 + 신규 후보 수 (상한 60) | dry-run 실측으로 확정 |

요청 간격은 `REQUEST_GAP_SEC = 1.5` 초로 자동 적용된다 (검색 페이지 사이 · 글 사이).

## 절차

VM (운영 SoT) 에서 실행한다.
**모든 실행은 출력을 파일로 남긴다** (`2>&1 | tee /tmp/backfill-<단계>.log`)
— 출력이 잘려도 재실행하지 않기 위함이다. 재실행 = 재접촉이고, 단시간 재접촉은 430 을 부른다
(2026-07-25 실측 2회: 성공 직후 몇 분 내 재실행 → 즉시 430 · 해제까지 2시간 이상).
수치가 잘렸으면 근사치로 기록한다 — 정확한 수치는 재접촉의 이유가 되지 않는다.

매 명령 공통 접두:

```bash
ssh -i ~/.ssh/seoulnow_deploy ubuntu@155.248.164.17 \
  'bash -lc "cd /home/ubuntu/bullet-in && set -a && source .env && set +a && export FMKOREA_PROXY=socks5://127.0.0.1:1080 && <명령>"'
```

1. **dry-run 실측** — 후보 규모 · 커버 기간 확인:

```bash
uv run python -m bullet_in.backfill_fmkorea --pages 3 --dry-run --force \
  --keyword 아스날 --keyword <선수1> --keyword <선수2>
```

확인: 신규 후보 수 · 후보가 공백 기간을 덮는지 · 이미 적재된 글이 안 섞였는지.
후보 목록이 공백 기간보다 과거까지 닿으면 페이지 수는 충분하다. 부족하면 `--pages` 를 늘려 다시 (재실행 간격 주의).

2. **소규모 적용** — `--limit 5` 를 붙여 실행. "적재 N · 중복 M" 로그와 말머리 · 원문 해소 실패 경고 비율 확인.

3. **멱등 확인** — 2 를 그대로 한 번 더. 방금 적재한 5건이 배제돼 후보에서 빠지고 그다음 신규분이 처리되면 정상 (같은 글 재적재 0).

4. **전체 적용** — `--limit` 없이 실행 (상한 60).

5. **적재 결과 확인** — 발행일 분포로 공백이 채워졌는지:

```sql
SELECT DATE(published_at), COUNT(*) FROM articles
WHERE source_id='fmkorea' AND published_at >= '<공백 시작 - 5일>'
GROUP BY 1 ORDER BY 1;
```

6. **수렴 확인 (다음 정기 회차 후)** — 백필 행은 적재만 되고 번역 · 렌더는 다음 회차가 흡수한다.
   회차 후 `title_ko IS NULL` 인 fmkorea 행이 0 인지 확인하고, 남으면 enrich 만 재실행한다
   (`docs/runbook/2026-07-19-enrich-only-pass.md`).
   백필 행은 과거 발행일 위치로 들어가므로, 렌더 전에 수렴이 끝나야 화면에 번역 전 상태가 노출되지 않는다.

## dry-run 후보를 갈라 보는 법 (2026-09-01 추가)

**dry-run 이 뱉는 후보 수는 「우리가 놓친 글」 이 아니다.**
2026-09-01 실측에서는 후보 27 건이 실제 회수 1 건이었다 (아래 실측 절).
후보를 그대로 보고하면 회수 규모를 크게 부풀린다.

후보는 **어느 단계에서 걸러지느냐**로 가른다.
판정이 도는 순서대로 놓으면 겹치지 않는다.

| 걸러지는 단계 | 갈래 | 이 실행이 새로 회수하나 |
| --- | --- | --- |
| 검색 결과 파싱 | `[공홈]` 말머리 | 아니다 — 본문도 안 받는다 |
| 후보 선별 (**배제 집합을 넘긴 경로만**) | 공백만 다른 기적재 글 | 아니다 — 본문도 안 받는다 |
| 본문을 받은 뒤 저장 판정 | 다른 소스로 이미 있는 글 | 아니다 — **본문은 받는다** |
| 어디에도 안 걸림 | 아직 안 온 글 | 아니다 — 정기 회차가 곧 가져간다 |

두 번째 줄의 단서에 주의한다.
공백 무시 비교는 **`exclude_titles` 를 넘긴 경로에서만** 작동한다 (백필과 보충의 따라잡기 회차).
정기 회차는 이 집합을 일부러 안 넘기므로 (재수집이 본문 등급을 올리는 경로를 살린다) 거기서는 이 갈래가 안 걸러진다.

세 번째 줄이 함정이다.
`--dry-run` 은 후보를 고르는 데서 멈추고 저장할지는 본문을 받은 뒤에 판정한다.
**제목이 DB 에 없다고 해서 그 글이 우리에게 없는 것은 아니다** — 같은 사건 기사가 원문 소스로 들어와 있으면 fmkorea 판은 저장되지 않는다.
첫 번째 줄도 같은 말의 사례다 — 「DB 에 없다」 는 판정 자체가 어느 비교 방식을 쓰느냐에 딸린 값이다.

그래서 회수 규모는 dry-run 수가 아니라 실행 뒤의 `적재 N` 으로 적는다.
적재분 가운데 발행 시각이 직전 회차 뒤인 것은 어차피 들어올 글이라 회수에서 뺀다.

## 2026-09-01 실행 실측 (`[공홈]` drop 이 검색 단계로 옮겨진 뒤)

같은 날 두 번 돌렸고 **두 실행의 후보는 같은 집합이 아니다.**

**① 아침 dry-run** (`--pages 3 --dry-run --force --keyword 아스날 --target title` · 검색 요청 3 회)

- 기존 308 건 배제 · **신규 후보 27 건**.
- 갈라 보니 공백만 다른 기적재 글 5 · `[공홈]` 15 · 나머지 7.

**② 저녁 실행** (같은 인자에 `--limit 15` · 배포된 새 코드 · 검색 요청 3 회)

- **`[공홈]` 15 건이 검색 단계에서 걸러져 본문 요청이 한 번도 안 나갔다** — 고치기 전이라면 15 건을 받아서 버렸을 자리다.
- 본문까지 받은 7 건 → **적재 2 · 동일 내용 생략 0 · 기존 기사 유지 5**.
- 적재 2 건 가운데 하나는 직전 회차 뒤에 올라온 당일 글이라 **실제 회수는 2026-08-19 자 한 건**.
- 430 재발 0.

①의 7 건과 ②의 7 건은 겹치는 것이 여섯이다.
아침 후보에서 가장 최신이던 글은 그날 밤 정기 회차가 문제없이 가져갔고, 저녁에는 그 사이 올라온 다른 글이 그 자리를 채웠다.

## 주의

- 스크립트는 적재까지만 한다 — 번역 · 분류 · 렌더를 여기서 돌리지 않는다 (수렴은 정기 회차).
- `--keyword` 미지정이면 config 키워드를 쓴다 — 앞의 "키워드 선택" 에서 든 이유로 백필에서는 피한다.
- `{page}` 자리표시가 없는 search_url 로 `--pages 2+` 를 주면 스크립트가 실행을 거부한다 (같은 페이지 반복 접촉 방지).
- 제목이 수집 후 수정된 글은 배제를 통과해 한 번 더 받아올 수 있으나, 원문 URL UNIQUE 가 행 중복을 막는다.
- 반대로 과거에 적재한 글과 제목이 완전히 같은 신규 글은 배제에 걸려 건너뛴다
  — 백필에서는 "덜 가져오는 쪽" 오류라 감수한다 (최종 리뷰 지적 · 알려진 한계).
