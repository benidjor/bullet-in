# 한 배포에 두 변경이 실릴 때 각자의 몫을 가른다 (2026-08-13)

병렬 세션이 각각 PR 을 올려 같은 회차에 배포될 때, 화면이 예상과 다르면 어느 변경 탓인지 가리는 절차다.

## 1. 왜 순서만으로는 안 갈리나

**화면 수치는 DB 값이 아니라 렌더가 만드는 수다.**
선수 페이지 개수 · 표시 쌍 · 사다리 줄 · 서빙 건수가 전부 그렇다.
그리고 렌더는 정기 회차에만 돈다 (회차 사이에 렌더만 따로 돌리면 번역 대기 중인 기사가 그대로 배포된다).

그래서 배포를 늦추거나 DB 를 중간에 재는 것으로는 안 갈리는 조합이 생긴다.

| 변경의 성질 | 실물 | DB 를 재면 갈리나 |
| --- | --- | --- |
| 데이터를 바꾼다 | 재추출 · 소급 · 값 정정 | 갈린다 |
| **표시 규칙만 바꾼다** | 배지 가드 · 라벨 · 서빙 필터 | **안 갈린다 — DB 가 그대로다** |

2026-08-13 에 이 조합이 났다.
재추출 (#266 계열) 과 표시 규칙 (#267) 이 같은 렌더에 처음 함께 나타나는데, 뒤엣것은 DB 를 안 바꾸므로 중간에 아무리 재도 두 몫이 안 갈렸다.

## 2. 해법 — 같은 사본에 코드 두 판본을 댄다

Gemini 호출도 DB 쓰기도 없고 운영 렌더도 안 건드린다.

```bash
# 변경 전 · 후 커밋에 detached 워크트리를 하나씩
git worktree add _workspace/<이름>-pre  <변경 전 커밋> --detach
git worktree add _workspace/<이름>-post <변경 후 커밋> --detach
for W in <이름>-pre <이름>-post; do (cd _workspace/$W && uv sync --extra dev -q); done

# 같은 사본에 두 판본을 대고 같은 지표 함수를 돌린다
PROJ=$B/<이름>-pre  MARIADB_URL=".../<사본>" uv run --project $B/<이름>-pre  python 지표.py A
PROJ=$B/<이름>-post MARIADB_URL=".../<사본>" uv run --project $B/<이름>-post python 지표.py B
```

지표 스크립트는 렌더 산출물을 만들지 않고 같은 함수로 수만 센다.

```python
from bullet_in.run import SERVING_SELECT_SQL, LINKED_HASHES_SQL, serving_rows
from bullet_in.serve.render import load_page_players, build_player_entries
served, hidden = serving_rows(rows, relevance_terms=[...], player_names=..., linked=linked)
entries = build_player_entries(served, load_page_players(eng))
print(len(entries), sum(e["count"] for e in entries),
      sum(len(e["ladder"]) for e in entries), len(served))
```

**사본은 하나만 쓴다** — 두 판본에 같은 데이터를 먹여야 차이가 코드 몫만 남는다.

## 3. 판독

```
A = 변경 전 코드 · 지금 데이터      → 데이터 변경만의 몫
B = 변경 후 코드 · 지금 데이터      → 다음 렌더의 예측값
B − A                               → 표시 규칙 변경의 순수 효과
```

- **B 가 실측과 맞으면 판독이 끝난다.** 뺄셈이 필요 없다.
- **어긋나면 그 자체가 신호다** — 그 회차가 새로 넣은 기사이거나, 변경이 예상과 다르게 도는 것이다.
2026-08-13 에 실측이 674 이고 B 가 672 였는데, 원인이 측정 시점 (세 시간 뒤 렌더) 이라는 것을 B 가 있어서 바로 짚었다.
- **데이터 변경 쪽이 0 이면 가장 깨끗하다** — 그 경우 다음 렌더의 차이 전부가 표시 규칙 몫이다.
2026-08-13 의 공홈 8건 재추출이 그랬다 (10행 전부 전후 동일).

**전후로 두 번 재면 데이터 변경의 몫도 확인된다.**
데이터를 바꾸기 전에 A · B 를 한 번, 바꾼 뒤에 한 번 재면 네 값이 나온다.
그때 A 와 B 가 각각 전후로 같으면 **데이터 변경이 화면에 0 이라는 것을 두 판본 · 두 시점으로 확인**한 것이다.

## 4. 함정

- **워크트리를 `uv run --project` 로 고정한다.**
셸 작업 디렉터리는 도중에 되돌아갈 수 있고, 그러면 메인 체크아웃의 **다른 브랜치 코드**로 재게 된다.
2026-08-13 에 실제로 겪었다 — 메인 체크아웃이 옛 기능 브랜치에 있어 존재하지 않는 함수를 인용할 뻔했다.
`cd` 로 옮겼다고 믿지 말고 `PROJ` 와 `--project` 를 명시한다.
- **절대 건수를 넘기지 말고 예측값과 함께 넘긴다.**
받는 쪽이 「646 이 나왔나」 로 판정하면 무관한 신규 기사 한 건에 실패로 읽힌다.
넘길 것은 **B (예측값)** 와 **B − A (그 변경의 몫)** 이고, 절대값은 잰 시점을 함께 적는다.
무엇을 어떤 형태로 넘기는지는 `docs/runbook/2026-08-13-handing-a-display-change-to-the-deploying-session.md` 가 정본이다.
- **건수를 넘길 때 어느 집합인지 함께 적는다.**
같은 이름의 수치가 술어에 따라 갈린다 — 2026-08-13 에 「명단이 완료인데 선수 축이 종결인 행」 이 한쪽은 9명 · 12건, 다른 쪽은 11명 · 14건이었다.
차이는 선수 페이지 술어를 거쳤는지였다.
- **detached 워크트리는 쓰고 나면 치운다** (`git worktree remove --force`).
판독이 끝나면 남길 이유가 없다.

## 5. 언제 이 절차 대신 순서를 바꾸나

배포를 회차 뒤로 미룰 수 있으면 그쪽이 더 간단하다.
**이 절차는 뒤로 못 미룰 때의 대안**이고, 미룬 경우에도 예측값을 미리 갖는 값이 있다.

2026-08-13 에 실제로 미룬 사례가 있다 — 재번역 · 신규 적재 · 표시 규칙이 한 회차에 겹칠 뻔해 표시 규칙을 다음 회차로 넘겼다.
회차 직전에 배포할지 뒤로 미룰지의 판단 기준은 `docs/runbook/2026-07-20-vm-cohost-bootstrap.md` §6.1 계열에 정리되고 있다 (별도 회차).
