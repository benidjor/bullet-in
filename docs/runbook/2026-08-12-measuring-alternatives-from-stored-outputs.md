# 저장된 판본 출력으로 대안 산출 방식을 재는 절차 (2026-08-12)

프롬프트 문구 탐색이 막혔을 때, **Gemini 를 다시 부르지 않고** 대안 설계를 재는 방법이다.
2026-08-12 역할 값 개정에서 문안 3판이 시소로 끝난 뒤 이 절차로 규칙 산출안을 찾았고, 추가 호출 0회로 후보 8종을 비교했다.

## 1. 언제 쓰나

- 문구 탐색을 중단했고 (시소 2판) 다른 산출 방식을 검토해야 할 때.
- 판정에 쓸 재료가 **이미 저장된 출력 안에 있을 때** — 모델이 낸 이름 표기 · 단계 · 목록 같은 것.
- 새 방식이 모델 호출을 늘리지 않고 후처리로 성립할 가능성이 있을 때.

## 2. 전제 — dry-run 이 원 출력을 남겼을 것

`2026-08-07-extraction-prompt-dryrun-measurement.md` 절차를 따랐다면 판본별 결과가 파일로 남아 있다.
그 파일이 이 절차의 재료다.
**결과를 채점 요약만 남기고 버리면 이 길이 막힌다** — 원 출력을 그대로 저장하는 이유가 여기에도 있다.

## 3. 절차

### 3.1. 기대값은 그대로 쓴다

호출 전에 박아 둔 `expected.json` 을 재사용한다.
새 잣대를 만들면 문안 판본과 대안을 같은 자로 못 잰다.

### 3.2. 채점기를 분리해 짠다

하네스 (호출) 와 채점기 (판정) 를 나눠, 채점기가 **저장된 출력만 입력으로 받게** 한다.

```
result_v0_r2.json   → 산출 방식의 입력 (모델이 낸 항목)
result_v1_r1.json   → 필요하면 보조 입력 (예: 거부권)
expected.json       → 잣대
```

### 3.3. 후보를 여러 개 한 번에 잰다

호출이 없으므로 변형을 늘리는 비용이 사실상 0 이다.
2026-08-12 에는 재료 조합 5종 · 거부권 유무 · 임계값 4단을 돌렸고 몇 초씩 걸렸다.

**변형을 표로 나란히 찍는다.**
한 줄에 하나씩 보면 어느 요소가 기여하는지 안 보인다.

### 3.4. 기여가 0 인 요소는 뺀다

이 절차의 가장 큰 소득이 이것이다.
2026-08-12 에는 한글 유사도 폴백을 넣어 뒀는데, 명단 표기를 재료로 쓰면 **임계값을 0.5 까지 낮춰도 결과가 같았다.**
호출이 없으니 이런 확인이 공짜다 — 그대로 뒀으면 쓰이지 않는 코드가 남았을 것이다.

## 4. 순환 위험과 대조법

**직접 만든 라벨로 직접 만든 규칙을 재면 수치가 부풀 수 있다.**
2026-08-12 의 라벨은 본문 구조 (소제목 · 등장 문단) 로 붙였고, 뒤이어 잰 규칙도 같은 구조를 본다.

- **다른 사람 · 다른 세션이 라벨을 준 행을 따로 채점한다.**
이번에는 병렬 트랙이 인계한 5건 (20쌍) 만 떼어 재서 19/20 을 얻었고, 그 수치를 전체와 나란히 적었다.
- 그런 행이 없으면 라벨을 만든 근거와 규칙이 보는 근거가 다른 표본을 골라 낸다.
- **순환 위험을 문서에 적는다.** 수치만 적으면 다음 사람이 그대로 믿는다.

## 5. 함정

- **분모가 무엇인지 밝힌다.**
채점기가 "추출이 못 뽑은 인물" 을 건너뛰면 그만큼 분모에서 빠진다.
그 수치는 후처리 방식의 정확도이지 종단 정확도가 아니다.
- **개선의 경로를 확인한다.**
어떤 행이 고쳐졌을 때 "무엇이 고쳤는지" 를 따로 확인한다.
2026-08-12 에는 개선 3건의 원인을 유사도로 적었다가 실측에서 전부 명단 직접 일치였음이 드러났다 — 원인을 잘못 적으면 다음 사람이 그 요소를 조정할 때 효과를 잘못 예측한다.
- **후처리로 옮기면 실패 방향이 바뀔 수 있다.**
모델이 값을 못 내면 폴백이 지켜 주던 구조에 후처리가 전 행을 채우면 그 폴백이 죽는다.
잔여 오답을 **방향으로 갈라** 재는 것을 절차에 넣는다 (트러블슈팅 `2026-08-12-wording-cannot-encode-structure.md` §5).
- **시제품에 DB 이름을 박지 않는다.**
세션 사본은 세션마다 다르므로 환경 변수나 인자로 뺀다.
