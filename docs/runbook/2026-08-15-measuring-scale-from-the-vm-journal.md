# VM 저널로 실패 경로의 규모를 재는 절차 (2026-08-15)

「이 경로가 몇 건짜리 문제인가」 를 코드나 DB 로는 못 재는 경우가 있다.
분기가 **아무것도 저장하지 않고 되돌아갈 때**가 그렇다 — 흔적이 로그에만 남는다.

트윗 흡수 설계에서 그 상황을 만났다.
`backtrack_promote` 는 트윗 카드가 가리키는 기사가 페이월이면 승격을 포기하고 트윗 URL 을 그대로 두는데, 이때 얻었던 기사 주소는 **어디에도 저장되지 않는다.**
그 주소를 되찾은 곳이 VM 저널이었고, 덕분에 「고칠 값이 있는가」 를 실물로 답할 수 있었다.

## 1. 저널이 유일한 근거가 되는 조건

아래 셋을 먼저 확인한다.
하나라도 아니면 DB 로 재는 편이 정확하다.

- 그 분기가 **행을 안 만들고 컬럼도 안 채운다** (실패가 데이터에 안 남는다).
- 그 분기에 **로그 한 줄이 있다** — 없으면 코드를 먼저 고쳐야 한다.
- 로그 줄에 **식별자가 실려 있다** (URL · 해시 · 핸들 중 하나).

트윗 흡수의 페이월 분기는 셋을 다 만족했다.

```python
if is_paywalled(final_url):
    log.info("backtrack 페이월 (Athletic) url=%s", final_url)
    out.append(it); continue
```

## 2. 절차

### 2.1. 보존 구간을 먼저 확인한다

**저널은 DB 보다 짧을 수 있다.**
구간을 모르면 「없다」 와 「안 남았다」 를 구분할 수 없다.

```bash
ssh -i ~/.ssh/seoulnow_deploy ubuntu@<vm> \
  'sudo journalctl -u bullet-in.service --no-pager -o short-iso | head -1 | cut -c1-25;
   sudo journalctl -u bullet-in.service --no-pager -o short-iso | tail -1 | cut -c1-25'
```

2026-08-14 실측에서는 `2026-07-20` ~ `2026-08-14` 로 **26일**이었다.
`articles` 의 가장 이른 적재는 06-29 라 **저널이 데이터보다 3주 짧다.**
그래서 이 방법으로 잰 값은 언제나 **하한**이고, 문서에 그렇게 적어야 한다.

**아래 §2.2 ~ §2.4 의 수치는 전부 2026-08-14 실측이고 기준선이 아니다.**
저널은 회차마다 줄이 쌓이므로 같은 명령이 다음 날 다른 값을 낸다 — 하루 뒤 (08-15) 에 다시 재니 페이월 줄이 53 → 72 · 고유 기사가 6 → 9 였다.
**수치를 인용할 때는 창과 측정일을 함께 적는다.**

### 2.2. 실패 사유별로 줄 수를 먼저 센다

어느 갈래가 큰지 모르는 채로 한 갈래만 파면 규모를 오해한다.

```bash
ssh <vm> 'sudo journalctl -u bullet-in.service --since "14 days ago" --no-pager \
  | grep -oE "backtrack (페이월|매칭 실패|near-miss \(카드 없음\)|미등록 도메인)" \
  | sort | uniq -c'
#   345 backtrack 매칭 실패
#   171 backtrack near-miss (카드 없음)
#    53 backtrack 페이월
#     8 backtrack 미등록 도메인
```

**이 계수가 설계를 바꿨다.**
페이월만 고치면 문제가 닫힐 줄 알았는데, 네 갈래 중 **작은 쪽에서 둘째**였다.
실제로 눈검수한 중복 16건 가운데 페이월 수정이 닿는 것은 6건뿐이었다.

### 2.3. 줄 수를 건수로 착각하지 않는다

**회차마다 같은 항목이 다시 처리되므로 줄 수는 부풀어 있다.**
`x_afcstuff` 는 매 회차 최근 트윗 30건을 다시 훑는다.

식별자로 접어야 실제 규모가 나온다.

```bash
ssh <vm> 'sudo journalctl -u bullet-in.service --since "14 days ago" --no-pager \
  | grep "backtrack 페이월" | grep -oE "url=\S+" | sed "s/^url=//" | sort -u | wc -l'
#   7
```

**53줄이 고유 URL 7건이었다.**
하루 8회 스케줄 × 14일이면 같은 항목이 여러 번 걸리는 것이 정상이다.
**창을 §2.2 와 같게 맞춘다** — 줄 수와 고유 건수를 다른 창에서 재면 비율이 뜻을 잃는다.

### 2.4. URL 은 쿼리를 떼고 다시 접는다

공유 파라미터가 회차마다 달라져 **같은 기사가 다른 줄로 보인다.**

```bash
... | sed "s/?.*//" | sort -u | wc -l
#   6
```

7 → 6 으로 하나가 더 접혔다.
`7510567` (빈센트 조셉) 이 서로 다른 `unlocked_article_code` 로 두 줄이었기 때문이다.

**이 한 건이 설계의 근거가 됐다** — 같은 기사가 수집 경로 안에서만 키 두 개로 갈라지므로, URL 정규화를 안 넓히면 흡수가 오히려 행을 늘린다.

### 2.5. 로그에서 얻은 식별자를 DB 와 맞댈 때는 경로로 맞춘다

저널의 URL 과 저장된 URL 은 **쿼리가 다르다.**
문자열을 그대로 비교하면 전건이 「DB 에 없음」 으로 나온다.

```python
from urllib.parse import urlsplit
idx = {}
for r in rows:                      # articles 전건
    idx.setdefault(urlsplit(r["url"]).path.rstrip("/"), []).append(r)

for u in PAYWALLED:                 # 저널에서 뽑은 URL
    print(u, idx.get(urlsplit(u).path.rstrip("/"), "없음"))
```

이 대조로 **8건 중 6건은 이미 전문 행이 있다**는 것이 나왔다.
**여기 모수 8 은 전 구간 값이다** — §2.4 의 6 은 14일 창이라 잣대가 다르다.
「고쳐도 합칠 상대가 없으면 소용없다」 는 반론을 여기서 닫았다.

## 3. 저널이 못 답하는 것

**로그에 안 실린 값은 로그로 못 잇는다.**

페이월 줄은 `url=` (기사 주소) 만 남기고 **어느 트윗이 걸렸는지는 안 남긴다.**
그래서 「이 수정으로 트윗 행이 몇 개 안 생겼겠는가」 는 저널로 답할 수 없고, 기사 쪽에서 접근해 「그 기사에 이미 행이 있는가」 로 우회했다.

- 규모를 로그로 재기로 했으면 **필요한 식별자가 그 줄에 있는지 먼저 본다.**
- 없으면 그 값은 **다음 회차에 로그를 늘려서 재는 것**이 정직하다 — 추정으로 채우지 않는다.

## 4. 이 절차로 답한 것과 못 답한 것 (2026-08-14 실측)

| 물음 | 답 | 창 · 측정일 | 근거 |
| --- | --- | --- | --- |
| 페이월 분기가 실제로 도는가 | 돈다 · 고유 기사 6건 | 14일 · 08-14 | §2.3 · §2.4 |
| 가장 큰 실패 갈래는 무엇인가 | 페이월이 아니라 매칭 실패 (345줄) | 14일 · 08-14 | §2.2 |
| 고쳐서 합칠 상대가 있는가 | 8건 중 6건은 전문 행이 있음 | 전 구간 · 08-14 | §2.5 |
| 트윗 행이 몇 개 안 생기는가 | **못 잼** | — | §3 |

**세 줄 다 「그때 그 창에서」 의 값이다.**
다음 회차가 같은 물음에 답하려면 다시 재야 하고, 이 표의 수를 기준선으로 물려받으면 안 된다.
