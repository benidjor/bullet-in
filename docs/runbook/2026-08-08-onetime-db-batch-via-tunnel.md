# 운영 DB 1회성 재처리 배치 실행 절차 — ssh 터널 · 백업 · 같은 날 대조 (2026-08-08)

운영 DB 를 일괄 재처리해야 할 때의 절차다.
선수별 단계 재추출 (PR #240 · 522건 · Gemini 호출) 에서 실행한 것을 일반화했고, 역할 값 소급 (PR #258 · 589 + 93건) 에서 다시 썼다.
백필 · 소급 재분류처럼 "운영 데이터를 한 번에 고쳐 쓰는" 작업이 대상이다.

## 1. 실행 위치 — VM 이 아니라 Mac 에서 터널로

- VM 체크아웃을 머지 전 브랜치로 바꾸면 안 된다.
정기 회차가 그 체크아웃을 그대로 실행하므로, 배치가 도는 동안 회차가 뜨면 미머지 코드가 운영에 올라간다.
- 대신 Mac worktree (개정 코드) 에서 ssh 터널로 운영 MariaDB 에 붙는다.
- **머지한 뒤에도 이 방식이 낫다** (2026-08-12 추가).
VM 에서 직접 돌리면 비대화형 셸의 PATH 문제와 실행 환경 준비가 따라붙는데, 터널은 이미 검증된 로컬 환경을 그대로 쓴다.

```bash
ssh -i ~/.ssh/seoulnow_deploy -o ExitOnForwardFailure=yes -f -N \
  -L 3311:127.0.0.1:3306 ubuntu@155.248.164.17
set -a; source .env; set +a
MARIADB_URL="mysql+pymysql://root:<pw>@127.0.0.1:3311/bulletin" \
  uv run python -m bullet_in.<배치 모듈> --state <경로> ...
```

- Gemini · Discord 키는 로컬 `.env` 의 것을 그대로 쓴다 (운영과 같은 키).
- **포트는 세션마다 다르게 잡는다** (2026-08-12 추가).
다른 세션이 이미 3310 을 쓰고 있으면 `Address already in use` 가 나는데, **그 상태에서도 명령은 성공한다** — 남의 터널로 붙기 때문이다.
그 세션이 터널을 닫으면 배치가 중간에 끊기므로, 실패 메시지를 보면 포트를 바꿔 자기 터널을 연다.
- 끝나면 터널을 닫는다: `pkill -f "ssh.*<포트>:127.0.0.1:3306"`.

## 2. 실행 전 3종 — 순서대로

1. **백업 덤프 (시각 포함 파일명 · VM 에 보관)** — 롤백의 전부다.

```bash
ssh <vm> 'TS=$(date +%Y%m%d_%H%M%S) && docker exec bullet-in-mariadb-1 \
  mariadb-dump -uroot -p<pw> bulletin <테이블> > ~/backups/<테이블>_backup_${TS}.sql'
ssh <vm> 'ls -l ~/backups/ | grep "$(date +%Y%m%d)"'   # 생성 확인
```

`ls -l ~/backups/ | tail` 로 확인하면 방금 만든 파일이 안 보일 수 있다 — 목록이 이름순이라 새 파일이 끝에 오지 않는다.
날짜로 걸러서 본다.

2. **같은 날 before 측정** — 실행 직전에 전체 덤프를 새로 떠서 로컬 사본 (예: `bulletin_before_MMDD`) 으로 복원하고 검증에 쓸 지표를 그 사본에서 잰다.
옛 사본 · 옛 기준선과 비교하면 개선 폭이 왜곡된다 (서빙 필터 변경 등으로 잣대가 달라져 있다).
**1번 백업 덤프가 곧 before 사본이다** (2026-08-14 추가) — 미리 안 떴어도 끝난 뒤 그 덤프를 로컬로 되살리면 같은 잣대로 전후를 잰다.
쌍 단위로 대조하면 총량 뒤에 가려진 이동까지 보인다 (u 소급 실측 = 총량 12 감소 뒤에 사라진 21쌍 · 새로 생긴 9쌍 · 역할이 바뀐 2쌍이 있었다).
3. **측정 잣대 보정** — 측정 스크립트를 설계 시점 사본에 먼저 돌려 설계 문서의 기준값이 재현되는지 확인한다.
재현되면 같은 잣대라는 증명이다.
재현되지 않으면 정의 차이를 먼저 찾는다 (이번엔 "고아 포함 여부" · "other 제외 여부" 두 정의 차이를 이 보정으로 잡았다).

## 3. 실행 창 · 중단 대비

- 정기 회차 (00 · 03 · … · 21시 KST) 의 enrich 와 429 를 두고 경쟁하므로 **회차 사이 빈 구간**에 돌린다.
소요는 호출당 약 4.5초로 환산해 그 구간에 들어가는지 먼저 계산한다.
- state 파일 필수 — 429 중단 시 재실행하면 이어서 처리하고 이미 끝낸 행은 다시 만지지 않는다 (재과금 · 이중 삭제 방지).
- 파이썬 stdout 은 파이프에서 블록 버퍼라 `print` 진행 메시지가 종료 시점에 몰려 나온다.
중간 진행은 로그의 HTTP 응답 줄 수나 DB 직접 조회로 본다.
- **state 파일은 호출이 다 끝난 뒤에야 채워진다** (2026-08-12 추가).
추출 배치는 대상 전체를 한 번에 호출해 결과를 모은 뒤 DB 반영으로 넘어가므로, 호출 구간 내내 state 는 0행이다.
진행 확인은 로그의 HTTP 응답 줄 수로 하고, state 행 수는 **반영 단계에 들어간 뒤에야** 진행률이 된다.

```bash
grep -c "HTTP/1.1 200" <로그>      # 호출 구간의 진행
wc -l < <state 파일>               # 반영 구간의 진행
```

- 소요는 실측으로 잡는다 — 2026-08-12 실측은 호출 589건에 14분 (분당 약 43건) 이었고, 런북 §3 의 4.5초 환산보다 훨씬 빨랐다.
회차 사이 구간에 들어가는지는 실측값으로 계산한다.

## 4. 검증 — 숫자만 보지 않는다

- before 와 **같은 스크립트 · 같은 날** after 를 재서 표로 대조한다.
- 이동 내역을 유형별로 훑는다 — 쌍 단위 diff (before/after TSV) 로 탈락 · 신규 · 값 이동을 뽑고 상위 유형마다 실제 기사를 눈으로 확인한다.
총량이 늘어도 (이번엔 +249쌍) 유형을 보면 의도된 확대인지 오염인지 갈린다.
- 알려진 사례 목록 (설계 · 지시에 명시된 해시들) 을 전건 재확인한다.
- **같은 이름의 지표가 잣대에 따라 다르다** (2026-08-14 추가) — 메모리 · 설계 문서의 기준선 숫자를 자기 쿼리 결과와 바로 대면 놀라게 된다.
「표시 쌍」 하나가 세 값이었다 — 원시 계수 (`role<>'mention'`) 844 · 조건이 더 붙은 DB 쿼리 607 · 렌더 계산 646.
**세 값의 자릿수가 같아서 더 위험하다** — 대놓고 틀린 값이면 측정 코드를 먼저 보는데, 그럴듯한 크기면 데이터를 의심하게 된다.
**놀란 값을 이상 징후로 보고하기 전에 전후를 같은 스크립트로 다시 재라** — u 소급에서 이 확인으로 오경보 하나를 걸렀다.
렌더된 HTML 을 세다 어긋나는 것은 다른 함정이다 — `docs/runbook/2026-08-11-premerge-screen-check-with-prod-copy.md` §3.
**잣대를 의심하는 절차 자체는** `docs/troubleshooting/2026-08-14-suspect-the-yardstick-not-the-data.md` 에 있다 (옛 수치가 재현 안 될 때의 진단 · 측정 코드가 서빙 규칙을 재구현해 없는 문제를 만든 사례).
- **표시 계층까지 본다** — DB 값이 맞아도 렌더 규칙 (예: other 단계는 선수 페이지 제외) 때문에 화면에 안 보일 수 있다.
렌더 코드가 이번 변경과 무관하면 다음 정기 회차가 새 값으로 재렌더 · 배포하므로, 회차 후 라이브를 실측하면 수동 배포가 필요 없다.

## 5. 뒷정리

- 배치가 만든 부수 산출물 (신규 후보 등재 목록 등) 은 파일로 보관한다 — 롤백 시 수동 정리 대상이다.
- 머지 후 VM `git pull` 은 별도로 필요하다 (회차는 자동 pull 안 함).
DB 는 이미 고쳐져 있으므로 pull 은 **이후 신규 데이터의 처리 경로**에 개정을 적용한다.
- pull 후 첫 정기 회차 성공 + 신규 데이터의 처리 결과 확인까지가 한 묶음이다.

## 7. 쓰기 없는 실측 회차 — 설계 회차가 운영 값을 잴 때

설계 회차는 운영 DB 를 읽기만 한다.
그때는 §2 의 백업과 §3 의 state 파일 · 실행 창 계산이 필요 없는 대신, 값이 도중에 움직이는 문제와 잣대 문제가 새로 생긴다.
2026-08-14 공저자 다중 귀속 설계 회차에서 쓴 절차다.

### 7.1. 터널은 §1 과 같고 mongo 도 함께 연다

포트는 세션마다 다르게 잡는 규칙이 그대로다 (§1).
`raw_payload` 를 봐야 하면 mongo 도 같은 명령에 얹는다.

```bash
ssh -i ~/.ssh/seoulnow_deploy -o ExitOnForwardFailure=yes -f -N \
  -L 3319:127.0.0.1:3306 -L 27019:127.0.0.1:27017 ubuntu@<vm>
```

### 7.2. 값을 스냅샷으로 고정한다 — 회차가 도는 사이에 움직인다

**정기 회차가 새 기사를 넣으므로 같은 쿼리가 한 시간 뒤에 다른 값을 낸다.**
이번 실측에서 기사 수가 측정 도중 688 → 693 으로 움직였고, 앞뒤로 잰 두 수치가 안 맞아 원인을 찾는 데 시간을 썼다.

- 필요한 컬럼만 **파일 하나로 떠서** 이후 측정을 전부 그 파일에서 돌린다.
로컬 DB 사본을 만들 필요는 없다 — 쓰기가 없으므로 파일이면 충분하고 뒷정리도 없다.
- 스냅샷에 **UTC 시각을 함께 적어** 문서의 모든 수치가 어느 시점 것인지 한 줄로 밝힌다 (`SELECT UTC_TIMESTAMP()`).
- **기사 총수는 판정 기준으로 쓰지 않는다** — 회차마다 움직인다.

### 7.3. 화면 수치는 서빙 코드를 불러서 만든다

규칙을 재구현하면 우선순위를 빠뜨려 없는 문제를 만들어 낸다 (실물 · 처방은 `docs/troubleshooting/2026-08-14-suspect-the-yardstick-not-the-data.md` §2).

- 렌더 함수를 `import` 해서 쓰고, 비교하려는 갈래만 갈아 끼운다.
- 인용할 옛 수치가 있으면 §2.3 대로 먼저 재현해 본다.

### 7.4. 뒷정리

- 터널을 닫는다 — `pkill -f "ssh.*<포트>:127.0.0.1:3306"` 뒤 실제로 없어졌는지 확인한다.
- 쓰기가 없었다는 것을 산출물에 명시한다 (백업도 롤백 대상도 없다는 뜻이라 다음 사람의 확인 범위가 줄어든다).

## 8. 외부 사이트에 붙는 소급 — 한 번만 받아 사본에 먼저 쓴다

§2 ~ §4 는 재료가 이미 DB 에 있는 소급을 전제한다.
저자 회수 (2026-08-19) 처럼 **외부 사이트에서 재료를 새로 받아 와야 하는** 소급은 두 가지가 더 붙는다.

### 8.1. 승인은 접촉 축별로 나눠 묻는다

한 배치가 여러 도메인에 붙으면 위험이 축마다 다르다.
저자 회수는 언론사 도메인 (BBC · 마르카 · 디 애슬레틱) 과 커뮤니티 도메인 (fmkorea) 두 축이었고, 뒤쪽은 자동 수집을 430 으로 막는 이력이 있어 성질이 아예 달랐다.
**한 덩어리로 물으면 위험한 쪽 때문에 안전한 쪽까지 막히거나, 안전한 쪽에 묻어 위험한 쪽이 통과한다.**

- 축이 나뉘면 안전한 쪽을 먼저 재고, 그 결과를 보고 위험한 쪽을 따로 묻는다.
- 안전한 쪽만으로 회수가 충분하면 위험한 축은 아예 안 열어도 된다.
- 저자 회수에서는 위험한 축이 **열 필요조차 없었다** — 커뮤니티 글 주소가 저장돼 있지 않아 소급 자체가 불가능했다 (mart · mongo 283건 모두 0건).
붙을 수 있는지보다 **재료가 남아 있는지**를 먼저 확인하면 승인 질문 하나가 통째로 사라진다.

### 8.2. 건수는 붙기 직전에 다시 센다

추정으로 승인을 받으면 실행 시점에 값이 갈린다 ([[count-targets-right-before-running]] 의 사례가 그대로 재발한다).

- 승인 요청에 적는 숫자는 **모집단을 실제로 센 값**이어야 한다.
- 승인을 기다리는 동안 할 일이 남아 있어 이 순서로도 손을 놓게 되지 않는다 (사본 복제 · 측정 스크립트 · 계수).

### 8.3. 원문은 한 번만 받는다 — 사본에 먼저 쓰고 화면을 본 뒤 운영에 넣는다

받아 온 결과를 곧장 운영에 쓰면 화면 변화를 **반영한 뒤에야** 보게 된다.
그렇다고 확인하려고 두 번 받으면 접촉이 두 배가 된다 (「출력 확인 목적 재실행 금지」 와 정면으로 부딪친다).

순서를 이렇게 잡으면 접촉 한 번으로 둘 다 된다.

1. 운영 백업을 뜬다 (§2 의 1번).
2. 그 덤프를 로컬 사본으로 되살린다 — **백업이 곧 before 사본이다.**
3. **사본을 대상으로** 배치를 돌린다 (외부 접촉은 여기서 한 번뿐이다).
4. 사본을 렌더해 §4 대로 전후를 대조하고 사람이 화면을 본다.
5. 확인이 끝나면 **사본의 결과 값만** 운영에 옮긴다 (추가 접촉 0).

옮길 때는 운영 쪽 조건을 함께 건다 (`WHERE <컬럼> IS NULL` 등).
사본을 뜬 뒤 회차가 돌아 운영에 새 행이 들어왔을 수 있고, 그 행은 배포된 코드가 처리할 몫이지 이 배치의 몫이 아니다.

### 8.4. 실패는 사유별로 세어 남긴다

「못 붙었다」 와 「붙었는데 원본에 없다」 는 다음 사람에게 전혀 다른 정보다.
